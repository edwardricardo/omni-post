## 5. What this says about the extraction campaign

`docs/reports/merge-campaign-2026-07-21.md` §3 states the branch was kept for exactly two things:

> `cluster-b-mfa` — §2F write-path **v1 reference** (DO-NOT-SHIP) + **A2** audit-actor read-path source.

**Be fair first: most of the branch genuinely landed.** 25 of 53 are on main, 4 are correctly superseded (and re-applying any of them would regress main), and 7 docs commits landed cleanly. That is **36 of 53 — 68% — correctly disposed of**, and several landed _better_ than the branch version: main's `MfaService` is +227 lines, its backfill script has per-row fault isolation, its `DeletePostUseCase` is compile-forced where the branch's was optional, its `rls-tenant-isolation` suite gained a 1:1 mapping test. Two of the four circuit-breaker commits are byte-identical picks (`git patch-id` matches). This was real, careful work.

**Now the quantification.** Against 11 unextracted code commits + 6 docs commits carrying stranded content:

- **A2** accounts for **1** (`35d44f4f`). The report was honest here — §1.1 explicitly says "The **A2 read path is PENDING**".
- **§2F write-path (DO-NOT-SHIP)** accounts for **4** as a class (`eb295f40`, `bd968112`, `a71bd837`, `70b75124`). Defensible as a class judgment, though `70b75124` diagnoses a root cause that the plan later recorded as _fixed_.
- **Neither claim covers 6 code commits:** `c64a718f` (CRITICAL), `0c15280c` (CRITICAL), `f5470dd4` (HIGH), `46a6282c` (MEDIUM), `95b4ec66` residue (MEDIUM), `6bb37e10` (LOW). **The three highest-severity items on the branch are in the uncovered set.** Plus 6 docs commits with stranded content the report does not mention at all.

**So: the "two things" description covers 5 of 11 live code commits and misses the top three by severity.**

**What kind of mistake was it?** The evidence supports one specific diagnosis: **extraction was tracked by PR and by topic label, not enumerated per commit.** Three lines of evidence:

1. **The report's own structure.** §1 is a PR→item table (`#124` N-SEC-1, `#125` N-SEC-2, …); §3 describes the residue in topic labels. Nothing in it is a per-sha ledger for the security cluster. A commit that did not belong to a named topic had no row to be missing from. `c64a718f`, `0c15280c` and `f5470dd4` all sat inside a stranded openspec change (`fc5a8b62`) whose _name_ never entered the campaign's vocabulary — so the topic index had no entry for them.
2. **Per-sha tracking existed, but only for the docs series.** `main:MASTER_PLAN_ES.md:49` carries an explicit cherry-pick ledger — "76e92a9b · 0c5bc998 · cdfb0f78 · 3d481563/e7b712f1" — and even records that "3d481563 quedó vacío tras el pick". The technique was available and was applied to the low-stakes half.
3. **Even within tracked picks, per-file completeness was never checked.** Three of five cherry-picked pairs landed with hunks amputated: `6b9fa24d`→`cdfb0f78` (content line dropped), `e7b712f1`→`aec96261` (a whole plan file dropped), `0c5bc998`→`445b4cee` (an ADR file dropped). All three score "clean" on subject match, author match and trailer presence; all three are flagged instantly by `git show <sha> | git patch-id --stable`. Only one of the three lost anything of value, but nobody knew that at the time.

**The compounding failure is that the verification then fed the plan.** Two claims on main assert as landed what is not:

- `main:MASTER_PLAN_ES.md:151` marks N-SEC-2 CERRADO and specifically credits "_+W-C2-1 (rutas admin `/admin/auth/{login,refresh}` a `AUTH_ROUTE_RULES`, 5/15min)_" — and `STANDARD_ROUTE_RULES:102-110` has no admin prefix.
- The provider-classifier entry says the 403 fix is done "solo en x/telegram/snapchat; pinterest/bluesky pendiente" — it is done for **none** of the five, so anyone starting on pinterest/bluesky builds on nothing.

That is the same inherited-verdict class the plan was written to correct, reproduced inside the plan. **A verification that asks "does a PR with this name exist on main?" produces exactly this result.** A per-sha, per-file diff would not have.
