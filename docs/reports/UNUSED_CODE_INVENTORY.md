# The Unused-Code Inventory — omni-post

## 1. How to read this

Every item below answers the same five questions the owner asked: **what it was built for · does it do what it says · does something else already do it · is it usable · or is deletion recommended.**

**The three classes:**

| Class           | Meaning                                                                                                                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DANGEROUS**   | It appears to protect, track, enforce, or report — and it does not. False confidence is worse than an acknowledged absence, because it stops someone from building the real thing. |
| **DEAD WEIGHT** | Correct code, unconsumed, harmless. It costs bundle size, build time, review attention, and the reader's belief that it matters.                                                   |
| **TRAP**        | Inert today. Arms the moment someone does the _correct_ thing — follows a deprecation notice, adds a provider method, writes the obvious query.                                    |

**Intent taxonomy** — why the code is unused, which is a different question from whether it works:

- **PLANNED** — a feature that was started and paused. The plan knows about it.
- **INFRASTRUCTURE_READY** — the capability is built and correct; the wiring is the only missing piece.
- **LEGACY** — superseded by something live. It lost, and nobody removed it.
- **DEAD_CODE** — no plan, no successor, no path to a consumer.

**Confidence** — **verified** means two independent passes agree or the claim was re-checked against source; **single-source** means treat it as a lead, not a fact. Everything in sections 2 and 3 is verified unless the row says otherwise.

**The standing rule: nothing is deleted without the owner's explicit validation.** This document recommends; it does not authorise. Only `DEAD_CODE` may carry a deletion recommendation at all — and where an item has a named owner in `MASTER_PLAN_ES.md` or an adjudicated decision in `openspec/changes/archive/**`, it is not dead code no matter how few consumers it has.

**One correction that changes how you read the rest of this section.** The adversarial pass overturned several claims from the first sweep, and the corrections are folded in below rather than kept as footnotes. Where a first-pass item was refuted, the refutation wins. Three of those refutations would have cost real work: `SecretRotationLog` ships populated (its writer is raw SQL inside its own migration), `OutboxInbox` was deleted on purpose with owner sign-off, and the i18n CSV keys are live in a nav-reachable component. None of those three appears here as a delete candidate.

### 2.1 The alert-notification channel is dead, and five workflows have been red for weeks-to-months behind it

**Where:** `.github/workflows/chaos.yml:84-108`, `nightly.yml`, `cleanup.yml:212-273`, `performance.yml`, `production-ci.yml:233-357`
**Class:** DANGEROUS · **Intent:** mixed (chaos + k8s + deploy are PLANNED; performance is DEAD_CODE)

**What it claims.** Five scheduled workflows guard the repository outside PR time: nightly chaos scenarios against the saga/outbox, a nightly full test suite, weekly preview-environment teardown, performance regression thresholds, and a staging→production deploy chain. Two of them (`chaos.yml`, `nightly.yml`) declare a `Notify on failure` step that files a GitHub issue so a failure cannot pass unnoticed.

**What it actually does.** Every one of the five has been failing continuously — chaos 25/25, production-ci 25/25, cleanup 23/23 (since 2026-03-15, five months), performance 25/25, nightly 25/25. And the notification that was supposed to surface this **has never fired once**: the `Notify on failure` step itself errors with `RequestError [HttpError]: Resource not accessible by integration`, because neither workflow declares a `permissions:` block and the default `GITHUB_TOKEN` cannot create issues. `gh issue list --state all` returns **zero issues in the entire repository, ever**.

So the failure mode is not alert fatigue. It is total silence. A genuine regression arriving tomorrow in any of those five surfaces is invisible.

Individually, each one is broken for a small, specific reason:

- `chaos.yml:81` runs `vitest run tests/chaos/`, but `apps/api/vitest.config.ts:45` includes only `tests/unit/**` and `tests/eval/**`, and both chaos files import from `node:test` — uncollectable by vitest. Reproduced locally: `No test files found, exiting with code 1`. **Zero tests have ever run in this workflow.**
- `nightly.yml:52` runs `cp apps/api/.env.example apps/api/.env` — a file removed when per-app `.env`s were consolidated per `SECURITY_CANON §Secrets`. Live log: `cp: cannot stat 'apps/api/.env.example': No such file or directory`. **One line.**
- `cleanup.yml:224` runs `aws eks update-kubeconfig --name omni-post-preview` against a cluster that does not exist; because `cleanup-report:277` declares `needs:` on it, the three jobs that _do_ work (artifacts/images/caches) are reported red.
- `performance.yml` has `continue-on-error: true` on all four substantive steps (`:79, :84, :165, :172`), so it cannot gate anything by design — and it fails in setup anyway, meaning the k6 job (`needs: db-stress`) has **never executed**.
- `production-ci.yml` — see 2.2.

**Who is misled.** Anyone glancing at the Actions tab and reading five red rows as "known noise". Anyone who believes a nightly chaos suite covers the saga engine. And most sharply: whoever merges the next saga change believing chaos coverage will catch a regression — the same class of gap that already let a real defect ship (`main` went red on `integration:saga-live` and the batch does not run on PRs).

**The fix.** In this order, because the order matters:

1. **Fix the workflows first** — `nightly.yml` is one line; `chaos.yml` is one line (`run: pnpm --filter @apps/api run test:integration`, which already runs both chaos files under node:test via `apps/api/scripts/run-tests.sh:222-224`); `cleanup.yml` needs the EKS job removed from `needs:` until §6.2 lands.
2. **Only then** add `permissions: issues: write`. Reversing the order manufactures exactly the P1 spam that does not currently exist.
3. Do **not** delete `chaos.yml`: `MASTER_PLAN_ES.md:288` carries **§4.1.b saga+outbox chaos (P1)** as an open item, which makes it PLANNED. Same for the k8s teardown (§6.2) and containerization (§6.1, explicitly PAUSED pending ADR-0017, branch conserved at `:167`).
4. `performance.yml` is the one genuine OWNER-DECIDES: drop `continue-on-error` on the two threshold steps and fix setup, or delete. A gate that cannot fail is not a gate.

### 2.3 Fitness #23 has never fired — 16 real tenant-isolation bypasses, and the plan's stated root cause is wrong

**Where:** `.github/workflows/fitness.yml:454` + `CLAUDE.md §Automated Compliance Checks #23`
**Class:** DANGEROUS · **Intent:** INFRASTRUCTURE_READY

**What it claims.** Blocks raw Prisma SQL outside the tenant-guard extension, because raw queries bypass the `$extends` middleware (layer 1) — CWE-639. Documented as hard-zero with three audited exceptions.

**What it actually does.** The regex requires a literal `(`: `\.\$(queryRaw|executeRaw|queryRawUnsafe|executeRawUnsafe)\(`. Prisma raw queries are **tagged template literals** — `` prisma.$queryRaw`SELECT …` ``. Harness under GNU grep 3.8 (what CI runs, not the local ugrep): `$executeRaw(` matches; `` $queryRaw`SELECT 1` `` does not. Of 30 raw call sites, exactly 4 are paren-form — and **all 4 are the files already on the exclusion list**. The match set is a strict subset of the exclusion set. The guard has never had anything to report.

**True violations: 16 lines across 4 files** — `apps/api/src/database/DatabaseOptimizer.ts` (12), `apps/api/src/infrastructure/outbox/OutboxClaimService.ts:75`, `apps/api/src/saga/SagaManagerLifecycle.ts:1070`, `apps/api/src/infrastructure/repositories/PrismaSemanticRetrievalAdapter.ts:42,63`.

**Who is misled.** Everyone. `SECURITY_CANON` presents #23 as layer 3 of the three-layer multi-tenant strategy. The green count has been read as evidence that no unguarded raw SQL exists. And critically — **`MASTER_PLAN_ES.md:214` records the wrong root cause inside N-AUTH-3's Definition of Done**, claiming that in ERE `\$` after `\.` acts as an end-of-line anchor making the regex unsatisfiable. GNU grep 3.8 disproves this: `\$` is an escaped literal and paren-form calls match cleanly. The plan explicitly frames that rationale as _"necesaria para no reproducir el bug al repararlo"_ — so the wrong diagnosis sits in the DoD of the item scheduled to fix it.

**The fix.** One character class: `\(` → `[(\`<]`, covering the paren, backtick, and generic `<Type>`forms. Mirror in`fitness.yml`exactly (the doc regex IS the CI regex). **Correct`MASTER_PLAN_ES.md:214`before N-AUTH-3 is worked** — otherwise the repair targets a grep-dialect problem that does not exist. Then triage the 16 sites: each needs either a UoW wrapper (so RLS layer 2 binds`app.account_id`) or an explicit `withSystemContext()`. **WIRE**, and treat the plan correction as part of the same change.

### 2.5 Fitness #14 is name-shaped, and one keyword defeats it

**Where:** `.github/workflows/fitness.yml:247`
**Class:** DANGEROUS · **Intent:** INFRASTRUCTURE_READY

**What it claims.** Blocks per-instance `private *Cache = new Map()`, because a per-pod Map cannot propagate invalidations cross-pod — revoked permissions and stale credentials stay valid on adjacent pods until local TTL expires (OWASP A07:2021).

**What it actually does.** The regex `^\s+private \w*[Cc]ache.*= new Map` matches contiguously after `private `. Harness: `private credentialsCache = new Map()` flags; **`private readonly credentialsCache = new Map()` does not.** One keyword. Worse, it is name-shaped rather than semantic: it reports 0 because nobody names them `*Cache`, while the exact per-pod security state the rationale describes sits in plain sight —

- `apps/api/src/security/enhancedValidator.ts:102` — `private suspiciousAttempts: Map<string, number> = new Map();` — a **brute-force counter**, precisely the cross-pod bypass named in the rationale
- `apps/api/src/ai/providers/AICircuitBreaker.ts:47` — `private readonly states = new Map<AIProviderName, CircuitState>();`
- `apps/api/src/ai/providers/InMemoryTokenBucketRateLimiter.ts:42` — `private readonly buckets = new Map<string, Bucket>();`

**Who is misled.** `LOGGING_CANON §Caching` names #14 as the enforcement behind "all cross-pod cached state MUST go through `TOKENS.CachePort`". It enforces a naming convention, not the invariant.

**The fix.** `private (readonly )?\w*[Cc]ache` closes the keyword hole; widening to security-state shapes (`*Attempt*`, `*Bucket*`, `*State*`) closes the semantic one — or invert to an allowlist. Then decide on the three named files: `enhancedValidator.ts` is itself unwired (see 2.13), so its Map is moot on deletion; the two AI ones are live and need a real answer. **WIRE** — new finding, ~2 lines plus a baseline decision.

### 2.6 Squawk and OWASP ZAP swallow their own exit codes

**Where:** `.github/workflows/audit.yml:206-214` (Squawk) · `.github/workflows/security-testing.yml:224-230` (ZAP)

#### The 7 `config: { rateLimit: {...} }` blocks — DANGEROUS · DEAD_CODE

### 6.3 Method lessons

Five recur often enough to be worth stating as rules for the next pass.

1. **A narrow grep generalised into a universal negative is the dominant error.** Four of the frontend refutations and two elsewhere share exactly this shape: three key prefixes tested → "references none of them"; an import-graph BFS from route roots → "zero callers" without the qualifier _tests are structurally invisible to this traversal_; `rg = 0` reported for a pattern that returns 2. Restate every "zero consumers" line as **"no route-reachable consumer; tests not separately checked"** unless a per-item test grep was actually run.

2. **Migrations carry data, not just DDL.** The `SecretRotationLog` refutation is the expensive one: the writer is a raw-SQL backfill inside the table's creating migration — the single most likely hiding place for a data-bearing insert, and the one place a `prisma.<model>.create` search can never see. Any "no writer" claim about a table must grep the migrations directory for `INSERT INTO "<Model>"`.

3. **Check the project's own decision record before writing "never built" or "Plan ID: none".** Three refutations (`OutboxInbox`, chaos.yml, the k8s/deploy jobs) share one root cause: the sweep searched code but not `openspec/changes/archive/**`, `PENDING_WORK_INVENTORY`, or `MASTER_PLAN §5.3`. Those carry adjudicated dispositions, user sign-offs, and NEEDS_EDWARD owners. §0.3 makes this non-optional for anything approaching a DELETE.

4. **Name collisions are the second-biggest source of both false positives and false negatives.** Confirmed in this pass: `correlationTracker` (a prom-client gauge field, not the OTel module) · `VersionCompareView` (two different files) · `updateMetrics` (a private method in `ai/orchestrator.ts` with 7 real callers) · `getPostAnalytics` (a LinkedIn provider method) · `VideoMetadata` (codegraph attributed 7 callers across a provider/API boundary) · `EmailSchema`/`PasswordSchema` et al. (10+ route files define their own). Resolve by reading the **import statement**, not the symbol hit. Codegraph follows dynamic dispatch that grep misses, but it also reports these collisions as edges — verify the edge, don't trust it.

5. **"Zero explicit references" means nothing for convention-discovered files.** Tailwind `@source` directives, CI tool configs, Storybook roots, `.gitattributes` entries, and canon-sanctioned test doubles are all consumed by mechanisms no import graph models. `ui-safelist.ts` is the cautionary example: 57 LOC, zero importers, and deleting it degrades the admin bundle silently.

- **E2E/Playwright suites, Storybook stories, `quality/`, `performance/`, `security/scripts/`, `scripts/`** — reached only where a workflow or a `package.json` script pointed at them. The `security/tests/` tree (7 real files after excluding two deprecated forwarding stubs and a helper) was found to have zero CI coverage; it was not itself reviewed.
- **Migration history.** Migrations were read only for specific cited models. No audit of migration drift, and no measurement of what the 32–35 indexes on empty tables actually cost at the Postgres level.
- **Runtime evidence of any kind.** Nothing was executed against a running application or a live database. Every "does it do what it says" verdict is a static-analysis verdict, with two exceptions: the CI/fitness harnesses (executed, including under GNU grep where the verdict was load-bearing) and two local test runs.
- **Bundle analysis.** No `next build`, no bundle analyzer. Every shipped-weight claim is import-graph inference. The one place that inference was tested — `TipTapContentEditor`'s six `@tiptap/*` deps — inverted: the barrel excludes the file, so no consumer pays bundle weight at all.
- **A full `knip` / `depcheck` reconciliation** against the 322-entry baseline. Individual dependencies were checked; the pool was not.

### Swept, but not to a standard I would call complete

- **Frontend "zero consumers" claims rest on an import-graph BFS from Next route roots.** That traversal is good — it is what caught the gitignored `/logs` page a filesystem walk would have missed — but **tests are structurally invisible to it**. Verification found three facade methods with committed test consumers presented as having none. Read every such claim as _"no route-reachable consumer; tests not separately checked"_ unless a per-item test grep is cited.
- **The rate-limit rule tables were sampled, not audited.** Three dead rows were reported; sixteen exist. Any row-level claim in that family should be re-walked.
- **The schema census read code, migrations for the named models, and seeds — but not the project's decision record.** Three items changed classification once `openspec/changes/archive/**`, `docs/archive/PENDING_WORK_INVENTORY.md` and `MASTER_PLAN_ES.md §5.3` were read. The most expensive miss was a "no writer anywhere" verdict on a table that ships with 29 rows inserted by raw SQL **inside its own creating migration** — the single most likely hiding place for a data-bearing backfill, and invisible to a `prisma.<model>.create` grep.
- **LOC figures were spot-checked, not systematically measured.** One (`ContentTemplates.tsx` at "1,318 LOC") is a 6× overstatement and cannot be reproduced from the named file. Several aggregate totals in the area reports were never re-derived — including the ones in §7 above, which inherit that uncertainty.
- **Six of 23 fitness checks were fully re-derived.** Two more were spot-checked clean. The remaining fifteen "satisfiable and genuinely 0" verdicts rest on a single pass.
- **No DELETE candidate was tested by removal.** Every "safe to delete" is an import-graph judgment, not a build.
- **i18n key drift was analysed for exactly one cluster, and the analysis was wrong.** Re-run it with a method that resolves `t()` call sites rather than prefix greps before trusting any key-level claim, including the "zero key drift between locales" clean bill.

### Standing method caveats

- **codegraph is blind to dynamic dispatch.** DI-token registration-versus-resolution was traced by hand throughout, and that hand-tracing is the likeliest single source of a false "unused."
- **Name collisions defeated a naive grep at least seven times** across the five areas: `correlationTracker` (a Prometheus gauge field, not the module); `VersionCompareView` (two unrelated files); `updateMetrics` (a private method in `ai/orchestrator.ts` with 7 real callers); `getPostAnalytics` (a LinkedIn provider method); `templateAnalytics` (the 501-throwing service versus the Prisma model); the `api-common` schema names versus ~10 route files' local Zod schemas; `VideoMetadata` (provider versus api). Any single-grep claim here should be re-run with the collision in mind.
- **Local `grep` is ugrep; CI runs GNU grep.** Regex verdicts were re-run under GNU grep where load-bearing, not everywhere.
- **§0.3 is binding.** Absence of consumers does not prove dead code. Nothing here authorises a deletion; only `DEAD_CODE` carries a deletion recommendation, and three delete recommendations in the CI area were withdrawn on verification because the plan carries named open owners for them (saga+outbox chaos; containerisation; Kubernetes).

### The recurring failure mode of the first pass

One error, committed independently in all five areas: **a narrow grep generalised into a universal negative.**

It produced: an i18n deletion that would have broken a live, nav-reachable component (three prefixes tested, whole cluster condemned); a "no writer anywhere" on a table shipping 29 seeded rows; an "unsatisfiable" verdict on a regex that is merely blind to two idioms; a "zero references repo-wide" on a config with eight inline directives across eight docs; a "never built" on a mechanism that was built, shipped, and deliberately deleted with user sign-off; a "two composition roots" on a symbol constructed in three places across two apps.

Adversarial verification caught twenty-four of these. The appropriate prior is that some survive.

The reassuring half is worth stating with equal precision: **across roughly 120 items, exactly one thing claimed unused turned out to have live production consumers** — `depcheck`, reachable from two declared npm scripts (`quality/scripts/bundle-analyzer.ts:325`, `run-quality-checks.sh:244`). The expensive error class — flagging live code as dead — was committed once. The common error was over-claiming _why_ something is dangerous, not _whether_ it is unused. That is the right shape of error for a document whose only power is to recommend.
