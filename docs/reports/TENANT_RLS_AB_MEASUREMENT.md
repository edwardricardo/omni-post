## Method, and what it does not claim

Plans are captured through a session whose `current_user` is `omnipost_app` — the
non-superuser, non-bypassing role the application connects as — with `app.account_id`
bound exactly as `PrismaUnitOfWork` binds it. A plan taken as the owner would carry no
policy qual and would understate every query here.

Each case pairs a REAL Prisma call from a named repository site with a hand-written SQL
mirror, runs both inside the same bound transaction, and compares the returned row
identities before taking any plan. The mirror is what `EXPLAIN` sees, because Prisma 7
emits its SQL through a driver adapter this script cannot subscribe to; the fidelity check
is what stops that mirror from drifting into a different question. Honest limits, stated
rather than implied:

- The mirror is **semantically** validated, not textually identical to Prisma's emission.
  Prisma may render a relation predicate as a join where the mirror writes `EXISTS`;
  where that distinction matters it is called out in the case's notes.
- **The check validates predicate and ordering, NOT projection.** `Q1`, `Q3`, `Q5` and `Q6`
  ask Prisma for `select: { id: true }` while their mirrors select the full column list, so
  the two sides return the same ROWS through different column sets. A mirror that drifted
  only in its projection would pass. That is deliberate — the identity of the rows is what
  decides whether the plan answers the same question — but it is a real limit, so a case
  whose column list matters must not rely on this check to notice.
- **An identity comparison over an empty result cannot fail**, so equal digests are only
  evidence when both sides actually matched something. Every case reports that, and a case
  matching nothing FAILS the run unless it declares itself a miss probe; `Q8` is the one
  such declaration here, and it is checked in reverse too — if it starts matching rows the
  run fails, because its plan would no longer be the empty-bucket plan it claims to be.
  Both guards run BEFORE the report is written, so a capture that failed one leaves nothing
  on disk.
- **The mirror tracks its source site as it is TODAY, not as it was when an earlier phase was
  captured.** Four sites changed emission between the two captures (see §Reading the after
  capture), and the fidelity check cannot detect that class on its own: both texts return the
  same rows, so the comparison passes while the plan describes a query nobody issues. Those
  four are named per case; the other nine are textually identical across both phases.
- Literal values are inlined, so these are **custom** plans. A generic plan for the same
  statement can differ.
- One database, one corpus, one machine. Numbers here are comparable to the other phase of
  the same file and to nothing else.

(Every timing quoted in this section is the MEDIAN of the capture's three runs.) Every other
`Post` path index-scans, because every existing `Post` index is `projectId`-led and those
queries supply a `projectId`. The account-wide feed supplies none — the tenant identity
lives one table away — so there is nothing for the planner to use.

`Q3` is the exact query D-S1-1's single new index
(`@@index([accountId, projectId], where: { deletedAt: null })`) exists to serve, and these
are the numbers it will be measured against. Two honest caveats attached now rather than
later: 20 000 posts is a small table, so 4 ms is the shape of the problem and not its
production cost; and the corpus gives every tenant the same size, so the join's cost does
not grow with a neighbour's data the way it would in a real account distribution.

Its paired count `Q4` is a **different** shape, and the distinction matters because it is
what the after phase gets compared against. `Q4` does not scan `Post` sequentially at all:

```text
Aggregate
  Nested Loop
    Seq Scan          rel=Project  rows=100  loops=1
    Index Only Scan   rel=Post  idx=Post_projectId_archivedAt_idx  rows=95  loops=100
```

It walks `Project` and probes `Post` — the inverse of a `Post` scan. At 1.279 ms its cost is
the 100-loop fan-out over a sequentially scanned `Project`, so it belongs with `Q6` below
rather than with `Q3`.

### The baseline had to be made reproducible first, and that is a finding

The first version of this capture ran `ANALYZE` after seeding. Re-running it over the
**identical, untouched corpus** produced two different plans: `Q2` moved from a Bitmap Heap
Scan to an Index Only Scan (0.081 → 0.030 ms) and `Q4` from a hash join over two sequential
scans to a nested loop with an Index Only Scan (3.05 → 1.32 ms). Nothing about the data
changed. The freshly bulk-inserted heap pages were not yet marked all-visible, so index-only
paths were unavailable until autovacuum reached them.

A baseline that changes shape on its own is not a baseline: the after phase would have read
that drift as an effect of the migration. The seeder now runs `VACUUM (ANALYZE)`, which sets
the visibility map before the capture. Verified rather than assumed, and re-verified since:
every independent full-cleanup-and-reseed capture taken against **this pre-migration schema**
reproduced its 13 plans with **identical node sequences and index choices**. The sharpest check
came when `Q13` was repointed at a parent that actually has media — the other **12 cases came
back identical down to `Actual Rows` and `Actual Loops`**, with only `Q13` moving, and only
from `rows=0` to `rows=1` on the same node and the same index.

That scoping to the pre-migration schema is deliberate and is not a hedge. `VACUUM` removes
the visibility-map drift; it does not make every plan stable, and the post-migration schema
introduced one case where it is not — `Q4` lands on a 0.11 % cost tie there and flips between
captures. The after reading states that under §"Reproducibility, and the noise band this
capture can support". The claim here is about these plans, not about every plan this harness
can produce. Execution times drift inside run-to-run noise
(single-digit microseconds on the sub-millisecond cases), which is why the tables in this
section quote the median of the capture's three runs and why the SHAPE, not the number, is
what the after phase must be compared on. Anyone re-running this should use the documented
command, which includes the seeding step, rather than capturing against a corpus someone else
left warm.

no mirror error can turn red, over a plan whose `Actual Rows` was `0`. A lookup that finds

refuses to write a report containing a case that matched nothing unless the case declares

same slice.** These five rows are what "degrading" is measured from. The expected benign
outcome is the same `Index Scan` node with the policy predicate appearing as an extra
`Filter` on it; a `Seq Scan` or a `Bitmap Heap Scan` replacing it is the trigger firing.

### One thing this capture deliberately does not settle

Whether Prisma issues those child reads as separate `postId IN (...)` statements or folds
them into the parent query as lateral joins was not measured. The `relationJoins` preview
feature is enabled in `infra/prisma/schema.prisma`, so both are possible, and this harness
cannot see Prisma's emitted SQL (see §Method). The cases above measure the child read as its
own statement, which is the shape the exemption's argument is written about; if the after
phase needs the other shape, the way to get it is a capture with
`relationLoadStrategy` stated explicitly on both sides, not an inference from these numbers.

### The fact that governs every reading below: the policy qual is never an index condition

In all 13 after-plans the row-security predicate appears as a **`Filter`**, never as an
`Index Cond`. That is structural, not incidental: the shipped policy is a disjunction whose
first arm (`current_setting('app.account_id', true) = '__system__'`) mentions no column, and
PostgreSQL cannot turn a disjunction with a non-indexable arm into an index condition. Counted
over every node of every plan in the block above, and independently recounted by the re-gate:
the qual lands **17× as a `Filter` and 0× as an `Index Cond`**.

**`Q1`, `Q2` and `Q5` are the proof**, and they are chosen deliberately over the more dramatic
`Q4` because all three reproduce identically across every capture. Each of them carries an
`accountId` index condition AND the policy qual as a filter, on the same node. From `Q1`'s
plan above:

```text
Index Scan  rel=Post  idx=Post_accountId_projectId_idx
  Index Cond: (("accountId" = 'tif-ab-a') AND ("projectId" = 'tif-ab-a-proj-0001'))
  Filter:     (("archivedAt" IS NULL)
               AND ((current_setting('app.account_id', true) = '__system__')
                    OR ("accountId" = current_setting('app.account_id', true))))
```

The **same column** is on both lines, which is what makes this decisive. `accountId` reaches
the index condition because the QUERY supplies it as a literal; row security's own reference to
that identical column stays in the filter and is evaluated per row anyway. So even in the best
case available — the tenant column indexed, and the index chosen — the policy is not served by
the index. No planner coin-flip can change that, because both halves are in the same plan node.

`Q4` **illustrates** what that fact costs, and nothing more: its plan choice is the unstable
one (§Reproducibility). In the captures where the planner picks `Post_accountId_projectId_idx`:

```text
Aggregate
  Hash Join
    Index Only Scan  rel=Post  idx=Post_accountId_projectId_idx
                     Filter = the policy qual
                     Actual Rows 9500   Rows Removed by Filter 9500
    Hash
      Seq Scan       rel=Project  rows=100  Rows Removed by Filter 417
```

it reads **19 000 index entries to keep 9 500** — no tenant selectivity, scanned end to end and
then filtered. In the captures where it picks a sequential scan the same 9 500 rows are filtered
away off the heap instead. Vivid either way, load-bearing neither way: every other conclusion in
this section rests on `Q1`/`Q2`/`Q5`.

### Verdict (a) — `Q3` did NOT move onto the new index

**No, and on this corpus it could not have.** `Q3` (`listGlobal` page 1) has the same node
sequence it had before the migration — `Limit → Sort → Hash Join → Seq Scan (Post) → Hash →
Seq Scan (Project)` — and reports `Indexes used: (none)`. Its execution median went from
4.305 ms to 6.754 ms, and the whole increase is on the `Post` sequential scan, which now
evaluates the policy qual on every one of the 20 003 rows it reads (`Rows Removed by Filter:
10503`, up from a `deletedAt`-only filter before).

Two independent reasons, and BOTH have to be fixed for the index to serve this query:

1. **The query still asks the old question.** `listGlobal` was deliberately left unconverted
   (its tenant predicate remains `project: { accountId, deletedAt: null }`), so there is no
   `accountId` predicate on `Post` for an `(accountId, projectId)` index to answer. The
   liveness half of that predicate is real and cannot simply be dropped: a soft-deleted
   project's posts keep `deletedAt IS NULL` themselves, so the join is doing work the local
   column does not replace.
2. **The policy cannot supply the missing predicate.** Per the fact above, the policy qual is
   a `Filter`. Even a `listGlobal` that supplied `accountId` locally would get the index
   condition from the QUERY, never from row security. That is not an inference: `Q1`, `Q2` and
   `Q5` are three queries that DO supply it locally, and every one of them still carries the
   qual as a per-row filter on the same node the index condition sits on.

This is the design's own "regression appears with its adjudication" clause, and the
adjudication is recorded in the last section of this reading rather than left implicit.

D-S1-1 justified `@@index([accountId, projectId], where: { deletedAt: null })` with: _"It

**Net, in one sentence: the one new index is chosen by three to four of the eight `Post`

## Reading the A′-vs-B′ comparison

Hand-written, outside the generated block. Written from the plan trees, same rule as above.

### What was compared, and what was deliberately not

The three shapes are the ones the design names — point read by id, `projectId`-filtered
listing, listing with no selective predicate — and **none of them carries a tenant predicate
of its own**. That is the whole design of the comparison: with the query silent about the
tenant, the policy is the only thing restricting rows, so the timing difference between arms
IS the policy's cost. They are therefore NOT the application's queries; the application's
queries are the 13 cases above, and nothing here should be read as a measurement of them.

Two guards make the arms comparable rather than merely fast. Every arm's rows are compared
against every other arm's for the same shape and the run refuses to write anything if they
disagree — a policy that lets different rows through is answering a different question, and a
policy that lets NOTHING through is trivially the fastest. And the swap is transaction-scoped:
each arm installs its policy, reaches `omnipost_app` with `SET LOCAL ROLE` in the same
transaction, measures, and rolls back, so the restore is the rollback itself rather than a
repair step that could fail. The three shipped policies were re-read afterwards and are
byte-identical (printed in the block above).

Four arms, not two. `B′` is the research's form verbatim, which carries **no `__system__`
escape** and therefore could not ship as written — under it every `withSystemContext()` flow
would see nothing. `B′+sys` restores that escape so a shippable version of B′ is measured.
`A′+init` is the shipped form with each `current_setting()` wrapped in `(SELECT ...)`, which
is semantically identical and exists because the first three arms differ in two ways at once;
this arm is what separates them.

### The results

Execution medians of three runs (ms):

| Shape                                    | `A′` (shipped) | `A′+init` | `B′`  | `B′+sys` |
| ---------------------------------------- | -------------- | --------- | ----- | -------- |
| `S1` point read by id                    | **0.014**      | **0.014** | 0.109 | 0.114    |
| `S2` `projectId`-filtered listing        | **0.024**      | 0.063     | 0.120 | 0.128    |
| `S3` listing with no selective predicate | 5.403          | **3.009** | 3.774 | 5.577    |

### `B′` never becomes an index probe either — and that is the load-bearing correction

The research's expectation for `B′` was "one `InitPlan`, evaluated once, followed by an index
probe on `Post(projectId)`, which already exists". Half of that is confirmed and half is not:

```text
Index Scan  rel=Post  idx=Post_projectId_createdAt_idx
            Index Cond = ("projectId" = 'tif-ab-a-proj-0001')     <-- from the QUERY
            Filter     = (hashed SubPlan 1)                        <-- the policy
  Seq Scan  rel=Project  rows=100  (SubPlan 1, loops=1)
```

The subplan IS evaluated once (`Actual Loops: 1`, ~0.08 ms to build the hash). But the index
condition comes from the QUERY's own `projectId` predicate, not from the policy — the policy
is a hashed membership `Filter` on top. On `S3`, which supplies no `projectId`, `B′` still
sequential-scans `Post`. So `B′` does not convert a scan into a probe; it changes what the
per-row filter costs.

### What actually drives the per-row cost: the `current_setting()` call, not the column form

`S3` is where this becomes unambiguous, because all four arms use the same
`Limit → Sort → Seq Scan` and differ only in the filter expression. Comparing the sequential
scan node alone:

| Arm       | Filter on the `Post` scan                                   | Scan node — embedded plan (ms) | Scan node — independent re-capture (ms) | Total `S3` median (ms) |
| --------- | ----------------------------------------------------------- | ------------------------------ | --------------------------------------- | ---------------------- |
| `A′`      | two `current_setting()` calls per row                       | 3.881                          | 4.146                                   | 5.403                  |
| `A′+init` | two InitPlan constants (`$0`, `$1`) per row                 | **1.833**                      | **1.775**                               | **3.009**              |
| `B′`      | one hashed set-membership per row                           | 2.517                          | 2.498                                   | 3.774                  |
| `B′+sys`  | one `current_setting()` call **plus** the hashed membership | 4.22                           | 4.205                                   | 5.577                  |

**Read the two scan-node columns as single-run readings, because that is what they are.** The
harness computes a median for the STATEMENT but not for an individual plan node, so each
scan-node figure comes from one run: the first column is the last-run plan printed in the
generated block above, which any reader can check without re-running anything, and the second
is the same node in an independent re-capture by the re-gate. The `Total S3` column is the
3-run median the script does compute. An earlier version of this table quoted a single figure
per arm that showed `A′` and `B′+sys` as exactly equal; that equality was a one-run
coincidence and is not reproducible, so the two columns are published instead of it.

`B′+sys` is still what settles the question, and the finding survives being stated precisely.
It is `B′` with the `__system__` arm added back, and **its scan node is indistinguishable from
`A′`'s**: across captures the two sit between 3.88 and 4.22 ms, a spread (0.34 ms) comparable to the
drift between captures of the SAME arm (`A′`'s own is 0.27 ms). `B′`'s entire advantage is erased by adding that one
disjunct back. The disjunct that mentions no column is the expense; the set-membership half is
nearly free once its hash exists.

What is **not** inside that spread is `A′+init` at ~1.8 ms — **~2.1-2.4× cheaper than either** across
the four pairings, which is the gap the follow-up is about. So the recorded win for `B′` on `S3`
is not a win for the set-membership FORM at all: it is a win for not calling
`current_setting()` per row, and `A′+init` collects that same win while keeping the shipped
policy's semantics, its column, and its escape.

### Recording it plainly, including where B′ wins

- **`A′` wins the two selective shapes outright**: `S1` 0.014 vs 0.109 (×7.8) and `S2` 0.024
  vs 0.120 (×5.0). On both, `B′` pays a full `Seq Scan` of `Project` to build its hash for a
  query that reads one or twenty rows. That cost is fixed per statement and scales with
  **projects per account**, exactly as the research predicted it would.
- **`B′` wins the unselective shape** — `S3` 3.774 vs `A′`'s 5.403 — and that is recorded
  plainly rather than explained away. It is also the only shape it wins, it wins it for a
  reason that is not its own form, and the version of it that could actually ship (`B′+sys`,
  5.577) **loses** the same shape.
- **`A′+init` beats every other arm on `S3`** (3.009) and ties `A′` on `S1`.
- **`A′+init` costs something on `S2`** (0.063 vs 0.024), and this is the one result that
  argues against it. The plan flipped index: `Post_projectId_archivedAt_idx` plus a `Sort`
  instead of `Post_projectId_createdAt_idx` walked in order. Wrapping the GUC read changes
  the estimated cost of the qual, and that moved a cost comparison the planner was making
  narrowly. A policy rewrite can therefore move plans in BOTH directions, and any follow-up
  that adopts it has to re-run these 13 cases rather than assume the `S3` win generalizes.

### The revisit trigger, verbatim, and its state

> if B′ measures well AND Slice 2 classifies many more than three tenant-owned tables → the
> per-table choice reopens (A′ and B′ are not mutually exclusive per table).

**First half: NOT met.** B′ measures well on exactly one of three shapes, and only in the
form that cannot ship. Its shippable form is at best a tie and at worst a loss on all three.
The second half is not yet knowable — the keyless-model triage has not run — but it does not
matter while the first half is unmet, and the trigger is a conjunction.

**And the guarantee is not on the table either way.** B′ and B′+sys are row-VISIBILITY rules.
Neither prevents a `Post` row from carrying a tenant key that disagrees with its project's;
they only stop such a row from being returned. The composite foreign key makes that row
unrepresentable, holds against a `BYPASSRLS` role, and holds when the GUC is unset. No policy
form provides that at any speed, which is why a B′ that had won all three shapes would still
not have been an argument for replacing A′ — only for pairing with it on tables where the
column is genuinely not worth carrying.

## Spike — Prisma shared-scalar relation pattern

### The question, and why the trio does not ask it

The Post trio dodges this by construction: `Post.accountId` participates in exactly one
relation (the composite one to `Project` — there is deliberately no direct `Account`
relation and no `Account.posts` back-relation), and likewise for the children toward
`Post`. The models that will hit it are the Slice 2 ones that ALREADY carry a direct
`Account` relation and would gain a composite parent relation over the same `accountId`
column. The pattern has to be decided before any of them migrate, which is what this spike
does.

### Protocol as run

Throwaway `spike.prisma` outside the repo, a throwaway `tif_spike` database on the same
server, dropped at the end. The model under test:

```prisma
model SpikeWidget {
  id        String @id @default(uuid())
  parentId  String
  accountId String
  label     String

  // Relation 1 — the direct Account navigation the Slice 2 models already carry.
  account SpikeAccount @relation(fields: [accountId], references: [id], onDelete: Cascade)

  // Relation 2 — the composite parent relation. `accountId` is shared with
  // relation 1; that sharing IS the spike.
  parent SpikeParent @relation(fields: [parentId, accountId], references: [id, accountId],
                                onDelete: Cascade, onUpdate: NoAction)

  @@index([accountId, parentId])
}
```

Prisma CLI 7.9.1, PostgreSQL 16.14. `prisma db push` was **not** used: its built-in
AI-consent guard refuses to run unattended, and that guard is right, so the DDL was taken
from `migrate diff --script` and applied to the throwaway database statement by statement —
byte-identical SQL, no destructive verb.

| #   | Protocol step                           | Command                                                             | Result                                                                                                                       |
| --- | --------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1   | `prisma validate`                       | `prisma validate`                                                   | **PASS** — "The schema at spike.prisma is valid"; no warning about the shared scalar                                         |
| 2   | `prisma migrate diff`                   | `migrate diff --from-empty --to-schema spike.prisma --script`       | **PASS** — emits BOTH foreign keys; the composite one carries `ON UPDATE NO ACTION ON DELETE CASCADE`                        |
| 3   | Generated-client typecheck              | `tsc --strict --exactOptionalPropertyTypes` over five create shapes | **PASS** — flat, checked, nested-under-parent, nested-under-account and `createMany` all compile                             |
| 4   | Negative control for step 3             | same, over three deliberately wrong shapes                          | **RED demonstrated** — exit 2 with TS2353 / TS2741 / TS2741; the typecheck can fail                                          |
| 5   | `db pull` round-trip                    | `prisma db pull` then `diff`                                        | **PASS** — both relations survive verbatim, including the shared `accountId` in both `fields` lists and `onUpdate: NoAction` |
| 6   | Runtime behaviour (beyond the protocol) | generated client against the throwaway database                     | see below — two hazards the protocol does not ask about                                                                      |

The DDL Prisma generated for the two coexisting constraints, read back from `pg_constraint`:

```text
SpikeWidget_accountId_fkey           FOREIGN KEY ("accountId") REFERENCES "SpikeAccount"(id)
                                       ON UPDATE CASCADE ON DELETE CASCADE
SpikeWidget_parentId_accountId_fkey  FOREIGN KEY ("parentId", "accountId")
                                       REFERENCES "SpikeParent"(id, "accountId") ON DELETE CASCADE
```

### What the generated input types actually do with a shared scalar

This is the useful part, and it is better than expected. Nesting removes the shared scalar
from the input entirely rather than making it optional:

| Input type                                      | Shape                                           |
| ----------------------------------------------- | ----------------------------------------------- |
| `SpikeWidgetUncheckedCreateInput`               | `{ id?, parentId, accountId, label }`           |
| `SpikeWidgetCreateInput` (checked)              | `{ id?, label, account, parent }`               |
| `SpikeWidgetUncheckedCreateWithoutParentInput`  | `{ id?, label }` — **no `accountId`**           |
| `SpikeWidgetUncheckedCreateWithoutAccountInput` | `{ id?, parentId, label }` — **no `accountId`** |
| `SpikeWidgetCreateManyParentInput`              | `{ id?, label }`                                |

So a nested create under the parent has no way to state a tenant key at all: Prisma derives
it from the parent row. That is exactly the derivation the threading design wants, and it is
enforced by the compiler rather than by review.

### Two hazards, measured rather than reasoned about

Both come from KEEPING relation 1 alongside relation 2. Neither is a toolchain failure, and
neither is visible in the three protocol steps.

1. **Two connects that disagree are accepted silently, and the PARENT wins.** A checked
   create with `account: { connect: { id: "acct-B" } }` and a parent belonging to `acct-A`
   type-checks, executes without error, and lands the row under **`acct-A`**. Prisma
   resolves the shared scalar from one relation and drops the other's value without a
   diagnostic. A caller who believed the `account` connect was the tenant assertion has
   written a row into a different tenant and been told it succeeded.
2. **`ON UPDATE CASCADE` on relation 1 rewrites the child's tenant key past relation 2's
   `NoAction`.** `UPDATE "SpikeAccount" SET id = 'acct-A2'` propagated into
   `SpikeWidget.accountId` and was accepted. The composite relation's `onUpdate: NoAction`
   exists precisely to keep a tenant re-point noisy (design D-S1-1); a sibling relation
   carrying Prisma's default `Cascade` over the same column defeats it.

The controls that make those two statements observations rather than guesses: a flat create
with a mismatched `(parentId, accountId)` pair IS refused (`P2003`), and a nested create
under the parent DOES land the parent's account (`acct-A`). So the engine is enforcing the
composite FK; hazard 1 is the input layer choosing a value before the FK ever sees a
conflict, and hazard 2 is a legal cascade the FK has no reason to refuse.

### Decision

**The protocol verdict is PASS: the shared-scalar pattern is viable on this toolchain.**
Nothing in steps 1-5 failed, so the design's named fallback rule ("any of the three fails →
fallback = the Post pattern") is NOT triggered, and this section does not pretend otherwise.

**The recommendation is nevertheless the Post pattern for Slice 2** — composite parent
relation only, `Account` navigation through the parent — on hazards 1 and 2 rather than on a
protocol failure. The Post pattern removes both by removing relation 1: with one relation
over `accountId` there is no second connect to disagree with, and no second `ON UPDATE` rule
to outvote `NoAction`. This is the pattern Slice 1's trio already uses, so it also keeps one
shape across both slices.

If a Slice 2 model is later argued into keeping its direct `Account` relation, these are the
guardrails the evidence says it needs, and they belong in that model's own decision record:
pin `onUpdate: NoAction` on **both** relations, and forbid the checked two-connect create
shape at the repository boundary so hazard 1 cannot be written.

**The rejected fallback stays rejected**, and this spike gives no reason to revisit it:
declaring the composite FK in raw SQL while the schema keeps a single-column relation would
have `prisma migrate dev`'s drift detection schedule the constraint's DROP in the next
generated migration. A guarantee the toolchain keeps trying to delete is not a guarantee.

### Re-running the spike

Nothing of it is committed: the schema, the throwaway database, the generated client and the
typecheck files were all created outside the repo and removed. The steps above are complete
enough to rebuild it — a `spike.prisma` with the model shown, a `prisma.config.ts` pointing
at a throwaway database, then `validate` → `migrate diff --script` → apply → `generate` →
`tsc` → `db pull` → `diff`.
