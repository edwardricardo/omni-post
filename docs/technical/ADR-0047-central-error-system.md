- **Consulted**: —
- **Informed**: Product Owner

- **Superseded by**: —
- **Related**: [ADR-0006](ADR-0006-result-type-over-throws.md) (the `Result` type stays, and its "single canonical error-mapping path" is what decision 2 builds; this record leaves its rule on raising in a route unamended); [ADR-0013](ADR-0013-three-logger-factory-model.md) (the logger an answered error is written through); [ADR-0045](ADR-0045-instruction-context-budget.md) (the byte budget the new check's line must fit); ADR-0046 (the plan-closure check, fitness #56, that decision 8 joins)

## Context

1. **No single place holds the errors or their messages.** Measured on `main` at `55fecbe5c` on 2026-11-20, by static counts over production source (tests, stories and generated code left out):
   - about 12 vocabularies of error codes hold about 200 distinct code strings. `USE_CASE_ERRORS` holds 10 of them (`packages/core/application/src/UseCase.ts:66-104`), the `ErrorCode` enum 23 (`packages/shared/src/errors.ts:7-46`), the administrators' sign-in 23 (`apps/api/src/admin/auth/adminAuthTypes.ts:416-444`), and 123 exist only as string literals passed to `err("…")`;
   - the API answers a failure in 6 body shapes. `BaseRouteHandler.sendError` writes `{ ok: false, error: "<sentence or code>" }` from 1,035 call sites (`apps/api/src/lib/route-handler/BaseRouteHandler.ts:273-286`), and the global handler writes `{ ok: false, error: { code, message, requestId, timestamp } }` (`apps/api/src/lib/errors/errorHandler.ts:84-101`);
   - about 100 places turn a code into a status, and three codes answer with two statuses each (`INVALID_TOKEN`, `MFA_INVALID`, `RATE_LIMIT_EXCEEDED`);
   - core and API hold about 500 distinct inline English sentences: 636 of the 751 `new UseCaseError(` calls pass a literal text, and 804 `sendError` calls pass a literal sentence;
   - the administration portal's catalogs word 13 codes (`apps/admin/lib/auth/types.ts:97-112`) and the client portal's word none. The client shows the API's English `message` first at 34 sites and its catalog only as a fallback.
2. **The canon already asks for one path, and the code contradicts it three times.** The coding standard asks for a single global handler and for every error body to carry `statusCode`, `message`, `correlationId` and `timestamp`; ADR-0006 asks for "a single canonical error-mapping path" and names `USE_CASE_ERRORS` the single source of application error codes. No body shape carries the four fields, the mapping is copied about 100 times, and 123 codes live outside the single source.
3. **The global handler maps by status only.** `getStatusCode` reads a `statusCode` property and otherwise answers 500 (`packages/shared/src/errors.ts:261-278`), so a raised `DomainError` or `UseCaseError` answers 500, and so does a raised Zod error, with the code `VALIDATION_ERROR`.
4. **A failure that names no reason made the gap visible.** The first-administrator command prints that it "could not be set up in this environment" and names no variable when the environment module refuses to load, and prints the text of a transaction of unknown outcome when the database cannot be reached, although no transaction began. The Maintainer decided on 2026-11-20 that its environment failures name the refused variables, names never values, and that it checks the connection before the transaction, with its own message. That repair is this system's first consumer.
5. **What a design must respect.** The core imports no framework and raises nothing (fitness #2 and #4), so its failures stay values in `Result`. Product text lives in each portal's locale catalogs, which fitness #51 holds complete and valid ICU, and the API reads no `Accept-Language`. The commands, the workers' persisted failures and the logs read errors too. The error body is a contract with many readers.
6. **What the tree already has that this decision reuses.** An in-house ESLint plugin with `RuleTester` suites (`packages/eslint-plugin-testing/src/index.js:1-9`); ESLint's own bulk suppressions, already a list that may only shrink (`eslint.config.ts:294-300`); a per-file baseline held in both directions (`scripts/testing/artifact-language-gate.mjs:15-21`); and a generated API contract with a drift gate (`.github/workflows/ci.yml:226-234`).

## Decision

Eight decisions. Each names what can be checked and the check that holds it. The exact types, file paths and unit split of the first slice are the contracts the writers build to; this record holds what is decided.

### 1. One registry of error codes in the shared kernel

1. **Home.** `packages/shared/src/error-registry/`, exported by `@shared/types`. It is plain constants with no import outside its own directory, so the domain, the application core, both portals and a Node script can all read it. One file per domain under `domains/`, and a file's name is its domain.
2. **An entry** is written once, as a key of its domain's table, and holds: its code (the key itself), its domain, its category, its HTTP status, an English message for operators and developers, its parameters, and the portals that can receive it.
3. **Code grammar.** `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*$`, at most 63 characters, unique across every domain. A code names its subject first (`ADMINISTRATOR_ALREADY_EXISTS`, `ENV_VARIABLES_REFUSED`). A generic condition is one code of the `common` domain, never one code per context.
4. **A code's string never changes.** A rename is a new code: one change adds it, moves every site that raises the old one, and removes the old entry with its catalog keys. A code a front reads today keeps its string until the change that moves that front. Two meanings under one string are split: the meaning the fronts read keeps the string and the other takes a new code.
5. **Categories.** Thirteen, a closed set. A category allows a fixed set of statuses, and an entry's status must be one of them; the compiler refuses any other, and so does the check. An entry's status is the one it answers when it is raised. A carrier of a status (decision 2.7) answers its code at the status it carries, which the code's category need not hold: `INTERNAL_ERROR` and `REQUEST_REFUSED` are answered that way, each registered once, at its own status.

   | Category          | Statuses           | Meaning                                                                                                                                                            |
   | ----------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
   | `validation`      | 400, 415, 417, 422 | The request is malformed, or breaks a rule its caller can correct; 417 is an `Expect` header the server does not meet, which the caller corrects by leaving it out |
   | `authentication`  | 401                | No valid identity                                                                                                                                                  |
   | `permission`      | 403                | The identity may not do this                                                                                                                                       |
   | `not_found`       | 404                | The subject does not exist for this caller                                                                                                                         |
   | `conflict`        | 409                | The subject's state refuses the operation                                                                                                                          |
   | `too_large`       | 413, 414, 431      | The request, or what it would touch, exceeds a bound of size                                                                                                       |
   | `timeout`         | 408                | The request did not arrive whole within the time the server waits for one; sent again unchanged, on a new connection, it may pass                                  |
   | `rate_limit`      | 429                | Too many requests                                                                                                                                                  |
   | `not_implemented` | 501                | The operation is not available                                                                                                                                     |
   | `upstream`        | 502, 504           | A provider or another service failed                                                                                                                               |
   | `unavailable`     | 503                | A failure that a retry may pass                                                                                                                                    |
   | `configuration`   | 500                | The installation is misconfigured                                                                                                                                  |
   | `internal`        | 500                | A defect, or a failure nothing classified                                                                                                                          |

   `timeout` stands apart from `too_large` because a consumer acts on it differently. RFC 9110, section 15.5.9: "The 408 (Request Timeout) status code indicates that the server did not receive a complete request message within the time that it was prepared to wait. If the client has an outstanding request in transit, it MAY repeat that request. If the current connection is not usable (e.g., as it would be in HTTP/1.1 because request delimitation is lost), a new connection will be used." A request too large fails again unchanged; one that timed out may not.

6. **Message.** English, one sentence a developer or an operator can act on. Its `{name}` placeholders are exactly the entry's declared parameters. It says nothing the code does not: no value of a secret, no personal data.
7. **Parameters.** Declared by name and kind (`string`, `number`, `boolean`, `string[]`), and typed from that declaration at every site that builds the error. A parameter holds a name, an identifier, a count or a limit; it never holds prose, a secret or personal data.
8. **The existing types join it; none is replaced.** `Result`, `ok` and `err` are unchanged. `UseCaseError` gains `UseCaseError.of(definition, params)`, which accepts only a definition the registry built: an object literal written by hand is refused, because the definition's type carries a mark only `defineErrors` can give, and `defineErrors` is refused in production source outside the registry's directory, `packages/shared/src/error-registry/` (a test file may call it, since production cannot import test code). The mark does not refuse a spread copy of a registered definition with a field changed, which keeps the mark: the lint rule `errors/no-inline-error` refuses that copy at an `of` call, and `of` keeps only the copy's code and reads every other field from the registry's own entry. The ten `USE_CASE_ERRORS` become the `common` domain with their strings unchanged, `USE_CASE_ERRORS` now derived from it. `DomainError` gains the same `of` when its context is swept. An error raised outside the core is a `RegisteredError`, the kernel's own class. The constructors that take a message stay until the sweep ends and are then removed, so the compiler holds what the lint rule held.
9. **Class identity is not the test.** A consumer recognizes an error by its `code`, compared by value, never by `instanceof`: the core's dual conditional export puts two constructors in one process (`packages/core/domain/src/errors/DomainError.ts:121-131`).

Held by: `pnpm check:errors` (grammar, uniqueness, category and status, message and parameters, file and domain) and a type test of the registry.

### 2. One API error body

1. **RFC 9457, `application/problem+json`.** Its members, and no other:

   | Member          | Type     | Required | Holds                                                                                  |
   | --------------- | -------- | -------- | -------------------------------------------------------------------------------------- |
   | `type`          | string   | yes      | `https://omnipost.app/problems/<CODE>`, the identifier RFC 9457 asks for               |
   | `title`         | string   | yes      | The code in words (`Administrator already exists`), the same for every occurrence      |
   | `status`        | integer  | yes      | The entry's status                                                                     |
   | `detail`        | string   | yes      | The entry's message with this occurrence's parameters                                  |
   | `code`          | string   | yes      | The registered code                                                                    |
   | `correlationId` | string   | yes      | The request's correlation id, or its request id when none was set (decision 2.10)      |
   | `timestamp`     | string   | yes      | The instant the body was built, ISO 8601 in UTC                                        |
   | `params`        | object   | no       | The declared parameters and their values; absent when the entry declares none          |
   | `issues`        | object[] | no       | For a request that fails validation: each problem's part, pointer, issue code and text |

2. **One function writes it.** `toProblem` builds the body from any failure and `sendProblem` sends it, for the global error handler, for the path no route matches, for the requests the framework refuses before it routes them and for a request that reaches a server that is closing alike; for a connection whose request cannot be read, where the framework hands over a socket and no reply, its twin `sendProblemOnSocket` writes the same body and the same line through the same builders. No other code sets a status and a body for a failure. A route answers a failure by calling `sendProblem`; it does not raise a registered error to the global handler, which stays the net for what is raised by accident. The body keeps no member of the old bodies: the readers that need one change in slice 1 (see Consequences).
3. **A front never shows an error's own message.** The body's text is the registry's message for the error's code, and a command prints the same; what an error object carries as `message` goes to the log. So a text the registry does not hold cannot reach a front on this path, however the error was built.
4. **An error with no registered code answers `INTERNAL_ERROR`.** It is logged in full with the correlation id. A request that fails validation answers `VALIDATION_FAILED` with `issues`; a path no route matches answers `ROUTE_NOT_FOUND` in the same body. A request the framework refuses answers the `http` code of its own cause, known by the framework's own error code: a body larger than the route accepts (`FST_ERR_CTP_BODY_TOO_LARGE`) answers `PAYLOAD_TOO_LARGE` at 413; a content type the route does not accept, one that does not parse or one no parser takes (`FST_ERR_CTP_INVALID_MEDIA_TYPE`, one cause), `UNSUPPORTED_MEDIA_TYPE` at 415; and at 400 an empty JSON body (`FST_ERR_CTP_EMPTY_JSON_BODY`) `JSON_BODY_EMPTY`, JSON that does not parse (`FST_ERR_CTP_INVALID_JSON_BODY`) `JSON_BODY_NOT_PARSABLE`, a body that a hook's stream delivers at another length than its `Content-Length` (`FST_ERR_CTP_INVALID_CONTENT_LENGTH`) `BODY_LENGTH_MISMATCH`, which over HTTP/1.1 the connection's own framing refuses first, and a `QUERY` request with no content type (`FST_ERR_ROUTE_MISSING_CONTENT_TYPE`) `CONTENT_TYPE_MISSING`. The framework also hands on, at 400 and under Node's code, the error the request's own body stream fails with, told by its identity, the error the request's message was destroyed with: with no `preParsing` hook in the API, that error is Node's `ECONNRESET` "aborted", raised when the connection closes before the body arrived whole, and it answers `REQUEST_BODY_ABORTED`; since the client is gone, nothing is sent and the line says so. A refusal whose cause the registry does not name answers as a carrier of its status (decision 2.7): below 500, `REQUEST_REFUSED` at that status, which tells the client its request was refused and that the server holds no more specific code; at 500 or above, `INTERNAL_ERROR`. The plugins the API registers were read on 2026-11-20 for every error they can raise on a request below 500: `@fastify/cookie` 11.0.2 raises none (its parser, `cookie` 1.1.1, never throws on a header, and its signing errors are the server's own calls), `@fastify/helmet` 13.0.1 none (only errors of its own configuration, at 500), `@fastify/swagger` 9.7.0 none (it serves no route of its own, and its errors are the document's, at 500), and `fastify-type-provider-zod` 6.1.0 only a schema's refusal, which Fastify raises as `FST_ERR_VALIDATION` and the table answers `VALIDATION_FAILED`; a plugin added later brings the rows of its refusals in the change that adds it. Either is logged at error and reported to Sentry, since an unnamed refusal is a gap of the table, closed by a row: its line carries the code, the name and the message the refusal carries, which is what the row is written from. The installed framework raises one only as a defect of its own (`FST_ERR_NOT_FOUND`, when the router matched not even the not-found handler's catch-all route); a body stream error of another code, which only a hook's stream could raise, would be another. Its other errors with a 4xx status reach no request: `FST_ERR_VALIDATION` is answered as a validation failure, `FST_ERR_CTP_INSTANCE_ALREADY_STARTED` and `FST_ERR_INVALID_URL` are raised while parsers and routes are registered, and `FST_ERR_ROUTE_MISSING_CONTENT` is no longer raised. The refusals the framework makes before it routes a request reach the same path through the application's `frameworkErrors` option, each under the code of its own cause: a path whose percent-encoding does not decode (`FST_ERR_BAD_URL`) answers `PATH_NOT_DECODABLE` at 400, and a path parameter longer than the router's limit (`FST_ERR_MAX_PARAM_LENGTH`) answers `ROUTE_PARAMETER_TOO_LONG` at 414. The third error the framework hands that option, a failing async route constraint (`FST_ERR_ASYNC_CONSTRAINT`), carries 500 and answers `INTERNAL_ERROR`; the API registers no constraint strategy that could raise it. The framework builds those requests outside the route lifecycle, so no hook of the application runs for them: their answer carries no security header, counts against no rate limit and no metric, and their correlation id is the request id. A connection whose parser fails reaches the same builders through the `clientErrorHandler` option, which Node hands the connection's error and its socket and no request. The request timeout (`ERR_HTTP_REQUEST_TIMEOUT`) answers `REQUEST_TIMEOUT` at 408 and headers over Node's limit (`HPE_HEADER_OVERFLOW`) `REQUEST_HEADERS_TOO_LARGE` at 431. Seven codes name what Node's parser refuses, each at 400. Two name the request-smuggling shapes a request's length can take, since a `Content-Length` inconsistent with the message's framing "might cause a security failure due to request smuggling or response splitting" (RFC 9110 §8.6). A request that declares both `Transfer-Encoding` and `Content-Length` answers `TRANSFER_ENCODING_CONFLICTS_WITH_CONTENT_LENGTH` when the parser reports the conflict, told by llhttp's reason, since llhttp raises it under the code of whichever header it reads second. A `Content-Length` sent more than once, with the same value or another (`HPE_UNEXPECTED_CONTENT_LENGTH`, "Duplicate Content-Length"), answers `CONTENT_LENGTH_REPEATED`. A `Transfer-Encoding` value llhttp refuses on its own, such as `chunked, gzip`, where `chunked` is not last, is refused when that header is read, before a `Content-Length` after it, and answers `REQUEST_HEADERS_NOT_PARSABLE` like any other header that does not parse: the bytes the parser held are not read to find a `Content-Length`, since they can hold only part of the request, and secrets. The sixth code is within the Maintainer's decision of 2026-11-20 that split `REQUEST_NOT_PARSABLE` by the part of the message that is wrong, with the smuggling conflict on its own, and not into one code per code of Node's parser: it names the second smuggling shape, not one of llhttp's codes. The seventh, `REQUEST_INCOMPLETE`, names a message the client cut by ending its side before it was whole (`HPE_INVALID_EOF_STATE`), wherever the cut falls: `llhttp_finish` (`deps/llhttp/src/api.c`) returns that code only while the parser's `finish` state is unsafe, which `deps/llhttp/src/llhttp.c` sets at a message's first byte and clears when the message completes, and it returns success for a parser already failed; Node calls it, and hands its error to the `clientError` listener, only when the client ends its side (`socketOnEnd`). The cause is told apart by that code alone, so it has a code of its own, as the error system's rule of uniformity asks of a cause that can be told apart, and the Maintainer decided it on 2026-11-20; its message tells the client to send the whole request before ending its sending side, where the codes of the part told it to check its headers or its chunks. The four others name the part of the message the error finds wrong: `REQUEST_LINE_NOT_PARSABLE`, `REQUEST_HEADERS_NOT_PARSABLE`, `REQUEST_BODY_FRAMING_NOT_PARSABLE` or `DATA_AFTER_REQUEST_UNEXPECTED`. Node's code names the part whenever llhttp raises it in one part only, wherever the request stands; for the two codes llhttp raises in more than one part, `HPE_STRICT` and `HPE_CR_EXPECTED`, the position decides: the body's framing while a request's own body is being read, otherwise the request line for `HPE_STRICT`'s reason after the version, and the headers for any other reason:

   | Node's code (`error.code`)                                                                                                                                                          | Part, and code answered                                                                                                                                                                                              |
   | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `HPE_INVALID_METHOD`, `HPE_INVALID_URL`, `HPE_INVALID_VERSION`, `HPE_INVALID_CONSTANT`, `HPE_PAUSED_H2_UPGRADE`                                                                     | The request line: `REQUEST_LINE_NOT_PARSABLE`                                                                                                                                                                        |
   | `HPE_UNEXPECTED_SPACE` (a first header line that starts with a space), `HPE_INVALID_HEADER_TOKEN`, `HPE_LF_EXPECTED`, `HPE_INVALID_CONTENT_LENGTH`, `HPE_INVALID_TRANSFER_ENCODING` | The headers: `REQUEST_HEADERS_NOT_PARSABLE`                                                                                                                                                                          |
   | `HPE_UNEXPECTED_CONTENT_LENGTH`                                                                                                                                                     | A `Content-Length` sent more than once: `CONTENT_LENGTH_REPEATED`                                                                                                                                                    |
   | `HPE_INVALID_CHUNK_SIZE`, `HPE_CHUNK_EXTENSIONS_OVERFLOW`                                                                                                                           | The body's framing: `REQUEST_BODY_FRAMING_NOT_PARSABLE`                                                                                                                                                              |
   | `HPE_CLOSED_CONNECTION`                                                                                                                                                             | Data after the message: `DATA_AFTER_REQUEST_UNEXPECTED`                                                                                                                                                              |
   | `HPE_INVALID_EOF_STATE` (the client ends its side in the middle of a message's line, headers or body)                                                                               | A message cut by its client: `REQUEST_INCOMPLETE`                                                                                                                                                                    |
   | `HPE_STRICT` (after the version, after the headers, in a chunk), `HPE_CR_EXPECTED` (after a header value, in a chunk)                                                               | By position: `REQUEST_BODY_FRAMING_NOT_PARSABLE` while a request's own body is read; otherwise `REQUEST_LINE_NOT_PARSABLE` for "Expected CRLF after version" and `REQUEST_HEADERS_NOT_PARSABLE` for any other reason |

   The codes are llhttp's `llhttp_errno` names as Node 26.13.1 vendors them (`deps/llhttp/include/llhttp.h`), each placed by the reasons `deps/llhttp/src/llhttp.c` raises it with, and Node's own `HPE_CHUNK_EXTENSIONS_OVERFLOW` and `HPE_HEADER_OVERFLOW`. No request makes Node raise the others: `HPE_INVALID_STATUS` is a response parser's; `HPE_INTERNAL`, `HPE_PAUSED` and the `HPE_CB_*` callback errors come from callbacks Node does not fail that way; Node's binding (`src/node_http_parser.cc`) turns `HPE_PAUSED_UPGRADE` into success before any error is built ("This isn't a real pause, just a way to stop parsing early"), and renames `HPE_USER` to the code its reason starts with, `HPE_HEADER_OVERFLOW`, `HPE_CHUNK_EXTENSIONS_OVERFLOW`, `HPE_JS_EXCEPTION` or `HPE_REENTRANT_EXECUTE`, the last two the server's own faults. A code the table does not name, a parser's or a socket's, answers as an unnamed refusal of the client's request wherever the request stands, and is never given a parser's code: `REQUEST_REFUSED` at 400, logged at error under Node's code. Node's code stays in the line as the cause's.

   With a request in flight whose own message fails, in its body or in a header llhttp checks once the request is dispatched, the failure is that request's: it is answered once, under its own correlation id, method, url and address, and its later failures, its body stream's once the connection closes, write no second line and send nothing. On a connection, an answer is never written ahead of the answer of a request that arrived before it. When an earlier answer on the connection is still to end, the failure's answer waits until every earlier answer has ended, as for a following message below, and its line names in `inFlightCorrelationId` the request it waited for last; the earlier requests finish and are answered as if nothing followed them, and the connection closes after the failure's answer. Node's own listener would write its 400 at once, ahead of an earlier answer not yet started, which the client would then read as the answer to its earlier request. When the failing request's own answer has already started by the time its failure is written, or was sent whole before its body arrived, no byte is written, since a second status line inside or after its response would answer it twice: the line says the failure came after the answer and the connection is destroyed at once, as Node's own handler does. A request is in flight from the first `onRequest` hook, which appends each request to its connection's list in the order they arrive, until its answer is sent and its own message has been read whole. Only the latest request can still be read when a failure arrives, since the parser reads one message at a time, and responses end in the order their requests arrived, so the request just ahead is the last of the earlier ones to end. The list holds no more than the requests Node itself keeps unanswered on that connection and is kept by the socket weakly, so it cannot outlive its connection; Node keeps the requests a connection holds in fields it does not document. A refusal waits until every answer ahead of it on its connection has ended, and never for one that already has. An answer has ended once its response emitted `close`, which Node documents as "Indicates that the response is completed, or its underlying connection was terminated prematurely (before the response completion)"; the tracking hook records that event for each request (`recordAnswerEnd`). No documented property of the response tells the same: `writableFinished` "Is `true` if all data has been flushed to the underlying system, immediately before the 'finish' event is emitted" and `writableEnded` "Is `true` after `response.end()` has been called. This property does not indicate whether the data has been flushed", and a response destroyed before it finished keeps both false while its `close` is already past; Node's `http.ServerResponse` documents no `destroyed` and no `closed`, and it extends `http.OutgoingMessage`, which extends `Stream`, not `stream.Writable`. So a tracked answer not started, started and streaming, or ended by its route but queued behind an earlier response has its `close` still to come, and can still reach the client; a finished one has handed its last byte over and emits `close` on the next tick; one destroyed before it finished (a route that destroys its hijacked response, or Fastify when a stream fails once the head is sent) emits `close` once and never finishes, though the bytes a queued one buffered are still written when it gets the connection; and a closed one has nothing more to send. After an answer that was cut, a chunked stream that failed once its head was sent, the refusal's bytes follow a chunked body that never received its last chunk: a client that reads that body in order takes the refusal's status line and body for more of its chunks and cannot parse the refusal, while the order holds and the refusal's line is written. The refusal waits for the nearest answer ahead that has not emitted `close`; once that one does, it reads the answers ahead again, since an answer destroyed while it was waited for says nothing of the answers before it, until none is still to end, and its line names in `inFlightCorrelationId` the request it waited for last, whose answer its own follows on the wire. When no answer ahead of a refusal is still to end, the refusal is written at once, as with no request in flight, with no `inFlightCorrelationId`: under the failing request's own id, method and url when the failure is that request's, and under an id generated for it, with null for the method and the url, when it is a message no request was read from. A route that hijacks its reply leaves the list like any other: Fastify attaches its `finish` listener, which runs the `onResponse` hooks, when the route starts (`lib/route.js:557-558`, `lib/reply.js:1014`), and `reply.hijack()` does not remove it (`lib/reply.js:134-150`); a hijacked reply still streaming is an answer in progress, which a refusal behind it waits for. The tracking hook is the first `onResponse` hook the server registers, and it runs synchronously, so no hook of the application runs ahead of it while a response closes.

   A message that fails after a complete request in flight is its own event, and the request in flight is not failed by it: that request is answered by its route and writes no line for the failure, and the failure gets an id generated for it, null for the method and the url, the connection's address, the code the table gives its cause exactly as with no request in flight, and one more field on its line, `inFlightCorrelationId`, the correlation id of the request in flight, the latest to arrive. Its answer is written after the answer in flight ends, never between or over it, since on a reused connection "responses are associated with requests by their order on that connection" (Node's documentation of `http.Agent`): it waits for that response's `close` event, which "indicates that the response is completed, or its underlying connection was terminated prematurely", then writes the problem while the socket can still be written and closes the connection. When the answer in flight closed the connection itself (`Connection: close`), or the client went away, nothing is written and the line says so. Node leaves closing the socket to the `clientError` listener when the client's end of its side cuts a message and when the request timeout fires (`socketOnEnd` and `onRequestTimeout` in Node's `lib/_http_server.js`, whose comments say the error path "will call socket.destroy(err)"). So whenever the client has ended its side of a connection whose refusal waits, at the failure or at a later call for it, the server ends its own side at once, as Node does when a client ends its side between messages, since the server allows no half-open connection; the refusal then finds a connection that can no longer be written, and its line says so. A client that ends its side after a failure llhttp raised needs nothing more: Node raises no error at the end of data for a parser already failed, and ends the server's side itself. While the client stays connected, nothing but the end of the answer in flight bounds the wait, and no timer is added. The server leaves the framework's `handlerTimeout` and `connectionTimeout` at 0, so a request in flight whose route never answers holds its connection, with its client connected, as long whether or not a message follows it: Node's request timeout bounds only a message still being received. When it fires for the following message, the request timeout is that message's failure, or a second error of a message already refused, and the client gets the answer in flight whole, then the refusal, then the close; Node's own listener would write its 408 at once, ahead of an answer in flight not yet started, and destroy the connection, which loses that answer. The failed message read whole after its request timeout was answered is not taken, and neither is a request pipelined after it, since the connection closes after its refusal: a request read on a connection already answered runs no route and no later hook, sends nothing, and writes one line that names the refusal (decision 2.9). Node's documentation of `clientError` says: "The socket **must be closed or destroyed** before the listener ends." This answer departs from it on purpose, in one case: while a refusal waits for the answer in flight and its client stays connected, the listener returns with the socket open, at the failure and at each later call for it, and the socket is closed once that answer ends, since closing it before would cut the answer in flight.

   As Node's documentation of `clientError` and the framework's of its option ask, the answer is written to the socket as one whole HTTP response, only while the socket can still be written, and the connection is closed. A connection is answered once. Node calls the listener again for it in three ways: for every later chunk of a parser that stays failed, since llhttp returns its error again; for the request timeout of the failed message, which stays among the messages Node times out; and for the end of data, when the client ends its side in the middle of a message the parser has not failed. None of them writes anything more; the last two end the server's side once the client has ended its own, as above. A connection the client reset, or one already destroyed, is left as it is, with no answer and no line of its own. No hook runs for these answers either.

   A `CONNECT` request answers `CONNECT_NOT_IMPLEMENTED` at 501 on its socket, then the connection closes. The server is not a proxy and opens no tunnel: RFC 9110 §9.3.6 says "An origin server MAY accept a CONNECT request, but most origin servers do not implement CONNECT", and §15.6.2 defines 501 as "the server does not support the functionality required to fulfill the request"; a 405 would name a target resource and the methods it allows (§15.5.6), and the target of a CONNECT is a host and a port, not a resource of this server. The registry's `NOT_IMPLEMENTED`, "This operation is not available", does not say that cause, so the `http` domain holds a code of its own for it. Node hands a CONNECT to the server's `connect` listener and, when nothing listens, closes the connection with no answer: "If this event is not listened for, then clients requesting a `CONNECT` method will have their connections closed." It passes the request, the socket, and "The first packet of the tunneling stream (may be empty)", and it removes its own listeners from the socket first: "After this event is emitted, the request's socket will not have a `'data'` event listener". So the listener reads and drops every byte that follows, that first packet included, keeps a socket error from being thrown, and ends the server's side when the client ends its own, as Node does between messages. The answer's line carries an id generated for it, the method and the target Node parsed (`url` is the target's authority form, `host:port`), and the connection's peer as its address, since the framework never reads the request. Behind a request still in flight on the connection, it waits for that request's answer, as every answer on a connection does, and names it in `inFlightCorrelationId`. A 501 is logged at error and reported, by the rule of decision 2.9, so a CONNECT a scanner sends is a Sentry event. A request with an `Upgrade` header is not this case: with nothing listening for `upgrade`, Node keeps it an ordinary request (its default `shouldUpgradeCallback` is `listenerCount('upgrade') > 0`), and the server's handler routes it.

   A request whose `Expect` header asks for something other than `100-continue`, which Node emits as `checkExpectation` and would answer with its own 417 and no body, is handed to the server as any other request and answers `EXPECTATION_UNSUPPORTED` at 417 from the first `onRequest` hook, under its own id, method, url and address; `Expect: 100-continue` is untouched. A request that reaches the server once it has begun to close answers `SERVER_CLOSING` at 503 from the first `onRequest` hook, before any other hook and its route; the server is built with `return503OnClosing: false`, since the framework's own refusal writes its body past every hook, and the framework still sets `Connection: close` on such a request, so the client sends it again on a new connection. Those two answers come before every other `onRequest` hook, the IP allowlist's included, so they carry the headers the security manager sets in its `onSend` hook and none of helmet's, which helmet sets in an `onRequest` hook registered after them, as the framework's refusals carry no security header.

5. **A failure of category `internal` or `configuration` answers as `INTERNAL_ERROR` on the wire.** Its own code and message go to the log and to the operator's command, never to an HTTP client.
6. **Only declared parameters are serialized.** A value the entry does not declare is dropped. A response header a failure needs (`Retry-After`, `WWW-Authenticate`) is derived from the entry's category and a declared parameter, never set where the failure is raised. No code derives such a header yet: every answer of the system carries none (`NO_HEADERS`, `apps/api/src/lib/errors/problem.ts:105`), so a 401 it answers has no `WWW-Authenticate` and a 429 no `Retry-After`, and the two 429s that send `Retry-After` are written by hand outside `sendProblem`; the plan row ERROR-BODY-DERIVED-HEADERS-NOT-BUILT holds the build.
7. **The classes not yet swept keep the status they answer today.** An `AppError` whose code is not registered answers in the same body with its own status, code and message, and any other error that carries an HTTP status keeps that status and answers `REQUEST_REFUSED` below 500 and `INTERNAL_ERROR` at 500 or above. Two functions hold this, and each is removed when the class it serves has no construction site left. These are the one exception to point 3, and every site that reaches them is in the baseline of decision 8.
8. **The generated contract publishes it once**, as the component schema `Problem`. `code` is a string of the code grammar, not an enumeration: the catalog of codes is the reference page of decision 4, so adding a code does not regenerate the contract. Every operation declares it as its `default` response in the change that closes the sweep, when that is true of every route.
9. **One log line per answer, the same fields on every path.** Every failure the server answers, or would answer if its client were still there, writes exactly one line: `code` (the code the failure carried, the framework's or Node's included, and otherwise the code answered), `wireCode`, `status`, `source`, `requestId`, `correlationId`, `method`, `url`, `ip`, `ipSource` and `error`, and on the line of a failure whose answer waited for an earlier request's, `inFlightCorrelationId`, the correlation id of the request it waited for last, whose answer its own follows; Sentry's report carries the same `ip`, `ipSource` and `inFlightCorrelationId`. `ip` is the client's address as `resolveClientAddress` derives it, through the one resolver the security canon names, and `ipSource` says where it comes from, decided by the same branches: `forwarded` when a trusted proxy reported an address other than its own, and `peer` when it is the connection's peer, as it always is under `socket-only`. The two travel together, kept from the moment the request arrives, since Node no longer gives a closed connection's peer; a peer that cannot be read is `unknown`, with the source `peer`. On a connection whose parser failed on a message no request was read from, with no request in flight or after a complete one, the address is the socket's peer, the one address there is, behind a trusted proxy the proxy's own, with the source `peer`, and `method` and `url` are null, since no request reached the server's handler. `error` is the failure as a list of fields, never the value: its name, its message, its code when it carries one, a numeric code written as its decimal string, its stack and, for an `AppError`, whether it is operational; each cause of its chain is carried in the same shape, its code included, up to five deep, the last one followed marked `causeOmitted` when the chain goes on, and a value that is not an `Error` as its type and its code. `requestId` is the request's id, the one the framework's own lines for the request carry as `reqId`, so the failure joins them by that value whatever correlation id a hook sets; on a connection whose parser failed on a message no request was read from, and on a CONNECT, it is the id generated for the answer, equal to its `correlationId`, which no line of the framework carries. It is named `requestId`, as Sentry's report of the same failure names it, and not `reqId`, which a request's own logger binds already: a route that hands `sendProblem` its request's logger would then write the key twice in one line. The line's message says when nothing reached the client: after an answer already sent, or on a connection that can no longer be written. A request read on a connection already refused for a failure of its parser is not taken (decision 2.4) and is no failure of its own: it gets no answer and writes one line at info, the level of the framework's own lines for a request, beside its "incoming request" line, so that whoever traces it finds where it ended. The line's message is "Request not taken: its connection was already refused", and its fields are `requestId`, `correlationId`, `method`, `url`, `ip`, `ipSource` and `refusalCorrelationId`, the correlation id of the refusal that closes its connection. `inFlightCorrelationId` is not reused for it: that field names a request ahead of a failure, and this one names a refusal ahead of a request. The line is not reported to Sentry, which takes only the lines at error. The severity follows from the status. A failure at 500 or above, of the server or of something it depends on, is logged at error and reported to Sentry, and so is a failure its raiser did not expect: a value no step classifies, a carrier of a status the table has no row for, a registered code that misses a declared parameter, a non-operational `AppError`. An expected refusal of the client's request is logged at warn and not reported. Every category's statuses are all below 500 or all at 500 or above, `timeout` with 408 among the first, so by category the rule reads: `not_implemented`, `upstream`, `unavailable`, `configuration` and `internal` at error, every other category at warn. The rule has no exception by code. `SERVER_CLOSING` was the case considered: its 503 is expected on every deployment, and the Maintainer decided on 2026-11-20 that it stays at error and reported like any other 503, declining a registry field that would mark a code as expected; its cost is at most one report per connection that was busy when the close began, on each deployment.
10. **The correlation id names one request.** It is the request's id, a random UUID the server generates for every request, unique across boots and instances; the framework's own request lines carry it as `reqId`. The answer to a connection whose parser failed on a message no request was read from carries one generated the same way. No header a client sends is read for it, since a header a client controls would let it choose the id another request's lines carry. Accepting one from an edge the API trusts is not decided: it would need the edge to overwrite that header on every request, the server to read it only when the immediate peer is a trusted proxy, as `resolveClientIp` decides, and a bound on its form. A hook that sets `request.correlationId` takes precedence over the request id in the body and the line, and the line still carries the request id as `requestId` (decision 2.9).

Held by: the handler's suites, the suites of the framework's refusals, of a connection whose parser fails (its mapping by a table-driven suite, every code a request can produce over a real socket), of a closing server and of the correlation id, all on the server `createServer` builds, the contract drift gate, and the lint rule of decision 4, which refuses a hand-written reply.

### 3. User-facing text lives in each front's catalogs, keyed by code

1. **A portal's text for a code is the catalog message `errorCodes.<CODE>`**, in every locale that portal declares, formatted with the body's `params`. The namespace holds registered codes and nothing else.
2. **The API never sends user-facing prose as the contract.** `title` and `detail` are English, for developers. A portal renders its own text for the code and falls back to one generic message, outside the namespace, for a code it does not know.
3. **An operator front reads the registry.** A command and a log line show the entry's English message with its parameters; they have no locale.
4. **A portal is held to the registry from the change that gives it the namespace.** From then on every code that names the portal has its key, no key is left without a code, each message uses only declared parameters, and the namespace cannot be removed.

Held by: `pnpm check:i18n` (fitness #51: every locale holds the default locale's keys and argument names, and every message is valid ICU) and `pnpm check:errors` (the two directions between registry and catalog, and the parameters).

### 4. Enforcement in three layers

1. **A lint rule at `error`: `errors/no-inline-error`**, in a new workspace package `@packages/eslint-plugin-errors`, built and tested as the existing in-house plugin is. It is syntactic and needs no type information. Its scope is every TypeScript source file of the tree but a named list of exclusions (test files, tooling, and the fronts, which get their own rule), so a new package is in scope the day it is created; a file under a source directory never leaves the scope by its name or its extension. An error class is an identifier that starts with an upper-case letter and ends in `Error`. The rule reports:
   - an error built outside the registry path: `new <Name>Error(…)` for any class but the runtime's own; a call of any static member of such a class but `of`; any other use of such a class as a value, so an alias cannot hide it; and a class that extends `Error` directly;
   - a registry path that does not start at the registry: a first argument of `of` that is not a member of a registry table imported from the shared kernel, and any use of `defineErrors` outside the registry's directory, `packages/shared/src/error-registry/`;
   - a failure answered by hand: any use of a legacy reply helper, and a `send` on a reply whose status is not a literal below 400 or whose body is an object literal with an `error` key or `ok: false`, anywhere but in the one file of the function that writes the body, which the rule's options name. A body literal whose `ok` is `true` excuses a status that is no numeric literal, and nothing else;
   - a code or a message written as a literal where a failure is returned: `err("…")`.

   A plain runtime `Error` needs no registered code: the rule keeps its default list of the runtime's own errors, so `new Error(…)` is not a site. It is the shape of a defect, its text reaches a log only (decision 2.3), and it answers `INTERNAL_ERROR`.

   The registry path is `<Class>.of(<TABLE>.<CODE>, params)`, which takes no text. The sites the tree holds today are listed in `eslint-suppressions.json`, per file and per rule, by ESLint itself. For each shape the contracts list the ways around it and what stops each; what no rule can see is stopped by decision 2.3 or is stated there as a limit.

2. **An integrity check, `pnpm check:errors`, fitness #57**, which runs two scripts. The registry gate holds decisions 1 and 3 and the reference page. The sites gate holds decision 8.
3. **A generated reference page, `docs/api/ERROR_CODES.md`**: every code with its domain, category, status, message, parameters and portals, and the trend of decision 8. The registry gate fails when the committed page is not what the registry yields.
4. **The boundary fails closed.** The body is built from the registry by the error's code, compared by value; what does not resolve answers `INTERNAL_ERROR`. So on the registry path no status and no text reach a client that the registry does not hold, whatever the lint rule missed. The exception is decision 2.7, for the length of the sweep: an `AppError` still answers with its own status, code and message, and its sites are counted.
5. **The rule's files are a guarded path.** `packages/eslint-plugin-errors/`, `scripts/testing/lib/error-scope.mjs` and `scripts/testing/error-sites-gate.mjs` are entries of the hooks' list of guarded paths (`.claude/hooks-py/pre_edit.py`): a session edits them only inside a window the Maintainer opens, as it does the workflows and the hooks themselves. So is `scripts/testing/lib/issue-reminder.mjs`, the module the sites gate's stall alarm keeps its issue through: it counts nothing, but a session that could edit it could silence the alarm. The patched-dependencies gate shares that module, so a change to either gate's reminder waits for a window too. The entries are in force once the change that adds them reaches the main branch, so the changes that write the rule, the list and the gate come before the guard. The sites gate's rule S9 (decision 8.4) is kept beside it.

### 8. The list of existing sites is verified to shrink

The baseline is the set of entries of the `errors/` rules in `eslint-suppressions.json`. Seven things hold it, and each is a check that exits non-zero:

1. **Per file, in both directions.** ESLint holds each file's count: a file with more sites than its entry fails `pnpm lint`, a file with fewer fails it until the entry is pruned, and a file with no entry must hold none. ESLint looks only at the files it lints, so the sites gate closes what that leaves: an entry whose file git no longer tracks fails, and so does an entry whose file the rule no longer reaches.
2. **The rule reaches every file it should, as ESLint resolves it.** For every tracked TypeScript file the sites gate asks ESLint itself for the effective configuration: a file inside a rule's scope has that rule at `error`, with the options the gate holds, run by the very plugin the rule package exports, and is not ignored; a file outside it is on the named list of exclusions for that rule, which has one home and which the configuration is built from. A list of test files or a global ignore widened so that a file of the scope leaves the rule, a later block that turns the rule off, a changed option, a copy of the plugin, a processor, or another parser or language for the file all fail here, whatever the text of the configuration says. No `eslint-disable` directive names an `errors/` rule, and none names no rule at all; no inline configuration comment names an `errors/` rule, whatever it sets.
3. **Against the base, on every pull request, per file and rule.** Renamed files are first read under their old paths. Then the head's count is at most the base's; a file the base does not list has no entry; a file whose count fell has changed content, or is deleted; and a file the base lists that was renamed is still inside the scope. A count rises in one case only, a recorded move.
4. **A change of the rule and a change of a count never share a pull request.** When the rule package, the scope list or the sites gate differs from the base, every count of a rule the base holds is unchanged. A rule weakened so that counts fall therefore cannot land: the lint run demands a prune, and the prune is the change of a count this refuses. A rule changed to find more sites lands with those sites fixed, or as a new rule, whose entries are its birth. **A limit remains, and the guard of decision 4.5 narrows it.** A rule weakened in a way that moves no count today passes, and a later pull request can then lower a count through it; no check of this record stops those two in a row. What stands in front of the first of them is that the rule's files are edited only inside a window the Maintainer opens.
5. **A history, one row per change, that adds up to the tree.** `scripts/testing/error-sites-history/` holds one file per row: the birth of a rule with its totals per context, or the sites a change fixed per context and the moves it made. The births minus everything fixed equal what the baseline yields, per context. On a pull request, counts that differ from the base's require exactly one new row, and the row is what the difference yields; equal counts add none; and no earlier row is edited. A row only ever subtracts, so the totals of the reference page only fall. Rows are separate files that add up in any order, so two changes of the sweep do not collide.
6. **A rename is not a change of count, and a move is recorded.** A file git reports as renamed keeps its count under its new path and needs no row; when the rename crosses two contexts the row records it as a move. A move between two different files is allowed inside one context, as a row that names the file that loses the sites and the file that gains them; the context's total may not rise.
7. **No feature closes over its contexts.** From slice 3, each context with a count above zero is an item of the feature that owns it, in the plan's own item format, open while the count is above zero; the sites gate fails when the item is missing or marked closed. Fitness #56 then refuses to close that feature. Until slice 3 the plan's existing item on the error bodies tracks the whole sweep.

**The stall alarm.** Beside the seven, and not a gate: `.github/workflows/error-sites-stall.yml` runs on a schedule and runs the sites gate with `--stalled --days 14 --remind`. When 14 days pass with no new history row while the total is above zero, it opens an issue. It blocks no merge, and it does not say whether the pace is enough.

What these verify, said plainly, each with its bound: a count never rises; a count falls only when its file changed under a rule and a scope that did not change in that same pull request, which says nothing of two pull requests in a row (the guard of decision 4.5 is what stands there); the history adds up to the tree; no feature closes over a context above zero, from slice 3 and with fitness #56 in the branch, not before. What they do not verify: that the list moves at all. Nothing above turns red when nobody sweeps; the stall alarm is what reports it.

Four more limits stay, stated rather than closed. A count is not a line: a change that fixes one site of a file and adds another keeps the count. A site rewritten into a shape the rule does not see (its list is in the contracts) lowers the count while the legacy answer stays; on the registry path decision 2.3 keeps its text from a front. A push straight to the main branch has no base to compare with: branch protection is what stops it. And a file deleted and added again under a root the scope excludes whole (the fronts and the tooling packages) leaves the list with no conversion, and nothing refuses a backend import of such a package.

This adopts the reading the Maintainer's request was given, with three changes for the same guarantee. The per-file baseline is ESLint's own file and not a second one, because a second count needs a second matcher or a second run of the rule, and either can disagree with `pnpm lint`. "A pull request of the sweep lowers the total" is stated as a property of every pull request, since no check can tell which pull request is "of the sweep": any change of the counts is a row, and a row only subtracts. And a move between two files of one context is allowed when it is recorded, so a refactor of a route file is not forced to convert it.

### Forks and questions of the design, decided

Fork 1 and questions 3 to 6 were decided by the Maintainer on 2026-11-20; fork 2 was settled on the same day by a standing rule. Each line says what was decided and where this record carries it; the option not taken is under Alternatives Considered.

1. **How a route answers a failure.** A route calls the one reply function, `sendProblem`, and does not raise to the global handler. ADR-0006 stands unamended, and so does the coding standard's rule on `Result`. Decision 2.2.
2. **The readers of the error body.** Settled by the standing rule that the frontend couples to the backend, not by a new answer: the readers change in slice 1, and the body keeps no member for an old reader. Decision 2.2 and the Consequences.
3. **The runtime's own `Error`.** It needs no registered code, and the rule keeps its default list of runtime errors. Decision 4.1.
4. **Moves between two files.** Unswept sites may move between two files of one context, as a move recorded in the history; a context's total may not rise. Decision 8.6.
5. **A list that stops shrinking.** A scheduled run opens an issue when 14 days pass with no new history row while the total is above zero. Decision 8, the stall alarm.
6. **Who may change the rule that counts the sites.** The rule package, the scope list, the sites gate and the reminder module its stall alarm speaks through are a guarded path of the hooks, edited only inside a window the Maintainer opens, and the sites gate's rule S9 is kept. Decision 4.5.

The origin of `type` is `https://omnipost.app`, as the SAML entity id already uses it (`packages/core/auth/src/ConfigureSamlUseCase.ts:49`), and the codes of the required password change belong to slice 2: both are decided too.

## Rationale

- **A code is the contract and the text is not.** RFC 9457 makes `type` the primary identifier and tells consumers not to parse `detail`. Google's AIP-193 makes the pair of domain and reason the machine identifier and keeps the message developer-facing. Azure's guidelines make the code string the contract and nothing else of the body. The W3C asks protocols for "language independent identifiers for errors". Every one of them separates the identifier from the wording, which is what lets each front own its wording.
- **A front words the code.** The frontend adjusts to the backend, the API negotiates no language, and fitness #51 already holds the catalogs. A server-side localized message would add a second home for product text.
- **One list, checked, as the compilers do it.** rustc's tidy check holds every error code to an explanation, a test and an emission; PostgreSQL generates its headers and its documentation table from one file. The registry gate and the generated page are the same two ideas.
- **Defined per domain, identified globally.** AIP-193 partitions reasons by domain, and Evans asks that a shared kernel stay small. One file per domain keeps a change local, and the kernel holds the definitions only, never behaviour.
- **Codes by value, not classes.** The tree's own comment on `VERSION_CONFLICT_CODE` records that `instanceof` fails across the core's two module instances. A registry of codes makes the by-value comparison the only one.
- **The lint rule during the sweep, the compiler after it.** A syntactic rule cannot prove a code is registered; a constructor that takes only a definition can. While both constructors exist the rule refuses the old one, and when the old one is deleted the type system replaces the rule's main report.
- **ESLint's suppressions as the baseline.** The tree already uses them as a shrink-only list. They count with the rule itself, so the baseline cannot disagree with the lint run, and they fail in both directions for every file ESLint lints; the sites gate holds the files it does not (`node_modules/eslint/lib/services/suppressions-service.js:83-124` prunes by lint results and by missing files only).
- **Internal failures collapse on the wire.** OWASP's error-handling guidance is that details are logged server-side and not returned. The operator still reads the specific code, in the log and in the command.

## Alternatives Considered

- **A baseline file of our own, on the model of fitness #53.** Rejected: the gate would re-run the rule over the tree or count with a matcher of its own. The first doubles the cost of `pnpm lint`; the second is a second definition of a site.
- **`no-restricted-syntax` selectors instead of a rule package.** Rejected: every selector shares one rule id, so the baseline's entries could not be told from any other restricted syntax, no `RuleTester` suite pins a selector, and a selector cannot express "inside the class's own `of`" or "imported from the shared kernel".
- **Pinning the text of the rule's block in `eslint.config.ts`**, as fitness #49 pins its rules. Rejected: a list of test files or a global ignore outside the block changes what the rule reaches without touching it. The sites gate asks ESLint for the resolved configuration of each file instead (`ESLint#calculateConfigForFile` and `ESLint#isPathIgnored`, verified on ESLint 9.39.5).
- **One history file with a row of totals per change.** Rejected: two changes of the sweep made in parallel both append to the same array and both state totals the other makes stale. Rows that only subtract, one file each, add up in any order.
- **A type-aware rule that proves the argument is a registry definition.** Rejected for now: type-aware linting is limited to three directories because the full project runs out of memory (`eslint.config.ts:28-38`). The typed `of` gives the same proof at compile time.
- **The server localizes the message** (RFC 9457's `Accept-Language`, AIP-193's `LocalizedMessage`). Rejected: decision 3's rationale.
- **A composite code, `<domain>.<REASON>`.** Rejected: every code a front reads today is a flat string, and a comparison by code alone would become ambiguous.
- **A code enumeration in the generated contract.** Rejected: every new code would regenerate a file every unit shares; the portals import the registry itself.
- **The registry in the application core.** Rejected: the portals cannot import the core, and a port may use only the vocabulary of `@core/application/UseCase`.
- **`neverthrow`, `effect`, an RFC 9457 plugin.** Rejected: `neverthrow` has had no release since February 2025; `effect` 4 is seven weeks old; the Fastify organization has no RFC 9457 plugin and the third-party ones have 227 and 14 weekly downloads. The body is one function.
- **One code per failure the handler cannot name.** Rejected: RFC 9457 advises against a problem type for what a status already says.
- **A route raises the registered error to the global handler.** Rejected: ADR-0006 rejected "Throw + global error handler" because signatures lie, error semantics collapse and routes must know every raised error, and those reasons still hold. It would also amend ADR-0006 and the coding standard, and a route's own `catch` could swallow the failure for the length of the sweep.
- **The body keeps `ok` and `message` until both portals read it.** Rejected: the frontend adjusts to the backend, never the reverse. The body would not be one shape from its first day, and the contract would change twice, once to add the members and once to remove them.
- **A registered code for the runtime's plain `Error`.** Rejected: a plain `Error` is the shape of a defect and its text reaches a log only. It would add 334 sites in 148 files to the baseline, each a failure nobody should see.
- **Only a rename keeps a count.** Rejected: a refactor that splits a route file would be forced to convert what it moves, which couples the open route refactors to the sweep.
- **No check reads the calendar.** Rejected: nothing else verifies that the list moves, and the list can stand still for months with every check green.
- **The sites gate holds a hash of the rule package's content.** Rejected: every change of the rule edits the pin, and its author writes its own reason, which is the case the hooks exist to stop.
- **No guard, with the limit stated.** Rejected: a change under the rule package that moves no count would pass every check, and only a review of that diff would stand.

## Consequences

- The coding standard's rule on the error body is amended by this record: the four fields become the body of decision 2. `statusCode` is `status`, `message` is `detail`, and `requestId` gives way to `correlationId`.
- The body of every raised error changes shape in slice 1: a failure the global handler answers, a request a route's schema refuses, and a path no route matches. A route that answers through a legacy helper is untouched. The readers, measured in both portals and the packages they share: the shared reader takes the code from the top level already and loses the server's sentence for a 4xx that is neither 401 nor 403 (`packages/api-errors/src/ApiError.ts:89-90`, `:101-125`); the client's request function builds its error from `message || error`, which is an object today and is nothing after, so its 34 screens would show an empty text (`apps/client/lib/api/clients/request.ts:50-53`, `:90-93`); the client's sign-in reader and the other readers of the form `error ?? message ?? <text>` show their own text, where today they are handed an object (`apps/client/lib/auth/authApi.ts:25`), and a reader of `message ?? <text>` alone shows its own text before and after (`apps/client/hooks/api/useBrandVoice.ts:52`); and the administrators' sign-in reader shows its generic text before and after (`apps/admin/lib/auth/backend-client.ts:132-145`). The readers change in slice 1 so that each reads the body whole: the client's request function and its `ErrorResponse` type, the shared reader and the client's sign-in reader read `detail` last, and the body keeps no member for them. The contracts list every reader.
- Every line the API writes for a request carries a UUID as its request id, where it carried `req-<n>`, and so does every answer's `correlationId`. A registered failure at 500 or above, and an operational `AppError` at 500 or above, now log at error and reach Sentry; a request that reaches a closing server is one of them, so a deploy whose edge still routes to the instance it stops shows in Sentry. A refusal the table has no row for answers `REQUEST_REFUSED` at its 4xx status where it answered `INTERNAL_ERROR`, a provider's 4xx carried as a status included. The `http` domain no longer holds `MALFORMED_REQUEST` or `REQUEST_NOT_PARSABLE`: each of their causes has a code of its own.
- Until its context is swept, a route keeps the body it answers today. Two families of body coexist for the length of the sweep, and the baseline is the list of where.
- `eslint-suppressions.json` grows by one entry per file that holds a site (522 files at birth, decision 5.5), and falls from then on.
- A change of the rule package, the scope list or the sites gate waits for a window the Maintainer opens, the rule for the fronts included.
- A change that adds a site to a file that holds some already fails `pnpm lint` for the whole file, not for the new line: ESLint reports every site of a file whose count is exceeded.
- A use case that returned a generic code returns a specific one once converted, so a caller that compared with `USE_CASE_ERRORS.CONFLICT` compares the category or the specific code. The first-administrator command is the first such caller.
- The debt this record names for the sweep: the `ErrorCode` enum and `AppError`, the legacy reply helpers, twelve copies of `mapErrorCode`, the vocabularies declared as types, `packages/api-errors`' own English messages, and the twelve free-text error columns of the schema, which hold a message where a code belongs.

## Legal impact

`none for the register today — the body adds no personal data, cookie, recipient or retention period; decision 1.7 forbids personal data in a parameter, and the change that first logs or persists an error's parameters updates the register if one holds any`

## Support impact

`docs/support/first-administrator.md — updated by the first consumers' change: the failures the command prints and where to look. Every later context's change updates its own page. The reference page docs/api/ERROR_CODES.md is where a ticket's code is looked up`

## Deployment impact

`docs/deployment/DEPLOYMENT_CHECKLIST.md — updated: GITHUB_TOKEN, which .github/workflows/error-sites-stall.yml reads: its scheduled run opens an issue when the list of existing sites stops shrinking, a signal the operator sees on the repository. No runtime variable, external account or post-deployment check is added, changed or retired, and the origin in type is a fixed string, not a variable`

## Revisit if

- An external consumer reads the API: a code then needs a deprecation period before it is removed, and decision 1.4 is amended.
- The API negotiates a language for another reason: server-side text for `title` becomes cheap, and decision 3.2 can be reopened.
- TypeScript's new compiler API replaces the one the inventory uses before slice 3 is built.
- ESLint changes the suppressions file's format, its exit codes or what its Node API answers for a file's configuration: decisions 8.1 and 8.2 rest on them.
- Fastify raises a refusal of a client's request that it does not raise today, or Node a parser code the table of decision 2.4 does not name: until it has a row, it answers `REQUEST_REFUSED` at its status, logged at error and reported (decision 2.4).
- An edge the API trusts sets a request id that should name the request: decision 2.10 is then amended.
- The registry passes about 500 codes or a domain file passes about 60: the reference page and the files are then reviewed for a split.
- A portal other than the two is added, or a front that has a locale and is not a portal: decision 3.4's discovery of portals is then extended.

## Risks and Mitigations

| Risk                                                                                             | Mitigation                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The registry grows a second vocabulary of synonyms                                               | The adjudication table merges before a context is swept; a generic condition is one `common` code                                                                                                                                                                                                                       |
| A parameter carries prose, and the message becomes a pass-through                                | The registry gate refuses a message that is only a placeholder; review holds the rest, and the reference page shows it                                                                                                                                                                                                  |
| A count is swapped: one site fixed, another added in the same file                               | A stated residual of every count baseline; ESLint prints every site of a file whose count is exceeded, never fewer                                                                                                                                                                                                      |
| An entry says a portal cannot receive a code that it does receive                                | The portal shows its generic text and logs the code; the adjudication of slice 3 assigns the portals from the route table                                                                                                                                                                                               |
| The baseline is regenerated to hide a rise                                                       | Decision 8.3 compares with the base, per file and per rule                                                                                                                                                                                                                                                              |
| A count falls without a conversion: a weakened rule, a widened ignore, a file moved out of reach | Decisions 8.2 to 8.4 and the guard of 4.5: the resolved configuration, changed content for every fall, no change of the rule beside a change of a count, and the rule's files edited only in a window the Maintainer opens. Not closed: a weakening that moves no count, used by a later pull request, in such a window |
| Text printed by a command is not an error value, so the rule does not see it                     | The first consumer converts by contract; the inventory lists such text separately                                                                                                                                                                                                                                       |
| Two units change the shared generated records at once                                            | One owner regenerates them between units: the suppressions file, the history, the reference page and the contract                                                                                                                                                                                                       |
| The two body families confuse a reader for the length of the sweep                               | The reference page states which contexts are swept, from the history                                                                                                                                                                                                                                                    |
