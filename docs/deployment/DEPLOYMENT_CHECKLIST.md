# Deployment checklist

What an operator creates and configures before deploying omni-post, and what they verify after. Every row names the file that makes it a requirement, so it can be re-derived from the tree, and the change that introduced it.

This page lists requirements and does not repeat their reference material: the variables are described in [ENVIRONMENT_VARIABLES.md](ENVIRONMENT_VARIABLES.md), where each secret lives and how it rotates in [SECRETS.md](../security/SECRETS.md), and how the images are built in [image-build-model.md](image-build-model.md) and [base-images.md](base-images.md). Where one of those pages disagrees with a row here, the evidence file the row names decides.

## How this page stays current

- **The pull request section.** A pull request that adds, changes or removes something listed here updates its row in the same pull request, or says why not in its `## Deployment impact` section: one line per requirement, `docs/deployment/DEPLOYMENT_CHECKLIST.md — added|updated|removed: <row>`, or `none — <reason>`. The [PR template](../../.github/pull_request_template.md) and the ADR template ([ADR-0001](../technical/ADR-0001-agent-orchestration.md)) carry that section.
- **Evidence.** Every row names what makes it a requirement: the workflow step, the env-schema line, the Dockerfile `ARG`, the Admin settings key, or the row of the [subprocessors inventory](../legal/inventories/subprocessors.generated.md#subprocessors).
- **Introduced by.** The first commit that added the row's name to its evidence file (`git log -S'<name>' --reverse -- <file>`), with the pull request that merged it when there is one. `2a1673b4` is the commit that created the API env schema, so a variable older than the schema shows it; `5603d6be` is the first commit of this repository. `—` means no commit was found, never a guess.
- **Owner.** `operator` wherever the tree names no owner.
- **No check reads this page yet.** The derived gate, `pnpm check:deployment`, is item N-CI-8 of the [Master Plan](../product/MASTER_PLAN.md): every `vars.X` and `secrets.X` a workflow reads and every env-schema variable gets a row and a classification.

### Where configuration lives today

Two channels feed the deployables:

1. **Environment variables**, validated when each process starts by four schemas: [`apps/api/src/config/env.ts`](../../apps/api/src/config/env.ts), [`apps/workers/src/config/env.ts`](../../apps/workers/src/config/env.ts), [`apps/admin/lib/env.ts`](../../apps/admin/lib/env.ts) and [`apps/client/lib/env.ts`](../../apps/client/lib/env.ts). A `NEXT_PUBLIC_` variable is inlined into a portal's bundle when its image is built; every other variable is read at run time. The four Dockerfiles set `NODE_ENV=production`.
2. **Admin settings groups**: encrypted `PlatformCredential` rows written from Admin → Settings (`PUT /admin/settings/:group`) and read through `PlatformCredentialService`. The groups and their keys are listed in [`credentialKeys.ts`](../../packages/core/settings/src/credentialKeys.ts).

[ADR-0034](../technical/ADR-0034-credential-model.md) decision 2 makes the Admin groups the single source for every operator-provisioned credential and removes those variables from the environment. It is accepted and not yet implemented, so the rows below say what the runtime reads today. Until it lands, the `STRIPE`, `PADDLE`, `RESEND`, `STORAGE` and `SOCIAL_*` groups are written and tested from Admin while the runtime builds its adapters from the environment (ADR-0034, context item 3): filling those groups changes nothing at run time.

### Sentry, end to end

1. **Project.** Create a project on sentry.io and copy its DSN from Project Settings → Client Keys. `production-ci.yml` passes one repository variable to both portal images, so both browsers report to the same project; a project per portal needs a second variable and a workflow change ([Open gaps](#open-gaps)). The server DSNs and the API's DSN may name the same project or others.
2. **Browser DSN, at build time.** Set the repository variable: `gh variable set NEXT_PUBLIC_SENTRY_DSN -R edwardricardo/omni-post --body '<DSN>'`. The `admin` and `client` image builds receive it as a build argument and inline it (`apps/admin/Dockerfile:68-69`, `apps/client/Dockerfile:68-69`). Unset, browser Sentry stays disabled.
3. **Server DSN, at run time.** Set `SENTRY_DSN` in each portal's runtime environment. Unset, the server uses the inlined browser DSN (`packages/observability/sentry-next/src/server.ts:59`); with neither, server Sentry stays disabled.
4. **API.** Fill Admin → Settings → `MONITORING`: `sentryDsn`, `sentryEnvironment` (default: `NODE_ENV`) and `sentryTracesSampleRate` (default: `0.1`). The API reads them once at boot (`apps/api/src/index.ts:467-481`), so a change takes effect on the next restart; without a DSN it logs that error tracking is disabled. The workers neither declare nor import `@sentry/node`.
5. **Verify.** In CI, the DEF-86 probe steps of `audit.yml` (lines 728-732, [`sentry-init-probe.mjs`](../../scripts/testing/sentry-init-probe.mjs)) boot each portal's production build with a dummy DSN and fail unless Sentry initializes: they prove the build loads the SDK, not that the configured DSN works. After the deployment, the first event from each portal, in the browser and on the server, and from the API arrives in its project.
6. **Legal.** The `@sentry/nextjs` and `@sentry/node` rows of the [subprocessors inventory](../legal/inventories/subprocessors.generated.md#subprocessors): Sentry receives error events with stack traces and request context, and a sample of performance traces. The API deletes `db.user`, the database user name Sentry's pg instrumentation writes on its spans, from every span before it leaves (`stripDatabaseUser`, `apps/api/src/observability/sentryInit.ts`); the portals load no database driver.
7. **Pending.** DEF-93: `initBrowserSentry` sets session-replay sample rates, but `@sentry/nextjs` 10.76.2 adds no replay integration by default, so no replay is recorded.

## Open gaps

What the tree cannot answer yet. Each one is a row to fill when the decision is made.

1. **Domain, TLS and DNS.** No document names the production domain, the TLS terminator, the certificate source or the DNS records.
2. **Where the images run.** Which platform pulls the GHCR images, and how runtime variables reach it, is not decided, and no document names either. The architecture document that described the target secret store, [SECRETS_PRODUCTION_ARCHITECTURE.md](https://github.com/edwardricardo/omni-post/blob/9fddf03d1ed40e5bda6ea1ccf7de6f25bc39fc9b/docs/security/SECRETS_PRODUCTION_ARCHITECTURE.md), was removed from the repository on 2026-10-17 (git history keeps it); that store is not in place.
3. **Metrics and alerts in production.** The production scrape configuration and the Alertmanager routing (Master Plan OBS-6) are not in the tree.
4. **Role audit rows.** ADR-0022's staging and production rows read "Does not exist"; each is mandatory before that environment serves traffic.
5. **The first admin user.** No production procedure creates it.
6. **`NEXT_PUBLIC_URL` of the admin image.** `production-ci.yml` passes no build argument for it, so a CI-built admin image keeps `http://localhost:3100` unless the variable is present when the image builds; whether the standalone server can take it at run time is not measured.
7. **One browser DSN for both portals.** A Sentry project per portal needs a second repository variable and a change to `production-ci.yml`.
8. **Repository secrets.** On 2026-10-11, `gh variable list` and `gh secret list` for the repository printed no entries. The Slack notices and the preview cleanup fail for want of their secrets (measured above); whether `DEPENDENCY_UPDATE_TOKEN` is set is not established.
9. **Owners.** Every row says `operator`: the tree names no person or team for any of them.
