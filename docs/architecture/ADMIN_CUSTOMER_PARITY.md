# PARITY LEDGER — `apps/client` (customer) ↔ `apps/admin` (admin)

**Purpose.** The authoritative answer to "what does admin lack?" and its mirror, "what does customer lack?" Written to serve the standing project rule: _any feature that applies to both sides must be implemented on both sides_ — not only security. Every row is a scoping unit.

**Method and epistemics.** Five audited angles (credentials, MFA, persistence, sessions/authz, product surface) plus an adversarial verification pass over each. Where a verifier refuted a claim, **the refutation wins** and the row reflects the refutation; the original claim is named in §8 so nobody re-derives it. I independently re-verified seven load-bearing claims in this session (marked ⊕). Confidence is stated per row:

- **confirmed** — two or more independent passes agree, or the verifier explicitly re-checked the absence by alternate name / alternate layer / DI wiring, or I re-checked it here.
- **single-source** — one angle asserted it, no verifier touched it. Treat as a lead, not a fact, before scoping.

Terminology: **admin** = `AdminUser` / `AdminSession` surface (`/admin/auth/*`, plus the legacy `/auth/*` stack in `apps/api/src/auth/authRoutes.ts`, which also targets admin tables). **customer** = `CustomerUser` surface (`/auth/customer/*`, `/auth/mfa/*`, `/activity-feed`).

## 2. DIRECTION SUMMARY

**Count over the 118 scored rows in §1** (excluding the two withdrawn rows and the ESSENTIAL block):

| Direction                                                           | Rows   | Share |
| ------------------------------------------------------------------- | ------ | ----- |
| **Admin ahead** (customer is behind)                                | **50** | 42%   |

### The headline

**The owner's worry is broadly right but not uniformly right, and the exceptions are load-bearing.** Admin leads on twice as many axes as customer — but customer leads on the axes where a mistake is _hardest to retrofit_, and admin carries the single largest unrated hole in the codebase.

**Where admin is AHEAD** (the owner already knows this, but for completeness): durable hashed sessions and everything downstream of them (rotation, listing, revoke, revoke-all, revoke-on-credential-change, concurrent cap, idle expiry, CSRF); password history + reuse prevention + an authenticated change-password endpoint; real password-strength enforcement; permission enforcement at all; the entire auth audit trail; permission-gated audit reads; rate limits on the reset paths; a bot gate; operator-settable lockout; the atomic single-statement credential write; the credential-free read DTO; and most of the shared UI chrome (theme, skip link, permission-denied, loading, help).

**Where admin is BEHIND — read this part carefully:**

1. **MFA login shape.** Customer runs a proper two-step challenge with a 128-bit single-use `jti`, IP+UA binding, tenant binding and a 180 s TTL (B12, B13). Admin runs a one-step re-submit in which the client **re-posts the password** after `MFA_REQUIRED`. The more privileged surface has the weaker MFA flow.
2. **Client-IP derivation.** Customer routes use `resolveClientIp`; admin's login/MFA path feeds raw `request.ip` into the brute-force counter and the IP block (A20). Per `SECURITY_CANON`, that is precisely the leftmost-entry spoof the resolver exists to close, and fitness #29 does not catch it.
3. **Port discipline in persistence.** Customer has **zero** Prisma bypasses of its repository port. Admin has 14 raw statements across 4 files, including a `PasswordService` that holds `PrismaClient` directly (C7).
4. **Backup-code regeneration** exists only on the customer side (B8).
5. **Transparent rehash** on the primary login route exists only on the customer side (A15) — so an Argon2 cost bump upgrades customers and silently no-ops for admins.
6. **Reset-token schema hygiene**: customer's token column is `@unique` and indexed; admin's is neither, on the most privileged table (A3).
7. **Enumeration posture at login**: customer returns a uniform verdict; admin returns `ACCOUNT_LOCKED`/`ACCOUNT_INACTIVE` as a distinct 403 _before_ password verification (A28).
8. **Domain modelling**: `AdminUser` has no entity at all (C8) — its invariants live in route handlers.
9. **Notification center, `global-error`, `EmptyState`, Storybook, and ~2.3× the frontend test coverage** are customer-only (F7, F15, F16, F18, F19).
10. **The largest single hole in this ledger is admin-side and unrated by every angle's severity column**: admin routes bind no tenant context anywhere, so nine admin service files issue guarded-model queries that throw `TenantContextMissingError` (C16). Dashboard, scheduling, pricing and billing reads are affected.

### What the shape says about how the two sides were built

Read the symmetric column: 37 rows where _neither_ side has the capability, and they cluster hard — no auth metrics, no auth alerts, no auth runbooks, both audit UIs orphaned, both audit label maps partial, `AdminLoginAttempt` and three password policies declared and never enforced, MFA disable revoking nothing on either side. **These were never built once, anywhere.** They are not parity gaps; they are product gaps that parity work will not surface.

Then read the "ahead" columns. The admin side was built **top-down from a security checklist** — sessions, CSRF, RBAC, history, audit, lockout — and is thin on _domain modelling_ and _port discipline_. The customer side was built **bottom-up from a domain model** — a rich `CustomerUser` entity, a clean repository chokepoint, a carefully designed MFA challenge, canonical IP resolution — and is thin on _the security checklist_. Each side is strong exactly where the other is weak, and the strongest single artifact in the repo (`passwordHashing.ts`, A16) is the one place a single module serves both.

That has a direct consequence for scoping: **this is not a "port admin's work to customer" job.** Roughly a third of the parity work runs the other direction, and the two directions have different shapes — customer→admin is mostly _replacing_ a weaker existing implementation (riskier, needs care), admin→customer is mostly _adding_ a missing one (safer, more volume).

### Highest-cost items, ranked by exploitability

1. **E6** — `/activity-feed` is an unscoped global `AuditLog` read available to any authenticated customer, including admin actions and other tenants' rows.
2. **C11** — `PATCH /team/:id/role` takes the _changer's identity from the request body_; a VIEWER promotes itself by naming a higher-level member.
3. **D3/D4** — customer refresh re-randomises `sessionId`, so one refresh permanently detaches a session from any revocation the victim can perform.
4. **A24** — a customer password reset revokes nothing; every pre-existing refresh token lives 7 more days.
5. **D11** — customer RBAC permissions are carried everywhere and enforced nowhere.
6. **C16** — admin dashboard/scheduling/pricing/billing reads are guard-dead.
7. **A7/A8/A9** — the customer password reset does not work at all, and its confirm path fails _silently_ as a 400.

### Explicitly NOT essential — arguments I rejected

These are the excuses that would let a real gap through, so I am naming them:

- **"Admins are few and technical, so they don't need a notification center / global-error boundary / test coverage."** No. Admin is the most privileged surface, it already renders breach and queue state as pull-only tables, and it has less than half the customer's frontend coverage (F7, F15, F19).
- **"Customers are less privileged, so session management matters less."** No. A hijacked customer session publishes to a brand's social accounts. And the customer side is where revocation is _structurally impossible_ (D1–D5), not merely absent.
- **"Customer RBAC doesn't matter because roles are cosmetic."** No. Four roles ship in the DB (`schema.prisma:137-165`), in the JWT, and in a team-roles UI, and C11 is a live escalation through them. Either enforce them or remove them from the product — the current state is the worst of both.
- **"Admin's one-step MFA is fine because it's an internal console."** No. B12/B13 make admin the surface that re-transmits the password and has no bounded challenge, on the most privileged account class.
- **"Customer doesn't need an audit trail — it isn't regulated."** No. The customer portal ships a privacy/DSAR page. E1 means a compromised customer account cannot be investigated at all.
- **"The reset flow's tenant-context failure is essential — tenant-scoped models can't be read unauthenticated."** No. Login (`customerAuthRoutes.ts:164`) and MFA login (`:237`) are equally unauthenticated and both declare the bypass correctly. A8 is two missing wrappers.

**One asymmetry I moved from ESSENTIAL to ACCIDENTAL during verification:** the admin role-hierarchy invariant living in a route handler (C10). It was originally rated a privilege-escalation-shaped gap; the route does enforce SUPER_ADMIN-only plus no-self-change, and there is exactly one caller. It is a _placement_ smell (LOW), not an escalation. **The direction inverts** — the real escalation is on the customer side (C11).

## 7. OPEN QUESTIONS — product/architecture forks, not engineering calls

1. **Is customer RBAC a product feature or is it decorative?** Four roles ship in the DB (`schema.prisma:137-165`), in the JWT, and in a team-roles UI, and nothing reads them. Enforcing them is a CRITICAL change (§5 item 4) and will _change behaviour for existing customers_ — some team member will lose an ability they have today. Removing them is also coherent. **The current state is the only incoherent option**, because C11 is a live escalation _through_ roles that are not enforced. This blocks §5 item 4.

2. **Customer session model: durable row, or `passwordChangedAt` epoch?** A `CustomerSession` table mirroring `AdminSession` buys per-device listing and revoke _as a customer-visible product feature_ and costs a table, a lifecycle, and a cleanup job. A `passwordChangedAt` column compared against the JWT `iat` closes revocation-on-credential-change (A24) with one column and no new table, but can never power "log out my other devices". **Is per-device session management a customer-facing feature you want to sell?** This determines the shape of §5 item 3.

3. **Should customers be operator-lockable?** Admin has `failedLoginAttempts`/`lockedUntil`/`lockReason` that support can set; customer has automatic brute-force only. Adding it means columns _plus_ an admin console surface to use them. **Is "lock this tenant user" a support workflow you want?** (D17 — today there is no kill switch for a compromised customer account short of deactivating the user.)

4. **Does the admin console need a notification center?** F7 is the largest customer→admin gap in the product surface, and every notification route is `requireClientAuth` — so it needs an admin twin, not a widened guard. **Is admin deliberately pull-only, or is that an accident?** I classified it ACCIDENTAL on the grounds that an operator console needs alerts more than a customer does; that judgment is yours.

5. **Is break-glass rotate the deliberate boundary for tenant API keys?** The admin console can rotate a tenant key by id and cannot list, create, or revoke (`apiKeyAdminRoutes.ts:85-86`). I classified that ESSENTIAL. If the intent was a full management view, it is a real gap.

6. **Should `withSystemContext` emit a runtime audit event?** Today the grep-able constant _is_ the control, documented as deliberate (`tenantContext.ts:20-22`). A global admin surface reading tenant data therefore leaves no runtime trace. **Compliance may need the record even though the design argues it doesn't.**

7. **Do the two admin auth stacks converge, or does the legacy one die?** Three admin credential-verification surfaces exist (`/admin/auth/login`, `/auth/login`, and the `AdminAuthService` vs `authServiceSession` split). The legacy stack is _ahead_ on rotation, fingerprint binding and stateful token verification, and _behind_ on audit action strings. §5 item 11 assumes deletion; converging instead is defensible but larger.

8. **Should the brute-force identifier be namespaced per surface?** Today an admin and a customer sharing an email share one lockout counter (A19). Namespacing is trivial; the question is whether the _shared_ counter was intentional (one human, one lockout) or accidental. As written it is a cross-surface DoS: lock the customer, lock the admin.

9. **Is the customer portal meant to be self-service for security?** MFA enrollment, session management and password change are all support-mediated or impossible today. If self-service is the intent, §5 item 10 is a product commitment, not cleanup. If not, the five live MFA endpoints should be removed rather than left as an unreachable surface.

10. **What is the product's password policy?** Three are declared (`min(8)` customer, `min(12)+classes` admin, `min(12)+classes+weak-patterns` shared-and-dead) and a fourth is operator-editable and enforced nowhere (`SecuritySettings`). Raising customer's floor **will lock out existing users on next change**. This is a migration/comms decision, not a code decision.
