# Multi-Tenant Isolation Guards

> Defense-in-depth strategy preventing cross-tenant data leaks (CWE-639:
> Authorization Bypass Through User-Controlled Key) in OmniPost.
>
> **Threat model:** customer A holds a valid JWT for account `A`. The API
> exposes endpoints that take resource IDs (post id, channel id, mention id,
> etc.) as path/query parameters. Without enforcement, customer A could
> request resources owned by account `B` by submitting `B`'s resource ID.
> The current code (pre-S2.1) relies on **every** repository method
> remembering to filter by `accountId` — verified to be inconsistently
> applied (e.g., `PrismaPostRepository.findById()` was missing the filter).
> One forgotten check = data leak.
>
> **Strategy:** three independent layers, each catching what the others
> miss.

---

## Layer 1 — `TenantContext` + Prisma `$extends` middleware

**File:** `apps/api/src/security/tenantContext.ts` + (S2.1b)
`infra/prisma/src/extensions/tenantGuard.ts`.

`AsyncLocalStorage`-backed `TenantContext { accountId }` is bound by the
customer auth middleware after the JWT is decoded. The Prisma `$extends`
extension reads it on **every query** to a tenant-scoped table and either:

- **Injects** `where.accountId = ctx.accountId` when the caller didn't
  set it explicitly.
- **Validates** that an explicit `where.accountId` matches the context
  (throws `TenantContextMismatchError` if not).
- **Throws** `TenantContextMissingError` if the table is tenant-scoped
  and there's no `TenantContext` and no `SystemContext`.

This catches programming mistakes (forgot to filter) AND tampering attempts
(passing a different `accountId` in a body/query parameter).

## Layer 2 — PostgreSQL Row Level Security (RLS)

**File:** `infra/prisma/migrations/20260527000000_add_rls_tenant_isolation/migration.sql`
(applied in S2.1c).

Each of the 53 tenant-scoped tables gets:

```sql
ALTER TABLE "<Model>" ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "<Model>"
  USING (
    current_setting('app.account_id', true) = '__system__'
    OR "accountId" = current_setting('app.account_id', true)
  )
  WITH CHECK (
    current_setting('app.account_id', true) = '__system__'
    OR "accountId" = current_setting('app.account_id', true)
  );
```

`AIPromptTemplate` has an extended USING that additionally allows
`accountId IS NULL` so global system templates remain visible to every
tenant. WITH CHECK retains the strict form — only the system context can
write NULL accountId rows.

The `PrismaUnitOfWork.executeInTransaction` binds the GUC via
`set_config('app.account_id', <value>, true)` at tx start, reading the
bound `TenantContext` / `SystemContext`. Three states:

- **TenantContext active** → real accountId. RLS sees only matching rows
  (plus NULL rows on AIPromptTemplate).
- **SystemContext active** → sentinel `'__system__'`. RLS passes for any
  row — explicit cross-tenant bypass for admin / scheduled sweeps.
- **Neither** → no `set_config`. `current_setting(name, true)` returns
  NULL, policy evaluates to false, tenant-scoped queries return 0 rows /
  reject writes (fail-closed default).

**Defense scope:** transactional queries (every mutating use case). Read
queries outside transactions depend on Layer 1 alone — acknowledged
trade-off.

**Operational note:** RLS only applies to non-superuser, non-BYPASSRLS
roles. Migrations + seed scripts run as DB owner (typically superuser
in local dev) and intentionally bypass RLS. The application role in
production MUST be `NOSUPERUSER NOBYPASSRLS` — verify with `\du` in psql
before deploying.

## Create-path parent-ownership (the guard does NOT validate parent–child consistency)

Layer 1 injects `accountId` from the bound context, but it does **not** verify
that a client-supplied **parent** id belongs to the caller. Without an explicit
check, a tenant could persist a row carrying its OWN `accountId` and a FOREIGN
`parentId` — an inconsistent row and a latent exfiltration channel.

**Recipe — for every enrolled model with a client-supplied parent id, the
create/move/repoint path MUST, BEFORE persisting:**

1. Resolve the parent through its **guard-scoped repository** (e.g.
   `projectRepository.findById(projectId)`). A foreign/nonexistent parent
   resolves to `EntityNotFoundError` under the caller's tenant context — this
   resolution IS the ownership check.
2. On that error, return **NOT_FOUND (404)** — never 403 (anti-enumeration: a
   403 confirms the resource exists). The error MUST survive as `NOT_FOUND`
   through BOTH the use-case `catch` and the route's status map (a probe that
   500s is a conformance failure, not a pass).
3. Thread the resolved parent's `accountId` onto the child row so the persisted
   row satisfies `child.accountId === parent.accountId` by construction. The
   guard then validates that value equals the bound context on write.

**Reference implementation (Slice 1):** `ConfigureExternalNotificationUseCase`
resolves the project via `ProjectRepositoryPort.findById` before `doWork`,
returns `USE_CASE_ERRORS.NOT_FOUND` on miss, and threads `project.accountId`
into the saved row; the create route maps `NOT_FOUND → 404`. Enforcement is the
MERGE-BLOCKING two-tenant integration test
(`apps/api/tests/integration/externalNotificationTenantIsolation.test.ts`),
which asserts a foreign-project create returns **404, never 500/403**, and
persists no row. There is no static/fitness guard for this invariant — the
per-slice integration test is the enforcement.

## Transitively-scoped tables (~30 models, FK to a tenant-scoped table)

These tables don't carry `accountId` directly — they inherit tenant
scope via a foreign key to `Project`, `Channel`, `Template`, etc.
**Layer 1 (Prisma `$extends`) cannot auto-inject** because there's no
`accountId` column to filter on. The repository adapters MUST do an
explicit join in the `where` clause:

```typescript
// CORRECT — joined filter
await prisma.post.findFirst({
  where: {
    id: postId,
    project: { accountId: requireTenantContext().accountId },
  },
});

// WRONG — leaks across tenants
await prisma.post.findFirst({ where: { id: postId } });
```

### `withSystemContext()` precedent (Slice 3) — deliberate, canon-verified bypasses

| Caller                                             | Wrap reason                  | Why the bypass is legitimate                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `linkRoutes` `GET /r/:shortCode` (public redirect) | `public-link-redirect`       | Capability-URL exemption (W3C TAG Capability URLs; OWASP exempts public resources from deny-by-default). The `shortCode` is a global-namespace capability token served to anonymous visitors — no tenant context exists. The success output is a bare `302 → originalUrl` (zero tenant/accountId/analytics leakage); the management surface stays 100% tenant-scoped. Signed product/security decision (engram obs 297, 2026-07-14). |
| `RecurrenceScheduler.tick`                         | `recurrence-sweep`           | `findActiveByNextScheduled` is cross-account by design; the sweep runs outside any customer request. The template-clone exfil is closed at CREATE, NOT by this wrap — the wrap only declares the context so the flip does not throw `TenantContextMissingError`.                                                                                                                                                                     |
| `PrismaTrackedLinkRepository.isShortCodeAvailable` | `shortcode-uniqueness-probe` | The short-code/vanity-slug namespace is GLOBAL (the public redirect resolves it cross-tenant). Under the caller's tenant context the guarded `findFirst` would miss a foreign collision → a P2002 at insert. System context restores global uniqueness semantics. Returns a boolean only — zero data exposure.                                                                                                                       |

**MANDATORY compensating control for the public redirect (D7):** the `/r/:shortCode`
route carries a dedicated NAMESPACE-keyed rate limiter
(`createNamespacedRateLimitPreHandler(httpRateLimiter, "redirect", RateLimitConfigs.REDIRECT)`)
that keys the bucket by `redirect:{clientIp}` — NOT the global limiter's `ip:url`
key. The global limiter keys by URL, so every guessed shortCode would hit a fresh
bucket and NOT throttle enumeration; the per-IP namespace bucket makes ALL `/r/*`
hits from one IP share one bucket (true anti-enumeration for both auto-generated
shortCodes and user-chosen vanity slugs). See SMELL-57 in the roadmap backlog for
the pre-existing, out-of-scope `vanitySlug` non-uniqueness issue.

**S2.1d will audit every adapter touching these tables and add the
joined-filter pattern where missing.**

## Global tables (denylist — guard bypasses)

Tables without `accountId` (or with `accountId` for searchability only —
see `AuditLog` below) because they are platform-wide, audit-only,
or admin-scoped:

### `AuditLog` design note (2026-05-30)

`AuditLog` has an `accountId` column for **searchability** (customer
queries via `AuditLogRepository.findByAccount(accountId, ...)`) but
remains in this denylist by design. Three reasons converging:

1. **Immutable evidence canon**: industry best practice (AWS SaaS
   Factory, ClickHouse, GSoft Consulting, AWS Prescriptive Guidance)
   keeps audit logs outside RLS so admin / compliance teams query
   cross-account unfiltered when a customer disputes an event.
2. **Compliance flows are already cross-account**: 5 admin readers
   (`AnalyticsComplianceHandlers`, `AnalyticsDashboardHandlers`,
   `auditRoutes`, `auditService`, `activityFeedService`) read across
   all accounts to surface system-wide health, audit trails, and
   forensic data. Wrapping them in `withSystemContext` would be
   ceremonial — RLS bypass is the canonical state for AuditLog
   reads.
3. **Customer scope is opt-in**: customer-facing endpoints filter
   explicitly via `findByAccount(accountId)`; the `accountId` column
   makes that filter efficient (indexed at `[accountId, createdAt]`)
   without conferring isolation guarantees.

The `accountId` column on write is best-effort: `AuditableService.
writeAuditLog` threads it through when the caller provides it.
Pre-existing rows (created before 2026-05-30) have `accountId = NULL`
and remain queryable by the cross-account flows.

## How to use `withSystemContext()`

Legitimate cross-tenant operations bypass the guard via an explicit
marker:

```typescript
import { withSystemContext } from "apps/api/src/security/tenantContext.js";

// Background job: data retention sweep across all tenants
await withSystemContext("system:data-retention-sweep", async () => {
  await retentionService.runRetentionCleanup();
});

// Admin impersonation flow
await withSystemContext(`admin-impersonation:userId=${adminId}`, async () => {
  return adminAccountService.exportTenantData(targetAccountId);
});
```

The Prisma guard:

- Detects `SystemContext` is active → skips tenant enforcement.
- Emits an audit event capturing the `reason` whenever a query runs
  under the bypass. The audit row is reviewable post-hoc.

### When NOT to use `withSystemContext()`

- Customer-facing code paths. If a customer endpoint hits
  `TenantContextMissingError`, the auth middleware did not bind context
  or the request reached unintended code. Fix the root cause; do NOT
  wrap the offending code in `withSystemContext` to silence the error.
- "Quick fixes" for development. Use the auth middleware path.
- Test fixtures that need cross-tenant data. Use `withSystemContext`
  with `reason: "test-fixture-seed"` — but production code never does
  this.

## Runbook: `TenantContextMissingError` in production logs

If you see this error in production logs or Sentry:

1. **Capture the stack trace.** It points to the use case / repository
   that ran the query without a context.
2. **Determine the trigger:**
   - HTTP request? → the auth middleware should have bound context.
     Why didn't it? (Public endpoint? Then the query should be on a
     global table.)
   - Background job / scheduler? → that job should be running inside
     `withSystemContext(...)`. Wrap the entry point.
   - Worker (apps/workers)? → workers don't go through customer auth;
     they need their own context binding. **TBD: separate item to wire
     tenant context in apps/workers composition root.**
3. **Fix the root cause.** Do NOT silence with a try/catch or by
   adding `withSystemContext` to product code.

## Runbook: `TenantContextMismatchError` in production logs

This is more severe — it indicates an attempted unauthorized
cross-tenant access (CWE-639). Possible causes:

1. **Customer tampered with a request parameter** (`?accountId=B` in
   query string). The guard correctly blocked it. Investigate for
   abuse; the error itself is the right outcome.
2. **Programming bug** — a use case is passing the wrong accountId
   (e.g., from a body payload instead of from the JWT). Fix the
   handler to use `requireTenantContext().accountId`.

The error class carries `model`, `contextAccountId`, and
`queryAccountId` fields for forensic logging.

## Resolved in S2.1d

The two known raw-pgvector gaps documented during S2.1a are now fixed:

1. **`PrismaStyleGuideRuleRepository.ts` (`updateEmbedding`)** — raw
   `$executeRaw` UPDATE on `StyleGuideRule` now carries
   `AND "accountId" = ${requireTenantContext().accountId}` in the WHERE clause.
2. **`PrismaGlossaryRepository.ts` (`updateEmbedding`)** — same fix on the
   `Glossary` table.

Both still use raw SQL because Prisma doesn't natively support pgvector
operations, but they are no longer cross-tenant exploitable.

See `docs/security/MULTI_TENANT_AUDIT_2026-05-27.md` for the full audit
methodology + verdict.

## Audit & rotation

- **List rotation:** when a new tenant-scoped model is added to
  `schema.prisma`, the tenant table list in
  `infra/prisma/src/extensions/tenantGuard.ts` MUST be updated. A
  CI check or pre-commit hook is candidate for a future fitness #24.
- **Denylist rotation:** new global models go in the denylist.
- **Annual review:** revisit which tables are tenant-scoped vs global.
  Tables can transition (e.g., a global "AppConfig" that becomes
  per-tenant).
