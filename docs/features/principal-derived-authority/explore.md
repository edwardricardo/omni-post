# Authority derived from client input — explore artifact

**Scope:** `apps/api/src`, `packages/core/**`, `infra/prisma/**`, the customer and admin HTTP surfaces, and the test estate that covers them.
**Method:** five parallel angles, one adversarial verification pass per angle, plus my own re-verification of every claim that survives into a recommendation below. Where a verifier refuted an angle, the refutation stands unless I re-ran the check myself — every such re-run is marked **(re-verified)**.

## 1. The defects

### Preliminary: what the two isolation layers actually cover

Every severity call below depends on one fact, so I re-derived it rather than inherit it. `tenantGuardCheck` enrols models in an **allowlist** (`infra/prisma/src/extensions/tenantGuard.ts:91-152`) and passes through everything absent from it (`:195-197`). Membership, re-verified by extracting the literal set and testing each name:

```
IN GUARD : apiKey, channel, customerUser, project, projectMember  (…and ~53 more)
ABSENT   : auditLog, account, post, postContent, postMedia,
           postComment, approvalRequest, approvalReview,
           notification, notificationPreference, customerRole
```

Three angles independently derived "58 enrolled of 59 accountId-bearing models"; my raw string extraction over the block returns 61 tokens, so I treat **membership** as load-bearing and decline to assert a cardinality. The `auditLog` omission is deliberate and documented at `infra/prisma/schema.prisma:259` and `docs/security/MULTI_TENANT_GUARDS.md:1227-1252`.

RLS is not a second net for any finding here: the policies bind only inside a UoW transaction (`infra/prisma/migrations/20260527000000_add_rls_tenant_isolation/migration.sql:49-58`), all findings are single-statement reads or non-UoW writes, and the live role bypasses RLS (`docs/security/MULTI_TENANT_GUARDS.md:365`). No global Fastify hook rescues anything: the only app-wide hooks are audit, metrics, rate-limit, IP allowlist, decrypt-audit-context, CSRF and perf timing (`apps/api/src/index.ts:390-494`), and CSRF short-circuits on `!path.startsWith("/admin/")` (`apps/api/src/security/csrfMiddleware.ts:38`).

### D1 — `GET /activity-feed` returns the entire `AuditLog` table to any authenticated customer — **CRITICAL**

**(re-verified.)**

| Step                                            | Evidence                                                                                                            |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Registered bare, authentication only            | `apps/api/src/index.ts:508`; `apps/api/src/audit/activityFeedRoutes.ts:79` — `preHandler: [requireClientAuth]`      |
| Filters built exclusively from the query string | `activityFeedRoutes.ts:16` (`accountId` optional), `:57` (`...(query.accountId && { accountId: query.accountId })`) |
| `request.customerUser` never read in the file   | zero occurrences of the identifier                                                                                  |
| Base predicate is `{ success: true }`           | `activityFeedService.ts:149-150`                                                                                    |
| Query executed unscoped                         | `activityFeedService.ts:116-129` — `this.prisma.auditLog.findMany({ where, include: { user: {...} }, ... })`        |
| `auditLog` outside the guard                    | verified above                                                                                                      |

**Exploit request:**

```http
GET /activity-feed HTTP/1.1
Authorization: Bearer <any valid customer access token>
```

No parameters. That is the whole exploit.

**Precondition:** possession of one valid customer JWT. Nothing more — no role, no tenant knowledge, no prior enumeration.

**Two corrections to the framing everyone inherited.** First, **`?accountId=<victim>` is not the exploit and is not even a tenant filter**: `activityFeedService.ts:165-168` maps it to `where.resourceId = <victim>; where.resource = "Account"`, which _narrows_ the result set to rows _about_ that Account entity. Supplying it makes the leak smaller. There is no parameter combination that scopes this endpoint, and no parameter to remove that closes it. Second, the corollary fix that follows from "the scope came from the client" — pass `request.customerUser.accountId` into that same slot — is **also a non-fix**: it yields `resource:"Account", resourceId:<mine>` and returns a near-empty feed while leaving the leak untouched. The fix must set `where.accountId`, or route through `AuditLogRepository.findByAccount`.

**What leaks.** `activityFeedService.ts:175-241` emits, per row: the actor's `id`, `name` and `email` joined from the **AdminUser** relation (`include: { user: ... }`, `:118-122`; `schema.prisma:271`); full `resourceId` UUIDs of other tenants' Accounts, Projects and Posts; a `description` rendering `${details.method} ${details.url}` — the complete request line including query string, written by the highest-volume writer at `apps/api/src/audit/auditMiddleware.ts:77-92` **(re-verified: that call passes `userId`, `action`, `resource`, `resourceId`, `details`, `ipAddress`, `userAgent`, `success` — and no `accountId`)**; and the action taxonomy (`Disabled MFA`, `Changed role`, `Generated API key`, `Changed system config`).

**The endpoint is also functionally incapable of serving its stated purpose**, which is why I treat it as a rewrite rather than a scoping patch. `where.userId` (`:152-154`) filters the **admin** actor FK, and the `include` joins only `user`, never `customerUser` — despite the schema carrying both relations (`schema.prisma:271-273`). A customer passing its own id gets zero rows; a customer's own actions render actor-less; the only identities the feed can display are the ones it must never display. There is no reachable correctly-scoped call today.

**Root cause is written down as a feature.** `docs/security/MULTI_TENANT_GUARDS.md:1237-1243` lists `activityFeedService` among "5 **admin** readers [that] read across all accounts" and concludes wrapping them would be "ceremonial". Its only route is behind `requireClientAuth`. The denylist decision for `AuditLog` — which is itself correct and canon-grounded — was taken on a false premise about who reads the table. Any fix that leaves that paragraph standing will be re-broken by the next reader of the canon.

**Blocker for the reader-only framing.** The write path barely populates `accountId`. `auditMiddleware.ts:77-92` passes none; `auditService.log` writes it conditionally; and **(re-verified)** the modern `AuditableService.logUserAction` (`apps/api/src/services/AuditableService.ts:142-154`) builds an entry with no `accountId` key at all — `UserActionOptions` (`:93-101`) has no such field, only `AccountActionOptions` (`:102-104`) adds it — and `writeAuditLog` resolves `entry.accountId ?? (actor.type === CUSTOMER ? actor.accountId : undefined)` (`:351`). **ADMIN- and SYSTEM-actor rows written through `logUserAction` land with `accountId` NULL.** A pure reader fix therefore ships a feed that is correct and nearly empty. The write path is in scope.

### D2 — `PATCH /team/:id/role` takes the changer's identity from the request body — **HIGH** (intra-tenant vertical escalation)

**(re-verified.)**

`apps/api/src/team/teamRoutes.ts:39` declares `changerMemberId: z.string().uuid()` in `UpdateRoleBodySchema`; `:149` destructures it; `:154` forwards it to the use case. The file contains **zero** references to `request.customerUser`. Its only preHandler is `requireClientAuth` (`:298`).

`packages/core/team/src/UpdateTeamMemberRoleUseCase.ts:57` loads the target, `:65` loads the **claimed** changer, `:84-90` feeds `changer.roleLevel` into `member.updateRole(...)`. The domain rule (`packages/core/domain/src/entities/CustomerUser.ts:353-376`) rejects `changerRoleLevel <= this._roleLevel` (`:360`) and `changerRoleLevel <= newRoleLevel` (`:365`). Seeded levels OWNER=100 / MANAGER=50 / MEMBER=20 / VIEWER=10 (`infra/prisma/seed.ts:501-503, 571-574, 636-638, 679-681`).

**Exploit, two requests:**

```http
GET /team?accountId=<own account uuid>
Authorization: Bearer <VIEWER token>
# GetTeamMembersQuery.ts:58-71 returns {id, roleName, roleLevel} for every member
# -> read the OWNER's uuid

PATCH /team/<own member uuid>/role
Authorization: Bearer <VIEWER token>
Content-Type: application/json
{ "newRole": "MANAGER", "changerMemberId": "<OWNER uuid>" }
```

Evaluation: `100 <= 10` false, `100 <= 50` false → allowed. VIEWER becomes MANAGER, with MANAGER's permission snapshot persisted (`UpdateTeamMemberRoleUseCase.ts:84-97`).

**Precondition:** any authenticated customer of the target account, at the lowest role, plus one higher-ranked member id — which the same surface hands out.

**Calibration — why HIGH, not CRITICAL, and this must be stated in the ticket.** The blast radius is **intra-tenant**. `PrismaCustomerUserRepository.findById` uses `findFirst` (`apps/api/src/infrastructure/repositories/PrismaCustomerUserRepository.ts:67`), `customerUser` **is** enrolled in the guard, so the guard injects the caller's `accountId` into both lookups and a foreign `changerMemberId` resolves NOT_FOUND. And the ceiling is MANAGER, not OWNER — the second condition at `CustomerUser.ts:365` blocks promotion to or above the changer's own level. Anyone writing a cross-tenant red test for this will write a test that cannot go red.

### D3 — `DELETE /team/:id` has no authorization check of any kind — **HIGH**

**(re-verified.)** `RemoveTeamMemberInput.changerMemberId` is declared at `packages/core/team/src/RemoveTeamMemberUseCase.ts:18` and **never read again** — the identifier appears exactly once in the file. `execute` (`:36-53`) validates `memberId`, loads it, calls `deactivate()`, persists. The only gate is `CustomerUser.deactivate` refusing OWNERs (`packages/core/domain/src/entities/CustomerUser.ts:403-406`).

```http
DELETE /team/<any non-OWNER member uuid>
Authorization: Bearer <VIEWER token>
{ "changerMemberId": "<any uuid at all>" }
```

Any authenticated customer deactivates every non-OWNER member of their tenant, MANAGERs included. This is **worse than D2** in kind: D2 at least _uses_ the forged value. An authorization parameter that is declared and never read is worse than no parameter, because every reader and every reviewer assumes a check that does not exist. It is not carried in the parity ledger.

### D4 — `GET /accounts` and `DELETE /accounts/:accountId` — cross-tenant enumeration and destruction — **CRITICAL, and it outranks D1**

**(re-verified.)** All five routes carry `preHandler: [requireClientAuth]` and nothing else (`apps/api/src/accounts/accountRoutes.ts:363, 373, 383, 393, 403`), registered live at `apps/api/src/index.ts:535-539`. `Account` is outside the guard (verified) — it _is_ the tenant, its key is `id`, not `accountId`, so no guard can ever cover it.

```
apps/api/src/accounts/accountRoutes.ts:188
  const accounts = await this.prisma.account.findMany({
    orderBy: { createdAt: "desc" },
    include: { projects: true },
  });
```

**No `where` clause exists.** One request returns every tenant's `id`, billing `email`, `name`, `maxProjects`, `isOnTrial`, `createdAt` — plus, via the nested `include`, **every project row of every tenant**. The nested read is not covered even though `project` _is_ enrolled: `tenantGuardCheck` receives one `model` and mutates only `args.where` (`tenantGuard.ts:186-219`); Prisma query extensions intercept top-level operations, so relation reads inside `include`/`select` ride along on the parent query uninspected. `MULTI_TENANT_GUARDS.md` never mentions nested includes, and `tenantGuard.test.ts` has no such case.

`PUT /accounts/:accountId` writes `name` and `maxProjects` by path param with no comparison to the principal (`:241, :257`). `DELETE /accounts/:accountId` (`:302-337`) runs `postContent.deleteMany` (`:316`), `postMedia.deleteMany` (`:319`) and `post.deleteMany` (`:324`) keyed on the **victim's** projectIds — all three models are outside the guard — before `account.delete` (`:335`). `channel.deleteMany` (`:329`) _is_ guarded, so it silently matches zero rows and the terminal delete then likely FK-fails, returning a 500 **after** the victim's posts, content and media are irreversibly gone. No transaction wraps the sequence.

**This is the worst finding in the sweep and it is not in the change title.** If the work ships D1+D2 only because those are the named defects, the strictly worse hole survives the workstream.

### D5 — approval review actor from the body, on an unguarded aggregate — **HIGH** (cross-tenant)

`apps/api/src/approvals/approvalRoutes.ts:37, 42` declare `reviewerId` in the approve/reject body schemas; `:143, :187` forward it verbatim; routes at `:284-324` carry `requireClientAuth` only. The file never references `request.customerUser`. `ApprovePostUseCase.ts:41-58` loads by id and calls `aggregate.addReview(command.reviewerId, ...)`. `ApprovalRequestAggregate.addReview` (`packages/core/domain/src/aggregates/ApprovalRequestAggregate.ts:384-405`) checks status is pending, `reviewerId !== submitterId`, and no duplicate review — nothing ties the reviewer to an authorized approver. `approvalRequest` and `approvalReview` are outside the guard **and** absent from the RLS migration, and `PrismaApprovalRequestRepository.ts:66-67` does `findUnique({ where: { id } })`. **Cross-tenant.**

**Verification killed the headline:** the sweep claimed this "publishes another tenant's post". It does not — `ApprovalRequestResolved` and `ApprovalReviewAdded` have zero subscribers in production code, and the routes call only the approval use cases. No post transitions state. The real impact is forged approval provenance on any tenant's request, recorded as fact in the domain event, plus an **irreversible availability hit**: a forged reject drives the aggregate to terminal REJECTED, and both `addReview` and `cancel` refuse a non-pending aggregate.

### D7 — `POST /team/invite` accepts `role: "OWNER"` with no hierarchy check — **MEDIUM today, HIGH latent; remediation order is load-bearing**

`teamRoutes.ts:25` permits `role: z.enum(["OWNER","MANAGER","MEMBER","VIEWER"])`; `InviteTeamMemberUseCase.ts:64-72` resolves the role snapshot by name from the **global** `CustomerRole` catalog with **no changer parameter at all**, and persists at `passwordHash: ""` (`:85`).

**Verification killed the "one-request account takeover" reading**, correctly: there is no acceptance path. `findByInviteToken` has zero callers, no `/accept-invitation` route exists in `apps/api`, and no such page exists in either portal — the `acceptUrl` in the email points at nothing. The obvious alternative activation route is also blocked, and **not by design**: `POST /auth/customer/request-password-reset` and `/reset-password` are public and **(re-verified)** are _not_ wrapped in `withSystemContext` — only login (`apps/api/src/auth/customerAuthRoutes.ts:164`) and mfa-login (`:237`) are — so their first repository call hits the enrolled `customerUser` model with no tenant context bound and throws `TenantContextMissingError` → HTTP 500.

**Therefore:** the invite escalation is capped only while customer password reset stays broken. Repairing that 500 in isolation — an obviously-correct bug fix any maintainer would make — silently converts D7 into a full OWNER takeover. **The `InviteTeamMemberUseCase` hierarchy check must land before or with the password-reset repair.** This ordering constraint appears in no ledger and is the single most consequential thing verification surfaced.

An unauthenticated caller chooses the tenant context the entire Prisma guard will then honour. `getTenantHealth` gates only on `verifyProjectAccess(tenantId, projectId)` — an object-relationship check, never a principal check. Chains directly off D4, which supplies the `(accountId, projectId)` pairs.

`taskRoutes.ts:53` (`createdById`), `ContentHandlers.ts:71` (`createdBy`), `:83` (`restoredBy`). No privilege inherited; version history and task provenance are attacker-authored.

### 2c. Systemic habit or isolated slips? Both, in two separable halves — and the trigger

**Systemic**, with a precise and almost sympathetic cause.

The team put authorization **in the domain layer**, which is what their own canon instructs. `CustomerUser.updateRole` enforces role hierarchy by level. `PostCommentAggregate.editBody` refuses a non-author. `CustomerUser.deactivate` protects the OWNER. **Those rules are correct and well written.** The domain then needs to know _who is acting_, so the use-case input DTO grows a parameter: `changerMemberId`, `reviewerId`, `editorId`. Inside a DTO, that parameter is indistinguishable from every other field — `{ memberId, newRoleName, changerMemberId }` reads as three equally ordinary strings. The route handler's job became "map the request onto the DTO", and it did that faithfully, field by field, **including the one field that must never come from the request**.

Three things let it survive:

1. **No transport step binds an actor field to the token subject.** `requireClientAuth` populates `request.customerUser` (`customerAuthMiddleware.ts:59-65`) and stops. `requirePermission` is structurally unusable on the customer surface: `resolveUser` reads `request.auth?.user ?? request.user` (`rbacMiddleware.ts:29-31`) **(re-verified)** and `request.user` is written at exactly one site — `integrationAuthMiddleware.ts:175`. Pairing it with `requireClientAuth` yields an unconditional 401. **The JSDoc directly above it — `"Client auth: request.user (set by requireClientAuth)"` (`:26-28`) — is factually false and is very likely why nobody noticed.** Consequently the customer `permissions` claim is dead weight: minted at `customerJwt.ts:28`, copied at `customerAuthMiddleware.ts:64`, and **read nowhere** (`rg "customerUser\??\.(permissions|roleName|roleId)" apps/api/src` → 0 hits, re-verified); `CustomerUser.hasPermission` has zero production callers.
2. **The tenant guard hid the damage.** It absorbed the cross-tenant half for nearly every enrolled model, so what remained was exactly (a) the unguarded models and (b) the entire **intra-tenant** dimension, which the guard by construction cannot see — and intra-tenant is precisely where role hierarchy lives.
3. **The type system is indifferent.** `customerUser?: CustomerRequestUser` is _optional_, so `request.customerUser.accountId` is a compile error while `query.accountId` is not. A `z.string().uuid()` produces a `string`, and every id in the DTO is a `string`. Nothing distinguishes "an id the server derived" from "an id the client typed".

**Isolated slips** account for the _distribution_, not the existence: `commentRoutes.ts:217` gets it right eleven lines from `:183` getting it wrong; `conversationNoteRoutes.ts:122` is the correct twin of `commentRoutes.ts:97`. That half is per-route drift and is fixed by deleting fields from schemas. The permission half is a genuinely **absent primitive** and cannot be fixed by auditing files.

**What the authors believed they were doing:** enforcing authorization in the domain, per canon, with the transport layer as a dumb mapper — and relying on a tenant guard they believed was the isolation boundary. Both beliefs are defensible. Neither is sufficient, because **no entity can validate an actor it was handed**, and a guard keyed on a column cannot see a boundary that has no column.

## 4. The correct design, from scratch

### The contract

A route must be **unable** to obtain scope or actor from anything but the authenticated principal. Three mechanisms, in decreasing order of leverage:

**(1) One `Principal`, non-optional, discriminated.** Delete `request.customerUser`, `request.auth` and `request.user` and replace them with a single required decoration. The app has never been deployed, so there is no compatibility argument for keeping three shapes; and the three-shape situation has already produced two silent wiring bugs and one latent ADMIN-by-API-key escalation.

```ts
// apps/api/src/security/principal.ts
declare const brand: unique symbol;
export type AccountScope = string & { readonly [brand]: "AccountScope" };
export type PrincipalId = string & { readonly [brand]: "PrincipalId" };

export interface CustomerPrincipal {
  readonly kind: "customer";
  readonly id: PrincipalId;
  readonly accountId: AccountScope;
  readonly roleLevel: number;
  readonly permissions: ReadonlySet<string>;
}
export type Principal = CustomerPrincipal | AdminPrincipal | IntegrationPrincipal;

declare module "fastify" {
  interface FastifyRequest {
    principal: Principal;
  }
}
```

`decorateRequest` installs a default that throws, so an unauthenticated route that touches `request.principal` fails at runtime rather than reading `undefined`.

**(2) Branded scope and actor types make a body-derived value a compile error.** `AccountScope` and `PrincipalId` are constructible in exactly one file — the principal factory. `z.string().uuid()` produces `string`, which is not assignable to either. Signatures become `findByAccount(scope: AccountScope, …)`, `UpdateTeamMemberRoleInput { changer: PrincipalId }`. The exploit stops being a review question and becomes a `tsc` failure.

**(3) Route-level customer permission declarations.** `requireCustomerPermission("member:manage_roles")` reading `principal.permissions`. The data already exists end to end and is inert: `CustomerRolePermission` rows (`schema.prisma:154-164`) seeded with `member:read`, `member:invite`, `member:remove`, `member:manage_roles`, `approval:review`, `account:manage`, `account:delete` (`infra/prisma/seed.ts:520-533`); snapshotted into the entity; minted into the JWT; copied onto the request; **never read**. `CustomerRole` is a global catalog with `name @unique` and no `accountId`, so an attacker cannot mint roles. This is the answer to the parity ledger's blocking question: with no users, "changes behaviour for existing customers" is not a constraint.

**(4) A scope the repository can prove came from the principal.** Repositories take `AccountScope`, never `accountId: string`. Delete `ActivityFeedFilters.accountId` — not because it was the leak (it was not), but because it is a misnamed resource filter that will be mistaken for scope again.

### What it costs

- One cast site (the principal factory) plus signature churn on ~60 repository/use-case methods that today take `accountId: string`. Mechanical, large, and **fully verifiable by the compiler** — the compiler finds every site, which is the opposite of an audit.
- One escape hatch to police: `as AccountScope`. Guard it with a hard-zero fitness grep outside `principal.ts`. The repo runs 29 such greps; the muscle exists.
- Collapsing three decorations touches every route file. Cheap per site, wide in blast radius, and it is the change that makes the rest stick.

Collapsing all three decorations is _not_ in the minimum slice — it can follow — but the customer principal must be non-optional and branded from day one, or steps 2–4 are patches.

4. **D4** — delete the customer account CRUD surface. It is strictly worse than D1 and shares the root cause exactly; shipping without it means the workstream's headline finding is not its worst finding.

- **`withSystemContext` stays admin-only.** Admin is legitimately cross-tenant (`admin/channelReauthRoutes.ts:19, 52-53`); there is no customer counterpart and there must never be one.
- **Cross-account audit forensics stays admin-only.** The customer feed is scoped by definition; the admin export (`auditRoutes.ts:352-364`, including `ipAddress`, `userAgent`, `user.email`) is correctly gated by `AUDIT_EXPORT` and has no customer twin.

- **`requireAdminAuth` binds no tenant context, `requireClientAuth` does.** Correct and must stay: admin is cross-tenant by construction.

## 6. Red tests

### Template — negative authorization (the repo has cross-tenant proofs but **zero** intra-tenant ones)

> **Given** a valid principal `P` (real signed JWT, lowest role that can reach the route), **when** the request supplies identity or scope field `F` set to a value that is not `P`'s own — a sibling member's id for actor fields, another account's id for scope fields — **then** the response is 403 or 404 (never 200, never 500), the persisted state is byte-identical to before, and no field of the foreign entity appears anywhere in the response body.

Three variants:

- **Scope field** → the `channelTenantIsolation.test.ts` two-tenant shape verbatim. Add a **fail-closed case** (a NULL-scoped row) whenever the model is outside the guard.
- **Actor field** → a _pair_: reject-when-elevated, **and** identical-outcome-when-the-field-is-absent. The second case is what pins the fix shape — deletion of the field, not a cross-check.
- **No such field, only `requireClientAuth`** → a **role-differential** test: the identical request under OWNER and under VIEWER. If the responses are identical, the route has no authorization model, and the test documents that as a failure rather than as coverage.

## 7. The fitness function

Two checks, very different baselines. Both regexes verbatim into `.github/workflows/fitness.yml` per CLAUDE.md §"Extending the suite" — the doc regex **is** the CI regex.

### #30 — actor identity or attribution accepted from the request. **HARD-ZERO ACHIEVABLE. Baseline: 6 (re-verified on this tree).**

```bash
# 30. No actor/principal identity or attribution accepted from the request. A route
# that reads WHO IS ACTING from params/query/body lets any authenticated caller name
# a different — often higher-privileged — principal, and either inherit its authority
# (the PATCH /team/:id/role escalation) or forge provenance the audit trail then
# records as fact (CWE-639 / CWE-863). The actor is ALWAYS derived server-side from
# the authenticated principal — the pattern already used at accountLifecycleRoutes.ts:141,
# adminUserRoutes.ts:206 and rbacRoutes.ts:280. Scope: apps/api/src — NOT a *[Rr]outes*
# glob, because ContentHandlers.ts is a handler module and would be missed (the same
# case-sensitivity class of miss that fitness #1's own comment documents).
# Excludes tests. Hard-zero after this change.
grep -rnE "(changerMemberId|changerId|actorId|createdById|createdBy|invitedBy|performedBy|changedBy|updatedById|requestedById|onBehalfOf|asUserId):\s*(z\.|IdSchema)" \
  apps/api/src --include="*.ts" | \
  grep -vE "/tests/|\.test\." | wc -l   # expect 0
```

Baseline, reproduced exactly:

```
apps/api/src/content/ContentHandlers.ts:71:      createdBy: z.string().min(1),
apps/api/src/tasks/taskRoutes.ts:53:           createdById: z.string().min(1),
apps/api/src/notifications/notificationRoutes.ts:52: actorId: z.string().uuid().optional(),
apps/api/src/team/teamRoutes.ts:26:            invitedBy: z.string().uuid().optional(),
apps/api/src/team/teamRoutes.ts:39:            changerMemberId: z.string().uuid(),
apps/api/src/team/teamRoutes.ts:43:            changerMemberId: z.string().uuid(),
```

**Rationale wording matters here.** An earlier draft framed the threat purely as _inherited authority_, which matches only 2 of the 6 hits — `actorId`, `createdById`, `createdBy` and `invitedBy` are forged **attribution**, not privilege inheritance. All six must still be server-derived, but a reviewer reading a privilege-only rationale would reject four as mis-scoped. The wording above covers both.

**False-positive profile:** the regex requires a Zod/`IdSchema` declaration on the same line, so it cannot match a domain field, a Prisma select, or a DTO interface of the same name — only a field the HTTP layer accepts from the wire. The 5+ admin sites that read `request.auth?.user?.id` match nothing. A correctly-written new route cannot trip it. **Known miss:** a body field named outside the alternation (e.g. `authorId`, `reviewerId`, `submitterId`, `deleterId`, `editorId` — all of which exist in this repo). **Extend the alternation to include them before landing**; it is cheap and auditable, and it will raise the baseline above 6, so re-derive the count at implementation time rather than trusting this number.

### #31b — client-supplied tenant scope on a customer-authenticated surface with no principal awareness. **RATCHET, not hard-zero. Baseline: 12 files (re-verified).**

```bash
# 31b. A customer-authenticated route file that accepts `accountId` from the wire and
# NEVER reads the authenticated principal anywhere in the file. The conjunction is what
# removes the false positives: a file that reads the principal is at least aware it
# exists, and for ENROLLED models the tenant guard converts a mismatch into a throw
# rather than a leak. A DENYLISTED model (auditLog, account, post, postComment,
# approvalRequest, notification) has NO backstop — which is exactly the /activity-feed
# and /accounts leaks. RATCHET at the baseline below, per the #1/#21 precedent.
FILES=$(grep -rl "requireClientAuth" apps/api/src --include="*.ts")
for f in $(grep -lE "accountId:\s*(z\.|IdSchema)" $FILES); do
  grep -q "customerUser" "$f" || echo "$f"
done | wc -l   # baseline 12
```

Baseline files, reproduced exactly:

```
brand-voice/brandVoiceRoutes.ts   posts/optimizedPostsRoutes.ts   projects/projectRoutes.ts
usage/usageRoutes.ts              accounts/accountRoutes.ts       audit/activityFeedRoutes.ts
brand-kit/brandKitRoutes.ts       approvals/approvalRoutes.ts     approvals/approvalWorkflowRoutes.ts
ai/promptTemplateRoutes.ts        tasks/taskRoutes.ts             team/teamRoutes.ts
```

**Hard-zero is not achievable and I will not pretend otherwise.** The naive form (any `accountId: z.` in a `requireClientAuth` file) has a **37-line / 14-file** baseline with real false positives — several files legitimately accept a foreign-key-shaped `accountId`, and for enrolled models the guard converts the attack into a `TenantContextMismatchError`. The `#31b` conjunction above is the honest approximation: smaller, and every one of its 12 files genuinely accepts a tenant identifier and has no code path that consults the principal. Its own false-positive profile is the inverse — a file that _mentions_ `customerUser` anywhere passes even if the specific route ignores it (`commentRoutes.ts` and `firstCommentRoutes.ts` both escape this way, fetching the principal for a null-check and discarding it). It is a ratchet, not a proof. Land it at 12, drop to 10 on day one as `activityFeedRoutes` and `teamRoutes` are fixed, then to 8 with `accountRoutes` and `optimizedPostsRoutes`.

### #23 is broken and must be repaired in the same change

**(re-verified.)** The documented check greps `\.\$(queryRaw|executeRaw|…)\(` — demanding a **parenthesis**. Every raw query in this repo uses the tagged-template form. I ran the full documented pipeline: **count = 0**, while 30 raw call sites exist across 8 files, including `database/DatabaseOptimizer.ts` (12) — which is precisely what serves the unguarded `optimizedPostsRoutes` reads — and `PrismaSemanticRetrievalAdapter.ts` (2), neither on the audited-exception list. `.github/workflows/fitness.yml` mirrors the identical broken regex, so CI is equally blind. **The guard on the guard has never fired.**

Repairing it to `\$queryRaw|\$executeRaw` (both forms) yields a post-fix baseline of **16**, not zero: 12 `DatabaseOptimizer` + 2 `PrismaSemanticRetrievalAdapter` + 2 in `SagaManagerLifecycle.ts` and `OutboxClaimService.ts` that appear on no exception list. Whoever ships the regex change needs a documented ramp-down for those, or CI goes red on unrelated code — CLAUDE.md requires `count = 0` on main before merging the wire.

## 8. Constraints

**Canon rules binding the fix:**

- **Multi-tenant isolation — no exception** (CLAUDE.md §Pragmatic Exceptions "Forbidden"). No `// canon-exception:` marker is available for any part of this work. Cross-tenant operations go through `withSystemContext()`, which IS the sanctioned path.
- **Security canon — no exception.** Missing tenant guards and raw SQL on tenant tables are explicitly named. The escape hatch is "wait for security review", not "skip it".
- **DI composition root — no exception** (ADR-0007). `accountRoutes.ts:355` resolving a raw `PrismaClient` into a route and `activityFeedService.ts:94` taking `PrismaClient` instead of the port both violate ARCHITECTURE_CANON §Hexagonal ("Routes import use cases only"). **Note precisely:** neither trips fitness #1 or #21 — I ran both, both return 0, because they resolve from DI rather than importing the singleton. The broken rule is prose with no regex behind it. A new fitness check for `container.resolve<PrismaClient>` inside `*Routes*` would have a non-zero baseline and needs a ramp-down, not a hard-zero claim.
- **UoW mandatory for mutating use cases.** `DELETE /accounts/:accountId` currently runs four `deleteMany` calls plus a `delete` with no transaction — that is why the failure mode is _partial irreversible destruction_.
- **`@layer` = exactly three values**; every new file needs `@file`/`@description`/`@layer` (fitness #9, #10).
- **Test framework boundaries:** `tests/unit/**` → vitest; `tests/integration/**` → node:test. Adding a node:test file to the vitest include, or vice versa, silently collects zero.
- **No sprint/phase references in comments** (fitness #8) — including in the new fitness rationale text.
- **TDD strict mode is enabled** for this project; the red tests in §6 precede the fix.

**Sensitive-edit paths and tripwires:**

- Edits to `apps/api/src/auth/**`, `apps/api/src/security/**` and `infra/prisma/src/extensions/tenantGuard.ts` sit on the `**/auth/**` / `**/security/**` hot paths that trigger the full 4R fan-out at pre-PR.
- The **pre-edit tripwire blocker** (`.claude/hooks-py/pre_edit_tripwire_blocker.py`) will fire on tripwire #5 (architectural pattern choice — new bounded-context-crossing types, which `Principal` is) and #1/#1b if any transitional comment uses `temporary`/`bridge`/`stub`/`TODO §X.Y`. Every such edit needs a `canon-check:` citation line or a `sensitive-edit` token.
- The **Plan Mode guard** (`pre_edit_planmode_guard.py`) blocks non-trivial edits on `workstream/*` branches without recent Plan Mode activity or a referenced `/root/.claude/plans/*.md`.
- Adding a model to `TENANT_SCOPED_MODELS` requires the 3-step checklist in SECURITY_CANON §Multi-Tenant Isolation (guard Set, RLS migration array, `MULTI_TENANT_GUARDS.md`).

**What the auth machinery itself constrains:**

- `requireClientAuth` must keep binding tenant context **synchronously before the first `await`** — `enterWith` semantics depend on it (`tenantContext.ts:73-83`). Any refactor that makes principal construction async breaks tenant propagation repo-wide.
- `requireAdminAuth` binds **no** tenant context by design. A unified `Principal` must not "helpfully" bind one for admins, or every admin read starts failing on tenant-scoped models.
- `TenantContextMismatchError` and `TenantContextMissingError` have **no mapping** in `lib/errors/errorHandler.ts`. Until they do, every guard rejection is a 500 that echoes both account ids. Any design that leans on the guard as an authorization decision inherits that failure mode.
- The customer JWT already carries `permissions` — no token format change is needed to enforce them, but rotating role definitions will not invalidate already-issued tokens carrying stale snapshots.
- `CustomerRole` is a **global** catalog with `name @unique` and no `accountId`. Any per-tenant custom-role feature is a schema change, out of scope, and must not be assumed.

## 9. Open questions for propose/design — genuine forks only

1. **Where does `AuditLog` tenancy live?** (a) Enrol `auditLog` in `TENANT_SCOPED_MODELS` and wrap the ~4 genuinely-admin readers in `withSystemContext("admin:audit-forensics")` — contradicts the immutable-evidence canon (`MULTI_TENANT_GUARDS.md:1227-1252`) and costs an ADR. (b) Keep it out of the guard and make `PrismaClient` unreachable from any customer-surface service, so `AuditLogRepository` is the only door — cheaper, matches what the port JSDoc already assumes, enforceable by a fitness grep. **Caveat for (b):** the obvious grep (`prisma.auditLog` outside three files) has a **9-file** violating baseline today and does not even match the canonical repository, which uses `this.getClient().auditLog.*` to pick up the active UoW transaction client. So (b) needs a better-shaped check than the one circulating. Either way, `MULTI_TENANT_GUARDS.md:1237-1243` must be corrected first.

2. **Does the branded-type contract land in this change or the next?** Branding is what converts the class from "audit discipline" to "compile error", but it touches ~60 repository signatures. The fork is: brand now and accept a large mechanical diff (compiler-verified, so provable), or fix the routes now with a plain `CustomerPrincipal` and brand in a follow-on (smaller diff, but the class can regrow between the two). My reading of the "reviewable and provable, never small" rule favours branding now — but this is a real fork with a real review-load tradeoff.

3. **Do the three request decorations collapse in this change?** Collapsing closes the latent ADMIN-by-API-key path and the two shipped wiring bugs, and touches every route file. Deferring keeps the diff focused but leaves a known latent escalation in the tree.

4. **Is the customer activity feed wanted at all?** It has zero consumers in either portal, cannot render customer actors, and its only correct behaviour today is a leak. Deleting it outright is a coherent outcome; rebuilding it is a product decision, not a security one.

5. **Where does the D7 / password-reset ordering constraint get enforced?** The invite hierarchy check and the `withSystemContext` repair on the three pre-identity customer auth routes are logically independent bugs whose _sequence_ is security-critical. Same PR, or an explicit blocking dependency between two PRs?

6. **What is the customer permission vocabulary?** The seed defines `member:*`, `approval:review`, `account:*`. Is the seeded set authoritative, or does the design get to define the vocabulary from the routes it needs to gate?

7. **Does `TenantContextMismatchError` → 403 land here?** It is not one of the two named defects, but every "RESCUED" row in §2 currently rescues via a 500 that leaks both account ids. Fixing it changes ~14 routes' observable behaviour and would make several §6 tests assert 403 instead of 500.

## 10. Risks (implementation only)

**Regression risk in the routes touched:**

- **`teamRoutes.ts` is the highest-risk file.** Deleting `changerMemberId` from two schemas turns at least two currently-green tests red (`teamRoutes.test.ts` "updates role successfully when changer outranks target" and its hierarchy sibling), and requires a coordinated frontend change (`useTeam.ts:67-83, 133-138, 153`; `TeamPage.tsx:29, 36`). If the frontend ships late, the API rejects a body field the client still sends — Zod strict-mode behaviour on the resulting shape must be checked, not assumed.
- **`accountRoutes.ts` deletion collides with ~28 green tests** across five `describe` blocks in `tests/unit/accountRoutes.test.ts`, several of which certify the vulnerability as intended behaviour. Budget for deleting the file _and_ its suite.
- **The `activityFeedService` rewrite invalidates all 8 of its unit cases**, one of which (`"includes actor information when user exists"`) explicitly locks in the AdminUser join.
- **The audit write-path change is the widest blast radius in the whole slice.** Making `accountId` required on `logUserAction` touches every `AuditableService` subclass and `auditMiddleware`, i.e. the request path for every audited route in the app. A defect there degrades observability globally and can throw inside `setImmediate` where the catch at `auditMiddleware.ts:93-96` swallows it.
- **Deleting `optimizedPostsRoutes.ts`** is low-risk (never registered) but `tests/unit/optimizedPostsRoutes.test.ts` exists and likely pins the required-`accountId` shape.

**Can the enforcement primitive be introduced without a sweeping refactor?**

Partly — and the split matters. `requireCustomerPermission` + a non-optional `CustomerPrincipal` is **additive**: new middleware, one new decoration, applied route-by-route. No existing call site must change to introduce it, so it can land ahead of the fixes it enables. **Branding is not additive** — `AccountScope` on `AuditLogRepository.findByAccount` forces every caller to change, and `PrincipalId` on the team use cases forces the DTOs to change. The refactor is wide but compiler-driven: `tsc` enumerates every site, which is qualitatively different from grepping for field names. **Collapsing the three request decorations is genuinely sweeping** and is the item most likely to need its own slice.

**Which existing tests would go green for the wrong reason:**

1. **The corrected-`?accountId=` case (T5) as originally drafted.** With the ledger's prescribed fixture it passes on vulnerable code, because supplying the parameter _narrows_ the query. Highest-consequence trap in the plan: it is the one case that names the parameter, and as drafted it certifies the leak.
2. **Any cross-tenant red test for D2.** `customerUser` is enrolled and `findById` uses `findFirst`, so a foreign `changerMemberId` already 404s. Such a test is green today, stays green after the fix, and proves nothing about the defect.
3. **Every existing `activityFeedService` unit case.** All 8 constrain by `userId`, so the unscoped path never executes; the mock's exact-equality filter honours whatever keys the SUT sends and invents none. Adding a second tenant to that fixture changes nothing — `where.userId` excludes the other tenant's rows before a missing `accountId` predicate could matter. Only a real-DB route test catches this.
4. **`teamRoutes.test.ts` under `createCustomerAuthMock`.** The mock never verifies signatures and defaults `roleName` to `"OWNER"` and `accountId` to `""`. A "VIEWER cannot…" test written against it silently runs as OWNER; a route that _did_ derive scope from the principal would scope to the empty string and still pass. It is consumed by 8 test files, so the default cannot simply be changed.
5. **`TeamMemberRow.test.tsx` (13 cases).** Named like authorization proofs, asserting DOM visibility only. They stay green through any server-side fix and through any server-side regression.
6. **Any suite silently dropped from a batch.** A missing path in `run_batch` exits 0 (SMELL-74), and a fully-skipped suite reports OK (SMELL-80). The new integration files must be confirmed _collected_, with `TIER` set, not merely observed green.
