# Foundation Practices

**Owner:** Platform engineering
**Status:** living document, started 2026-10-15; it grows with every unit that teaches a practice.

The practices the next application adopts from its first commit, so it does not pay twice for what omni-post paid for in rework, the Testing Refoundation above all. The decision ids, metric ids, work-unit ids (`D25`, `M5`, `WU-2.2b` and the others) and log entries (`L57`) cited as evidence below belong to that refoundation's tracker (its Decisions log, metrics and Log) and its fixed plan, both removed from the tree on 2026-11-10 and read at the [permanent link](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md). The next application shares this repository's stack (TypeScript, Fastify, Next, Prisma on Postgres) and none of its domain: nothing here is about social media, providers or posts. Each entry is one practice, written as what to create and enforce on day one. The document records practices, never which packages to use.

## Where this is going

1. This document grows while the lessons happen.
2. It is turned into a prompt.
3. The prompt generates a skeleton of the next application.
4. The skeleton becomes the template, and counts as one only when every gate it carries shows a real red, a non-zero exit, on a planted violation.

## How to use this document

### Entry format

Every entry is a `###` heading with its permanent ID and the practice in one line, followed by four fields:

```markdown
### FP-NNN — <practice in one line>

- **Practice:** what the next application creates or enforces, stated so it can be checked.
- **Why:** what not having it cost omni-post, with the path to the evidence.
- **Day-one enforcement:** the kind (construction, gate or hook), what the next application sets up
  at its first commit, and how omni-post's precedent carries over.
- **Loosen if:** the measurable condition under which the rule may be relaxed, or "never" with the
  reason.
```

IDs are permanent: a new entry takes the next free number, and an entry that a later lesson sharpens is updated in place rather than duplicated.

### Strict first

Every practice starts at its strictest form: at zero, with no baseline and no grandfathered files. Retrofitting strictness costs far more than relaxing it. omni-post made method-level JSDoc canon with nothing enforcing it; its gate, which landed on 2026-10-11, holds only the files a change touches, and the rest waits for a reconciliation that started from 1,028 of 2,134 in-scope files holding 9,648 violations (FP-006). Relaxing a rule that already holds at zero is one edit.

So every strict rule names, in its **Loosen if** field, the measurable condition under which it may be relaxed. A rule is never loosened out of fatigue, and a field that says "never" means never.

### Scar versus lesson

An entry records the practice that makes a defect class impossible, or caught on the first commit that introduces it. It never records omni-post's remediation. Many of omni-post's gates carry the shape of their history: a ratchet, a quarantine, a touched-files scope, a list of excepted files. Those exist because the defect was already in the tree; on day one there is nothing to grandfather, so the entry states the version with an empty baseline.

Each entry says how omni-post's precedent carries over:

| Carry-over       | Meaning                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| By construction  | The next application makes the defect unrepresentable (a type, a fail-closed default, no escape hatch)       |
| Generalized gate | omni-post's gate, without its repository-specific scope, baseline and exceptions, runs from the first commit |
| omni-post only   | The precedent answers a defect the next application cannot have; the lesson stays, the gate does not         |

### Areas

Entries are grouped under one of these areas, in this order: Repository and toolchain, Architecture, Testing, CI and gates, Security and tenancy, Dependencies, Documentation, AI-assisted workflow. An area gets its heading with its first entry.

### How it grows

The "Foundation practices flow" paragraph of [CLAUDE.md](../../CLAUDE.md) §Documentation Policy is the rule: every unit that adds an ADR, adds or changes a CI gate or fitness check, or demolishes and redoes code records here, in the same pull request, the practice it teaches, or says in the pull request body `none for foundation practices — <reason>`. No check reads this document.

## Architecture

### FP-005 — One composition root from the first route; routes receive their use cases, never the container

- **Practice:** Each deployable has one composition root, and it alone wires concrete adapters. A route plugin receives the use cases it calls as its options; neither a route nor a per-request guard can reach the container, a repository, the database client, an adapter or a provider. Layer rules (dependencies point inward, routes reach only use cases) are enforced by a dependency-rule check whose known-violations baseline is empty on the first commit. The rule that no package imports an application is one rule over every workspace package, never one rule per package group.
- **Why:** A container referenced outside the composition root is a service locator: it hides a module's dependencies until run time ([ARCHITECTURE_CANON.md](../architecture/ARCHITECTURE_CANON.md) §Dependency Injection, decided in [ADR-0033](../technical/ADR-0033-layer-boundaries-and-composition-root-injection.md)). On 2026-10-15 the shrink-only baseline [`.dependency-cruiser-known-violations.json`](../../.dependency-cruiser-known-violations.json) still holds 75 `routes-no-container` entries, 74 route modules and one route-handler module; the routes workstream sized the conversion at about 15,200 lines of code in 49 slices for 25 route files, plus about 1,670 for the other 51 modules ([MASTER_PLAN.md](../product/MASTER_PLAN.md) §5.12 and §6). The failure is a run-time one: 22 test harnesses omitted a required option and registered the API metrics token as `undefined`, the container handed that `undefined` back without error, and the brute-force adapter dereferenced it on the customer login path (fitness #43 in [CLAUDE.md](../../CLAUDE.md)). The direction rules were written one per package group, so the groups nobody listed had none: until 2026-11-12 no rule kept an adapter or a provider from importing an application, and ten more groups still have none ([`.dependency-cruiser.cjs`](../../.dependency-cruiser.cjs); plan item PACKAGES-NO-APPS-REMAINING-GROUPS in [cross-cutting.md](../product/plan/cross-cutting.md)). No such import existed, but only because nobody had written one.
- **Day-one enforcement:** construction and gate. Construction: the composition root exists before the first route; route plugins and guards are typed to take their dependencies as options; the container is attached to neither the server nor the request; tests build routes through the same wiring, so a missing dependency fails to compile instead of resolving to `undefined`; the container refuses to register `undefined` at run time, so a cast that defeats the compiler still fails where the container is built. Gate: the dependency-rule check runs in CI with an empty baseline. Carry-over: by construction for the unreachable container, generalized gate for omni-post's rule set without its baseline. Its packages-to-applications rule matches the packages by one pattern over the workspace, so a new package group is covered the day its directory is created.
- **Loosen if:** never: a dependency resolved at run time is one that neither the compiler nor a reviewer sees, the failure fitness #43 caught after the fact.

### FP-037 — A health probe asks one question that reads no table, and every reader of a health status counts a degraded dependency as usable by one shared rule

- **Practice:** The database probe is a ping the data port exposes (one round trip that reads no table), never a read of an entity, so its latency measures the connection and never the size of the data; it makes one attempt bounded by a timeout, and its next refresh is the retry. A status has three values, `healthy`, `degraded` and `unhealthy`, and one function says which of them can serve: `healthy` and `degraded` can, `unhealthy` and anything unknown cannot. Every reader asks that function: the status code of each health route (200 for a usable report, 503 otherwise, the body saying which) and the readiness of a worker; the start command waits for that 200. The cached report refreshes faster while it is unhealthy than while it is healthy, so a recovery shows in seconds.
- **Why:** omni-post's database probe listed every account, so volume alone could make it slow and mark the database degraded (DEF-22); the workers counted only `healthy` as ready, so a database that answered in 1.1 s made them not ready and a start waited in vain; the API answered 503 for `degraded` on `/health` and 200 on its detailed report, so a database slower than one second read as down; and after a 34 s Redis pause the API stayed 503 for about 50 s, a 30 s cache refresh added to a check that took up to 18 s to give up (`docs/product/plan/chain.md`, F-01 record: DEF-22, WORKERS-READY-FAILS-ON-A-SLOW-DATABASE, API-HEALTH-SLOW-RECOVERY-AFTER-REDIS-PAUSE).
- **Day-one enforcement:** construction. Construction: the data port declares `ping` from its first version and the probe is written against it; the usable rule is one exported function that the routes and the readiness verdict import, so a reader cannot invent its own; the health manager is built with the two refresh intervals and the single attempt; the tests hold each route's status for each of the three values, and the probe's two bands (healthy up to its latency threshold, degraded above it, unhealthy past the timeout). Carry-over: `packages/monitoring/health-checks/src/usable.ts`, the port's `ping` in `packages/ports/src/RepoPort.ts`, and the cases of `apps/api/tests/unit/health/`.
- **Loosen if:** never for the probe reading no table; the set of statuses that can serve changes only by a recorded decision of the product owner, with every reader changed in the same change.

### FP-043 — One registry of error codes, one error body and a lint rule that refuses an error written in place, from the first route

- **Practice:** Every error the application raises or answers is an entry of one registry of codes in the shared kernel, written once with its code, its category, its status, a message for developers and its declared parameters, and is built only from that registry, by a call that takes a registered code and its parameters and no text. The API answers every failure in one body (RFC 9457, `application/problem+json`, with the registered code and the request's correlation id) that one function writes; the body's text is the registry's message for the code, never the error's own message, so a failure with no registered code answers a generic internal code. Each front words a code in its own locale catalogs, keyed by the code, and a check holds every catalog of a front to the codes that name that front, in both directions. A lint rule at `error` refuses an error built outside the registry, a code written as a literal and a failure answered by hand, over every source file but a named list of exclusions that one module holds, from which the lint configuration is built; a check holds the resolved lint configuration of every file to that list.
- **Why:** omni-post had no such place. Measured on 2026-11-20: about 12 vocabularies held about 200 codes, the API answered a failure in 6 body shapes, about 100 places turned a code into a status (three codes with two statuses each), core and API held about 500 inline English sentences, and one portal worded 13 codes and the other none ([ADR-0047](../technical/ADR-0047-central-error-system.md), Context, item 1). When the rule was turned on, the sites it had to list held 3,492 sites in 522 files, a sweep of many changes (ADR-0047, decision 5.5).
- **Day-one enforcement:** construction and gate. Construction: the registry, the body's function and the rule exist before the first route, and an error class's constructor takes only a registered definition, so the compiler refuses a message. Gate: the rule at `error` with no list of existing sites, and a check that loads the registry and holds its code grammar, the uniqueness of each code, each status to its category, each message's placeholders to its parameters, every code to a reference in code and the catalogs to the codes, with a reference page generated from the registry; omni-post's are `@packages/eslint-plugin-errors` and `pnpm check:errors` (fitness #57, the battery step `errors`). Carry-over: generalized gate, without the list of existing sites and the history that verifies it shrinks, which exist only because the defect was in the tree.
- **Loosen if:** never for the registry and the one body; the rule's reports of an error class may be dropped once no error class has a constructor or a factory that takes a message, because the compiler then refuses what the rule reported (ADR-0047, decision 4).

## Testing

### FP-001 — Each test file has exactly one collector, chosen by its file-name suffix, and that collector runs in a required check

- **Practice:** The file-name suffix decides which runner collects a test (unit, integration, live, end-to-end, load); every runner's configuration excludes the other tiers' suffixes; every runner is mapped to a CI job that is a required check. A test file that no required check runs, or that two runners run, is a failure.
- **Why:** A test no collector runs never executes, while it still reads as coverage in the tree, in review and in a coverage report; a file two collectors run executes under two environments, and its green says nothing about the tier it was written for. At the Testing Refoundation baseline (metric M5), omni-post had 23 orphan test files and at least 10 collected twice, and on 2026-10-14 its quarantine still listed 29 test-shaped files that no required check runs (fitness #30 in [CLAUDE.md](../../CLAUDE.md); "The suffix picks the collector" in [CODING_STANDARDS.md](CODING_STANDARDS.md); [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md)).
- **Day-one enforcement:** construction and gate. Construction: the suffix table and a shared exclude list exist before the first test, and every runner configuration takes the list. Gate: a reach check lists every tracked test-shaped file, asks each runner what it collects, maps each runner to the required checks, and fails on a file collected zero or two times; its quarantine (path, reason, owner and date per entry) starts empty and may only shrink. Carry-over: generalized gate, fitness #30's reach engine with an empty quarantine.
- **Loosen if:** never for "exactly once": a test that runs nowhere is not a test. The quarantine is the only exception, one named file at a time, and it may only shrink.

### FP-002 — A test run that collects zero tests fails

- **Practice:** Every test entry point treats an empty collection as a failure. No option that lets an empty run pass exists anywhere in the tree, and a runner that counts an empty file as a pass is wrapped so that zero tests, per file and in total, exits non-zero. Counts come from a machine-readable reporter, never from parsing formatted output.
- **Why:** omni-post's nightly chaos job ran `vitest run tests/chaos/` for the life of its workflow against node:test files that vitest's `include` globs never covered; it collected nothing and reported green over scenarios it never executed. node:test counts a file that registers no test as one passing test, and counts parsed from a formatted report read as zero the day its text changes (fitness #31 in [CLAUDE.md](../../CLAUDE.md)).
- **Day-one enforcement:** gate. A check refuses the pass-with-no-tests opt-out in every tracked manifest, configuration and workflow, and holds the runner wrapper's zero guards and its reporter in place. Carry-over: generalized gate, fitness #31.
- **Loosen if:** never: an empty run cannot be told apart from a broken collection.

### FP-011 — A test double of a dependency's error carries the shape measured on the real dependency

- **Practice:** A test that simulates an error a library or driver raises builds it with one shared fixture per error family, and the fixture reproduces the shape measured by raising that error through the real dependency, with the version and the date of the measurement in its header. No test writes such an error as an object literal from memory or from the dependency's documentation. The code that maps a dependency's error to a typed answer also has one integration test that raises the error through the real dependency, and an upgrade of that dependency re-runs the measurement.
- **Why:** omni-post's repositories recognised a unique-constraint violation by `meta.target`, the field the Prisma 5 and 6 query engine filled. Prisma 7 runs every query through a driver adapter, which reports the constraint at `meta.driverAdapterError.cause.constraint` and never sets `meta.target`: measured on PostgreSQL 16 on 2026-10-15 through 7.9.1 and 7.10.0, four readers never matched, and a team invitation colliding with a soft-deleted member answered 400 "Failed to save team member" instead of its documented 409. Every unit suite over those readers stayed green, because their doubles raised the old shape ([`statefulCustomerUserPrismaFake.ts`](../../apps/api/tests/unit/helpers/statefulCustomerUserPrismaFake.ts) before the fix; the measured fixture [`prismaKnownRequestErrors.ts`](../../apps/api/tests/unit/helpers/prismaKnownRequestErrors.ts); the one reader [`constraintViolation.ts`](../../infra/prisma/src/extensions/constraintViolation.ts); the end-to-end proof [`teamInviteDuplicateEmail.integration.test.ts`](../../apps/api/tests/integration/teamInviteDuplicateEmail.integration.test.ts)).
- **Day-one enforcement:** construction. The error fixtures exist before the first test that needs one, each with its measurement header, and the one reader of each error family is a shared module the repositories import, so a shape change is fixed in one place and caught by the integration test that crosses it. Carry-over: by construction.
- **Loosen if:** never: a double written from memory proves only that the code agrees with the memory, which is how four dead branches read as tested.

### FP-012 — A test double of an external command answers only the inputs its test planned, and refuses any other by name

- **Practice:** A double that stands in for an external command or endpoint (a `curl`, a CLI, an HTTP service) matches the exact inputs its test plans for, answers each with the planned result, and exits non-zero naming any input it was not built for. It records each call before it answers, so a test that plants a failure can assert the exact calls that led to it. A double never succeeds by default.
- **Why:** omni-post's node:test runner probes two readiness URLs before its live tiers. Its suite's `curl` double answered every URL with success, so a new or misspelt probe passed every live case without being read, and a planted failure was counted against a call log one entry off from what the stopping cases assumed (book rows SB-127 and SB-150 in [review-suggestions-book.md](../reports/review-suggestions-book.md); [`runTestsGate.behavior.test.ts`](../../apps/api/tests/unit/saga/runTestsGate.behavior.test.ts), fixed on 2026-10-16).
- **Day-one enforcement:** construction. The helpers that build command doubles take the planned inputs as a required table and have no default answer, so a double that succeeds on an input nobody planned cannot be written. Carry-over: by construction.
- **Loosen if:** never: a double that answers anything proves only that the code called something.

### FP-015 — A test waits on the observable result of the work it started, and a lint rule rejects every fixed wait in test code from the first sprint

- **Practice:** A shared test kit, importable from every test tier and free of any test framework, gives condition waiters that poll the result with a deadline naming what they wait for, a one-shot gate, a deferred and one fixed clock instant. Time-driven behaviour (an expiry, a retry delay, an interval) runs on fake timers. A lint rule at error, on every test file and test helper, rejects every fixed wait: a promise a timer resolves, a fixed-delay waiter of the runtime's timer promises, a browser driver's fixed timeout, any delay including zero. A wait no result can replace carries a marker comment on the line above that names one kind from a closed set and a reason, and the rule reports an unknown kind, a missing reason and a marker above no wait.
- **Why:** A fixed wait assumes the work is done when the time is up; on a loaded runner it is not, and the test fails, hangs, or asserts on a state the work has not reached. omni-post paid for the class three times before it had the kit: DEF-82, a recovery suite that failed intermittently when a second saga engine advanced the same row, whose proof needed a hand-written gate to order the two engines; DEF-84, a unit case whose real child processes took 7.4 s in CI against the runner's 5 s default; DEF-89, twenty 20 ms `settle()` waits in one saga suite ([MASTER_PLAN.md](../product/MASTER_PLAN.md) §5.11). When the rule was written on 2026-10-17 it found 108 fixed waits in 49 test files, and fixing them took six pull requests, which also found a cache TTL test whose option never reached the cache, so it proved nothing, and a routes suite that failed under 8 of 9 shuffled orders (the rule's row in [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md) §Gates; [`no-fixed-time-wait.js`](../../packages/eslint-plugin-testing/src/rules/no-fixed-time-wait.js); [`determinism/`](../../packages/vitest-shared/src/determinism/)).
- **Day-one enforcement:** construction and gate. Construction: the kit exists before the first asynchronous test, and the test-writing guide names it as the way to wait. Gate: the lint rule runs at error on every test glob from the first commit, with the marker's kinds as a closed list and no suppression file. Carry-over: generalized gate, `testing/no-fixed-time-wait` without omni-post's ignore list of dead files and its exclusion of end-to-end specs no required check runs.
- **Loosen if:** a new kind of deliberate wait joins the closed list only with a case that shows no observable result can replace it; the rule itself, never: a fixed wait cannot be told apart from a race that happens to pass.

### FP-016 — A unit test starts no process; code that spawns receives its process runner, and a lint rule holds the unit tier to it from the first commit

- **Practice:** Code that runs an external command takes its process runner as a dependency, and its unit test passes a double that answers only the planned commands (FP-012). A test that must start a real process, a test of a build or CI script, lives in one named directory that a separate step runs. A lint rule at error over the unit tier rejects every value import of the runtime's process module, in every syntax the language offers, and allows a type-only import and the module's name passed to a module-mocking call.
- **Why:** A spawned child's start-up cost lands inside the runner's time budget and its result depends on what the machine has installed. omni-post's DEF-84 was a unit case whose class ran `mkdir`, `find` and `npm ls` for real behind a seam that covered only two of its commands; it took 7.4 s in CI against Vitest's 5 s default and passed on the retry ([MASTER_PLAN.md](../product/MASTER_PLAN.md) §5.11). When the rule landed on 2026-10-18 the unit tier held 18 files that spawn, all of them tests of scripts or of the test collectors, and the class could only be held by a convention nobody checked (the rule's row in [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md) §Gates; [`no-child-process-in-unit.js`](../../packages/eslint-plugin-testing/src/rules/no-child-process-in-unit.js)).
- **Day-one enforcement:** construction and gate. Construction: the process runner is a port from the first module that spawns, and the scripts directory and its step exist before the first script test. Gate: the lint rule runs at error on the unit tier from the first commit, with the scripts directory as its only exception. Carry-over: generalized gate, `testing/no-child-process-in-unit` without omni-post's two further exceptions, the collectors' suites and the runner's behaviour suite.
- **Loosen if:** never for the unit tier: a test that must start a process is not a unit test, and it moves to the scripts directory. A syntactic rule cannot see a module that spawns on a test's behalf, so the port is the defence there.

### FP-017 — The integration tier runs every night in a seeded random order, file and test, on fresh services, with no retry and one alarm

- **Practice:** The integration runner takes an order mode and a seed: it orders the collected files by a hash of the seed and each path, prints the seed once before the first file, refuses a malformed seed, and hands the same seed to the test runner's in-file shuffle, so the printed seed replays both orders. A scheduled job runs the whole integration tier several times a night, each run on a database and a cache created for that run alone, each with its seed and replay command printed on the run's page, with no automatic retry. One alarm job reads every run's result: on any result but success it comments on the one open issue it owns, recognised by a marker in its body, or opens it once, listing each failed run with its replay command, and fails; on a green night it closes that issue.
- **Why:** A test that passes only after another test has created its rows reads as green in the merge gate's fixed order and on a reused database, and turns red the day the order or the data changes. The first time omni-post ran its integration tier this way, on 2026-10-18, 16 suites that passed in byte order failed on fresh databases, each on state an earlier test in its own file had created, and the reused local database had hidden 13 of them; a later run found a 17th (dispatches 39097507468 and 39111917425; the two rows of [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md) §Gates; [`run-tests.sh`](../../apps/api/scripts/run-tests.sh); [`nightly.yml`](../../.github/workflows/nightly.yml)). The second red dispatch of that proof commented on the open alarm issue instead of opening another (run 39098860445).
- **Day-one enforcement:** construction and gate. Construction: the runner's order mode and seed exist before the first integration test, and each test creates the rows it reads. Gate: the scheduled randomized job and its alarm run from the first integration suite. Carry-over: generalized gate, omni-post's `TEST_ORDER=random` runner option and its `integration-randomized` job with the alarm, without the live tier's exclusion, which exists because omni-post's live suites still depend on their order.
- **Loosen if:** the number of runs a night may fall once a measured month of nights shows no failure that only the extra runs caught; the random order, the fresh services and the absence of retries, never: a retried red reports a dependence as luck.

### FP-018 — A test's duration stays far below its timeout on the CI runner, and a passing test that comes close to it fails the check

- **Practice:** Every CI test job writes each test's duration to a machine-readable report, and a check fails any test that passed in more than half of its own timeout, so a test drifting toward its budget is fixed while it still passes. The fix lowers the test's cost; it never raises the timeout and never cuts a property's runs or inputs to fit. A test-data generator that builds a large table or index is measured, and the test that uses it states that cost.
- **Why:** A test that spends a large share of its timeout passes or fails with the machine's load. omni-post's scheduling-CSV property took 394 to 406 ms on a developer machine, beside sibling properties at 7 to 129 ms, and timed out at 5,253 ms against its 5,000 ms timeout in the nightly's cache-bypassed full suite (run 39106941417); the same timeout then failed the package tests of a pull request that did not touch the file (#651). The code under test was not the cost: the property's 100 generated inputs parsed in about 7 ms in total. The property library built a map of all 1,112,064 code points for one string generator, about 380 to 400 ms and 85 MB retained once per process; an equivalent generator brought the property to 12 to 13 ms with the same invariants, runs, seed and timeout (#653; [`schedulingCsv.property.test.ts`](../../packages/core/bulk-scheduling/tests/unit/schedulingCsv.property.test.ts)).
- **Day-one enforcement:** gate. The duration check runs in every CI test job from the first test, reading the runner's report, with no list of excepted tests. Carry-over: none to generalize; omni-post has no duration check and found this test only when it crossed its timeout, so the next application starts with the check.
- **Loosen if:** the half may rise for one test only when the test's cost is a measured wait on an external resource in the integration tier, named in the check's configuration with its measured duration on the CI runner; never by raising a timeout to make a test pass.

### FP-021 — A test block that cannot fail is a lint error from the first commit, and a suppression file, if one ever exists, only shrinks

- **Practice:** One classifier reads every test block's assertions, syntactically, for every test framework the repository runs, and three lint rules at error report the classes it names that cannot fail: a block in which no assertion runs, a block whose every assertion is true by construction (a literal against a literal, a size against zero), and a block whose every assertion on every path checks only presence, type or truthiness. A truthiness check of a verdict, the success flag a result carries (`ok`, `success`), pins a state the code under test computes and is not presence, unless the test reads it through a mock's own record, a value the test wrote itself. The test runner's own rules hold the rest of the class on the files that runner collects, and on no other runner's: a test with no assertion, an assertion outside a test or under a condition, a focused or disabled test, a commented-out test and a duplicate title. Test files print nothing to stdout, and no configuration block turns one of these rules off for named test files: a file that must print to stdout is not a test file, and lives outside the test globs. The classifier is the one any audit of the test suite reads, so a block is classified the same way in the editor, in lint and in a report. The classifier lists candidates; it never decides a deletion. A test leaves only by naming the regression it catches and a kept test that goes red with it, and a doubtful verdict is settled by mutating the code under test.
- **Why:** A block that cannot fail reads as coverage in the tree, in review and in a coverage report while it restricts nothing, and nothing in omni-post counted them: before the classifier existed, the Testing Refoundation estimated at most 272. When the rules landed on 2026-10-24 the tree held 612 existence-only, 17 empty and 17 tautological blocks, beside 1,442 conditional `expect` calls, 34 tests with no `expect`, 16 `expect` calls outside any test and 99 `console` calls that write to stdout in test files: 2,241 violations in 337 files, all captured in [`eslint-suppressions.json`](../../eslint-suppressions.json) (the rules' row in [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md) §Gates; [`classify.js`](../../packages/eslint-plugin-testing/src/classify.js); "Test Quality Rules" in [CODING_STANDARDS.md](CODING_STANDARDS.md)). The configuration also carried one exemption, `no-console` off over a list of three runner entry points under `apps/api/tests/`, which no runner collected and nothing but another dead file imported, and the check that pins the rules pinned that block by its form; when the three files were deleted on 2026-10-29, the list, its block and the check's pin had to change in the same pull request, because a lint configuration refuses a block over an empty file list (fitness #49 in [CLAUDE.md](../../CLAUDE.md) and its row in [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md) §Gates). Reading the block's shape instead cost omni-post in both directions: a demolition slice deleted a test whose `if (!result.ok)` never runs on a healthy subject and goes red the moment an allowed value is dropped, and another kept two blocks as the only exercise of a limit that a sibling also pinned, both found by mutation ([the tracker's §Log of 2026-11-06](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md)). The re-audit of 47 distinct blocks deleted under that reading found 2 whose regression nothing else caught. A reading that called a success verdict presence made asserting success weaker than asserting failure: `expect(result.ok).toBe(true)` restricted a value while `assert.ok(result.ok)` did not, and the verdict narrowing of 2026-11-08 took 103 of 149 existence-only blocks out of the class, a split a mutation sample checked in both directions ([TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md), D62).
- **Day-one enforcement:** gate. The classifier and the three rules run at error on every test glob from the first test, beside the runner's rules on the files it collects, with no suppression file: a block that cannot fail never lands. A check pins each rule at error in the lint configuration, refuses an inline directive that turns one off, and pins the number of lines that turn one off, in every literal spelling the lint tool accepts (`"off"`, `0`, `["off"]`, `[0]`), so an exemption in any of those spellings and any layout is a visible edit of the gate; a severity reached through a variable stays a stated residual of a textual check. Carry-over: generalized gate, the three `testing/*` rules and the `vitest/*` set without omni-post's suppression file. A repository that inherits violations puts them in a generated suppression file that may only shrink: a deleted or fixed block leaves an unused entry, and lint exits non-zero until the same change prunes it.
- **Loosen if:** a class is narrowed, never switched off, and only by a rule option a measurement justifies: with the code under test gutted, the blocks the option leaves out fail, so they restrict behaviour after all. Never by an inline directive or a hand-edited suppression file.

### FP-031 — A migration never inserts rows of the application, and a test migrates an empty database and fails on any table holding a row other than the migration tool's own record

- **Practice:** A schema migration changes structure only. Reference data, defaults and "so the screen arrives populated" rows are created by the application's own code or by an explicit seed step that a run chooses to take, never by a migration. One test in the tier that runs against a real database creates a database of its own, applies every migration to it with the command the start procedure documents, and fails unless the only table holding a row is the migration tool's own record of what it applied. The failure names each offending table. A migration that must remove rows an earlier migration inserted is a new migration, because an applied migration is verified by its checksum and is never edited; it deletes by a predicate that names the inserted rows alone, so a row a later writer recorded is not touched.
- **Why:** omni-post's creating migration of its secret-rotation log inserted 29 rows, one per catalogued secret, all saying the secret was rotated on 2026-04-21, "so the dashboard arrives populated instead of empty". Nothing writes that table, so the rows were its only content, and for a checkout whose secrets the start command had generated that day they said something false. A reader of the audit also took the populated table for a working capability: the unused-code inventory refuted the claim "no writer" because the rows were there ([UNUSED_CODE_INVENTORY.md](../reports/UNUSED_CODE_INVENTORY.md), its correction of 2026-11-12). The first start-from-empty step found them by measuring the migrated database, not by any check: 83 migrations applied, rows only in `_prisma_migrations` and that table. The rows left through a new migration, [`20261112000000_remove_secret_rotation_baseline`](../../infra/prisma/migrations/20261112000000_remove_secret_rotation_baseline/migration.sql), and [`migratedDatabaseIsEmpty.integration.test.ts`](../../apps/api/tests/integration/migratedDatabaseIsEmpty.integration.test.ts) holds the rule.
- **Day-one enforcement:** construction and gate. The test exists in the first commit that has a migration, in the integration tier a required check runs, so the first migration that inserts a row is red; its only allowance is the migration tool's own table. The start procedure documents the migration command, and the test runs that same command, so what is tested is what an operator runs. Carry-over: omni-post's test and its removal migration, generalized to the new application's migration tool and its record table.
- **Loosen if:** never for rows of the application. A table the migration tool itself requires (its own record, a lock table) may be added to the test's allowed list only by naming it with its owner and the reason the tool needs it.

### FP-035 — Every application that has components runs its component stories from its first component, on one shared preview and console contract, so the story rule is met only by a story that ran

- **Practice:** A rule that every component lands with its story holds in every application that has components, and each such application has its story runner from its first component: its own run script, its own step in the local battery and its own CI job, under one pass criterion (renders with no page error, writes nothing to the console's error and warning channels, passes its play function, zero accessibility violations at error). What the applications share lives once, in an existing shared package: the preview annotations (the accessibility check, the toolbars, the decorator that frames a story in the application's own intl provider and theme) and the console contract that fails a story on a console error or warning. Each application's own configuration holds only what is its own: its story globs, its styles, its catalogs, its default theme. A component that has no runner cannot be counted as covered by a story file.
- **Why:** omni-post made a story per component canon on 2026-10-06 and removed the admin portal's Storybook the same day because it had never built, so for 45 days the gate required a story of every new admin component and nothing ran it ([ADR-0035](../technical/ADR-0035-stories-part-of-creating-ui.md), its Consequences: "Admin stories do not run yet"). A gate whose runner is missing for one application is met by keeping the component out of the gate's reach: the form of the required password change was written as a component private to its page, under `apps/admin/app/`, with no story, where the gate does not look ([cross-cutting.md](../product/plan/cross-cutting.md), row ADMIN-CHANGE-PASSWORD-FORM-NO-STORY). Re-creating the admin's runner on 2026-11-20 found that the client's preview and console contract could not be reused without a copy, because no shared package held them.
- **Day-one enforcement:** construction and gate. Construction: the shared preview and the console contract exist in a shared package before the first component of the first application; a new application's preview is a call to the shared factory with its own provider, catalogs and default theme. Gate: the story-per-component check counts every application's component roots from the first commit at zero, and the battery and CI run every application's stories; an application whose components have no runner fails the check rather than being left out of it. Carry-over: generalized gate, `pnpm check:stories` with an empty baseline and one battery step and CI job per application.
- **Loosen if:** never for "every application": a story rule one application cannot run invites components to be placed outside the rule. A component that cannot render in isolation is exempted by a recorded decision naming it, never by moving it out of the counted roots.

### FP-040 — A test that types a secret into a user interface asserts through values it reads, never through a matcher that captures the page when it fails, and a lint rule holds that in the test's directory

- **Practice:** A test that drives a real browser and types a secret into it (a password, a token, a code) keeps that secret out of every file the run writes. Its assertions read a value and compare it: a polled address, a polled visibility flag, a list of texts, the names of the cookies. It never uses the test framework's page or locator matchers, because a failed one writes a snapshot of the page, with the value of every input, into the error-context file. The test's own configuration records no trace, no screenshot and no video; reports through reporters that print no step title, since the title of a step that fills a field holds the value; turns the framework's failure snapshot off; and never retries a test that spends a single-use credential. The run's output directory is never uploaded. A lint rule, scoped to the directory that holds the test and its configuration, refuses those matchers by name, and the names are read from the installed framework's type declarations, not typed by hand. What the rule and the configuration do not guard is written in the configuration's header as a limit, not left to be discovered: a run that overrides the configuration on the command line, the framework's debug log, a matcher called by a computed name, and an assertion over an input's value or over a page snapshot.
- **Why:** omni-post's first-administrator journey signs in with a single-use password and then types a new one. The independent verification planted ten defects in the portal, the API and the command, and after each failure no file of the run (the run log, the API's and the portal's logs, the test-results directory, the temporary directory) held either password, and a scan of every process's command line and environment during a passing run found none. It then removed the one line of the configuration that turns the failure snapshot off (`apps/admin/e2e/first-administrator/playwright.config.ts:20`) and failed a locator step: the error-context file gained a page snapshot, and three of its lines held a password. That line was held until then by a comment, and nothing stopped the next edit from adding a page matcher; the lint rule now does (`eslint.config.ts:380-400`). The same verification found that the framework's debug log prints each fill's value to standard error under any configuration, which is why the limits are stated.
- **Day-one enforcement:** construction and gate. Construction: the first browser test that types a secret lands in a directory of its own, with its own configuration holding the settings above and the header that states the limits, and the lint rule for that directory lands in the same commit. Gate: the lint rule runs in the repository's lint, in the local battery and in CI, with its red path shown on a planted page matcher in the directory (lint exits non-zero with the rule's message); the test's red path is shown once by hand on the configuration, by removing the snapshot setting, failing a locator step and finding the typed value in the error-context file, because no check can fail a test on purpose. Carry-over: omni-post's lint block and configuration, generalized to the new application's test framework and the secrets its tests type.
- **Loosen if:** the framework offers a setting that masks or omits input values in its failure snapshot, and the removal probe above shows no typed value in any file of a run that fails a locator step with the rule off; the rule is then replaced by that setting. Never because a test's secret "is only a test value": the value a journey types is a real credential of a real database for the length of the run.

## CI and gates

### FP-003 — A gate fails closed when its scope path is missing, its scan read nothing or its measurement returned no result

- **Practice:** Every gate asserts that each path it scans exists before scanning, holds the number of files or items it read against a floor, and exits non-zero, distinctly from a violation, when an input cannot be read. A gate's command line refuses an argument it cannot read, such as a flag given no value or an argument it does not know, as a usage error; it never falls back to a default scope. An exclusion glob names the path it means, anchored to the directory it is for, never a bare directory name that source code can share. Every positive scope glob of every test and coverage configuration matches at least one tracked file. A gate that measures through a remote service, such as an advisory database, reads its verdict from the tool's structured output and never from its exit code or its prose: only a document that parses as the expected result counts as measured, and anything else (a request error, a timeout, output that is not the result) is "could not measure", retried within a bounded time per attempt and then failed under its own title, never passed and never reported as a finding.
- **Why:** `grep -r` on an absent directory exits 2 and prints nothing, and `| wc -l` renders that as `0`: a green annotation over an invariant nobody measured. omni-post's fitness #2, #3 and #4 spent the whole period after a layer relocation in that state, and #4, both of whose path arguments were gone, scanned nothing at all. The third occurrence of the class created fitness #36: per-glob coverage thresholds kept "gating" two directories after both layers moved, and resolving every test configuration found a glob that matched no file ([CLAUDE.md](../../CLAUDE.md) §Automated Compliance Checks). The fallback is the same class: until 2026-10-16 the reach engine's source-resolution check, given `--root` with no value, read `argv[1] ?? findMonorepoRoot()`, so it checked the whole repository and exited 0 over a scope nobody asked for ([`source-resolution.ts`](../../packages/test-contracts/src/source-resolution.ts); book row SB-123 in [review-suggestions-book.md](../reports/review-suggestions-book.md)). The remote case is the mirror image: omni-post's dependency-audit step told "found advisories" from "endpoint down" by matching network-error text, so on 2026-10-22 an audit attempt that hung 250 s and ended in pnpm's `operation timed out`, a wording the list did not hold, failed the required check as a vulnerability finding on its first attempt while nothing had been measured (run 39712476313; the step "Run security audit" in [ci.yml](../../.github/workflows/ci.yml)). Since then the step reads `pnpm audit --json`, bounds each attempt to 60 s, and counts as measured only a document with an `advisories` map and `metadata.vulnerabilities`. Later, the duplicate-code gate ignored `**/reports/**` to skip a mutation-report output, which also skipped every source directory named `reports`: ten source files went unread, and 19 clones in them reached no baseline until the ignore was narrowed to `**/reports/mutation/**`.
- **Day-one enforcement:** construction and gate. Construction: one shared helper performs the scope assertions and floors, and another parses a gate's arguments strictly (exit 2 on a usage error); every gate calls both, so a new gate cannot skip them. A gate that calls a remote service classifies a parsed result into measured clean, found and could not measure, and its suite feeds it a fake of each class, a request error and a hang among them. Gate: the scope-glob check, fitness #36's form, runs from the first test configuration. Carry-over: generalized gate.
- **Loosen if:** never: a gate that reads nothing reports its invariant as held, and one that reads an error as a result reports a measurement that never happened.

### FP-004 — A gate merges only after its red path shows a real non-zero exit

- **Practice:** A new or changed gate merges only after a planted violation made it exit non-zero, the tree was restored byte for byte, and the gate passed again. An error annotation never stands in for an exit code. A gate's rule lives in one script with its own suite, which the CI step and the canon both invoke; it is never written inline in a workflow step, and never copied into a document.
- **Why:** An `::error` annotation alone leaves the job green and proves nothing (step 3 of "Extending the suite" in [CLAUDE.md](../../CLAUDE.md); fitness #34 pairs every annotation with an exit in the same step). omni-post's fitness #28, in its old form, required the numeric hop-count spelling of `trustProxy` that a framework release had made dangerous; measured, a `trustProxy: 2` planted in the entry file returned count 0 and passed cleanly, while `trustProxy: true` was caught. A gate that mandates the defect it exists to prevent is worse than no gate. An inline rule has no suite to hold its red: omni-post's fitness #37 was a node heredoc written twice, byte for byte, in its canon block and its workflow step, so every change edited both copies and proved its red by hand on the extracted step, nothing pinned the rule between those changes, and checking a coverage marker's slice against the committed test ledger needed one more hand proof per case ([ADR-0039](../technical/ADR-0039-decorative-demolition-coverage-exception.md) Decision 4).
- **Day-one enforcement:** construction and gate. Construction: every gate is a script with its own test suite, and that suite holds at least one planted violation that must exit non-zero, so the red path is proven again on every run instead of once in a pull request. Gate: a check pairs every error annotation in a workflow with an exit in the same step. The generated skeleton is accepted as the template only when every gate it carries shows this red. Carry-over: generalized gate, the self-tested script form of fitness #30, #36, #37 and #44 to #48 plus fitness #34.
- **Loosen if:** never: a gate whose red was never observed is an assertion nobody measured.

### FP-008 — Every root config a package extends is part of the build cache key

- **Practice:** Every root configuration a package extends is an input of that package's build cache entry. A check derives the set from the `extends` chains, root-to-root links included, and fails when a member is missing from the cache's inputs.
- **Why:** omni-post's build cache hashed each package's own inputs plus a declared global list and nothing else, so a root compiler config a package merely extends was invisible to the hash. Editing it invalidated zero cache entries, and every dependent task replayed a `dist` compiled with the previous compiler settings under a green exit code, a false green reproduced end to end in [CI_CACHE_INTEGRITY_AUDIT.md](../reports/CI_CACHE_INTEGRITY_AUDIT.md) (fitness #33 in [CLAUDE.md](../../CLAUDE.md)).
- **Day-one enforcement:** gate. The extends walk, fitness #33's form, runs from the first shared configuration. Carry-over: generalized gate.
- **Loosen if:** never: a stale cache hit is a false green with no visible signal.

### FP-013 — Every CI job sets up the runtime and the package manager through one shared step, which reads the runtime version from one file

- **Practice:** One shared setup step (a composite action or its equivalent) installs the runtime, the package manager and the dependency tree for every CI job that needs them, and pins each third-party action it uses at one major. The runtime version is written in one file (`.nvmrc`) and the package manager's in one field (`packageManager`), and every setup reads them; no workflow writes a version literal. A job that needs the runtime alone sets it up directly from the same file, with a comment saying why it skips the shared step.
- **Why:** omni-post's shared step pinned `actions/setup-node@v4`, `pnpm/action-setup@v4` and `actions/cache@v4` while the jobs that set up Node directly had moved to `actions/setup-node@v7` and `pnpm/action-setup@v6`, so two majors of each action ran in one pipeline, and support for pnpm 12, the version `packageManager` pins, arrived only in `pnpm/action-setup` v6.1.0. Eight places in six workflows wrote the runtime major as the literal `"26"` while `.nvmrc` already held it: the engines gate held every manifest to the `.nvmrc` major ([`engines-node-gate.mjs`](../../scripts/testing/engines-node-gate.mjs)), and nothing held the workflows to it (book rows SB-209, SB-250 and SB-251 in [review-suggestions-book.md](../reports/review-suggestions-book.md); [`action.yml`](../../.github/actions/setup-node-pnpm-cache/action.yml)).
- **Day-one enforcement:** construction and gate. Construction: the shared setup step exists from the first workflow, takes no runtime-version input and reads `.nvmrc`; the package manager comes from `packageManager`. Gate: a check over the workflow files refuses a runtime-version literal anywhere, refuses a direct use of the runtime, package-manager or cache setup actions outside the shared step unless the job is on a list with its reason, and holds every reference to an action at one major. Carry-over: the shared step is omni-post's `setup-node-pnpm-cache` action; omni-post has no gate for the rule, so the next application builds the check new.
- **Loosen if:** a job must run a runtime version other than the one `.nvmrc` names, such as a compatibility matrix; then that job alone lists its versions in one place, with the reason beside them.

### FP-019 — A workflow merges only after each of its jobs has run green once, and every secret and service it reads is provisioned

- **Practice:** Every job of a new or changed workflow shows one green run before it merges; a scheduled or dispatched job is dispatched once on the branch. Every secret, variable and external service a step reads has a row in the deployment checklist that says it is provisioned, and a job for infrastructure that does not exist yet is not written until the infrastructure exists.
- **Why:** omni-post's `Cleanup & Maintenance` ended in `failure` on 32 of 32 scheduled runs from 2026-03-15 to 2026-10-18: on every run whose steps are recorded, one job configured AWS credentials for a preview cluster that never existed and the report posted to Slack through a webhook nobody had configured. `Performance Tests` ended in `failure` on 88 of 95 runs from 2026-05-11 to 2026-10-18, the rest cancelled: its first job died 40 times copying an env file that had moved and 48 times on a stress script whose workspace imports nothing had built, and the load test gated on it never ran. A workflow that is always red reports nothing: the day a real failure arrives, it looks like every other day (DEF-101 in [MASTER_PLAN.md](../product/MASTER_PLAN.md); WU-6.P2 in [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md)).
- **Day-one enforcement:** construction and gate. Construction: the deployment checklist exists before the first workflow, and the pull request that adds a workflow fills its rows and links the green run of each job. Gate: a check derives every `secrets.X` and `vars.X` the workflows read and fails when the checklist has no row for one. Carry-over: omni-post's [DEPLOYMENT_CHECKLIST.md](../deployment/DEPLOYMENT_CHECKLIST.md) is the precedent; its derived gate, `pnpm check:deployment`, is plan item N-CI-8 (`docs/product/plan/chain.md`) and does not exist yet, so the next application builds the check new.
- **Loosen if:** never for the green run: a job never seen green has never shown what its green means.

### FP-023 — A check lands wired: the commit that adds it also runs it in CI and in the local battery

- **Practice:** A check (a script that exits non-zero on a violation) is a root `check:*` command, and the commit that adds it adds its CI step, in a required job, and its step in the local battery. A check discovers what it holds (the portals, the locales, the packages) from the tree instead of listing them, so the next instance of what it checks is held without an edit to the check.
- **Why:** omni-post's two portals each carried an i18n catalog validator, `apps/admin/scripts/i18n-validate.mjs` and `apps/client/scripts/i18n-validate.mjs`, run only by their package's `i18n:lint` script, which no workflow, battery step or hook called: the check existed and enforced nothing until 2026-10-26, when one gate replaced both (fitness #51 in [CLAUDE.md](../../CLAUDE.md); [`i18n-lint.mjs`](../../scripts/testing/i18n-lint.mjs); the decision on `@formatjs/icu-messageformat-parser` in [`dependency-decisions.json`](../../scripts/testing/dependency-decisions.json)). Each validator also hard-coded its locales, as `["en", "es"]` and `["es", "en"]`, so a third locale would have been held by neither, and neither read the arguments inside a rich-text tag.
- **Day-one enforcement:** construction and gate. Construction: a check is born as a root script with its own suite, its `check:*` command, its CI step and its battery step, in one commit. Gate: a check derives every `check:*` command of the root manifest and every check script, and fails when one is not invoked by a CI step of a required job and by the battery. Carry-over: omni-post's fitness #44 holds its numbered CI steps and their canon blocks to one inventory, but nothing ties a package script to CI, so the next application builds the check new.
- **Loosen if:** never for a check: one that nothing runs measures nothing. A command that only prints a report for a reader is not a check, and is named so the derivation excludes it (for example `report:*`).

### FP-026 — A test change is accepted on a mutation measured against the base, and CI refuses a deleted or rewritten test block without that record

- **Practice:** A change that deletes or rewrites a test block carries a committed record of a differential mutation run: one realistic mutation of the subject, run against the test files at the base and at the head. A rewrite counts only when the base stays green and the head goes red under the mutation; a deletion only when a test that stays still catches it; a test whose base form fails on the new code while the head is green is a measured behaviour change, never a declared one. A CI check binds every block the change deletes or rewrites, read from the base and head test ledgers by id and body hash, and refuses one with no record whose hashes equal the ledgers and whose verdict covers its kind. A block whose body reappears under another id, a block of a runner the tool cannot drive yet, and a block whose test imports a source the change edits are listed for review, never refused.
- **Why:** omni-post accepted rewritten tests because each went red under a mutation of its subject, with the base form never run: replayed against the base test files, 24 of the 29 blocks a hard probe could not decide were already caught at the base, and between the ledger's first commit and 2026-11-08 (counted at main `05d4b83d`), 18 of 58 merges to main removed or rewrote 695 test blocks with no measurement tied to any of them (the tracker's §Log and D61, [read at its permanent link](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md)).
- **Day-one enforcement:** construction and gate. Construction: the test ledger names every block by id and body hash from the first commit, and the mutation tool writes its record keyed by them. Gate: the record-coverage check runs on every pull request, in a job that installs nothing, fails closed when the base or a ledger cannot be read, and shows its red path before it merges.
- **Loosen if:** a class of blocks is exempt only while the tool cannot measure it, such as a runner with no adapter yet, each exempt block counted and listed, and the exemption removed in the change that brings the adapter; never for a record nobody ran.

### FP-027 — A gate's counted class or exemption ships with the condition that retires it, and the gate enforces that condition on the real population in an explicit mode, apart from its per-change evaluation

- **Practice:** Every class a gate counts without refusing, and every exemption it carries, names in the same change the measurable state that retires it, and the gate itself fails closed with "delete it" when that state is reached. The retire check is a property of the whole population (the repository's own ledger or inventory), so it runs in an explicit mode (`--retire-check`) that the package script, the local battery and the CI step pass, never inside the per-change evaluation that the gate's own test suite drives with fixtures: a check that adds output on every run turns every base-form case of that suite red on the new code, and the gate then refuses its own evolution.
- **Why:** omni-post wrote 54 fitness checks and kept several past the remediation they were written for, consuming CI time while detecting nothing (the Product Owner's rule of 2026-11-09, L57 and L58 of the Phase 2 record). The first attempt to enforce a retire condition inside the record-coverage gate's main path made the gate's own suite red wholesale on the new code, so the one block the change deleted could not get the mutation record fitness #54 requires: the record read UNDECIDED `base-red-clean`, measured twice (the tracker's §Log, WU-2.3c, [read at its permanent link](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md)).
- **Day-one enforcement:** construction and gate. Construction: the gate's entry point takes the retire mode as a flag with a usage error on repetition, and every wiring of the gate (package script, battery step, workflow step) passes it, held by a suite case per class (no matching row → exit 1 naming the class; the flag absent → the check skipped). Gate: the same check is listed in the gate-retirement audit the plan carries (row GATE-RETIREMENT-AUDIT, `docs/product/plan/cross-cutting.md`), so a class whose population is gone cannot outlive it unnoticed.
- **Loosen if:** a class's population is known to return (a tier that reappears each release), in which case its retire condition names the inventory that proves the return instead of failing closed; never by removing the flag from one of the three wirings.

### FP-030 — A gate that lets a change through by a named remedy is probed with that remedy when it lands, for each kind of change it refuses

- **Practice:** A gate that refuses a change unless the change carries a named remedy (a measured record, a marker, a classification row) is run, when it lands, once per kind of change it refuses, each time with the remedy attached, and each run must exit zero. A kind of change that no remedy path reaches is repaired in the gate or named as unremediable in its text; it is never left for the first change that meets it.
- **Why:** omni-post's fitness #54 refuses a deleted test block unless a record measured it or the block's test imports a changed source. On 2026-11-10 the deletion of `scripts/testing/metrics.mjs` together with its suite, `apps/api/tests/unit/scripts/testingMetrics.test.ts`, was reached by neither path: the suite built the script's path with `path.join(REPO_ROOT, "scripts", "testing", "metrics.mjs")`, which the literal rule did not read, so the gate refused all 16 of its blocks with `no-record` and the stated remedy could not be met by a record either, since no measurement exists for a test of a script that leaves with it ([`record-coverage-core.mjs`](../../scripts/testing/lib/record-coverage-core.mjs); fitness #54 in [CLAUDE.md](../../CLAUDE.md)).
- **Day-one enforcement:** construction and gate. Construction: the gate's suite holds one case per kind of change the gate refuses, each carrying its remedy and expecting exit zero, beside the case that expects the refusal without it. Gate: the pull request that adds or changes the gate shows each of those runs. Carry-over: generalized gate; omni-post's fitness #54 suite holds the case for the `path.join` form.
- **Loosen if:** never for a remedy the gate itself names; a kind of change that cannot be remedied is stated as such in the gate's text, with the review that decides it.

### FP-032 — A CI job repeats the documented start sequence on a clean checkout, prepares nothing the documentation does not, and holds the database empty once every application has started

- **Practice:** From the commit that writes the start procedure, one CI job runs exactly the command the developers' and the deployment documentation give, on a fresh checkout, and nothing else prepares the run: no service containers, no environment file, no secret and no variable of the CI system. The command starts its backing services from the same compose file a developer uses, generates its own environment, migrates the database and starts every application from source, and exits 0 only when each application's health route answers 200, and each web application also serves its first page and forwards a request to the API it started. After the whole start the job counts the rows of every table exactly, never by the planner's estimate, and fails unless the only table holding rows is the migration tool's own record; the failure names each table with its count, and a listing that returns no table fails too. A failed run prints the logs the command left, never the generated environment file.
- **Why:** omni-post had several ways to start and CI repeated none of them. Its integration job brought the API and the workers up on service containers, with a synthesized environment file, an application role and a seed, and no job started the web applications at all, so what a clean checkout does was never measured. The first runs of the start sequence found three defects no check had seen: on a fresh checkout both web applications answered 500 until their workspace dependencies were built (DEF-85); the environment variables page omitted five required variables (DEF-97); and every boot of the API writes one row into the event store, so the database is empty after the migration and not after the start (API-BOOT-WRITES-A-SYSTEM-HEALTH-EVENT). Evidence: the F-01 record in [chain.md](../product/plan/chain.md), the row in [cross-cutting.md](../product/plan/cross-cutting.md), and the job `Platform Start` in [ci.yml](../../.github/workflows/ci.yml).
- **Day-one enforcement:** gate. The job lands in the same commit as the start procedure, runs on every pull request, and becomes a required check once it has passed on the main branch. The documentation and the job name one command, so changing either without the other shows in review. The row count belongs to the job, exempts only the migration tool's table and fails closed. Carry-over: generalized gate, omni-post's `Platform Start` job without its wait figures, which are measured on the new application's runners.
- **Loosen if:** the job leaves only when another required job starts the same applications from the same compose file on a database migrated from empty on every pull request. The row count admits a table only by a recorded decision of the Product Owner that names it, never because an application's boot happens to write to it.

### FP-034 — A check that must block runs on an event that can block, fails closed on its own failure, and a gate holds that it is wired

- **Practice:** A hook that enforces something a session must not go on without runs on an event the harness lets refuse, and turns every failure of its own (input it cannot read, a missing or malformed input file, an exception, a failure to import its own helpers) into that refusal with a message that names the repair. Its state is kept by what the harness reports, keyed by session and by agent, never inferred from the transcript. The harness is told to refuse when the hook itself cannot run (Claude Code's `"onFailure": "block"`), and the hook refuses a harness too old to honour that. An off switch exists for the person who owns the hooks, set outside the session, and announces itself at every prompt and in the log while it is on, whoever set it. A static gate holds that the hooks are tracked, executable and wired on their events, each entry held to an allowlist of keys: the refusal on failure present, a timeout that leaves room for their work, and nothing that runs the hook in the background or filters it out.
- **Why:** omni-post's agent harness could not block at session start: `SessionStart` shows its stderr and goes on, and `InstructionsLoaded`, which reports the instruction files loaded, runs asynchronously and ignores its exit code; the first event that refuses is the prompt. A hook that exits with any code other than the refusal code, crashes on its own import, cannot start, or is killed at its timeout lets the prompt through unless it is wired with `"onFailure": "block"` (Claude Code 2.1.295 and later), so a check that only reported its own failure would have passed every session it could not judge. The first version of this check left the key out, and with its executable bit lost the model answered (measured); a gate that read only that the hook was listed passed it with `async: true`, which runs it in the background, and beside `disableAllHooks: true`. A subagent's hook input carries its parent's transcript, and the transcript lags the conversation, so a guard reading it would miss a read made a moment earlier (ADR-0045, amendment "the enforcement"; `.claude/hooks-py/user_prompt_instruction_check.py`, `.claude/hooks-py/pre_tool_record_guard.py`).
- **Day-one enforcement:** construction and gate. Construction: each blocking hook's entry point catches everything and exits with the refusal code, and its suite holds that refusal on input that is not JSON, on a missing input file, on an exception and on an import failure, each run as a process; the switch has a case that it lets the prompt through, warns and logs. Gate: the repository gate that holds the instruction context also refuses a settings file that turns every hook off, sets the off switch or the harness version the hook reads in its `env` block, or does not run each hook on its event and matcher, an entry with a key outside its allowlist (a blocking one without `"onFailure": "block"`, a recording one with it, `async`, `if`, `shell`, `args` or any unknown key), a timeout under the hook's work, and a hook that is untracked or not executable in git's index and on disk; omni-post's is rule W1 of `scripts/testing/instruction-context-gate.mjs`, run in CI.
- **Loosen if:** the harness gains a blocking event at session start, or refuses by itself a session that lacks a required instruction file; the hook then moves to that event or retires, and its wiring leaves the gate with it.

### FP-038 — A check required to merge pulls nothing from a public registry that has no mirror or retry, and the mirror's failure path is shown before the check is required

- **Practice:** Before a job becomes a check required to merge, every image, package or action it pulls from a public registry is read through a mirror that falls back to the origin, or is retried a bounded number of times, and the mirror's failure path is run once and shown to leave the job green: a mirror that does not answer is skipped and the pull goes to the origin. The configuration says which pulls the mirror covers and which it does not, so a reader never takes it for every pull the job makes. A pull that cannot be mirrored or retried is listed with its owner before the check is required.
- **Why:** omni-post's four image builds pulled their base image from the public Docker Hub with no retry and no mirror, and were optional, so an outage or a rate limit there failed a job nobody had to wait for. On 2026-11-20 the Product Owner decided that the image scan and the platform start become required to merge; from then on a rate limit at one registry would have blocked every merge, and only the Maintainer can lift a required check. The mirror was added to the builder's configuration and its failure path was measured locally with the builder image the workflow starts and a mirror host that does not resolve: the build exits 0 and the builder logs "trying next host", so the mirror removes the rate-limit failure and adds none. Not measured: a mirror that answers with HTTP 429 or 5xx, and the run inside the CI system. The mirror also reaches only what the builder pulls: the service images of other jobs and of Compose, the image build's frontend named by tag and a scan action named by a branch still reach their origin unmirrored or unpinned, and are items of the F-01 record in [chain.md](../product/plan/chain.md) (SERVICE-IMAGES-PULL-STRAIGHT-FROM-DOCKER-HUB, DOCKERFILE-FRONTEND-NOT-DIGEST-PINNED, TRIVY-ACTION-UNPINNED). Evidence: IMAGE-1 in that record, the job `container-security` in [production-ci.yml](../../.github/workflows/production-ci.yml) and the contexts of [main.json](../../.github/rulesets/main.json).
- **Day-one enforcement:** construction. The workflow that holds a job configures the mirror in the same commit that makes the job required, and the pull request that makes it required carries the run of the failure path, the pulls the mirror does not cover and the owner of each. No gate exists for it yet: a derived list of the pulls of every required job, compared with the mirror's coverage, is the check the next application builds. Carry-over: omni-post's `buildkitd-config-inline` of the job `container-security`.
- **Loosen if:** the origin registry serves the project's pulls with no rate limit that a merge can reach (a pull authenticated with the project's own account, for example), or the job's images come from a registry the project hosts; the mirror may then leave, and its red path with it.

### FP-039 — A check that judges other tools' output by its words reads a value a tool quotes from the tree as data, by that tool's line grammar and only in that tool's log

- **Practice:** A check that turns a run red on the words other tools print (a warning word, an error word) states, beside its rule, each kind of line on which a tool prints data rather than speaks: a value it copies from the tree, such as a test's title or a file's name. Each exception is keyed to the log of the one tool that prints that line and to the tool's line grammar, leaves out only the data field, and still reads the rest of the line, every other line of that log and every other log. A line the grammar no longer matches is read whole, so a change to the tool's output turns the run red, never quietly green.
- **Why:** omni-post's battery verdict reads any line holding `warn`, `warns`, `warning` or `warnings` as a warning, with no allowlist, and the record-coverage gate prints the title of each test block a change deletes or rewrites. On 2026-11-20 a static battery went red with every step at exit 0 on the block "should log operational errors as warnings", a block of the base its author could not rename, and 66 of the ledger's 15,562 block titles held such a word (BATTERY-VERDICT-READS-A-TEST-TITLE-AS-A-WARNING in [cross-cutting.md](../product/plan/cross-cutting.md); [`battery-verdict.mjs`](../../scripts/testing/battery-verdict.mjs)).
- **Day-one enforcement:** construction. The exception lands in the commit that wires the first tool printing data from the tree into the check, and the check's suite holds that tool's line with a warning word in its data field (green), the same word elsewhere on the line, the tool's line after other text on the same line, the same line in another tool's log and the tool's own problem lines (each red). Carry-over: omni-post's `warningTextOf` and its cases for the record-coverage gate's block lines (`apps/api/tests/unit/scripts/batteryVerdict.test.ts`).
- **Loosen if:** never by a list of accepted lines or words; a tool that stops printing data from the tree loses its exception in the same change.

### FP-041 — A build on the default branch restores its cache only on an exact match, and the probe that judges the cache keeps the wider match, read-only

- **Practice:** A job that builds on the default branch restores its build cache only under the exact key of the commit it builds, never by a prefix that matches an earlier commit's entry: a first attempt builds from source, and only a rerun of the same commit replays. Other refs may restore by prefix. The condition is written once in the workflow and every cache step takes it by reference, and one job alone saves entries. A scheduled probe that compares a cached build with a cold one keeps the prefix on every ref, because it feeds no build, and its failure names each known cause that can leave it with nothing to compare.
- **Why:** omni-post's `Build Check` failed on `main` when a dependent package compiled against a restored, partial `dist` of a workspace package (the `CI` run 42714808192, and again on 2026-11-06, run 42251592175): the build tool replays a cached `dist` without its incremental-build record, so a dependent's compiler rebuilds that package while others read its half-written declarations. Each failure cost a manual rerun of a merge. The Maintainer decided on 2026-11-20 to drop the prefix on `main` (`.github/workflows/ci.yml:44-74`). The first version of the change dropped it from the probe too, and its review showed the probe would then fail whenever its schedule fired while the commit's own build was still running, so the probe keeps it (`.github/workflows/cache-divergence.yml:91-105`). Not measured: what a first attempt on `main` costs in minutes.
- **Day-one enforcement:** construction. The workflow that first adds a build cache writes the restore condition once, with the default branch restoring on an exact match, one saving job, and the probe beside it. No gate holds the two files' keys together: the coupling is a convention that the comments of both files state, and a check that compares them is what the next application builds.
- **Loosen if:** the build tool verifies a restored output before a dependent reads it (a hash of the restored tree, or the incremental-build record stored with it), shown by a run on the default branch that replays an earlier commit's entry and compiles against it with no rebuild; the prefix may then return there.

### FP-044 — Only the default branch saves a CI cache; every other ref restores, and the images of a matrix build take one cache scope each

- **Practice:** CI caches are saved by runs on the default branch only. Every other ref, every pull request included, restores what the default branch saved and saves nothing. Each cache is a conditional pair of steps that share their inputs. On the default branch, a cache step restores and saves at the end of a job that passed, after every later step that writes into the cached path. On any other ref, a restore-only step runs. Each image of a matrix build exports its layers under its own scope, named after the image, and only on the default branch. A cache that a third-party action writes on its own is turned off or conditioned the same way when the action is adopted.
- **Why:** In omni-post every pull request saved its own caches, and a cache saved by a pull request can be read only by that pull request. On 2026-11-24 the repository held 10.61 GB of caches against the provider's 10 GB limit:
  - 6.63 GB of image layers and 2.86 GB of package stores, saved by pull requests;
  - 1.07 GB saved by the default branch;
  - ten dependency-update pull requests open at once.

  The provider evicted the default branch's build cache, and the scheduled cache probe restored nothing and failed (run 45419741816; `docs/reports/CI_CACHE_INTEGRITY_AUDIT.md` §6). The four images of the container job also shared the backend's default scope, so each build overwrote the cache of the one before it, and a run kept only the last image's layers.

- **Day-one enforcement:** construction. The first workflow that caches anything writes each cache as the pair: the restoring-and-saving step under `if: github.ref == 'refs/heads/main'`, and the restore-only step under `if: github.ref != 'refs/heads/main'`. The pair's inputs are written once, with a YAML anchor on the first step's `with:` mapping or a step that computes the key. Each image of a matrix build gets its own scope and exports only on the default branch. No gate checks this. What the next application builds is a check that refuses a saving cache step, or a layer export, without a condition on the ref. Read on 2026-11-24 from GitHub's workflow syntax source: a workflow or a job can also set `cache-mode` (`read`, `write`, `write-only`, `none`), which the cache token enforces. The documentation states no expression support for it and lists it in no context-availability row, so it fits a workflow whose triggers all take the same access, not one that runs on both the default branch and pull requests.
- **Loosen if:** the provider counts pull-request caches apart from the default branch's quota, as its documentation states; or a month of the most pull requests ever open at once keeps the repository's total cache, pull-request entries included, under half the limit. Pull requests may then save again.

## Security and tenancy

### FP-007 — Tenant isolation fails closed from the first tenant-bearing model

- **Practice:** The data-access tenant guard refuses a model it does not know unless that model is on a documented global list. The migration that creates a tenant-bearing table enables row-level security and its policy in the same file. The application connects as a role that owns no table and carries neither superuser nor bypass-row-security, so the policies apply to it.
- **Why:** omni-post's guard silently skips a model it does not know (fail-open by construction), so `DeletionRecord` landed carrying the tenant column with neither the guard's list nor any documented list knowing it existed (fitness #39 in [CLAUDE.md](../../CLAUDE.md)). Row security arrived in ten separate `add_rls_*` migrations between 2026-05-27 and 2026-09-09, and the policy on every guard-enrolled table (58 when measured) did nothing for the running application: it connected as `postgres`, a superuser with `BYPASSRLS` that owned every table, and with tenant B bound a read of `Project` returned tenant A's rows. The integration suite had proven the policy against a synthetic role, not against the application's ([ADR-0022](../technical/ADR-0022-rls-enforcement-posture.md); [RLS_POSTURE_RED_BASELINE.md](../reports/RLS_POSTURE_RED_BASELINE.md)).
- **Day-one enforcement:** construction and gate. Construction: the guard throws on an unknown model; the first migration creates the application role without those attributes; the migration that creates a tenant-bearing table carries its policy. Gate: a check derives the tenant-bearing models from the schema and requires each one to be enrolled or documented, fitness #39's form; an integration test against the migrated database requires, for every enrolled model, row security on, at least one policy, and no ownership by the application role, the form of omni-post's RLS coverage gate, which is an integration test because catalog state is not greppable ([CLAUDE.md](../../CLAUDE.md) §Automated Compliance Checks). Carry-over: by construction for the guard, generalized gate for the enrollment check and the coverage test.
- **Loosen if:** never: omni-post's canon admits no exception for multi-tenant isolation ([CLAUDE.md](../../CLAUDE.md) §Pragmatic Exceptions), and the next application inherits that rule.

### FP-014 — A response cache keys every cached response of an authenticated route by its caller, and the application refuses to boot a cache rule that does not

- **Practice:** The cache is read only after the route's own hooks have admitted the request, as the route's last pre-handler, never from a global request hook. A cache rule of an authenticated route names the caller's credential in its key, as a digest and never the credential itself, because a hit still skips the handler and its ownership check, and the application refuses to start when a rule of a registered route leaves the caller out: when the route carries one of the authenticating hooks, compared by identity, or when the rule does not declare its route public. A rule without that declaration is refused, so an authenticating hook the check cannot see still fails the boot. Caller-supplied values are escaped before they enter a key, so one request cannot pose as another.
- **Why:** omni-post's response cache answered a hit from a global `onRequest` hook, before any route hook ran, and its dashboard rule varied by query only, so for five minutes one account's project dashboard was served to another account and to a caller with no token; four provider rules behind the same authentication hook did the same. A token past its expiry kept receiving the response it had cached, because the route's authentication never ran on a hit. A comment above the post rules said the credential was required, and nothing enforced it; those rules wrote the raw bearer token into the key, a Redis key name that `X-Cache-Key` echoed and the admin hot-keys route listed (DEF-104 in [MASTER_PLAN.md](../product/MASTER_PLAN.md) §5.11; [`cacheHitBeforeAuth.integration.test.ts`](../../apps/api/tests/integration/cacheHitBeforeAuth.integration.test.ts); [`cacheRouteCoverage.ts`](../../apps/api/src/lib/cache/cacheRouteCoverage.ts)).
- **Day-one enforcement:** construction and gate. Construction: the cache plugin appends its read to the hooks of each cached route as the route registers, records those hooks and runs the caller check before the application is ready, with no list of exempt rules; the key builder digests every header it varies by. Gate: an integration test over the real application caches one account's response and requires another account, a caller without credentials and the same caller with an expired token to be refused by the route, and a unit test plants a rule without the caller on an authenticated route and requires the boot to fail. Carry-over: generalized gate, omni-post's `assertCachedResponsesVaryByPrincipal`, without the dead-rule baseline its route-coverage twin carries.
- **Loosen if:** never: a cached response keyed without its caller reaches callers the route would refuse, and the canon admits no exception for multi-tenant isolation ([CLAUDE.md](../../CLAUDE.md) §Pragmatic Exceptions). A route leaves the check only by declaring itself public, a reviewed declaration the check refutes when the route authenticates.

### FP-020 — Every telemetry SDK removes what it must not send in one hook at its init, and a test on the real SDK proves none of it reaches the payload

- **Practice:** Each telemetry SDK a deployable starts (error tracking, tracing) is created in one init module, with a send-time hook that removes the attributes it must not send and a closed list of those attribute names: credentials, user identifiers, the database user. A test starts the real SDK through that module with an in-memory transport, runs an instrumented call (a database query against a refused connection is enough) and fails when a listed attribute reaches the recorded payload. An upgrade of the SDK, or of an instrumentation it brings, re-runs that test before it merges.
- **Why:** omni-post's Sentry SDK writes the database user on every pg connect and query span. From 10.54.0 Sentry vendors the instrumentation that does it, so the override bands that hold the OpenTelemetry instrumentations at their fixed releases (GHSA-qqmp-wf37-98f9) never reached Sentry's copy, and the 11.x line keeps the attribute in a new package. Measured on 2026-10-22 with Sentry initialized before `pg` loads, 2 of 3 spans carried `db.user` into the envelope on 10.76.2 and on 11.8.0; the API's `beforeSendSpan` brought it to none. What had kept it out of production until then was an accident of boot order, `pg` loading before Sentry ([DEPENDENCY_AUDIT_RECORD.md](../security/DEPENDENCY_AUDIT_RECORD.md), row `@sentry/node` + `@sentry/nextjs` and §"Blocked floors"; [`sentryInit.ts`](../../apps/api/src/observability/sentryInit.ts)).
- **Day-one enforcement:** construction and gate. Construction: the init module carries the hook and the list from its first commit, and every exporter is created there, so no second SDK starts outside it. Gate: the payload test above runs in the integration tier, and a unit test requires the init to hand the hook to the SDK. Carry-over: generalized gate; omni-post holds the hook, its unit test and the payload gate [`sentryPayload.integration.test.ts`](../../apps/api/tests/integration/sentryPayload.integration.test.ts), which the Integration Tests job runs on every pull request: it starts Sentry through the real init before `pg` loads, records every envelope in memory, and fails when `db.user` reaches the transport or when no pg span does.
- **Loosen if:** never: an attribute that has left the process cannot be recalled, and a dependency's release notes do not list the attributes it adds.

### FP-024 — The machine-readable API document is off by default, opened per environment by a typed flag, served by routes it never lists, and with a relative server

- **Practice:** The OpenAPI document's routes register through one function that takes a boolean, and the composition root passes it a flag from the validated environment schema whose default is off; an unset or malformed value never serves them. Those routes are hidden from the document, so the document, and any client code generated from it, is identical whichever way the flag is set, and the document declares a relative server so a viewer resolves against the origin that served it. The registration refuses to start when it is enabled without the document's generator, instead of serving nothing. An interactive reference page ships only with the CSP change it needs, decided on purpose; otherwise viewers read the document.
- **Why:** omni-post served its Scalar reference and the full OpenAPI document, every route, parameter and schema, in every deployment, production included, with no environment gate; the hand-rolled document route listed itself in the document, so the generated API types carried it, and passing Scalar a URL broke Scalar's own document routes (one answered 500, the other an empty 200). Nothing caught any of it because no test booted the application and asked for `/docs`, and the page itself never rendered: the API's CSP blocks Scalar's inline script in every environment (DEF-144). Evidence: DEF-142 in [MASTER_PLAN.md](../product/MASTER_PLAN.md), [`apiReference.ts`](../../apps/api/src/lib/apiReference.ts).
- **Day-one enforcement:** construction and gate. Construction: the flag sits in the environment schema with its default off from the first commit that adds a reference, and the reference registers only through the one function. Gate: an integration test boots the real application under the test environment and requires every reference route to answer 404 and the document to list none of them; the same test pins the relative server; a unit test proves the enabled routes serve the document as JSON and YAML, register nothing else under the prefix, and refuse to register without the generator. Carry-over: omni-post holds [`apiReferenceGate.integration.test.ts`](../../apps/api/tests/integration/apiReferenceGate.integration.test.ts) and [`apiReference.test.ts`](../../apps/api/tests/unit/lib/apiReference.test.ts).
- **Loosen if:** never by default: the document is a map of the attack surface, and an environment that wants it says so in its own configuration, reviewed with the deployment.

## Dependencies

### FP-009 — A check that derives facts from dependency fields reads a checked list for what the fields cannot say, so no package bends a field to suit it

- **Practice:** A package declares under `dependencies` everything its code loads when it runs, and under `devDependencies` only what its tests, types and build use, whether or not it is ever deployed. A check that derives a fact from those fields, such as which dependencies reach production, takes what the fields cannot say from an explicit list in its own input: one entry per package, with the reason it never reaches production. The check refuses an entry with no reason, a name no private workspace carries, and a package that a production manifest declares outside `devDependencies`, and it counts every declaration a tooling package makes as a tooling declaration, so a workspace that only tooling needs is tooling too.
- **Why:** omni-post's legal subprocessors inventory decided "production" from the fields alone: a workspace counted as tooling only when other manifests declared it, and only under `devDependencies`. Its test-contracts package is private, runs only in CI and is declared by no manifest, so moving the four packages its code loads when it runs (`vitest`, `typescript`, `yaml`, `tsx`) to `dependencies` would have recorded them as production recipients in the legal register, and the package kept them under `devDependencies`: a field written to suit a gate instead of to describe the run. Measured on 2026-10-15, a list naming that package was not enough on its own: once it declared the shared test-configuration workspace under `dependencies`, that workspace stopped counting as tooling and `vitest`, its peer, read as production (fitness #45 in [CLAUDE.md](../../CLAUDE.md); [`subprocessors.mjs`](../../scripts/legal/subprocessors.mjs); the `tooling` list of [`subprocessors.json`](../legal/classification/subprocessors.json)).
- **Day-one enforcement:** construction and gate. Construction: the production-or-tooling derivation reads its list from its first commit, empty, and derives tooling as a fixed point over every declaration a tooling package makes. Gate: the inventory check fails on each refused entry, and its suite plants every refusal and a listed package whose run-time dependencies would otherwise read as production. Carry-over: generalized gate, fitness #45's subprocessors generator with its `tooling` list.
- **Loosen if:** never: a field written to suit one check misstates what the package needs to run, and every other tool that reads the field inherits the error. The list grows only by a reviewed entry with its reason.

### FP-010 — A dependency-freshness gate measures every tool the manifests declare, and holds a code generator in lockstep with the runtime packages it generates for

- **Practice:** A freshness check compares every direct development dependency, the tools that build, test, lint and generate code, with its latest stable release past a maturity buffer, and fails once a lag outlives a fixed budget with no recorded hold. Its population is read from the manifests' `devDependencies` by the check itself, never hand-listed: a tool leaves it only by an entry in the check's own list, with its reason, and that list starts empty. A code-generating CLI and the runtime packages it generates for (an ORM's CLI, its client and its driver adapter) are declared as one family, with the reason they move together, and the check fails when any member resolves to a version its siblings do not, whether an importer declares it or another member resolves it as a dependency or a peer.
- **Why:** omni-post's holds gate measures a hand-kept population of testing and quality tools ([`toolchain-population.json`](../../scripts/testing/toolchain-population.json); [ADR-0036](../technical/ADR-0036-dependency-update-cadence.md)). The Prisma CLI, which generates the database client on every install and in the build stage of all four images, was not in it: 7.10.0 matured on 2026-09-01, its 30-day budget ran out on 2026-10-01, and the tree stayed on 7.9.1 until 2026-10-15 with nothing failing, although the catalog comment had recorded on 2026-10-03 that a newer mature release existed. When the family moved that day, lockfile preference kept the `prisma` 7.9.1 peer of `@prisma/client` 7.10.0 under two importers until the three packages were updated together, a split no manifest shows. Since then the gate measures the CLI's freshness and declares the three as the family `prisma`, which it holds to one version, reading the two production members for equality only; with `@prisma/adapter-pg` planted at 7.9.1 it exits 1 naming that member, its version and its importer. Its population is still hand-kept: a tool added to a manifest is not measured until someone lists it ([`holds-gate.mjs`](../../scripts/testing/holds-gate.mjs), residuals 1 and 3; SB-212 in [review-suggestions-book.md](../reports/review-suggestions-book.md) records the same gap for other families).
- **Day-one enforcement:** gate. The freshness check, with its maturity buffer and budget, runs from the first manifest, reads its population from the manifests' `devDependencies` minus a reasoned exclusion list that starts empty, and fails on a family whose members resolve to two versions; each family is declared in the commit that adds its generator. Carry-over: the family check is a generalized gate, the `families` of omni-post's holds gate as they run; the derived population has no precedent here, because omni-post's population is hand-kept, so the next application builds that part new.
- **Loosen if:** never for the derivation or the family check: a hand-kept population drifts from the tree the moment a tool is added, which is how the Prisma CLI went unmeasured. The budget's length is a recorded decision, as ADR-0036's 30 days are, never a per-package exception.

### FP-022 — Every direct dependency proves its use with real sites in the tree or carries the owner's decision, held by a gate from the first commit

- **Practice:** A check derives, for every direct dependency the manifests declare, the files that use it in the tracked tree, each site with its kind (a runtime import, a type-only import, a test mock, a string in a configuration, a stylesheet load, a command line) and its path class (production, test, configuration). A dependency counts only the sites its scope can use: a production dependency its production imports and stylesheets; a development dependency its imports, stylesheets and command lines and the configuration strings of configuration files; a types package the type-only files of the package it types. A mock never counts, and neither does a configuration string in the check's own modules and suites, which name every field, protocol and tool the check reads and plant packages as fixtures; their imports still count. A dependency under a fixed floor of distinct files stays pending until a reviewed decisions file records the owner's outcome: kept, with its ground, what it does and the replacement weighed, or remove, with what replaces it. The check writes the derived record to a tracked file and fails when the record is stale, when an entry is malformed or no longer applies, and when the pending count differs from its exact baseline in either direction; an input it cannot read in full stops it as a failure of its own, never as zero sites.
- **Why:** omni-post declared 175 direct dependencies and recorded which of them reach production, for the legal register, but nothing recorded which of them were used. Use was measured by hand, one package at a time: on 2026-10-22 `@monaco-editor/react`, `@fastify/rate-limit`, `papaparse` and `react-email` each turned out to serve two files or fewer, and each left in its own pull request (#678, #679, #698, #694); the method left no record a later pass could compare against. `@fastify/websocket`, declared by the API since the first commit, had no site anywhere and stood behind a knip `ignoreDependencies` entry the whole time, until `deps-remove-1` removed both on 2026-10-25. The ledger's first run, on 2026-10-24, found 128 of the 175 under the floor of 3 real sites and 19 with no site at all ([`dependency-ledger.json`](../../dependency-ledger.json); WU-2.2b in [TESTING_REFOUNDATION.md](https://github.com/edwardricardo/omni-post/blob/a72e052577f4c74903de2e7b48487daa85658c7f/docs/development/TESTING_REFOUNDATION.md)). Its first version also counted its own source: the string `"lint-staged"` in the module that reads the `lint-staged` key raised that tool from one real site to two, and its suites' fixture strings were the only site the record listed for `vite`.
- **Day-one enforcement:** gate. The check runs in CI and in the local battery from the first manifest, with an empty decisions file and a pending baseline of 0: a dependency is decided in the commit that declares it, so it lands kept or does not land. Carry-over: generalized gate, omni-post's fitness #50, `pnpm check:deps-ledger`, and its battery step `deps-ledger`, without the 128 pending names it starts from.
- **Loosen if:** the floor is lowered for one site kind, by a recorded decision, when a measured sample of the decisions file shows the owner keeping more than nine in ten of that kind's dependencies under the floor on the same ground; never by an exemption list, and never by raising the pending baseline without a decision behind each name it adds.

### FP-042 — An image's language runtime is held to its vendor's release list by a gate of its own, because an image scanner reads the OS packages and the module manifests, never the runtime executable

- **Practice:** The job that builds an image asks the built image which runtime it runs, through the runtime's own version command run inside the image, and only reports that version. A job of its own, which no merge requires and nothing that publishes waits for, runs a gate that compares each reported version with the vendor's published release list: it fails when a later stable release of the same major line is marked as a security release, naming each one with its date and the base to raise, and fails closed, never passing, when the list cannot be fetched within a bounded number of attempts, is not the shape it expects, or does not list the image's own version. The job exists for two red cases outside the team's repair, a vendor's lag in shipping a fixed base and a third party's host not answering, so the check runs where its red is seen and blocks nothing: no merge, no scan and no publication. Its other red cases are the team's to repair, and each says where to look: an image whose build job reported no version is named as not checked, a version the gate cannot read as a stable release is refused, and a failure of the gate itself has an outcome of its own, so it never reads as a verdict. The job is skipped when the build job did not run, since nothing was built and its red would not be about the runtime, and when the run itself is cancelled. Each run judges again, so the first run after the cause is repaired, or after the list answers, is green. The gate imports only the runtime's standard library, so it runs before anything is installed, and its rule is a pure function its suite pins without a network.
- **Why:** omni-post's images run a distroless Node base, which ships the `node` executable without a package record, and its image scan (Trivy, `CRITICAL,HIGH`, exit code 1) reads the OS packages and each module's `package.json`. Measured on 2026-10-22, the images ran Node v26.12.0 a day after four High advisories were fixed in v26.12.1, and the scan reported 0 and exited 0; until 2026-11-20 the only reader of Node's release index was a manual review of the maturity watchlist ([`maturity-watchlist.json`](../../scripts/testing/maturity-watchlist.json); [base-images.md](../deployment/base-images.md), §"Moved to Node 26.12.1 on 2026-10-22"; DEF-160 in [chain.md](../product/plan/chain.md)). When the gate landed, the four images cached on the development box, built eight weeks earlier on Node v24.21.0, failed it against v24.22.1 and v24.22.3. Inside the job every merge requires, the gate would have stopped every merge, the image scan and the publication for as long as the distroless base lagged a security release, about two days for v26.13.1 ([base-images.md](../deployment/base-images.md), §"Moved to Node 26.13.1 on 2026-11-14"), or for as long as the release list did not answer.
- **Day-one enforcement:** gate. The gate lands with the first image, in a job of its own that no merge requires and nothing that publishes waits for; it judges every image after it is built, on the version the image's build job reports, and its suite plants a later security release, a later release that is not one, a later security release of another line and of a pre-release, an index that cannot be fetched or parsed, and each malformed entry. Carry-over: generalized gate, omni-post's `Node Runtime Advisory` job of [`production-ci.yml`](../../.github/workflows/production-ci.yml), fed by the `Node version` step of `Container Security`, and [`node-runtime-advisory-gate.mjs`](../../scripts/testing/node-runtime-advisory-gate.mjs), for whichever runtime the next application's images ship.
- **Loosen if:** the image scanner reports the runtime executable's own advisories, measured by scanning an image whose runtime is behind a published security release and watching the scan fail; the gate then retires, and its job and the version step that feeds it leave with it.

## Documentation

### FP-006 — Method-level documentation is enforced on every in-scope file from the first commit, not only on touched files

- **Practice:** The documentation rules (a file header, and on every exported function and public method a description, one entry per parameter and the return value) run over the whole tree, at zero, in the same lint pass as every other rule, with no baseline and no touched-files scope. An inline disable comment does not exempt a file.
- **Why:** omni-post's canon required method-level JSDoc and nothing enforced it: measured on 2026-10-10, 35% of public methods carried no JSDoc at all and 31% carried the canon's tag form. The gate that landed on 2026-10-11 holds only the files a pull request touches, in a configuration the ordinary lint run does not load, and the rest waits for a reconciliation still open, which started from 1,028 of 2,134 in-scope files holding 9,648 violations that day (fitness #47 in [CLAUDE.md](../../CLAUDE.md); N-CI-5 and N-CI-6 in [MASTER_PLAN.md](../product/MASTER_PLAN.md) §1).
- **Day-one enforcement:** gate and hook. The rules live in the main lint configuration, so the CI lint run and the pre-commit hook enforce them on every file. Carry-over: generalized gate, fitness #47 without the touched-files scope that answers omni-post's backlog.
- **Loosen if:** a measured sample of the documentation shows a required tag restating the type signature in more than half of its occurrences; that tag's requirement is then dropped by a recorded decision, never the whole rule.

### FP-025 — Every artifact is written in one language and names roles, never people, from the first commit, held by a gate

- **Practice:** Every tracked artifact (code, comments, configuration, CI, documentation, plans) is written in one language. Four classes are exempt, and no others: product locale data; a document with a twin in that language; immutable content, such as an applied database migration whose checksum the migration tool verifies; and detector vocabulary, such as the word list of a check that must name the other language's words it detects. An artifact names the role that decides (who decides what the product does, who decides how it is built and delivered), never the person who holds it. A person's identity stays only in a governance page, which maps each role to its holder with the dates they held it, and in the identities a tool or a link needs. The ADR template names roles in MADR's decision-makers, consulted and informed fields. A gate counts, per tracked file, lines in another language and mentions of a person, and fails on any count above zero; its allowlist holds only the four exempt classes and the identities the roles rule keeps, each entry with its reason.
- **Why:** omni-post wrote its artifacts in two languages and named its one decision-maker in them. Measured on 2026-10-28, 83 tracked files held 2,975 Spanish lines and 187 files held 887 mentions of that person, 713 of them where a role decides, such as the decision-maker field of six accepted ADRs; every change could add more, because nothing counted them, and the tracked plans and trackers quoted each request verbatim in the language it was made in ([ADR-0040](../technical/ADR-0040-artifact-language-and-role-attribution.md) §Context).
- **Day-one enforcement:** construction and gate. Construction: the governance page and the ADR template's role fields exist in the first commit, so the first ADR names a role; the agent instructions require a translated request in every feature document, keep the original outside the tree, and have the pull request that implements a request quote its translation, so the approval of that pull request approves the translation. Gate: the count runs in CI and in the local battery at zero, with an allowlist limited to the four exempt classes and the identities the roles rule keeps. Carry-over: generalized gate, omni-post's artifact-language gate without its per-file baseline.
- **Loosen if:** never for the roles rule: a name goes stale the day its holder changes, and the governance page already resolves every role to a person. The language rule gains an allowlist entry only inside the four exempt classes, such as a new locale's data, each with its reason; a new class only by a recorded decision, and never a baseline.

### FP-028 — One plan, ordered by feature and by dependency, from the first commit; a finding outside a task's scope is attached to its feature, and its viability is decided when the feature opens

- **Practice:** The product has one plan, ordered by dependency and organised by feature: what makes the rest possible comes first, and each feature has one record that says what is built, in which order and when it is finished. Work that belongs to no feature has one cross-cutting part, and ideas with no slice have one parking part. A finding a task makes outside its scope is attached to the plan in the same change, with a descriptive id, `path:line` evidence and the task that found it, to its feature, to the cross-cutting part, or to parking; whether it is worth doing is decided when its feature opens, not when it is found. No second document lists pending work.
- **Why:** omni-post listed pending work in three documents with no order by feature: 562 live rows and 110 live units had accumulated when the plan of 2026-11-10 placed each of them, and every finding of a task had kept adding a row to the oldest of them ([PLAN.md](../product/PLAN.md), section "Where the old plans went"; [ADR-0044](../technical/ADR-0044-feature-ordered-plan.md)).
- **Day-one enforcement:** construction. The plan, its cross-cutting part and its parking part exist in the first commit, and the agent instructions name them as the destination of out-of-scope findings, so no rule names another document. Carry-over: omni-post's plan, with the rules of its `## Rules` section.
- **Loosen if:** never for the single list; the parts of the plan may be split further, by a recorded decision, when one of them holds more items than a reader can order in one sitting.

### FP-029 — A count that claims everything was moved is run against the source by id, never against an index built from the source

- **Practice:** When a migration, a split or a deletion claims that every item of a source document was moved, the claim is checked by listing the items by their id in the source itself and finding each one in the destination. An index built from the source to drive the move is not evidence of the source: its shape decides what it holds, so a count of it agrees with itself whatever the source holds.
- **Why:** the first index of omni-post's Master Plan took only the rows that start with a checkbox, and 191 lines of rows without one were in no record until a check by id against the source found them, before publication (pull request #858 records the control and those 191 lines in its Verification section; the corrected count, 562 live rows and tasks, and the rule that says which lines count as a live item are in [PLAN.md](../product/PLAN.md), section "Where the old plans went").
- **Day-one enforcement:** construction. The brief of any move names the source's own id grammar and asks for the control count to be taken from the source by that grammar; the checker that reports "all moved" prints the ids it did not find.
- **Loosen if:** never; the control is one pass over the source, and a source with no stable ids gets its lines numbered first.

### FP-033 — The instruction context an agent loads by itself holds rules and has a byte budget from the first commit; a record that grows with every change is read as a file, never loaded

- **Practice:** The files an agent loads at the start of every session hold rules: what to do and what never to do. A record (a ledger, an audit trail, a table of rows with dated history) lives in its own document that is read as a file, and is never imported into the loaded context, neither with an import line nor as the body of a rule. A short rule that loads only when a governed file is touched says where the record is, what to search in it before a change and what the change must record there. The loaded files have a byte budget from the first commit. When the record is the long form of rules that stay loaded (each check of a suite with its full block), what stays loaded is an index derived from the source that enforces it, each entry's name copied from the CI step that runs it, and a gate holds the index, the record and the enforcement to one set, so none of the three can drift from the other two.
- **Why:** omni-post's security canon grew by the dependency audit record it carried until it was 319,025 bytes, 295,719 of them the record, about 98,000 tokens of every request; the loaded project files went from 449 KB on 2026-10-15 to 572 KB on 2026-11-14. On 2026-11-17 the largest model refused every request of the project, "Hello" included, and probes showed the refusal follows the size of the loaded instruction content: the same amount read as a file with the Read tool did not count, and neither an import inside a path-scoped rule nor the record as that rule's body deferred it ([ADR-0045](../technical/ADR-0045-instruction-context-budget.md), the probe table). Its root instruction file carried the full block of each of its 54 fitness checks, 157,314 of its 201,668 bytes; once the blocks moved to a reference read on demand, the suite was stated in three files, and a list summarised by hand would have reworded every rule, so its lines copy the workflow's step names and the inventory gate holds the three files to one set (ADR-0045, the amendment of 2026-11-18).
- **Day-one enforcement:** construction, and gate for the carry-over. Construction: the rules document and the record are two files from the first commit, and the record's first line says it is read as a file; the path-scoped rule exists with the first governed file. Gate: a check derives, of the files git tracks in the project and read from the project root, a set that is never smaller than what the harness loads of them at session start, exactly where the harness's behaviour is cheap to derive (the entry files it reads from the project root) and over-counting on purpose where an exact copy of its parser could drift with its next version (every `@` token wherever it is written, a rule counted as loaded unless its front matter proves it path-scoped, a link at the rules directory, at its parent or under it refused), so its errors are false reds and never false greens; it does not count what loads only on a match (a path-scoped rule's body, a subdirectory's instruction file or rules directory), files git does not track (in omni-post's main checkout `CLAUDE.local.md` and `.claude/CLAUDE.md` load at every session start and are not counted; the manifest lists them as local), what a session started in a subdirectory loads beyond that set, or the user's and the organization's instruction files. It holds that set to a checked-in manifest in both directions and to a byte ceiling, refuses a record that is loaded and a rule glob that matches nothing without a stated reason, and keeps the ceiling within a small slack of the measured bytes (a tool lowers it and never raises it), so two branches never conflict on one exact figure while any growth past the ceiling is a visible edit; growth back into the slack a reduction leaves, at most 1,024 bytes here, passes with no edit; omni-post's is `scripts/testing/instruction-context-gate.mjs` (`pnpm check:instruction-context`, the battery step `instruction-context`). Carry-over: a check compares the files the harness reports as loaded with the manifest and blocks the session that lacks one, and a pre-edit hook blocks an edit of a governed file when the record was not read, each with its red path shown; omni-post's are the hooks `.claude/hooks-py/instructions_loaded.py` and `user_prompt_instruction_check.py`, which compare the reported loads with the manifest at every prompt, the first event that can block, and `pre_tool_record_guard.py`, which refuses an Edit, Write or MultiEdit of a governed file, and a Bash write it can derive (a destination pre-bash reads, a file named beside an in-place writer, the manifest and lockfile of a pnpm command that writes them, every builtin of the installed pnpm classified and held complete by a test that reads its list), until the session or the agent has opened the record. An opening is a tool call the harness performed, the Read or the Grep tool on the record, and never a Bash command: its text says what it would run, not what ran (`false && rg x <record>` names a search that never happens), so a guard that read it would report an opening it cannot know. A write the guard cannot derive passes unjudged: a script or a pnpm command that runs code, an interpreter one-liner (`python3 -c`, `node -e`, `perl -pi`), another package manager, a path built from a variable, `git apply`, and a checkout or a rebase that names no governed file. The gate's rule W1 holds that they are wired (FP-034). The index of a suite's checks is held by the gate that holds the suite's inventory, from the first check: the same set of numbers in the CI steps, the blocks and the index, and each index entry's name and command equal to its step's.
- **Loosen if:** the budget's figure is revised only by a measurement of the provider's current limit on instruction content, recorded in a new ADR; the rule that a record is never loaded stays while the record grows with every change.

### FP-036 — A feature closes only when no item under its record is open, and a gate refuses a closed feature that holds one

- **Practice:** Every item attached to a feature, or found while it is open, is one line of the feature's record, and its closure has one of two marks, each written at the start of the item's text with no punctuation of its own: resolved by a change, marked with that change's number, or closed by a decision, marked with the role that decided, a date no later than the day of the check and the decision itself in words. A feature is marked closed only when every item of its record carries one of the two marks. A check reads the plan's table of features and the record of each closed one, fails on an open item and names the feature and the item, and fails closed when the table or a record cannot be read; each record states how many items it holds, and any line of a closed record shaped like an item that the check does not read as one (nested, at the top level, inside a note, at the start of another entry's continuation, after a code fence nothing closes, or behind backticks that do not pair) fails it, so a record the check misreads cannot pass and an item cannot be hidden by where it is written: between refusing valid prose and letting an item hide, the check refuses. A table that groups features with no state column is not judged, and the check says so as a limit rather than reading it as closed.
- **Why:** omni-post's first feature closed with 24 rows of its record open, and its second came within one change of closing with 22. An item under a closed feature has no date and no owner, because no slice opens the feature again ([cross-cutting.md](../product/plan/cross-cutting.md), item ROWS-WAIT-UNDER-CLOSED-F-01; [ADR-0046](../technical/ADR-0046-feature-closes-with-no-open-item.md)).
- **Day-one enforcement:** construction and gate, from the plan's first feature. Construction: the plan's tracking rule names the two marks, and every record states its item count. Gate: a check that reads only the plan's files runs in CI and in the local battery, with its red path shown on a planted open item, an unreadable entry, an item written outside its list and a count that differs from its list; omni-post's is `scripts/testing/plan-closure-gate.mjs` (`pnpm check:plan-closure`, the battery step `plan-closure`). Carry-over: the grammar of the two marks and the gate's fail-closed paths.
- **Loosen if:** never for the rule; the marks' grammar changes only by a recorded decision, with the check changed in the same change.
