# Foundation Practices

**Owner:** Platform engineering
**Status:** living document, started 2026-10-15; it grows with every unit that teaches a practice.

The practices the next application adopts from its first commit, so it does not pay twice for what omni-post paid for in rework, the Testing Refoundation above all. The next application shares this repository's stack (TypeScript, Fastify, Next, Prisma on Postgres) and none of its domain: nothing here is about social media, providers or posts. Each entry is one practice, written as what to create and enforce on day one. The document records practices, never which packages to use.

## Where this is going

1. This document grows while the lessons happen.
2. It is turned into a prompt.
3. The prompt generates a skeleton of the next application.
4. The skeleton becomes the template, and counts as one only when every gate it carries shows a real red, a non-zero exit, on a planted violation.

It is read by whoever starts the next application, by whoever writes that prompt, and by every unit in this repository that teaches a practice.

## How to use this document

### Entry format

Every entry is a `###` heading with its permanent ID and the practice in one line, followed by four fields:

```markdown
### FP-NNN — <practice in one line>

- **Practice:** what the next application creates or enforces, stated so it can be checked.
- **Why:** what not having it cost omni-post, with the path to the evidence.
- **Day-one enforcement:** the kind (construction, gate or hook), what the next application sets up
  at its first commit, and how omni-post's precedent carries over.
- **Loosen if:** the measurable condition under which the rule may be relaxed, or "never" with the
  reason.
```

IDs are permanent: a new entry takes the next free number, and an entry that a later lesson sharpens is updated in place rather than duplicated.

### Strict first

Every practice starts at its strictest form: at zero, with no baseline and no grandfathered files. Retrofitting strictness costs far more than relaxing it. omni-post made method-level JSDoc canon with nothing enforcing it; its gate, which landed on 2026-10-11, holds only the files a change touches, and the rest waits for a reconciliation that started from 1,028 of 2,134 in-scope files holding 9,648 violations (FP-006). Relaxing a rule that already holds at zero is one edit.

So every strict rule names, in its **Loosen if** field, the measurable condition under which it may be relaxed. A rule is never loosened out of fatigue, and a field that says "never" means never.

### Scar versus lesson

An entry records the practice that makes a defect class impossible, or caught on the first commit that introduces it. It never records omni-post's remediation. Many of omni-post's gates carry the shape of their history: a ratchet, a quarantine, a touched-files scope, a list of excepted files. Those exist because the defect was already in the tree; on day one there is nothing to grandfather, so the entry states the version with an empty baseline.

Each entry says how omni-post's precedent carries over:

| Carry-over       | Meaning                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| By construction  | The next application makes the defect unrepresentable (a type, a fail-closed default, no escape hatch)       |
| Generalized gate | omni-post's gate, without its repository-specific scope, baseline and exceptions, runs from the first commit |
| omni-post only   | The precedent answers a defect the next application cannot have; the lesson stays, the gate does not         |

Entries are grouped under one of these areas, in this order: Repository and toolchain, Architecture, Testing, CI and gates, Security and tenancy, Dependencies, Documentation, AI-assisted workflow. An area gets its heading with its first entry.

## Architecture

### FP-005 — One composition root from the first route; routes receive their use cases, never the container

- **Practice:** Each deployable has one composition root, and it alone wires concrete adapters. A route plugin receives the use cases it calls as its options; neither a route nor a per-request guard can reach the container, a repository, the database client, an adapter or a provider. Layer rules (dependencies point inward, routes reach only use cases) are enforced by a dependency-rule check whose known-violations baseline is empty on the first commit.
- **Why:** A container referenced outside the composition root is a service locator: it hides a module's dependencies until run time ([ARCHITECTURE_CANON.md](../architecture/ARCHITECTURE_CANON.md) §Dependency Injection, decided in [ADR-0033](../technical/ADR-0033-layer-boundaries-and-composition-root-injection.md)). On 2026-10-15 the shrink-only baseline [`.dependency-cruiser-known-violations.json`](../../.dependency-cruiser-known-violations.json) still holds 75 `routes-no-container` entries, 74 route modules and one route-handler module; the routes workstream sized the conversion at about 15,200 lines of code in 49 slices for 25 route files, plus about 1,670 for the other 51 modules ([MASTER_PLAN_ES.md](../product/MASTER_PLAN_ES.md) §5.12 and §6). The failure is a run-time one: 22 test harnesses omitted a required option and registered the API metrics token as `undefined`, the container handed that `undefined` back without error, and the brute-force adapter dereferenced it on the customer login path (fitness #43 in [CLAUDE.md](../../CLAUDE.md)).
- **Day-one enforcement:** construction and gate. Construction: the composition root exists before the first route; route plugins and guards are typed to take their dependencies as options; the container is attached to neither the server nor the request; tests build routes through the same wiring, so a missing dependency fails to compile instead of resolving to `undefined`. Gate: the dependency-rule check runs in CI with an empty baseline. Carry-over: by construction for the unreachable container, generalized gate for omni-post's rule set without its baseline.
- **Loosen if:** never: a dependency resolved at run time is one that neither the compiler nor a reviewer sees, the failure fitness #43 caught after the fact.

## Testing

### FP-001 — Each test file has exactly one collector, chosen by its file-name suffix, and that collector runs in a required check

- **Practice:** The file-name suffix decides which runner collects a test (unit, integration, live, end-to-end, load); every runner's configuration excludes the other tiers' suffixes; every runner is mapped to a CI job that is a required check. A test file that no required check runs, or that two runners run, is a failure.
- **Why:** A test no collector runs never executes, while it still reads as coverage in the tree, in review and in a coverage report; a file two collectors run executes under two environments, and its green says nothing about the tier it was written for. At the Testing Refoundation baseline (metric M5), omni-post had 23 orphan test files and at least 10 collected twice, and on 2026-10-14 its quarantine still listed 29 test-shaped files that no required check runs (fitness #30 in [CLAUDE.md](../../CLAUDE.md); "The suffix picks the collector" in [CODING_STANDARDS.md](CODING_STANDARDS.md); [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md)).
- **Day-one enforcement:** construction and gate. Construction: the suffix table and a shared exclude list exist before the first test, and every runner configuration takes the list. Gate: a reach check lists every tracked test-shaped file, asks each runner what it collects, maps each runner to the required checks, and fails on a file collected zero or two times; its quarantine (path, reason, owner and date per entry) starts empty and may only shrink. Carry-over: generalized gate, fitness #30's reach engine with an empty quarantine.
- **Loosen if:** never for "exactly once": a test that runs nowhere is not a test. The quarantine is the only exception, one named file at a time, and it may only shrink.

### FP-002 — A test run that collects zero tests fails

- **Practice:** Every test entry point treats an empty collection as a failure. No option that lets an empty run pass exists anywhere in the tree, and a runner that counts an empty file as a pass is wrapped so that zero tests, per file and in total, exits non-zero. Counts come from a machine-readable reporter, never from parsing formatted output.
- **Why:** omni-post's nightly chaos job ran `vitest run tests/chaos/` for the life of its workflow against node:test files that vitest's `include` globs never covered; it collected nothing and reported green over scenarios it never executed. node:test counts a file that registers no test as one passing test, and counts parsed from a formatted report read as zero the day its text changes (fitness #31 in [CLAUDE.md](../../CLAUDE.md)).
- **Day-one enforcement:** gate. A check refuses the pass-with-no-tests opt-out in every tracked manifest, configuration and workflow, and holds the runner wrapper's zero guards and its reporter in place. Carry-over: generalized gate, fitness #31.
- **Loosen if:** never: an empty run cannot be told apart from a broken collection.

### FP-011 — A test double of a dependency's error carries the shape measured on the real dependency

- **Practice:** A test that simulates an error a library or driver raises builds it with one shared fixture per error family, and the fixture reproduces the shape measured by raising that error through the real dependency, with the version and the date of the measurement in its header. No test writes such an error as an object literal from memory or from the dependency's documentation. The code that maps a dependency's error to a typed answer also has one integration test that raises the error through the real dependency, and an upgrade of that dependency re-runs the measurement.
- **Why:** omni-post's repositories recognised a unique-constraint violation by `meta.target`, the field the Prisma 5 and 6 query engine filled. Prisma 7 runs every query through a driver adapter, which reports the constraint at `meta.driverAdapterError.cause.constraint` and never sets `meta.target`: measured on PostgreSQL 16 on 2026-10-15 through 7.9.1 and 7.10.0, four readers never matched, and a team invitation colliding with a soft-deleted member answered 400 "Failed to save team member" instead of its documented 409. Every unit suite over those readers stayed green, because their doubles raised the old shape ([`statefulCustomerUserPrismaFake.ts`](../../apps/api/tests/unit/helpers/statefulCustomerUserPrismaFake.ts) before the fix; the measured fixture [`prismaKnownRequestErrors.ts`](../../apps/api/tests/unit/helpers/prismaKnownRequestErrors.ts); the one reader [`constraintViolation.ts`](../../infra/prisma/src/extensions/constraintViolation.ts); the end-to-end proof [`teamInviteDuplicateEmail.integration.test.ts`](../../apps/api/tests/integration/teamInviteDuplicateEmail.integration.test.ts)).
- **Day-one enforcement:** construction. The error fixtures exist before the first test that needs one, each with its measurement header, and the one reader of each error family is a shared module the repositories import, so a shape change is fixed in one place and caught by the integration test that crosses it. Carry-over: by construction.
- **Loosen if:** never: a double written from memory proves only that the code agrees with the memory, which is how four dead branches read as tested.

### FP-012 — A test double of an external command answers only the inputs its test planned, and refuses any other by name

- **Practice:** A double that stands in for an external command or endpoint (a `curl`, a CLI, an HTTP service) matches the exact inputs its test plans for, answers each with the planned result, and exits non-zero naming any input it was not built for. It records each call before it answers, so a test that plants a failure can assert the exact calls that led to it. A double never succeeds by default.
- **Why:** omni-post's node:test runner probes two readiness URLs before its live tiers. Its suite's `curl` double answered every URL with success, so a new or misspelt probe passed every live case without being read, and a planted failure was counted against a call log one entry off from what the stopping cases assumed (book rows SB-127 and SB-150 in [review-suggestions-book.md](../reports/review-suggestions-book.md); [`runTestsGate.behavior.test.ts`](../../apps/api/tests/unit/saga/runTestsGate.behavior.test.ts), fixed on 2026-10-16).
- **Day-one enforcement:** construction. The helpers that build command doubles take the planned inputs as a required table and have no default answer, so a double that succeeds on an input nobody planned cannot be written. Carry-over: by construction.
- **Loosen if:** never: a double that answers anything proves only that the code called something.

### FP-015 — A test waits on the observable result of the work it started, and a lint rule rejects every fixed wait in test code from the first sprint

- **Practice:** A shared test kit, importable from every test tier and free of any test framework, gives condition waiters that poll the result with a deadline naming what they wait for, a one-shot gate, a deferred and one fixed clock instant. Time-driven behaviour (an expiry, a retry delay, an interval) runs on fake timers. A lint rule at error, on every test file and test helper, rejects every fixed wait: a promise a timer resolves, a fixed-delay waiter of the runtime's timer promises, a browser driver's fixed timeout, any delay including zero. A wait no result can replace carries a marker comment on the line above that names one kind from a closed set and a reason, and the rule reports an unknown kind, a missing reason and a marker above no wait.
- **Why:** A fixed wait assumes the work is done when the time is up; on a loaded runner it is not, and the test fails, hangs, or asserts on a state the work has not reached. omni-post paid for the class three times before it had the kit: DEF-82, a recovery suite that failed intermittently when a second saga engine advanced the same row, whose proof needed a hand-written gate to order the two engines; DEF-84, a unit case whose real child processes took 7.4 s in CI against the runner's 5 s default; DEF-89, twenty 20 ms `settle()` waits in one saga suite ([MASTER_PLAN_ES.md](../product/MASTER_PLAN_ES.md) §5.11). When the rule was written on 2026-10-17 it found 108 fixed waits in 49 test files, and fixing them took six pull requests, which also found a cache TTL test whose option never reached the cache, so it proved nothing, and a routes suite that failed under 8 of 9 shuffled orders (the rule's row in [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md) §Gates; [`no-fixed-time-wait.js`](../../packages/eslint-plugin-testing/src/rules/no-fixed-time-wait.js); [`determinism/`](../../packages/vitest-shared/src/determinism/)).
- **Day-one enforcement:** construction and gate. Construction: the kit exists before the first asynchronous test, and the test-writing guide names it as the way to wait. Gate: the lint rule runs at error on every test glob from the first commit, with the marker's kinds as a closed list and no suppression file. Carry-over: generalized gate, `testing/no-fixed-time-wait` without omni-post's ignore list of dead files and its exclusion of end-to-end specs no required check runs.
- **Loosen if:** a new kind of deliberate wait joins the closed list only with a case that shows no observable result can replace it; the rule itself, never: a fixed wait cannot be told apart from a race that happens to pass.

### FP-016 — A unit test starts no process; code that spawns receives its process runner, and a lint rule holds the unit tier to it from the first commit

- **Practice:** Code that runs an external command takes its process runner as a dependency, and its unit test passes a double that answers only the planned commands (FP-012). A test that must start a real process, a test of a build or CI script, lives in one named directory that a separate step runs. A lint rule at error over the unit tier rejects every value import of the runtime's process module, in every syntax the language offers, and allows a type-only import and the module's name passed to a module-mocking call.
- **Why:** A spawned child's start-up cost lands inside the runner's time budget and its result depends on what the machine has installed. omni-post's DEF-84 was a unit case whose class ran `mkdir`, `find` and `npm ls` for real behind a seam that covered only two of its commands; it took 7.4 s in CI against Vitest's 5 s default and passed on the retry ([MASTER_PLAN_ES.md](../product/MASTER_PLAN_ES.md) §5.11). When the rule landed on 2026-10-18 the unit tier held 18 files that spawn, all of them tests of scripts or of the test collectors, and the class could only be held by a convention nobody checked (the rule's row in [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md) §Gates; [`no-child-process-in-unit.js`](../../packages/eslint-plugin-testing/src/rules/no-child-process-in-unit.js)).
- **Day-one enforcement:** construction and gate. Construction: the process runner is a port from the first module that spawns, and the scripts directory and its step exist before the first script test. Gate: the lint rule runs at error on the unit tier from the first commit, with the scripts directory as its only exception. Carry-over: generalized gate, `testing/no-child-process-in-unit` without omni-post's two further exceptions, the collectors' suites and the runner's behaviour suite.
- **Loosen if:** never for the unit tier: a test that must start a process is not a unit test, and it moves to the scripts directory. A syntactic rule cannot see a module that spawns on a test's behalf, so the port is the defence there.

### FP-017 — The integration tier runs every night in a seeded random order, file and test, on fresh services, with no retry and one alarm

- **Practice:** The integration runner takes an order mode and a seed: it orders the collected files by a hash of the seed and each path, prints the seed once before the first file, refuses a malformed seed, and hands the same seed to the test runner's in-file shuffle, so the printed seed replays both orders. A scheduled job runs the whole integration tier several times a night, each run on a database and a cache created for that run alone, each with its seed and replay command printed on the run's page, with no automatic retry. One alarm job reads every run's result: on any result but success it comments on the one open issue it owns, recognised by a marker in its body, or opens it once, listing each failed run with its replay command, and fails; on a green night it closes that issue.
- **Why:** A test that passes only after another test has created its rows reads as green in the merge gate's fixed order and on a reused database, and turns red the day the order or the data changes. The first time omni-post ran its integration tier this way, on 2026-10-18, 16 suites that passed in byte order failed on fresh databases, each on state an earlier test in its own file had created, and the reused local database had hidden 13 of them; a later run found a 17th (dispatches 39097507468 and 39111917425; the two rows of [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md) §Gates; [`run-tests.sh`](../../apps/api/scripts/run-tests.sh); [`nightly.yml`](../../.github/workflows/nightly.yml)). The second red dispatch of that proof commented on the open alarm issue instead of opening another (run 39098860445).
- **Day-one enforcement:** construction and gate. Construction: the runner's order mode and seed exist before the first integration test, and each test creates the rows it reads. Gate: the scheduled randomized job and its alarm run from the first integration suite. Carry-over: generalized gate, omni-post's `TEST_ORDER=random` runner option and its `integration-randomized` job with the alarm, without the live tier's exclusion, which exists because omni-post's live suites still depend on their order.
- **Loosen if:** the number of runs a night may fall once a measured month of nights shows no failure that only the extra runs caught; the random order, the fresh services and the absence of retries, never: a retried red reports a dependence as luck.

### FP-018 — A test's duration stays far below its timeout on the CI runner, and a passing test that comes close to it fails the check

- **Practice:** Every CI test job writes each test's duration to a machine-readable report, and a check fails any test that passed in more than half of its own timeout, so a test drifting toward its budget is fixed while it still passes. The fix lowers the test's cost; it never raises the timeout and never cuts a property's runs or inputs to fit. A test-data generator that builds a large table or index is measured, and the test that uses it states that cost.
- **Why:** A test that spends a large share of its timeout passes or fails with the machine's load. omni-post's scheduling-CSV property took 394 to 406 ms on a developer machine, beside sibling properties at 7 to 129 ms, and timed out at 5,253 ms against its 5,000 ms timeout in the nightly's cache-bypassed full suite (run 39106941417); the same timeout then failed the package tests of a pull request that did not touch the file (#651). The code under test was not the cost: the property's 100 generated inputs parsed in about 7 ms in total. The property library built a map of all 1,112,064 code points for one string generator, about 380 to 400 ms and 85 MB retained once per process; an equivalent generator brought the property to 12 to 13 ms with the same invariants, runs, seed and timeout (#653; [`schedulingCsv.property.test.ts`](../../packages/core/bulk-scheduling/tests/unit/schedulingCsv.property.test.ts)).
- **Day-one enforcement:** gate. The duration check runs in every CI test job from the first test, reading the runner's report, with no list of excepted tests. Carry-over: none to generalize; omni-post has no duration check and found this test only when it crossed its timeout, so the next application starts with the check.
- **Loosen if:** the half may rise for one test only when the test's cost is a measured wait on an external resource in the integration tier, named in the check's configuration with its measured duration on the CI runner; never by raising a timeout to make a test pass.

### FP-021 — A test block that cannot fail is a lint error from the first commit, and a suppression file, if one ever exists, only shrinks

- **Practice:** One classifier reads every test block's assertions, syntactically, for every test framework the repository runs, and three lint rules at error report the classes it names that cannot fail: a block in which no assertion runs, a block whose every assertion is true by construction (a literal against a literal, a size against zero), and a block whose every assertion on every path checks only presence, type or truthiness. The test runner's own rules hold the rest of the class on the files that runner collects, and on no other runner's: a test with no assertion, an assertion outside a test or under a condition, a focused or disabled test, a commented-out test and a duplicate title. Test files print nothing to stdout. The classifier is the one any audit of the test suite reads, so a block is classified the same way in the editor, in lint and in a report.
- **Why:** A block that cannot fail reads as coverage in the tree, in review and in a coverage report while it restricts nothing, and nothing in omni-post counted them: before the classifier existed, the Testing Refoundation estimated at most 272. When the rules landed on 2026-10-24 the tree held 612 existence-only, 17 empty and 17 tautological blocks, beside 1,442 conditional `expect` calls, 34 tests with no `expect`, 16 `expect` calls outside any test and 99 `console` calls that write to stdout in test files: 2,241 violations in 337 files, all captured in [`eslint-suppressions.json`](../../eslint-suppressions.json) (the rules' row in [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md) §Gates; [`classify.js`](../../packages/eslint-plugin-testing/src/classify.js); "Test Quality Rules" in [CODING_STANDARDS.md](CODING_STANDARDS.md)).
- **Day-one enforcement:** gate. The classifier and the three rules run at error on every test glob from the first test, beside the runner's rules on the files it collects, with no suppression file: a block that cannot fail never lands. A check pins each rule at error in the lint configuration and refuses an inline directive that turns one off. Carry-over: generalized gate, the three `testing/*` rules and the `vitest/*` set without omni-post's suppression file. A repository that inherits violations puts them in a generated suppression file that may only shrink: a deleted or fixed block leaves an unused entry, and lint exits non-zero until the same change prunes it.
- **Loosen if:** a class is narrowed, never switched off, and only by a rule option a measurement justifies: with the code under test gutted, the blocks the option leaves out fail, so they restrict behaviour after all. Never by an inline directive or a hand-edited suppression file.

## CI and gates

### FP-003 — A gate fails closed when its scope path is missing, its scan read nothing or its measurement returned no result

- **Practice:** Every gate asserts that each path it scans exists before scanning, holds the number of files or items it read against a floor, and exits non-zero, distinctly from a violation, when an input cannot be read. A gate's command line refuses an argument it cannot read, such as a flag given no value or an argument it does not know, as a usage error; it never falls back to a default scope. Every positive scope glob of every test and coverage configuration matches at least one tracked file. A gate that measures through a remote service, such as an advisory database, reads its verdict from the tool's structured output and never from its exit code or its prose: only a document that parses as the expected result counts as measured, and anything else (a request error, a timeout, output that is not the result) is "could not measure", retried within a bounded time per attempt and then failed under its own title, never passed and never reported as a finding.
- **Why:** `grep -r` on an absent directory exits 2 and prints nothing, and `| wc -l` renders that as `0`: a green annotation over an invariant nobody measured. omni-post's fitness #2, #3 and #4 spent the whole period after a layer relocation in that state, and #4, both of whose path arguments were gone, scanned nothing at all. The third occurrence of the class created fitness #36: per-glob coverage thresholds kept "gating" two directories after both layers moved, and resolving every test configuration found a glob that matched no file ([CLAUDE.md](../../CLAUDE.md) §Automated Compliance Checks). The fallback is the same class: until 2026-10-16 the reach engine's source-resolution check, given `--root` with no value, read `argv[1] ?? findMonorepoRoot()`, so it checked the whole repository and exited 0 over a scope nobody asked for ([`source-resolution.ts`](../../packages/test-contracts/src/source-resolution.ts); book row SB-123 in [review-suggestions-book.md](../reports/review-suggestions-book.md)). The remote case is the mirror image: omni-post's dependency-audit step told "found advisories" from "endpoint down" by matching network-error text, so on 2026-10-22 an audit attempt that hung 250 s and ended in pnpm's `operation timed out`, a wording the list did not hold, failed the required check as a vulnerability finding on its first attempt while nothing had been measured (run 39712476313; the step "Run security audit" in [ci.yml](../../.github/workflows/ci.yml)). Since then the step reads `pnpm audit --json`, bounds each attempt to 60 s, and counts as measured only a document with an `advisories` map and `metadata.vulnerabilities`.
- **Day-one enforcement:** construction and gate. Construction: one shared helper performs the scope assertions and floors, and another parses a gate's arguments strictly (exit 2 on a usage error); every gate calls both, so a new gate cannot skip them. A gate that calls a remote service classifies a parsed result into measured clean, found and could not measure, and its suite feeds it a fake of each class, a request error and a hang among them. Gate: the scope-glob check, fitness #36's form, runs from the first test configuration. Carry-over: generalized gate.
- **Loosen if:** never: a gate that reads nothing reports its invariant as held, and one that reads an error as a result reports a measurement that never happened.

### FP-004 — A gate merges only after its red path shows a real non-zero exit

- **Practice:** A new or changed gate merges only after a planted violation made it exit non-zero, the tree was restored byte for byte, and the gate passed again. An error annotation never stands in for an exit code.
- **Why:** An `::error` annotation alone leaves the job green and proves nothing (step 3 of "Extending the suite" in [CLAUDE.md](../../CLAUDE.md); fitness #34 pairs every annotation with an exit in the same step). omni-post's fitness #28, in its old form, required the numeric hop-count spelling of `trustProxy` that a framework release had made dangerous; measured, a `trustProxy: 2` planted in the entry file returned count 0 and passed cleanly, while `trustProxy: true` was caught. A gate that mandates the defect it exists to prevent is worse than no gate.
- **Day-one enforcement:** construction and gate. Construction: every gate is a script with its own test suite, and that suite holds at least one planted violation that must exit non-zero, so the red path is proven again on every run instead of once in a pull request. Gate: a check pairs every error annotation in a workflow with an exit in the same step. The generated skeleton is accepted as the template only when every gate it carries shows this red. Carry-over: generalized gate, the self-tested script form of fitness #30 and #44 to #48 plus fitness #34.
- **Loosen if:** never: a gate whose red was never observed is an assertion nobody measured.

### FP-008 — Every root config a package extends is part of the build cache key

- **Practice:** Every root configuration a package extends is an input of that package's build cache entry. A check derives the set from the `extends` chains, root-to-root links included, and fails when a member is missing from the cache's inputs.
- **Why:** omni-post's build cache hashed each package's own inputs plus a declared global list and nothing else, so a root compiler config a package merely extends was invisible to the hash. Editing it invalidated zero cache entries, and every dependent task replayed a `dist` compiled with the previous compiler settings under a green exit code, a false green reproduced end to end in [CI_CACHE_INTEGRITY_AUDIT.md](../reports/CI_CACHE_INTEGRITY_AUDIT.md) (fitness #33 in [CLAUDE.md](../../CLAUDE.md)).
- **Day-one enforcement:** gate. The extends walk, fitness #33's form, runs from the first shared configuration. Carry-over: generalized gate.
- **Loosen if:** never: a stale cache hit is a false green with no visible signal.

### FP-013 — Every CI job sets up the runtime and the package manager through one shared step, which reads the runtime version from one file

- **Practice:** One shared setup step (a composite action or its equivalent) installs the runtime, the package manager and the dependency tree for every CI job that needs them, and pins each third-party action it uses at one major. The runtime version is written in one file (`.nvmrc`) and the package manager's in one field (`packageManager`), and every setup reads them; no workflow writes a version literal. A job that needs the runtime alone sets it up directly from the same file, with a comment saying why it skips the shared step.
- **Why:** omni-post's shared step pinned `actions/setup-node@v4`, `pnpm/action-setup@v4` and `actions/cache@v4` while the jobs that set up Node directly had moved to `actions/setup-node@v7` and `pnpm/action-setup@v6`, so two majors of each action ran in one pipeline, and support for pnpm 12, the version `packageManager` pins, arrived only in `pnpm/action-setup` v6.1.0. Eight places in six workflows wrote the runtime major as the literal `"26"` while `.nvmrc` already held it: the engines gate held every manifest to the `.nvmrc` major ([`engines-node-gate.mjs`](../../scripts/testing/engines-node-gate.mjs)), and nothing held the workflows to it (book rows SB-209, SB-250 and SB-251 in [review-suggestions-book.md](../reports/review-suggestions-book.md); [`action.yml`](../../.github/actions/setup-node-pnpm-cache/action.yml)).
- **Day-one enforcement:** construction and gate. Construction: the shared setup step exists from the first workflow, takes no runtime-version input and reads `.nvmrc`; the package manager comes from `packageManager`. Gate: a check over the workflow files refuses a runtime-version literal anywhere, refuses a direct use of the runtime, package-manager or cache setup actions outside the shared step unless the job is on a list with its reason, and holds every reference to an action at one major. Carry-over: the shared step is omni-post's `setup-node-pnpm-cache` action; omni-post has no gate for the rule, so the next application builds the check new.
- **Loosen if:** a job must run a runtime version other than the one `.nvmrc` names, such as a compatibility matrix; then that job alone lists its versions in one place, with the reason beside them.

### FP-019 — A workflow merges only after each of its jobs has run green once, and every secret and service it reads is provisioned

- **Practice:** Every job of a new or changed workflow shows one green run before it merges; a scheduled or dispatched job is dispatched once on the branch. Every secret, variable and external service a step reads has a row in the deployment checklist that says it is provisioned, and a job for infrastructure that does not exist yet is not written until the infrastructure exists.
- **Why:** omni-post's `Cleanup & Maintenance` ended in `failure` on 32 of 32 scheduled runs from 2026-03-15 to 2026-10-18: on every run whose steps are recorded, one job configured AWS credentials for a preview cluster that never existed and the report posted to Slack through a webhook nobody had configured. `Performance Tests` ended in `failure` on 88 of 95 runs from 2026-05-11 to 2026-10-18, the rest cancelled: its first job died 40 times copying an env file that had moved and 48 times on a stress script whose workspace imports nothing had built, and the load test gated on it never ran. A workflow that is always red reports nothing: the day a real failure arrives, it looks like every other day (DEF-101 in [MASTER_PLAN_ES.md](../product/MASTER_PLAN_ES.md); WU-6.P2 in [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md)).
- **Day-one enforcement:** construction and gate. Construction: the deployment checklist exists before the first workflow, and the pull request that adds a workflow fills its rows and links the green run of each job. Gate: a check derives every `secrets.X` and `vars.X` the workflows read and fails when the checklist has no row for one. Carry-over: omni-post's [DEPLOYMENT_CHECKLIST.md](../deployment/DEPLOYMENT_CHECKLIST.md) is the precedent; its derived gate, `pnpm check:deployment`, is Master Plan item N-CI-8 and does not exist yet, so the next application builds the check new.
- **Loosen if:** never for the green run: a job never seen green has never shown what its green means.

## Security and tenancy

### FP-007 — Tenant isolation fails closed from the first tenant-bearing model

- **Practice:** The data-access tenant guard refuses a model it does not know unless that model is on a documented global list. The migration that creates a tenant-bearing table enables row-level security and its policy in the same file. The application connects as a role that owns no table and carries neither superuser nor bypass-row-security, so the policies apply to it.
- **Why:** omni-post's guard silently skips a model it does not know (fail-open by construction), so `DeletionRecord` landed carrying the tenant column with neither the guard's list nor any documented list knowing it existed (fitness #39 in [CLAUDE.md](../../CLAUDE.md)). Row security arrived in ten separate `add_rls_*` migrations between 2026-05-27 and 2026-09-09, and the policy on every guard-enrolled table (58 when measured) did nothing for the running application: it connected as `postgres`, a superuser with `BYPASSRLS` that owned every table, and with tenant B bound a read of `Project` returned tenant A's rows. The integration suite had proven the policy against a synthetic role, not against the application's ([ADR-0022](../technical/ADR-0022-rls-enforcement-posture.md); [RLS_POSTURE_RED_BASELINE.md](../reports/RLS_POSTURE_RED_BASELINE.md)).
- **Day-one enforcement:** construction and gate. Construction: the guard throws on an unknown model; the first migration creates the application role without those attributes; the migration that creates a tenant-bearing table carries its policy. Gate: a check derives the tenant-bearing models from the schema and requires each one to be enrolled or documented, fitness #39's form; an integration test against the migrated database requires, for every enrolled model, row security on, at least one policy, and no ownership by the application role, the form of omni-post's RLS coverage gate, which is an integration test because catalog state is not greppable ([CLAUDE.md](../../CLAUDE.md) §Automated Compliance Checks). Carry-over: by construction for the guard, generalized gate for the enrollment check and the coverage test.
- **Loosen if:** never: omni-post's canon admits no exception for multi-tenant isolation ([CLAUDE.md](../../CLAUDE.md) §Pragmatic Exceptions), and the next application inherits that rule.

### FP-014 — A response cache keys every cached response of an authenticated route by its caller, and the application refuses to boot a cache rule that does not

- **Practice:** The cache is read only after the route's own hooks have admitted the request, as the route's last pre-handler, never from a global request hook. A cache rule of an authenticated route names the caller's credential in its key, as a digest and never the credential itself, because a hit still skips the handler and its ownership check, and the application refuses to start when a rule of a registered route leaves the caller out: when the route carries one of the authenticating hooks, compared by identity, or when the rule does not declare its route public. A rule without that declaration is refused, so an authenticating hook the check cannot see still fails the boot. Caller-supplied values are escaped before they enter a key, so one request cannot pose as another.
- **Why:** omni-post's response cache answered a hit from a global `onRequest` hook, before any route hook ran, and its dashboard rule varied by query only, so for five minutes one account's project dashboard was served to another account and to a caller with no token; four provider rules behind the same authentication hook did the same. A token past its expiry kept receiving the response it had cached, because the route's authentication never ran on a hit. A comment above the post rules said the credential was required, and nothing enforced it; those rules wrote the raw bearer token into the key, a Redis key name that `X-Cache-Key` echoed and the admin hot-keys route listed (DEF-104 in [MASTER_PLAN_ES.md](../product/MASTER_PLAN_ES.md) §5.11; [`cacheHitBeforeAuth.integration.test.ts`](../../apps/api/tests/integration/cacheHitBeforeAuth.integration.test.ts); [`cacheRouteCoverage.ts`](../../apps/api/src/lib/cache/cacheRouteCoverage.ts)).
- **Day-one enforcement:** construction and gate. Construction: the cache plugin appends its read to the hooks of each cached route as the route registers, records those hooks and runs the caller check before the application is ready, with no list of exempt rules; the key builder digests every header it varies by. Gate: an integration test over the real application caches one account's response and requires another account, a caller without credentials and the same caller with an expired token to be refused by the route, and a unit test plants a rule without the caller on an authenticated route and requires the boot to fail. Carry-over: generalized gate, omni-post's `assertCachedResponsesVaryByPrincipal`, without the dead-rule baseline its route-coverage twin carries.
- **Loosen if:** never: a cached response keyed without its caller reaches callers the route would refuse, and the canon admits no exception for multi-tenant isolation ([CLAUDE.md](../../CLAUDE.md) §Pragmatic Exceptions). A route leaves the check only by declaring itself public, a reviewed declaration the check refutes when the route authenticates.

### FP-020 — Every telemetry SDK removes what it must not send in one hook at its init, and a test on the real SDK proves none of it reaches the payload

- **Practice:** Each telemetry SDK a deployable starts (error tracking, tracing) is created in one init module, with a send-time hook that removes the attributes it must not send and a closed list of those attribute names: credentials, user identifiers, the database user. A test starts the real SDK through that module with an in-memory transport, runs an instrumented call (a database query against a refused connection is enough) and fails when a listed attribute reaches the recorded payload. An upgrade of the SDK, or of an instrumentation it brings, re-runs that test before it merges.
- **Why:** omni-post's Sentry SDK writes the database user on every pg connect and query span. From 10.54.0 Sentry vendors the instrumentation that does it, so the override bands that hold the OpenTelemetry instrumentations at their fixed releases (GHSA-qqmp-wf37-98f9) never reached Sentry's copy, and the 11.x line keeps the attribute in a new package. Measured on 2026-10-22 with Sentry initialized before `pg` loads, 2 of 3 spans carried `db.user` into the envelope on 10.76.2 and on 11.8.0; the API's `beforeSendSpan` brought it to none. What had kept it out of production until then was an accident of boot order, `pg` loading before Sentry ([SECURITY_CANON.md](../security/SECURITY_CANON.md), row `@sentry/node` + `@sentry/nextjs` and §"Blocked floors"; [`sentryInit.ts`](../../apps/api/src/observability/sentryInit.ts)).
- **Day-one enforcement:** construction and gate. Construction: the init module carries the hook and the list from its first commit, and every exporter is created there, so no second SDK starts outside it. Gate: the payload test above runs in the integration tier, and a unit test requires the init to hand the hook to the SDK. Carry-over: generalized gate; omni-post holds the hook, its unit test and the payload gate [`sentryPayload.integration.test.ts`](../../apps/api/tests/integration/sentryPayload.integration.test.ts), which the Integration Tests job runs on every pull request: it starts Sentry through the real init before `pg` loads, records every envelope in memory, and fails when `db.user` reaches the transport or when no pg span does.
- **Loosen if:** never: an attribute that has left the process cannot be recalled, and a dependency's release notes do not list the attributes it adds.

## Dependencies

### FP-009 — A check that derives facts from dependency fields reads a checked list for what the fields cannot say, so no package bends a field to suit it

- **Practice:** A package declares under `dependencies` everything its code loads when it runs, and under `devDependencies` only what its tests, types and build use, whether or not it is ever deployed. A check that derives a fact from those fields, such as which dependencies reach production, takes what the fields cannot say from an explicit list in its own input: one entry per package, with the reason it never reaches production. The check refuses an entry with no reason, a name no private workspace carries, and a package that a production manifest declares outside `devDependencies`, and it counts every declaration a tooling package makes as a tooling declaration, so a workspace that only tooling needs is tooling too.
- **Why:** omni-post's legal subprocessors inventory decided "production" from the fields alone: a workspace counted as tooling only when other manifests declared it, and only under `devDependencies`. Its test-contracts package is private, runs only in CI and is declared by no manifest, so moving the four packages its code loads when it runs (`vitest`, `typescript`, `yaml`, `tsx`) to `dependencies` would have recorded them as production recipients in the legal register, and the package kept them under `devDependencies`: a field written to suit a gate instead of to describe the run. Measured on 2026-10-15, a list naming that package was not enough on its own: once it declared the shared test-configuration workspace under `dependencies`, that workspace stopped counting as tooling and `vitest`, its peer, read as production (fitness #45 in [CLAUDE.md](../../CLAUDE.md); [`subprocessors.mjs`](../../scripts/legal/subprocessors.mjs); the `tooling` list of [`subprocessors.json`](../legal/classification/subprocessors.json)).
- **Day-one enforcement:** construction and gate. Construction: the production-or-tooling derivation reads its list from its first commit, empty, and derives tooling as a fixed point over every declaration a tooling package makes. Gate: the inventory check fails on each refused entry, and its suite plants every refusal and a listed package whose run-time dependencies would otherwise read as production. Carry-over: generalized gate, fitness #45's subprocessors generator with its `tooling` list.
- **Loosen if:** never: a field written to suit one check misstates what the package needs to run, and every other tool that reads the field inherits the error. The list grows only by a reviewed entry with its reason.

### FP-010 — A dependency-freshness gate measures every tool the manifests declare, and holds a code generator in lockstep with the runtime packages it generates for

- **Practice:** A freshness check compares every direct development dependency, the tools that build, test, lint and generate code, with its latest stable release past a maturity buffer, and fails once a lag outlives a fixed budget with no recorded hold. Its population is read from the manifests' `devDependencies` by the check itself, never hand-listed: a tool leaves it only by an entry in the check's own list, with its reason, and that list starts empty. A code-generating CLI and the runtime packages it generates for (an ORM's CLI, its client and its driver adapter) are declared as one family, with the reason they move together, and the check fails when any member resolves to a version its siblings do not, whether an importer declares it or another member resolves it as a dependency or a peer.
- **Why:** omni-post's holds gate measures a hand-kept population of testing and quality tools ([`toolchain-population.json`](../../scripts/testing/toolchain-population.json); [ADR-0036](../technical/ADR-0036-dependency-update-cadence.md)). The Prisma CLI, which generates the database client on every install and in the build stage of all four images, was not in it: 7.10.0 matured on 2026-09-01, its 30-day budget ran out on 2026-10-01, and the tree stayed on 7.9.1 until 2026-10-15 with nothing failing, although the catalog comment had recorded on 2026-10-03 that a newer mature release existed. When the family moved that day, lockfile preference kept the `prisma` 7.9.1 peer of `@prisma/client` 7.10.0 under two importers until the three packages were updated together, a split no manifest shows. Since then the gate measures the CLI's freshness and declares the three as the family `prisma`, which it holds to one version, reading the two production members for equality only; with `@prisma/adapter-pg` planted at 7.9.1 it exits 1 naming that member, its version and its importer. Its population is still hand-kept: a tool added to a manifest is not measured until someone lists it ([`holds-gate.mjs`](../../scripts/testing/holds-gate.mjs), residuals 1 and 3; SB-212 in [review-suggestions-book.md](../reports/review-suggestions-book.md) records the same gap for other families).
- **Day-one enforcement:** gate. The freshness check, with its maturity buffer and budget, runs from the first manifest, reads its population from the manifests' `devDependencies` minus a reasoned exclusion list that starts empty, and fails on a family whose members resolve to two versions; each family is declared in the commit that adds its generator. Carry-over: the family check is a generalized gate, the `families` of omni-post's holds gate as they run; the derived population has no precedent here, because omni-post's population is hand-kept, so the next application builds that part new.
- **Loosen if:** never for the derivation or the family check: a hand-kept population drifts from the tree the moment a tool is added, which is how the Prisma CLI went unmeasured. The budget's length is a recorded decision, as ADR-0036's 30 days are, never a per-package exception.

### FP-022 — Every direct dependency proves its use with real sites in the tree or carries the owner's decision, held by a gate from the first commit

- **Practice:** A check derives, for every direct dependency the manifests declare, the files that use it in the tracked tree, each site with its kind (a runtime import, a type-only import, a test mock, a string in a configuration, a stylesheet load, a command line) and its path class (production, test, configuration). A dependency counts only the sites its scope can use: a production dependency its production imports and stylesheets; a development dependency its imports, stylesheets and command lines and the configuration strings of configuration files; a types package the type-only files of the package it types. A mock never counts, and neither does a configuration string in the check's own modules and suites, which name every field, protocol and tool the check reads and plant packages as fixtures; their imports still count. A dependency under a fixed floor of distinct files stays pending until a reviewed decisions file records the owner's outcome: kept, with its ground, what it does and the replacement weighed, or remove, with what replaces it. The check writes the derived record to a tracked file and fails when the record is stale, when an entry is malformed or no longer applies, and when the pending count differs from its exact baseline in either direction; an input it cannot read in full stops it as a failure of its own, never as zero sites.
- **Why:** omni-post declared 175 direct dependencies and recorded which of them reach production, for the legal register, but nothing recorded which of them were used. Use was measured by hand, one package at a time: on 2026-10-22 `@monaco-editor/react`, `@fastify/rate-limit`, `papaparse` and `react-email` each turned out to serve two files or fewer, and each left in its own pull request (#678, #679, #698, #694); the method left no record a later pass could compare against. `@fastify/websocket`, declared by the API since the first commit, had no site anywhere and stood behind a knip `ignoreDependencies` entry the whole time, until `deps-remove-1` removed both on 2026-10-25. The ledger's first run, on 2026-10-24, found 128 of the 175 under the floor of 3 real sites and 19 with no site at all ([`dependency-ledger.json`](../../dependency-ledger.json); WU-2.2b in [TESTING_REFOUNDATION.md](TESTING_REFOUNDATION.md)). Its first version also counted its own source: the string `"lint-staged"` in the module that reads the `lint-staged` key raised that tool from one real site to two, and its suites' fixture strings were the only site the record listed for `vite`.
- **Day-one enforcement:** gate. The check runs in CI and in the local battery from the first manifest, with an empty decisions file and a pending baseline of 0: a dependency is decided in the commit that declares it, so it lands kept or does not land. Carry-over: generalized gate, omni-post's fitness #50, `pnpm check:deps-ledger`, and its battery step `deps-ledger`, without the 128 pending names it starts from.
- **Loosen if:** the floor is lowered for one site kind, by a recorded decision, when a measured sample of the decisions file shows the owner keeping more than nine in ten of that kind's dependencies under the floor on the same ground; never by an exemption list, and never by raising the pending baseline without a decision behind each name it adds.

## Documentation

### FP-006 — Method-level documentation is enforced on every in-scope file from the first commit, not only on touched files

- **Practice:** The documentation rules (a file header, and on every exported function and public method a description, one entry per parameter and the return value) run over the whole tree, at zero, in the same lint pass as every other rule, with no baseline and no touched-files scope. An inline disable comment does not exempt a file.
- **Why:** omni-post's canon required method-level JSDoc and nothing enforced it: measured on 2026-10-10, 35% of public methods carried no JSDoc at all and 31% carried the canon's tag form. The gate that landed on 2026-10-11 holds only the files a pull request touches, in a configuration the ordinary lint run does not load, and the rest waits for a reconciliation still open, which started from 1,028 of 2,134 in-scope files holding 9,648 violations that day (fitness #47 in [CLAUDE.md](../../CLAUDE.md); N-CI-5 and N-CI-6 in [MASTER_PLAN_ES.md](../product/MASTER_PLAN_ES.md) §1).
- **Day-one enforcement:** gate and hook. The rules live in the main lint configuration, so the CI lint run and the pre-commit hook enforce them on every file. Carry-over: generalized gate, fitness #47 without the touched-files scope that answers omni-post's backlog.
- **Loosen if:** a measured sample of the documentation shows a required tag restating the type signature in more than half of its occurrences; that tag's requirement is then dropped by a recorded decision, never the whole rule.
