## Technical Approach

One record per `(post, channel)` — `PostChannelPublication` — lives inside the `Post` aggregate and is the only source of publication truth. The root writes it (declare targets, open an episode, record an attempt, mark/clear/expire a retraction), recomputes the post-level word from COMPLETE publications in the same transaction, and locks content the instant the post has **live content** anywhere — a fully published channel or a failed channel whose fragments are still on the platform. A channel is never "partially published": a thread that stops mid-way is `EXCLUDED` with its live fragments recorded and pending retraction (N-COR-10's mechanism; manual until then), the customer is alerted on the media they have on — in-app and email by their per-type preference, Slack/Teams by the configs they keep active — and the application's action window bounds the alert cycle, never the lock. The worker reaches the root through the same `@core/posts` use case the API uses, resolved from the workers' own composition root over the relocated Post persistence adapters (D1). The wait step reads the record, a failed channel is an outcome, the saga forward-completes, and the promotion step becomes a reconciliation. Transient retry stays in BullMQ attempts with the budget enforced by the domain. Re-drive is owned: episode-scoped job identity, per-channel reread at the pivot, `/start` admitted from the record, a second saga answered 409, a channel with live fragments refused by name. No external integration event is added (Q19).

**The alert transition, in ONE place.** `ChannelPublication.alertTransition(): "none" | { raise; supersededAlertKey? } | { resolve; cause }` is the only code that decides whether an alert event is emitted, and it is evaluated at the end of every root method that touches a record:

1. `actionWindowExpiredAt ≠ null` ⇒ `retractionAlertHash ≠ null` ? resolve(`ACTION_WINDOW_EXPIRED`) and null the hash : none — **precedence over every other clause**: after expiry nothing is ever raised again for this `(post, channel)`, including on a later change of the live set (alert spec); the hash stays null so a later `clearPendingRetraction` emits nothing either.
2. `pendingRetraction ∧ retractionBlockedCause ≠ null ∧ hash(liveFragments) ≠ retractionAlertHash` ⇒ raise (`supersededAlertKey` = the previous key when the hash was non-null); set the hash.
3. `¬pendingRetraction ∧ retractionAlertHash ≠ null` ⇒ resolve(`RETRACTED` | `MANUALLY_REMOVED`); null the hash.
4. otherwise none (a redelivered outcome with `applied: false` never reaches this method).

### D6 — Attempt budget, classification, and where automatic retry runs

The historical mentions of `toEveryActiveConfig` in Q18's row, in the Data Flow snippet below and in tasks §2 describe the 1b2 apply as it landed; this paragraph is the as-built.

### D18 — The customer's action window is APPLICATION-parametrized (Q16); expiry closes the alert, never the lock (Q17)

**Parameter.** `RETRACTION_ACTION_WINDOW_HOURS: z.coerce.number().int().min(1).max(720).default(72)` in the `server` block of `apps/api/src/config/env.ts` (the `SAGA_WAIT_POLL_MS` shape, `:309`), documented in `.env.example`, `.env.test.example` and `docs/deployment/ENVIRONMENT_VARIABLES.md`; read only through `env` (SECURITY_CANON) — **and only in `apps/api`**: the sweep reads it, converts it to a `window` duration and passes that value down; the domain never sees env (S-a-2). **Default 72 h, rationale**: the act is a manual removal on a third-party platform by a customer who may be reached only by an email they read on working days — three days covers a weekend; longer would leave a post reading "Partially Posted"/failed with an open alert cycle for most of a week; shorter would finalize before a customer who acts on Monday morning could. It bounds the ALERT CYCLE only, so a wrong value is never a lost fragment.

**AS BUILT 2026-09-23 (rev 3.8) — the registration shape below PRESCRIBED the defect this change had already paid for, and is corrected in place rather than edited away.** It read `() => withSystemContext("system:retraction-action-window", …)`, which wraps the WHOLE tick in the system scope. The per-row `withTenantContext` then nests inside it, `resolveGucScope` answers the system sentinel whenever a system context is present (`tenantGuc.ts:119-124`), and **every write binds `__system__`** — layer 1 is skipped and the row's account is read by nobody. It compiles, it reads correctly, and it is silent. This is SMELL-149, and rev 3.6 of this same document states the rule two hundred lines above: _"nesting does not work: `resolveGucScope` answers the system sentinel whenever a system context is present"_. The document held the answer and prescribed its opposite in another section, which is the failure mode worth naming: a contract that carries a defect outlives the defect. Built SEQUENTIAL instead — the system scope is a PARAMETER of `sweep()`, supplied at the registration site, and it covers DISCOVERY ONLY; the per-row loop runs after it, not inside it. The pin asserts BOTH halves (`tenantAccountId` per row AND `systemReason` undefined per row), because asserting only the account PASSES on the nested version: the tenant store is populated there, it is simply not what the GUC reads.

**The sweep.** `RetractionActionWindowSweep` (`apps/api/src/infrastructure/retention/RetractionActionWindowSweep.ts`) registered in `index.ts` beside the deletion-record degrader (`:950-962`) as `scheduler.register("retraction-action-window-sweep", () => sweep({ systemScope: "system:retraction-action-window" }), 15 * 60 * 1000)` — recurring work goes through `BackgroundTaskScheduler` (LOGGING_CANON §Background Tasks), is unregistered by `shutdownAll()`, and a 15-minute cadence is a constant because the window's precision is hours. Each tick: (1) `window = env.RETRACTION_ACTION_WINDOW_HOURS` as a duration, `olderThan = now − window`; discovery under the system context through a new read port `PendingRetractionSweepReader.listExpired({ olderThan, limit: 100 })` (db-prisma adapter; the canon-sanctioned cross-tenant path — `withSystemContext()` is what declares a cross-account read; predicate `pendingRetraction ∧ retractionBlockedCause IS NOT NULL ∧ actionWindowExpiredAt IS NULL ∧ actionWindowStartedAt ≤ olderThan`, oldest first, over the partial index of D3; returns `(postId, channelId, accountId)` only); (2) per row, `withTenantContext({ accountId })` (`tenantContext.ts:65`) → `ExpireRetractionActionWindowUseCase` (`packages/core/posts/src`) → guarded `PostRepository.findById` → root `expireRetractionActionWindow({ channelId, now, window })` (D4 — the SAME `window` value, re-asserted by the root) → `savePublication` inside `executeResultInTransaction` (GUC bound, ADR-0023) — both isolation layers hold on every write; (3) the tick's summary `{ scanned, expired, skipped, failed }` is awaited and logged (the `:954-959` discipline), metrics `retraction_action_window_expired_total` and `retraction_action_window_sweep_failures_total`, an ERROR log per failed row. **Poison rows (S-a-4)**: a row whose write keeps failing is retried on every tick because the predicate still selects it, and it never blocks its neighbours (each row is its own transaction; a failure is counted and the loop continues); but discovery is `limit: 100` oldest-first, so more than 100 simultaneously failing rows would fill every page and starve younger expired rows — the signal is a FLAT non-zero `retraction_action_window_sweep_failures_total` across ticks, and the remedy is the row's cause (the ERROR log names it), not a bigger page. **Idempotent and race-safe**: the predicate excludes expired rows; the root refuses a second expiry (`applied: false`); a concurrent customer confirmation or N-COR-10 retraction races through the CAS — the loser reloads and finds nothing to expire (confirmed → `pendingRetraction` false) or expires the still-pending row (the confirmation then still clears it, Q17).

**Effects, restated from the root method (D4).** The channel's outcome is finalized `EXCLUDED` with `reasonCode = ACTION_WINDOW_EXPIRED` (a cause the record is READ for, never recomputed from elapsed time); the post's word is recomputed by `applyDerivedStatus()` under D15.1 (`FAILED` or `PARTIALLY_PUBLISHED`; it was already so); the standing alert is resolved with cause `ACTION_WINDOW_EXPIRED` and NOTHING is raised again for that `(post, channel)` — `alertTransition()` clause 1 has precedence over the re-send clause, so a later change of the live set updates the record silently; the fragment references, `hasLiveContent()` and the content lock are untouched; `redrivable()` stays false; the confirm act (D9) stays available and, once nothing is live on any channel, releases the lock. **Rejected**: computing "expired" at read time; a domain method that reads the window itself (S-a-2 — the domain has no env); running the sweep in the workers (no scheduler-owned system sweeps live there; the API root owns every other retention sweep, `index.ts:898-1029`); a customer-set window (Q16: the application owns it; the customer's parameters are `customer-notification-policy`'s).

### D19 — Publication predicates fail closed: absent is not empty, and a publication write needs a tenant (rev 3.3; decided by the orchestrator as a security-canon consequence — no product content)

**What was found, and what the tree says.** The 1b ledger (finding 1) stated that under `withSystemContext()` the row-secured `channelPublications` include hydrates EMPTY, so "no records" reads as `noLiveContent()` and the lock disengages for a system reader. Measured, the GUARDED client has exactly three cases: (i) tenant-bound — the guard injects `where.accountId` (`infra/prisma/src/extensions/tenantGuard.ts:213-223`) and the binding opens the two-statement batch with the tenant's GUC (`tenantGucBinding.ts:113-117`): the post's own rows; (ii) system — the guard steps aside (`tenantGuard.ts:203-206`), `resolveGucScope` answers `__system__` (`tenantGuc.ts:119-124`) and the record's policy admits every row under that sentinel (`20260917093257_add_post_channel_publication/migration.sql:174-181`): the include hydrates in FULL, the predicates run over exactly the post's records (the composite FK pins them to one tenant) and are correct — but layer 1 is bypassed, so a WRITE from that aggregate carries no injected tenant; (iii) neither — the guard throws `TenantContextMissingError` before any query (`:208-211`; `post`, `postContent`, `postMedia` are enrolled, `:128-131`), and off the guarded client an unset GUC hides the `Post` row itself as `omnipost_app` (`Post` is row-secured, `20260910000000_rls_initplan_post_trio/migration.sql:63`; a NULL setting satisfies no predicate, `20260917093257…:26-27`; measured in `tenantGucBinding.ts:11-15`). The empty-set-with-a-visible-parent state is therefore not produced by the SCOPE; it is produced by the MAPPING: a Prisma result whose `channelPublications` is absent — the include not requested — is mapped to `[]` (`PostAggregateMapper.ts:62` optional, `:253` `?? []`) and the root defaults the same way (`PostAggregate.ts:154`). "Records not loaded" and "no records" share one value, and that value unlocks the post (`:321-322`). That is the fail-open, it is one omitted `include` away from any loader, and it is what this decision closes; the ledger's sentence about the system scope is corrected here rather than carried.

**Rule.** The aggregate never answers a record-derived predicate — `isEditable`, `hasLiveContent()`, `redrivable()`, `derive()`, every admission — from a load whose record visibility is not TOTAL for that post, and a publication WRITE always runs under a tenant. Three mechanisms, all in PR 1c:

1. **Absent is unrepresentable — at the mapper's input type, with the assertion sites deleted and the list loaders out of the aggregate path (restated rev 3.4 C1).** A required property on `PrismaPostWithRelations` is enforced only where no assertion intervenes: TypeScript admits `p as PrismaPostWithRelations` whenever the target is the source plus extra properties, so a required `channelPublications` raises NO error at the five cast sites in `PrismaPostRepository.ts` — `:84` (`findById`, which DOES include the records, `:73-76`) and `:275`, `:313`, `:339`, `:372` (the four list loaders, whose `include` blocks at `:259-265`, `:299-305`, `:328-334`, `:358-364` carry no `channelPublications`). "No longer compiles" is therefore false today, and the five casts are what makes it false. The mechanism has two parts. (i) `PostAggregateMapper.toDomain` takes `Prisma.PostGetPayload<{ include: typeof POST_AGGREGATE_INCLUDE }>` — one exported `const` include object (`contents`, `media`, `contentVersions`, `channelPublications` with the joined `channel.provider`) that `findById` passes to `findFirst`, declared with `satisfies Prisma.PostInclude` and `as const` so `typeof` keeps every flag literal (a bare object literal widens each `true` to `boolean`, and `PostGetPayload` over that type resolves to a UNION of payload variants that dissolves the required-ness; the mapper body then fails to compile, loudly — and re-adding an assertion is NOT the admissible fix for that error) — so a query issued without that include cannot be passed to the mapper; `PrismaPostWithRelations` (exported at `src/index.ts:48`) becomes an alias of that payload type, the optional `channelPublications?` at `:62` and the `?? []` at `:253` go, and the FIVE `as PrismaPostWithRelations` assertions are DELETED. (ii) `PostAggregateState.publications` becomes required on reconstitution (D4, T1c.5a) and the default at `PostAggregate.ts:154` goes; `create()` sets `[]` explicitly — an in-memory post has declared no targets, which is true by construction. Residual, named: a future `as` written against a query result is the one door the compiler cannot close; the review reads for it today, and a one-line grep tripwire over `packages/adapters/db-prisma/src/post/` for `as PrismaPostWithRelations` / `as Prisma.PostGetPayload` is proposed as a fitness candidate (§7.2 backlog) rather than shipped inside 1c — it is the class of gate this repo already runs, and a grep is the right instrument for a textual pattern.

## ADR-0024 outline — "The durable record of a post's publication, per channel"

Status Accepted · Date · Deciders Edward. **Context**: intent never persisted; counts, not outcomes; post-pivot `FAILED` with live content; `PublishLog` as accidental state; a thread that stops mid-way with its fragment ids discarded. **Decision**: (1) `PostChannelPublication` inside the `Post` boundary is the sole source of publication truth; (2) `post.status` is a ROLLUP over COMPLETE publications — entry is an FSM transition, resolution a record-gated projection, agreement asserted before every save; (3) a channel is all-or-nothing across fragments: never persisted partially published, its live fragments held as an explicit pending-retraction state; (4) content locks on `hasLiveContent()` — never on the word, never released by time; (5) the provider is derived from the channel (ADR-0016; in memory only for the v1 payloads); (6) `PublishLog` is a receipt mirror until N-COR-9; (7) `PARTIALLY_PUBLISHED` requires at least one fully published channel; none-published is `FAILED` regardless of live fragments or an expired window; (8) the record carries the content fingerprint as audit; (9) `publishThread` returns what went out on the error path; (10) a stranded channel raises one alert per live-fragment set, decided by the root in one place; in-app and email deliver by the customer's existing per-type switch (default on), Slack/Teams by the customer's active configs as a shared switch (Q21), every delivery idempotent through one ledger; (11) the application parametrizes the action window (72 h default, passed to the domain as a value) — expiry finalizes the outcome and ends the alert cycle, never the lock; (12) the confirm act ships with the state; (13) no external integration event is added — `post.published`/`post.failed` keep their v1 shapes; (14) both executables resolve the same use case over the relocated Post persistence adapters; (15) an absent record set is unrepresentable, a publication predicate is answered only from a total-visibility load, and a publication write runs only under a tenant — every system-scoped consumer re-reads per tenant (D19). **Alternatives**: A, C, D, E (research §1, explore §6); the DTO-adapter shortcut (D1); a partially-published channel state (rev 2 C1); thread resume instead of retraction; urgent-overrides-preference (rev 3); a per-medium preference row and a `Notification.dedupeKey` (rev 3.1); a customer-set window. **Consequences**: OCC contention accepted with a 1.975 s-bounded worker retry; a schema migration with #39/RLS; a second migration (enum value + ledger; `Notification` untouched; the value not reversible in place); the closed notification-type set grows; a recurring sweep in the API process; two writes per success until N-COR-9; the N-COR-9 window as re-derived; a deploy that requires the reconstruction; a manual retraction exit until N-COR-10; `post.failed` fires for the first time. **Revisit if**: a per-channel saga (E) becomes necessary, N-COR-10 makes `NO_CAPABILITY` unreachable for every provider, or `customer-notification-policy` replaces the per-type switch. **References**: research S13, S14, S17–S19; ADR-0016; ADR-0023; N-COR-1 design rev2.
