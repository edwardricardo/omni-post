## 1. Current behaviour end-to-end on a partial failure

Trace, 3 channels, 2 publish, 1 fails:

| Hop                 | Evidence                                                          | What happens                                                                                                                                                                                                        |
| ------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker, per channel | `apps/workers/src/publishHandler.ts:379-388` / `:331-344`         | Upserts ONE `PublishLog` row per `dedupeKey` with `status: "OK"` or `"ERR"` and the receipt in `payload`.                                                                                                           |
| Worker → saga       | `publishHandler.ts:407-412`, `:366-371`, `:848-858`               | Emits `publish.job.completed` / `publish.job.failed` over Redis pub/sub.                                                                                                                                            |
| Wait step           | `packages/shared/src/saga.ts:796-834`                             | Reads `checkJobsStatus(jobIds)` → `{completed, failed, pending}`. Writes `publishingComplete: status.failed === 0` into stepData at `:826`, then **returns `outcome:"failed"` at `:829-834`** because `failed > 0`. |
| Engine              | `apps/api/src/saga/SagaManagerExecution.ts:614-649`, `:1085-1087` | Retryable post-pivot step, 3 retries (`saga.ts:1007-1011`), then `failSaga`. **No compensation** past the pivot (canon, Azure §5).                                                                                  |
| Promotion step      | `saga.ts:865-946`                                                 | **Never reached.** Its `newStatus = publishingSuccess ? "PUBLISHED" : "FAILED"` (`:891`) is unreachable dead code — the wait step fails first. N-COR-1 design.md:59 deletes it.                                     |
| Post row            | —                                                                 | Stays `DRAFT`, `publishedAt` null, `version` unchanged.                                                                                                                                                             |

**Net observable**: the saga ends `FAILED`; the post is `DRAFT`; two providers hold live content the database has no record of. `docs/api/saga.md:79-85` records a measured sibling of this class ("a four-channel publish reached FAILED with all four channels successfully published").

### The compounding harm: DRAFT is the re-publishable, editable state

- `SagaIntegration.ts:428-432` admits `/start` **only** for `status === "DRAFT"` → a partially published post is exactly the one shape the guard lets through again.
- `PublishStatus.isEditable()` (`PublishStatus.ts:182`) is true for `DRAFT` and `FAILED` → the user can edit copy already live on two providers, then re-publish it.
- The only mitigation is accidental and lives in the worker: `publishHandler.ts:726` (`dedupeKey = job.dedupeKey ?? \`${postId}:${channelId}\``) + `:733-739`skip when the log is`OK`. A whole-post re-drive therefore re-publishes ONLY the failed channel. That is a real idempotency property — but it is unowned, undocumented as a product guarantee, and it emits no `publish.job.completed` for the skipped channels (`:734-739`returns before`notifySaga`), so a re-drive advances only on the 30 s poll.

## 2. The structural fact that decides the option space

**A post's channel targets are NEVER persisted.**

- `PostAggregate` (`PostAggregate.ts:53-65`, `:88-110`) has no channel collection. `PostAggregateState` has no field for it.
- `SchedulePostUseCase.ts:139-151, :194-199` validates each channel exists, then **echoes `input.channelIds` back in the output DTO without persisting them**.
- `infra/prisma/schema.prisma:697-776`: `model Post` has NO channel relation. No `Post↔Channel` join table exists anywhere; `channelIds String[]` appears in the schema exactly once, on `RecurringPost.channels` (`:2581`) — a denormalised template field, not a post target.
- The target set lives only in the saga row's `stepData["schedule-publishing-jobs"].channelIds` — a field **N-COR-1 is adding right now** (design.md:59); it did not exist before.

Consequently there are TWO different sets and only one is recorded:

- **intended targets** — nowhere durable outside the saga row;
- **observed attempts** — `PublishLog`, one row per `(postId, channelId)` (unique `dedupeKey`, `schema.prisma:945`; upsert at `PublishLogRepository.ts:19-33`). A channel whose job was evicted or never ran has **no row at all**.

`markAsPublished(providerResults)` (`PostAggregate.ts:399-421`) does NOT persist the results — it passes them straight into the `PostPublished` event payload (`:418`) and nothing else. They are write-only.

### The other door into the same defect (LIVE, unguarded)

Five wired webhook processors flip the WHOLE post to `PUBLISHED` on ONE channel's confirmation, bypassing the aggregate, the FSM, `publishedAt` and `version`:

- `facebookWebhookProcessor.ts:421-424` — `prisma.post.update({ where: {id: postId}, data: {status: "PUBLISHED"} })`, no status guard
- `xWebhookProcessor.ts:444` · `instagramWebhookProcessor.ts:343` · `youtubeWebhookProcessor.ts:400` · `tiktokWebhookProcessor.ts:363`
- All registered at `webhookHandlerCore.ts:110-116` — reachable, not dead.

Each one _correctly_ updates its own `PublishLog` row first (`facebookWebhookProcessor.ts:402-418`) and _then_ wrongly rolls it up to the post. Three consequences:

1. A partially published post whose one success is Facebook becomes `PUBLISHED` — and `PUBLISHED` is TERMINAL (`PublishStatus.ts:45`), so it can never be retried, edited or promoted.
2. `publishedAt` stays null → invisible to top-performers (`PrismaPostQueryRepository.ts:339-352` requires `status PUBLISHED` **and** `publishedAt not null`), and N-COR-1's promotion answers such a post with `INTERNAL_ERROR` (`CompletePostPublishingUseCase.ts:298-306`, "is PUBLISHED but carries no publishedAt; refusing to fabricate one") — which fails the saga step. **This is a live interaction between the webhook path and N-COR-1 as shipped.**
3. `version` is not bumped → the CAS is blind to it (same class as design.md W1).

## 5. Canon constraints

- **ADR-0016 (Accepted)** — "the canonical targeting unit is the channel… the provider is always derived from the channel, never chosen as an independent targeting dimension", app-wide; receipts live in `PublishLog`. It DELETED `PublishingQueue`, whose `providers[] + results Json` was the provider-level result blob. **N-COR-8 must not reintroduce a `results Json` on the post**, and should key by channel.
  - Corollary: `PostPublishingStarted(targetProviders: ProviderType[])` (`PostEvents.ts:118-136`) and `markAsFailed(failedProviders: ProviderType[])` (`PostAggregate.ts:426`) are at the PROVIDER granularity ADR-0016 rejected, while `markAsPublished` is keyed by channel id (`CompletePostPublishingUseCase.ts:356-368` builds `results[channel.channelId]`) under a parameter literally named `providerResults`. The name lies (B9 confirmed): a consumer reading `PostPublished.providerResults` keys as provider names gets channel UUIDs. Schema `postPublishedV1` (`EventSchemaRegistry.ts:60-72`) is `z.record(z.string(), …)` so it accepts the lie silently.
- **ARCHITECTURE_CANON §Saga** — pivot = point of no return; post-pivot retryable = forward recovery only; no compensation past `pivotStepIndex` (enforced, `SagaManagerExecution.ts:1085-1087`). Any partial-failure answer is FORWARD recovery; "undo the 2 that published" is not on the table.
- **ARCHITECTURE_CANON §Outbox** — domain events in the same tx as the state mutation; N-COR-1's `executeResultInTransaction` (ADR-0023) is the seam an `err` must use to roll back.
- **N-COR-1 R1** — all-or-nothing promotion; the use case refuses any non-total outcome with `NOT_IMPLEMENTED` (`CompletePostPublishingUseCase.ts:146-153`), explicitly naming N-COR-8. That refusal is the seam this change fills; it must be replaced, not bypassed.
- **Fitness**: #39 (any new `accountId`-bearing model must be enrolled in `TENANT_SCOPED_MODELS` + denylist-documented + RLS), #38 (any new `deletedAt` model must be SWEPT or quarantined, quarantine floor 6 may only shrink), #40 (one transaction seam), #7 (deterministic dedupeKey), #4 (no throws in core), #2, #6, #23, #30, #9/#10.
- `Post.status` is a free string (`schema.prisma:701`) → a new status value is code-only. The FSM (`PublishStatus.ts:28-52`) is the real gate, and `PUBLISHED` is terminal with zero outgoing edges (`:45`).

### Leaning (input to Edward, NOT a decision)

**B is the model; the first slice should be B-sized in the write path and C-sized in the status vocabulary.** The reasoning is that A and C both choose a WORD for the post before the system has a RECORD of what happened per channel — and ADR-0016 already ruled that the channel is the canonical unit. A post-level status word chosen over a per-channel record that does not exist is a rollup over data nobody owns; that is the same "duplication-by-divergence" ADR-0016 deleted when it removed `PublishingQueue.results`. Concretely: persist the intended target set + per-channel outcome inside the Post aggregate boundary first, leave the post status vocabulary unchanged for that slice (the post stays out of `PUBLISHED`, which N-COR-1 already enforces), and decide the status word in the follow-up once a read model can answer "which channels". If Edward wants the user-visible answer sooner, A is the cheaper path and its migration cost is genuinely zero — but it should then be explicit that `PARTIALLY_PUBLISHED` is a label over `PublishLog` and that `PublishLog` is neither tenant-guarded nor a record of INTENT.

## 8. Product questions for Edward's pre-propose round

**Q1 — Is a post that reached 2 of 3 channels "published" for the numbers the business counts?**
Three surfaces answer independently today: the dashboard tile counts `status === "PUBLISHED"` (`apps/client/app/[locale]/dashboard/page.tsx:62`); top-performers requires `status = PUBLISHED` **and** `publishedAt not null` (`PrismaPostQueryRepository.ts:339-352`); `incrementPostPublished()` is called at SCHEDULE time, not publish time (`SchedulePostUseCase.ts:192` — a pre-existing defect). One answer for all three, or does each surface answer differently?

**Q2 — What can the user DO after a partial failure?**
Retry only the failed channel, retry everything, or abandon and re-create? Today NEITHER retry exists: there is no retry capability anywhere in the tree, and the only re-publish path (`SagaIntegration.ts:428-432`) requires `DRAFT` — which a partially published post happens to still be.

**Q3 — Is a partially published post EDITABLE?**
Today yes, twice over: the post stays `DRAFT`, and even in `FAILED` the FSM allows edits (`PublishStatus.ts:182`). So a user can right now rewrite copy that is already live on two providers and re-publish it. Should content LOCK the moment the first channel publishes?

**Q4 — Terminal state, in-progress state, or no post-level word at all?**
(a) a distinct terminal state the user sees ("Partially published"); (b) the post stays in-progress until every channel resolves, with retries; (c) the post-level word is derived from a per-channel list and stops being a decision. This is the FSM/ADR question and it drives whether there is a migration.

**Q5 — Should ONE provider's webhook flip the WHOLE post to PUBLISHED?**
Five wired processors do exactly that today, unguarded and without `publishedAt` (`facebookWebhookProcessor.ts:421-424`, `xWebhookProcessor.ts:444`, `instagramWebhookProcessor.ts:343`, `youtubeWebhookProcessor.ts:400`, `tiktokWebhookProcessor.ts:363`). It is the same defect through a different door, and it can strand a post in terminal `PUBLISHED` with a null timestamp — a state N-COR-1's promotion refuses with `INTERNAL_ERROR`. Does N-COR-8 own this, or is it its own slice?

**Q6 (optional) — What happens on DELETE or ARCHIVE of a post live on 2 providers?**
Related: `PublishLog.postId` is nullable with `onDelete: SetNull` (`schema.prisma:948`), so a hard delete orphans the only record that the publication happened.

## 9. First-slice boundary and non-goals (proposed, for Edward to cut)

**In**: the durable per-channel publication record (targets + outcome) inside the Post aggregate boundary; replacing `CompletePostPublishingUseCase`'s `NOT_IMPLEMENTED` refusal (`:146-153`) with the decided semantics; the wait step no longer collapsing a partial into a step failure (`saga.ts:829-834`); the ADR.

**Out (name them, don't absorb them)**: the 5 webhook rollups (pending Q5); a customer-facing per-channel UI; channel-scoped retry as a user-triggered action (needs Q2 first); the `providerResults` rename across the event + schema (mechanical, but touches `EventSchemaRegistry` versioning); `incrementPostPublished()` at schedule time; `getJobStates` per-job identity (only if the chosen option needs it); ADR-0020 number collision.

**Risks**: (1) `packages/shared/src/saga.ts` is under concurrent edit — N-COR-8 must rebase on N-COR-1 PR3, not on `6737984a`; (2) any option that persists per-channel state with `accountId` triggers fitness #39 + an RLS migration, and with `deletedAt` triggers fitness #38's quarantine floor; (3) the webhook rollups can produce `PUBLISHED`-without-`publishedAt` at any time, which N-COR-1 already fails on — this can surface as a "N-COR-1 regression" that is actually this class; (4) the read-model blast radius is 7 status unions + 6 UI maps if a new status word is chosen, which pushes past the 400-line CODE budget on its own.
