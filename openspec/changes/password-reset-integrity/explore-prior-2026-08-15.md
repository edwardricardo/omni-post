# EXPLORE — Customer credential write path: the revert, the token claim, and the write API underneath both

**Scope:** the customer password-reset write path (`packages/core/customer-auth` + `PrismaCustomerUserRepository`), the admin reset-confirm path (`apps/api/src/admin/auth/PasswordService.ts`), and the repository write primitive both sit on.
**Method:** four independent angles plus an adversarial verification pass over each. Where a verifier refuted a claim, the refutation stands unless I re-verified the original myself; every such case is marked. I re-read every file cited below.

---

## 1. The defects

### D1 — The customer password reset writes the new hash, then reverts it, and reports success

**REAL. Confirmed line-for-line, deterministic, no race required.**

Mechanism:

| Step    | Location                                                     | What happens                                                                                                                                                                                                                                                                                         |
| ------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| load    | `packages/core/customer-auth/src/ResetPasswordUseCase.ts:50` | `findByResetToken(token)` → entity reconstituted from the row; `_passwordHash` holds the **old** hash (`PrismaCustomerUserRepository.ts:270` maps `row.passwordHash` into the props; entity assigns at `CustomerUser.ts:132`)                                                                        |
| bind    | `ResetPasswordUseCase.ts:55`                                 | `const user = userResult.value` — the **only** binding of `user` in the method                                                                                                                                                                                                                       |
| hash    | `:63`                                                        | `const newHash = await this.hasher.hash(...)` — a local, never written to the entity                                                                                                                                                                                                                 |
| write A | `:67`                                                        | `updatePasswordHash(user.id, newHash)` → `PrismaCustomerUserRepository.ts:223` `customerUser.update({ where: { id }, data: { passwordHash } })`. Column now holds `newHash`.                                                                                                                         |
| mutate  | `:73`                                                        | `user.clearResetToken()` → `CustomerUser.ts:487-491` touches `_resetToken`, `_resetTokenExpiry`, `_updatedAt` **only**                                                                                                                                                                               |
| write B | `:74`                                                        | `save(user)` — **one argument** → `PrismaCustomerUserRepository.ts:172` `const hash = passwordHash ?? user.passwordHash` resolves to the **old** hash → `:176` `passwordHash: hash` inside `baseData` → `:201-204` `upsert({ where: { id }, create: {...}, update: baseData })`. **Column reverts.** |
| return  | `:76`                                                        | `ok({ message: "Password reset successfully" })`                                                                                                                                                                                                                                                     |

Nothing between `:67` and `:74` refreshes the entity. I looked specifically: `CustomerUser` has no `changePassword`; `_passwordHash` is assigned only at the constructor (`CustomerUser.ts:132`) and inside `acceptInvitation` (`:465`); the getter at `:233-235` is read-only. So the revert is guaranteed, not probabilistic.

**The port's JSDoc documents the opposite behaviour**, which is why the call site reads as correct: `packages/core/domain/src/repositories/CustomerUserRepository.ts:66-68` — _"If passwordHash is provided it is persisted; otherwise the existing hash is preserved on update."_ It is not preserved; it is overwritten with the in-memory snapshot.

**The Result of `save` is not checked** at `:74` — while `updatePasswordHash`'s Result **is** checked seven lines earlier at `:68`. Adjacent lines, opposite discipline.

**What a user experiences — and here the brief needs correcting.** The revert is not what a user hits first. `POST /auth/customer/reset-password` (`apps/api/src/auth/customerAuthRoutes.ts:576-585`) is public with no `preHandler`, and its handler (`:416-447`) does **not** wrap the flow in `withSystemContext` — unlike `/auth/customer/login` (`:164`) and `/auth/customer/login/mfa` (`:237`), which do, with an explicit comment at `:161` naming the guard. The repository receives the **guarded** Prisma client (`setup.ts:61-64` registers `options.prisma.$extends(tenantGuardExtension(...))` as `TOKENS.PrismaClient`; `setupCustomerAuthUseCases.ts:49` injects it). `customerUser` is tenant-scoped (`infra/prisma/src/extensions/tenantGuard.ts:114`); `findFirst` is guarded (`:155`); with neither system nor tenant context bound the guard throws (`:205-206`). `PrismaCustomerUserRepository.ts:160-167` swallows it into `err(EntityNotFoundError)` → `ResetPasswordUseCase.ts:51-53` → `err("INVALID_TOKEN")` → HTTP **400 "Invalid or expired reset token"** (`customerAuthRoutes.ts:437`).

So: **D1 is a latent lost-update sitting behind a total outage of the endpoint.** The first live behaviour of a fixed endpoint would be the silent revert. That ordering is the single most important fact in this document.

> **Calibration note.** One verifier declined to certify the "100% of requests" quantifier: `enterTenantContext` uses `AsyncLocalStorage.enterWith` (`apps/api/src/security/tenantContext.ts:83-85`), whose own JSDoc calls the binding "irreversible within the current async frame", and nothing clears it at response end. Whether a context bound by an earlier authenticated request can leak into a later keep-alive request cannot be settled by reading source. I did not settle it either. What **is** settled: no code path binds a context on this route's happy path. If there is no leakage, the 400 is universal; if there is leakage, some resets would run under a **foreign tenant's** `accountId` — which is worse, not better. One integration test against the real guarded client resolves it (§5d).

**Severity: HIGH as a defect, currently unreachable.** A credential endpoint that returns a success receipt for a no-op is the worst failure mode in this class. It is not a lockout — the old password still authenticates, login is untouched, and new tokens can be requested (each no-oping identically). The token _is_ burned each time, so each attempt costs the user one link.

**The same shape exists a second time, at `LoginCustomerUseCase.ts:191-194` + `:226`** — transparent rehash writes the upgraded hash via `updatePasswordHash`, then `save(targetUser)` writes `targetUser.passwordHash` (the old one) back. The comment at `:184-190` documents the defect as if it were the design.

> **Refutation that stands.** One angle graded this "BROKEN-TODAY, executes in production right now". It is **dormant**, not live: the write is gated on `this.hasher.needsRehash(targetUser.passwordHash)` (`:191`), which resolves to `argon2.needsRehash(storedHash, ARGON2_PARAMS)` (`apps/api/src/auth/passwordHashing.ts:83-84`), and every customer hash is produced by `hashPassword` with those exact params (`:30-36`, `:45-47`). There is no second hasher for customers and no `passwordHashAlgo` column on `CustomerUser` (contrast `AdminUser`, `PasswordService.ts:278`). So the branch never fires today. It **arms itself the moment anyone bumps a value in `ARGON2_PARAMS`** — which the comment at `passwordHashing.ts:27-28` advertises as the safe way to upgrade. That comment is now a trap: bumping the cost produces an infinite per-login rehash for every non-MFA customer.

### D2 — The reset token is not atomically consumed

**The brief's framing is REFUTED. The token is NOT reusable. The real defect is a TOCTOU double-consume.** Three independent verifiers reached this conclusion; I re-read both call sites and agree.

**Admin path** — `apps/api/src/admin/auth/PasswordService.ts`:

- `:228-232` `findFirst({ where: { passwordResetToken: token, passwordResetExpires: { gt: new Date() } } })`
- `:274-288` `adminUser.update({ where: { id: user.id }, data: { …, passwordResetToken: null, passwordResetExpires: null } })`

The predicate names only the primary key — that part of the brief is exactly right. But the **same statement nulls the token**, so a _sequential_ replay fails the lookup at `:228` and correctly returns `INVALID_TOKEN` (`:239-241`). Single-use holds for sequential use.

What does not hold is atomicity. Between the read and the write there is no transaction and no compare-and-swap, and the gap contains: `validatePasswordStrength` (`:244`), a loop of up to five argon2id `verifyPassword` calls (`:251-254`), one argon2id `hashPassword` (`:261`), and a second `findUnique` round-trip (`:264-267`). Two concurrent requests bearing the same live token both pass `:228`, both hash, both reach `:274`. Both succeed, both log `success: true` (`:291-296`), both revoke all sessions (`:299-309`). Last writer owns the account.

> **Calibration.** One angle stated the window as "~300-600 ms / 6 argon2 ops". The loop is `user.passwordHistory.slice(-5)` and `passwordHistory` defaults to `[]` (`infra/prisma/schema.prisma:183`), so a never-rotated account contributes **zero** verifies. Honest range: **1 to 6 argon2id operations** at m=64 MiB / t=3 / p=4 (`passwordHashing.ts:30-36`). Trivially winnable at either end. Rate limiting does not close it — the attack needs two concurrent requests.

**Customer path** — the identical shape: `ResetPasswordUseCase.ts:50` → `PrismaCustomerUserRepository.ts:152` `findFirst({ where: { resetToken: token, deletedAt: null } })`, then `:74` → `:201-204` `upsert({ where: { id } })`. Two extra differences from admin, both worse:

- **Expiry is not in the predicate.** The customer query filters `{resetToken, deletedAt}` only; expiry is checked afterwards in the entity (`ResetPasswordUseCase.ts:58`). The admin query _does_ filter `passwordResetExpires: { gt: now }` (`:231`).
- **Compounded by D1:** a won race writes the _old_ hash anyway.

**What an attacker gets** (admin path, the live one): they need a token they should not have — and the token travels as a **query parameter** (`adminAuthRoutes.ts:263`, `RequestPasswordResetUseCase.ts:79`), the most-logged part of a URL, and is stored **in plaintext** (`schema.prisma:176`) in a schema that hashes its other bearer secrets and says why (`:220-224`, `AdminSession.refreshTokenHash` — _"protects against DB exfiltration leaking live tokens"_). Given a token, they wait for the victim to click and fire concurrently. The victim sees "Password reset successfully" and cannot log in; there is no lockout signal, no failed-login counter, no security event marked failed. Secondary: both requests compute `updatedHistory` from the same snapshot (`:269`), so one password never enters history — `preventPasswordReuse: 5` is defeated.

**Severity: MEDIUM-HIGH for admin (live, needs a leaked token plus a won race); the customer half is the same shape behind the same dead guard as D1.**

**Scope correction the brief needs:** D1 is customer-side and tenant-guarded; the `PasswordService` instance of D2 is **admin**-side, and `adminUser` is **not** in `TENANT_SCOPED_MODELS` (verified: no match in `tenantGuard.ts`), so it is not behind the guard and is live end-to-end. If the change means the _customer_ token, D1 and D2 are the same statement. If it means the admin token, they are two files and two tables. §7 addresses both readings.

### D3 — found while verifying: one reset token issued for N accounts, against a `@unique` column

Not in the brief; it is in the same 90-line file and the same port surgery would touch it.

`RequestPasswordResetUseCase.ts:54` generates **one** token **outside** the loop, and `:58-60` writes that same token onto every `CustomerUser` sharing the email across accounts. But `resetToken` is `String? @unique` (`schema.prisma:347`). The second row's upsert violates the constraint; `PrismaCustomerUserRepository.ts:206-213` swallows it into a returned `err`; `:60` ignores the Result entirely; the email goes out unconditionally at `:74-86`. Because the repository writes on `this.prisma` (autocommit, §3), the **first** row does get the token and the rest silently do not.

So a user whose email appears in two accounts gets one link that resets an arbitrary one of their accounts. Even without the constraint, the _intent_ — one token that resets the password in every tenant — is a cross-tenant credential design that should be rejected on its merits, not left to a unique index to block.

**Severity: MEDIUM. Latent (needs a duplicated email across accounts) but structural.**

**Criterion — when is a whole-object write correct aggregate persistence, and when is it a lost-update generator?** Three conditions, all required:

1. **Completeness** — the projection covers every column the write touches; no field is written from a value the entity never read.
2. **Exclusivity** — no other writer mutates those columns between this entity's load and its save.
3. **No side channel** — the port offers no way to change a persisted field without going through the entity.

Applied:

- `PrismaPostRepository` — **correct aggregate persistence.** Mapper-driven and complete (`:446` `PostAggregateMapper.toPrismaCreate`), one writer per aggregate, no side channel, and tx-aware (`:445-455`). Do not touch it.
- `PrismaChannelRepository.save` (18 columns on the update branch) — **correct granularity, missing plumbing.** Credentials are encrypted as a unit; `accountId` is deliberately excluded from `update`. Retrofit the tx client only.
- `PrismaCustomerUserRepository.save` — **fails all three.** Incomplete (19 of 26 scalars, `passwordHash` written from a possibly-stale field); non-exclusive (`PrismaCustomerMfaUserRepository` writes `mfaEnabled`/`mfaSecret`/`mfaLastUsedTotpStep` on the **same row**, from a different repository, with a different discipline); and the side channel is in the port signature. It is a lost-update generator wearing aggregate clothing.

The distinction is not column count. It is **whether the entity is authoritative for every column it writes.**

### Every repository in the same position on the transaction client

Measured, not estimated:

- `rg -l getTransactionClient apps/api/src --type ts` → **11 files**, one of which is `PrismaUnitOfWork.ts` itself (the definition, `:114`). **10 consumers**: `PrismaAdminMfaUserRepository`, `PrismaCustomerMfaUserRepository`, `PrismaOutboxWriter`, `PrismaAccountSubscriptionAdapter`, `PrismaAdminSessionRepository`, `PrismaAdminUserRepository`, `PrismaAuditLogRepository`, `PrismaBulkScheduleBatchRepository`, `PrismaConversionRepository`, `PrismaPostRepository`.
- Files under `apps/api/src/infrastructure` containing a Prisma write verb: **86**. Of those, **10** are tx-aware. **76 are not (88%).**

> **Refutation that stands.** One angle wrote "its 11+ siblings have it", implying `PrismaCustomerUserRepository` is the outlier. It is in the **overwhelming majority**. That does not soften D1 — it means the root cause is systemic and the remedy "rewrite this one adapter" is scoped roughly an order of magnitude too small. It also means **bundling a 76-file problem into a 2-file credential fix is the wrong move** (§7).

Consequences of the gap, stated accurately:

- **Atomicity is a lie** wherever a use case wraps a non-tx-aware repository. Rollback undoes nothing.
- **The RLS GUC does not bind.** `set_config(..., true)` (`PrismaUnitOfWork.ts:84-88`) is transaction-local. But — correcting one angle — this is not a property of the 76: **every** query outside a UoW transaction lacks the GUC, including all reads and all writes of the 10 "correct" repositories whenever no ambient transaction exists. Enforcing RLS breaks the whole non-transactional surface, not the 76 specifically. Today it is invisible because the app role bypasses RLS.
- **"Self-deadlock hazard"** was asserted by one angle and is **not instantiated** in this path. In D1's own flow both `set_config` branches are skipped (no context bound), so the UoW transaction issues **zero** statements and holds no locks.

## 4. What is the CORRECT design, built from scratch?

The application has never been used. There is no compatibility to preserve, no live state to migrate, no external consumer. So the question is not "what is the smallest safe patch" — it is **what would I build if this file were blank**.

### The repository write API — is a 19-column snapshot save the right primitive at all?

**No. Delete `save()`.** Not amend it, not make `passwordHash` conditional. Delete it.

The reasoning is the criterion in §3. A whole-object write is honest only when the entity is the sole, complete, freshly-read authority for every column it writes. `CustomerUser`'s row fails that permanently, and not by accident: **two repositories own the same row with opposite disciplines.** `PrismaCustomerMfaUserRepository` does field-level compare-and-swap on `customerUser` (`:99-123`, `:144-165`) while `PrismaCustomerUserRepository` overwrites 19 columns from a snapshot. Two aggregate roots over one row is incoherent, and no amount of fixing `passwordHash` resolves it.

There are exactly two coherent designs. This is a **genuine fork** and I will name both, then recommend.

**(A) One true aggregate + optimistic concurrency.** Fold MFA state into `CustomerUser`, delete `PrismaCustomerMfaUserRepository`, add a `version Int` column, and make `save(user)` a versioned whole-object write (`updateMany where { id, version }`, `count === 0 → CONFLICT`). This is what `ARCHITECTURE_CANON §DDD` describes and what `PrismaPostRepository` already is. It makes the snapshot honest by making it complete, exclusive, and side-channel-free.
_Cost:_ a schema migration, a domain rewrite of the MFA surface, and it converts every silent lost update into a visible `CONFLICT` the callers must handle. It also throws away the best-built code in this area.

**(B) Persistence expresses intent.** `CustomerUser` is not an aggregate root with a single writer; it is a record with several independent, concurrently-safe intents. Make the repository a command surface with one method per intent, each a single conditional statement naming its own precondition:

```
create(user, passwordHash)                                  → the only whole-object write; create branch only
claimPasswordReset(token, newPasswordHash)                  → Result<void, "INVALID_TOKEN">
issueResetToken(userId, token, expiresAt)                   → Result<void, "NOT_FOUND">
recordLogin(userId, at)
changeRole(userId, roleId)
deactivate(userId)
```

This is exactly what the two best-built pieces in the codebase already do: `PrismaAdminUserRepository.update` (`:211-238`, sparse partial update, documented contract, tx-aware) and `PrismaCustomerMfaUserRepository.claimTotpStep` (`:144-165`, conditional single statement, count-gated, disambiguated). Neither needs a version column. Neither can revert a column it did not name. Both are already proven, one of them by a concurrency test.

**Recommendation: (B).** Not because it is smaller — because the write path's problems are _concurrency and intent_, and (B) answers both in the same statement while (A) answers them by adding a serialization layer on top of a projection that is still wrong (incomplete, and co-owned). (A) is defensible and should be an ADR if anyone wants it; it is not the design the evidence points at.

### The token claim primitive

One statement, predicate names the token, count-gated. The template is in-tree; copy it:

```
const { count } = await client.customerUser.updateMany({
  where: { resetToken: token, resetTokenExpiry: { gt: now }, deletedAt: null },
  data:  { passwordHash: newHash, resetToken: null, resetTokenExpiry: null },
});
if (count !== 1) return err("INVALID_TOKEN");
```

This closes **D1** (no snapshot, nothing to revert), **D2** (the claim is the predicate; a concurrent second request matches zero rows), and the **expiry-outside-the-predicate** gap, in one write. It needs **no transaction at all** — a single statement is atomic by definition, which is a better answer than making the transaction honest.

Two deliberate contract changes fall out, and both are improvements:

- **`TOKEN_EXPIRED` and `INVALID_TOKEN` collapse into one.** Today `ResetPasswordUseCase.ts:58` distinguishes them and `customerAuthRoutes.ts:437-440` surfaces the distinction — a token-validity oracle. Collapsing removes it. (Client impact: open question, §8.)
- **The read disappears from the write path.** `findByResetToken` stays only if something else needs it; nothing does.

Admin side, same shape, one extra concern: `passwordHistory` is read at `:235`/`:264` and written at `:279` — a read-modify-write that is racy independently of the token. Either move the history read inside the same statement's precondition, or wrap read+write in a real transaction. Naming the token in the `where` alone does not fix history.

### Transaction-client handling

Two answers, and they are not in tension:

1. **For this write path: don't need one.** A single-statement claim is atomic. Remove the UoW from `ResetPasswordUseCase` rather than pretending it works.
2. **For the repository: add it anyway.** `private getClient() { return PrismaUnitOfWork.getTransactionClient() ?? this.prisma; }`, routing all 10 sites, copying `PrismaPostRepository.ts:445-455`. Cheap, ten lines, and it makes the _other_ callers (`InviteTeamMemberUseCase`, `UpdateTeamMemberRoleUseCase`, `RequestPasswordResetUseCase`) honest with respect to `ARCHITECTURE_CANON:145`, and binds the RLS GUC for their writes.

The 76-repository version of this is a separate workstream with its own fitness function and its own ADR (§7). Fixing one adapter as a side effect of a credential fix is correct; fixing 76 is not.

### Where the password hash lives in the entity/use-case contract

The hash should be **read-only for verification and write-only by command.** Concretely:

- Keep `get passwordHash()` (`CustomerUser.ts:233`) — `LoginCustomerUseCase` legitimately needs it to verify and to test `needsRehash`.
- **No persistence path ever writes it from the entity snapshot.** That is the invariant, and it is the one a test can pin (§5c).
- The hash reaches the database only through `create(user, hash)` and `claimPasswordReset(token, hash)` — both of which take it as an explicit argument, so omitting it is a **compile error**, not a silent revert. That inverts today's default, where the easiest thing to write is the wrong thing.
- `CustomerUser.acceptInvitation(passwordHash)` (`:458-471`) then becomes the odd one out: it mutates `_passwordHash` in memory with no persistence path. Either give it a matching `claimInvite(token, hash)` command or delete it with `setInviteToken` — both are dead code today.
- Separately: `isPendingInvitation` (`:308-315`) reading `_passwordHash === ""` is a status sentinel in a credential column. Replace with explicit state. Not in this change.

### The minimum coherent slice for THIS change

Not "smaller is safer" — **a change must be reviewable and provable**, and this one is provable exactly when the endpoint is reachable and the outcome is asserted.

**Slice 1 — the credential channel (this change):**

1. Bind `withSystemContext` on the four bare pre-identity handlers (`customerAuthRoutes.ts:103` register, `:401` request-reset, `:416` reset, and the refresh handler), matching the shape already at `:164`/`:237`. **This must land in the same change but as its own commit**, and never _before_ item 2 — otherwise the first live behaviour of a reachable endpoint is the silent revert.
2. Port surgery: delete `save(user, passwordHash?)` and `updatePasswordHash`; add `create(user, hash)`, `claimPasswordReset(token, hash)`, `issueResetToken(userId, token, expiresAt)`.
3. Rewrite `ResetPasswordUseCase` to one call; rewrite `RequestPasswordResetUseCase` to one token **per user** (closes D3's mechanics); rewrite `RegisterCustomerUseCase` to `create`.
4. Add `getClient()` to the adapter, all 10 sites.
5. Red tests §5a-§5d; rewrite `customerAuthUseCases.test.ts:481-494`.

**Slice 2 — the remaining intents (immediately after, same change or a chained PR):** `recordLogin`, `changeRole`, `deactivate`, invite creation. Until this lands, `save()` still exists for those four callers and the snapshot hazard remains. It belongs to this design, not to a backlog — leaving `save()` alive keeps the footgun loaded and re-arms `LoginCustomerUseCase.ts:226` on the next `ARGON2_PARAMS` bump.

**If you take only one sentence from this section:** delete `PrismaCustomerUserRepository.save` and `updatePasswordHash`, and delete the `passwordHash?` parameter from the port. That is the honest answer, and the compiler will find all eight call sites.

## 6. Constraints

**Canon (binding):**

- `ARCHITECTURE_CANON §Unit of Work` — "Every mutating use case MUST use UoW" and "Never write to a repository outside `executeInTransaction`". The single-statement claim is atomic without one, which is arguably _more_ correct than the canon's literal text. **This is a real fork** (§8): either keep a UoW and make the repository honour it, or amend the canon sentence with an ADR. Recommendation: do both — the repository gets `getClient()` regardless, so the canon holds literally at zero extra cost.
- `ARCHITECTURE_CANON §Hexagonal / Ports` — the claim primitive is a port method on `packages/core/domain/src/repositories/CustomerUserRepository.ts`; the `updateMany` lives in `apps/api/src/infrastructure/repositories/`; the use case sees a typed `Result` and never a Prisma type.
- `ARCHITECTURE_CANON §DI` — wiring changes only in `apps/api/src/infrastructure/container/setupCustomerAuthUseCases.ts`.
- `CODING_STANDARDS` — `Result<T,E>` across boundaries, no `throw` in domain/application, `@file`/`@layer` headers on new files, tests in the same change.

**Fitness functions:**

- **#23** (no raw Prisma queries) — the CAS **must** be a typed `updateMany`, not `$queryRaw`. `PrismaCustomerMfaUserRepository.ts:102-103` says this in-tree: _"Raw SQL is banned here (fitness #23); the typed JSONB `equals` filter IS the CAS."_
- **#21** (no prisma singleton outside composition roots), **#3** (no `any`), **#4** (no raw throws), **#9/#10** (`@file`/`@layer`), **#8** (no sprint/phase refs in comments).

**Sensitive paths / tripwires:** `apps/api/src/auth/**`, `apps/api/src/admin/auth/**`, `apps/api/src/security/**` are credential surfaces — the pre-edit tripwire blocker applies, and `SECURITY_CANON` allows **no** canon-exception for multi-tenant guards. Any change to the guard wrapping goes through `withSystemContext()`, which **is** the canon-sanctioned path (`CLAUDE.md §Pragmatic Exceptions`, forbidden list). Tripwire #7 (Plan Mode on `workstream/*` branches) applies to the apply phase.

**Schema constraints on the token fix:**

- `CustomerUser.resetToken String? @unique` (`schema.prisma:347`) — the unique index means the claim can key on the token alone and is index-backed. It also means D3's one-token-for-N-rows loop violates the constraint; the fix must issue one token per user.
- `AdminUser.passwordResetToken String?` (`schema.prisma:176`) — **not unique, not indexed** (absent from the index block at `:211-214`). A `updateMany` on it is a sequential scan on every unauthenticated attempt. Keying on `{ id, passwordResetToken }` uses the PK and avoids the scan; adding a unique index is a migration (out of scope, file it).
- Both columns store the token **in plaintext**, unlike `AdminSession.refreshTokenHash` (`:220-224`). Hashing at rest is a schema + flow change (out of scope, file it).

**Tenant guard mechanics that constrain the fix:** `update`, `updateMany` and `upsert` are all in `WHERE_OPERATIONS` (`tenantGuard.ts:158-160`) and `customerUser` is tenant-scoped (`:114`). **The claim `updateMany` still throws without a bound context.** Switching to a single statement does not remove the need for `withSystemContext` on the pre-identity routes; it only removes the silent-success failure mode.

**One mechanism that is already correct and must not be broken:** `TOKENS.UnitOfWork` is constructed from `TOKENS.PrismaClient` — the **guarded** client (`setupRepositories.ts:217` + `setup.ts:61-64`). So the `tx` handed to repositories inside `executeInTransaction` is extension-derived and the tenant guard applies inside transactions. Adding `getClient()` does not open a guard bypass.

## 8. Open questions for propose/design

1. **Aggregate-with-version (A) or intent-named commands (B)?** §4 recommends (B) and gives the reasoning, but (A) is the literal `ARCHITECTURE_CANON §DDD` reading and would require deleting `PrismaCustomerMfaUserRepository` — the best-built file in this area. Only a human should decide to delete that.
2. **Does the UoW canon rule bend for a single-statement claim, or does the repository get `getClient()` and keep the ceremony?** `ARCHITECTURE_CANON:145/149` is written in the present indicative about behaviour that holds in 10 of 86 cases. Either the fix keeps a decorative transaction, or the canon text changes. An ADR either way.
3. **Multi-account password reset (D3): what is the intended product behaviour?** One token per account and N emails? One email listing the accounts? Reset scoped to one account chosen at request time? The mechanical fix (one token per user) is unambiguous; the UX is not, and the current design writes one credential-recovery token across tenant boundaries.
4. **Collapsing `TOKEN_EXPIRED` into `INVALID_TOKEN`.** The claim predicate cannot distinguish them without a second query, and distinguishing them is a validity oracle. Does `apps/client` depend on the distinction (`customerAuthRoutes.ts:437-440` currently surfaces two different 400 messages)?
5. **Scope of `withSystemContext` binding.** Four bare pre-identity handlers exist. Fix all four in this change, or only the two on the reset path? Fixing all four is cheaper and closes the class; fixing two keeps the diff on-topic. There is a real reviewability tradeoff.
6. **Does slice 2 chain onto this PR or merge separately?** Leaving `save()` alive between the two slices keeps the footgun loaded for four callers and keeps `LoginCustomerUseCase.ts:226` armed against a future `ARGON2_PARAMS` bump.

## 9. Risks (implementation only)

**Regression risk in the other callers of any method redesigned.**
Deleting `save()` is compiler-checked across 8 call sites, so _finding_ them is free. The behavioural risks are:

- `InviteTeamMemberUseCase.ts:111` relies on the upsert taking its `create` branch (fresh `randomUUID` id, `passwordHash: ""`). A new `create()` must be a genuine `create`, not an upsert — otherwise a duplicate id becomes a silent overwrite instead of a constraint error.
- `RegisterCustomerUseCase.ts:149` is the only two-argument caller; `create(user, hash)` must keep the hash mandatory there.
- `CompleteCustomerMfaLoginUseCase.ts:184` and `UpdateTeamMemberRoleUseCase.ts:97` check `save`'s Result today; their replacements must return the same typed errors or the error contract shifts under them.
- A **partial** fix that only removes `passwordHash` from the `update` branch (keeping `save`) would make `CustomerUser.acceptInvitation` (`:465`, the entity's only password mutator) structurally unable to persist — a silent no-op the moment an invite-accept flow gets wired. That is the same silent-loss class as D1, re-armed by the fix for D1. It is dead code today, so this is latent, not live — but it is a reason to prefer deletion over conditional spreading.

**Is "honour the transaction client" harder than it looks?** Three subtleties, ordered by how likely they are to bite:

- `PrismaUnitOfWork.getTransactionClient()` returns a `Prisma.TransactionClient`, not a `PrismaClient` — it lacks `$transaction`, `$extends`, `$connect`. Every method routed through `getClient()` must typecheck against the narrower union (`PrismaAdminUserRepository.ts:79` declares exactly `PrismaClient | Prisma.TransactionClient`). Methods that call anything outside the model API will not compile — which is good, but it is work.
- `txStorage` is a **module-level** `AsyncLocalStorage` (`PrismaUnitOfWork.ts:33`). If two copies of the module are loaded — which fitness **#27** exists to prevent, because workspace `exports` point at `dist` while `--conditions development` resolves to `src` — the store instance differs and `getTransactionClient()` returns `undefined` silently. A test that runs under the wrong resolution mode would prove nothing and look green.
- **Not** a risk, verified: the UoW is constructed from the **guarded** client (`setupRepositories.ts:217`), so joining a transaction does not bypass the tenant guard.

**Can the entity express the corrected contract without a domain rewrite?** Yes, on design (B). `passwordHash` stays a constructor prop and a getter; the only change is that no persistence path reads it for a write. Design (A) is a different answer — it needs a `version` column, a migration, MFA state folded into the entity, and `CONFLICT` handling at every call site. That is a domain rewrite, and it is the main reason to prefer (B).

**Keeping a rewrite reviewable.** The honest answer here _is_ a rewrite (delete two port methods, add three, touch eight call sites, plus route wrapping and four test files). Mitigations: work-unit commits with the route-binding commit separate from the port surgery; the chained-PR skill if the diff crosses 400 lines; slice 2 as a follow-on PR; and — most important — the red tests land **first** and stay red until the last commit, so the diff has an external correctness oracle rather than a reviewer's reading of it.

**Tests that would go green for the wrong reason after the change.** Four, all identified, all must be dealt with in the same change:

- `apps/api/tests/unit/customerAuthUseCases.test.ts:481-494` — call-count assertions against a stateless mock. Green today, green after any fix, proves nothing. **Rewrite, do not leave.**
- `apps/api/tests/unit/infrastructure/repositories/PrismaCustomerUserRepository.save.test.ts` — tests argument shaping of a method that will cease to exist. Its two invariants (no scalar `role` argument; `roleId: "" → NULL`) are real and must migrate to whichever method inherits them.
- `apps/client/tests/e2e/tests/auth.spec.ts:186-196` — navigates to a hardcoded fabricated token and asserts a success banner without ever logging in with the new password. It cannot fail on D1 and cannot fail on the fix.
- Any new integration test that is written but **not named in a `run_batch`** — it will never execute and will read as coverage. Five customer-auth/MFA suites are in exactly that state today (verified: 0 matches each in `run-tests.sh`).

**One risk specific to the D2 fix.** `PasswordService.confirmPasswordReset` has two non-consuming failure exits between the read and the write — `PASSWORD_TOO_WEAK` (`:246`) and `PASSWORD_REUSED` (`:256`) — which correctly leave the token usable so a user who picks a bad password can retry with the same link. A naive rewrite that claims the token up front regresses that behaviour into a one-shot-per-attempt link. The claim must happen at the write, not at the read.
