The behavioural invariant: in `apps/api`, the provider the root hands both adapters IS the object `getAmbientGucScope()` reads today (`tenantContext.ts:177-179` → `resolveGucScope(ambientTenantContextProvider)`), so every scope the relocated code binds is byte-identical to today's. What changes is only WHO chooses the provider — the composition root instead of an ambient import — which is what lets a worker root choose its own (D2 of N-COR-8).

### D1 — Provider injection shape: `TenantContextProvider` + `resolveGucScope`, REQUIRED on both constructors, options last

**Choice.**

The `getAmbientGucScope` import lines (`PrismaUnitOfWork.ts:14`, `PrismaPostRepository.ts:35`) are deleted; `PrismaPostRepository.ts:28` gains `resolveGucScope`. `static getTransactionClient()` and the module-level `txStorage` are untouched (D7). `PostAggregateMapper.ts` and `PrismaOutboxWriter.ts` change zero bytes. The mapper sits FLAT at `src/post/PostAggregateMapper.ts` (C10), so the repository's sibling import becomes `./PostAggregateMapper.js`; `../unitofwork/PrismaUnitOfWork.js` (from `src/post/` and `src/outbox/`) resolves at the new location by construction of the D1 layout.

**Why the provider, not a narrower port.** `TenantContextProvider` (`tenantGuard.ts:35-38`) is already the type `setup.ts:74-75` hands the guard and the type `resolveGucScope` (`tenantGuc.ts:119-124`) takes; the mapping "system wins over tenant, else undefined" lives in ONE function precisely so two layers cannot derive different scopes from one provider (`tenantGuc.ts:110-115`). A `GucScopeProvider { scope(): string | undefined }` would add a second abstraction that every root then has to adapt to, and it would move the system-sentinel mapping to the caller — the opposite of what `resolveGucScope` was placed in `infra/prisma` for. N-COR-8 D2 already constructs against `TenantContextProvider`. Rejected.

**Why REQUIRED on the UoW too (not only the repository).** `new PrismaUnitOfWork(prisma)` compiles today and binds the ambient scope. If the provider were optional, that same expression would keep compiling after the move and bind NOTHING — under `withSystemContext` a sweep would see zero rows, in a unit tier with mocked clients nothing would notice, and 51 test constructions would silently change what they prove. Explore §2.2(b) makes exactly this argument for the repository; it holds for the UoW with the same force. A required parameter turns 54 silent reinterpretations into 54 compile-time/RUNTIME breaks that are planned (C1), not discovered. **Cost, stated:** it is also why the forecast grows (§Work units).

**Why options stay last on the UoW** (explore §2.2(a)): `setupProjectUseCases.ts:71-74` and `setupAccountUseCases.ts:71-74` pass `HARD_DELETE_TX_OPTIONS` positionally; `hardDeleteSerializableRace.test.ts:212`, `mfaBackupCodeSingleUse.integration.test.ts:410` and `PrismaUnitOfWork.test.ts:146` likewise. D1's literal `(prisma, tenantProvider)` would type-check only if the provider type were loose and would reinterpret the Serializable options as a provider on the hard-delete path.

**Why the repository keeps D1's `(prisma, outboxWriter, tenantProvider)` order with `outboxWriter: OutboxWriter | undefined`.** TypeScript refuses an optional parameter before a required one (TS1016), so with the provider required the outbox slot must be typed `| undefined` and passed explicitly. The 9 test sites that build the repository without an outbox therefore write `undefined` in the middle — which is a feature, not a wart: "this repository writes no outbox rows" becomes visible at the call site instead of implicit. `no-useless-undefined` is not configured (measured: `eslint.config.ts` has no `unicorn` rules), so the form is lint-clean. **Rejected alternatives:** (a) reorder to `(prisma, tenantProvider, outboxWriter?)` — canon-consistent (optional last) but it lets a production root omit the outbox writer silently, which drops domain events (ADR-0023's outbox coupling), and it forces an N-COR-8 D2 amendment; (b) make `outboxWriter` required with a no-op double in the 9 tests — the right end state but it deletes the two `if (this.outboxWriter)` guards (`:642`, `:776`), a behaviour edit outside "move and wiring" (backlog B11); (c) an options object — deviates from D1/D2 for no churn saving.

**Why the root passes the provider as an imported VALUE, not a container token.** `setup.ts:74-75` already passes `ambientTenantContextProvider` by value to the guard; "layer 1 and layer 2 read the same object" is a fact of the wiring because it is the SAME import (fitness #40 residual (2)). A `TOKENS.TenantContextProvider` would register a module constant, and the container double in `setupProjectUseCases.test.ts:48` answers unknown tokens with `{}` — a `{}` provider makes `resolveGucScope` throw `getSystemContext is not a function`. Rejected.

### D2 — The #40 Part B token: the inline expression `resolveGucScope(this.tenantProvider)`

**Choice.** No accessor. Each relocated site carries the derivation literally; the gate admits exactly two expressions inside the call window: `getAmbientGucScope()` and `resolveGucScope(this.tenantProvider)`.

**Why.** Part B "proves the scope EXPRESSION" (residual (2)) and its window rationale says a scope argument that is not readable at the call site is a violation for the same reason. A private `gucScope()` accessor (explore Q3) would move the derivation into a method body the grep never reads — two classes, two bodies, each free to drift — and the gate would then prove only that a method of that NAME was called. `getAmbientGucScope()` is admissible as a name because it is ONE module-level function with a fixed body; a per-class accessor is not that. Admitting bare `resolveGucScope(` was also rejected: `resolveGucScope(someHandBuiltProvider)` would pass. The chosen token binds the expression to the constructor-injected property; that the composition root hands the same object to the guarded client is residual (2) at the new sites, proven by the root-wiring unit test and by `tenantGucTransactionBinding` on a real database.

**Prettier reflow, measured and within the window** (`.prettierrc` `printWidth: 100`): the `:187` line becomes 101 characters and `:566` / `:658` become 102, so all three exceed 100, reflow to the multi-line form, and the token lands on call+2 — inside the call+3 window, exactly like `PrismaProjectRepository.ts:383-388` today.

**Population after the move:** `apps/api/src` 10 (13 today minus the 3 relocated; `sagaTenant.ts` ×2 exempt) + `packages/adapters/db-prisma/src/post` 3 = **13**. Floor stays **10** — the margin the gate had before the move is restored, and the floor line does not change.

**Scope decision.** Part B's second scope is the three D1 subdirectories, NOT the whole package: `packages/adapters/db-prisma/src/post`, `…/src/outbox`, `…/src/unitofwork`. The flat db-prisma files hold 6 `withGucBoundTransaction(` sites (`MentionRepository.ts:84,:108`, `ProjectRepository.ts:42,:130`, `PostRepository.ts:75,:136`) that pass `SYSTEM_TENANT_SCOPE` / an explicit account / `undefined` — the explicit-scope worker convention residual (4) already names. Scoping the whole package would flag all six; exempting them would grow `SCOPE_EXEMPT` from one file to four, which residual (3) forbids ("may only shrink"). The subdirectory scope also gets its own existence loop, so the gate fails closed if a relocated home disappears — it pins the D1 layout as a side effect. **This amends spec R5's wording** ("SHALL include `packages/adapters/db-prisma/src`") to the three subdirectories — correction C4; the orchestrator carries it into the spec.
