# EXPLORE — MFA backup-code single-use: the claim predicate does not name the claim

---

## 1. Scope of the defect

### 1.1 What is broken

`MfaUserRepositoryPort.markBackupCodeUsed` is contracted as an atomic single-use claim (`packages/ports/src/MfaUserRepositoryPort.ts:96-112`). Both production adapters implement it as **read → mutate in JS → conditional write, where the write's predicate names the whole JSONB column rather than the claimed index**:

`apps/api/src/infrastructure/adapters/PrismaCustomerMfaUserRepository.ts:85-124` (admin twin, byte-for-byte including the justification comment, at `PrismaAdminMfaUserRepository.ts:80-119`):

```ts
:91   const row = await client.customerUser.findUnique({           // snapshot read
:94     where: { id: userId }, select: { mfaBackupUsedAt: true } });
:96   const snapshot = row.mfaBackupUsedAt;
:97   const usedMap = normalizeUsedAt(snapshot);
:98   usedMap[String(codeIndex)] = usedAt.toISOString();           // UNCONDITIONAL overwrite
:104  const { count } = await client.customerUser.updateMany({
:105    where: { id: userId,
:107             mfaBackupUsedAt: { equals: snapshot } },          // codeIndex ABSENT
:114    data: { mfaBackupUsedAt: usedMap } });
:116  if (count === 1) return ok(undefined);
```

`codeIndex` appears exactly once in the method body, at `:98`, as a JS object key. It is nowhere in the `where`.

The one-sentence statement of the fault: **a compare-and-swap whose comparand is a read taken inside the same method is a lost-update detector scoped to that method — never a single-use claim scoped to the code.** Contrast the correct sibling 18 lines below (`:142-166`): `claimTotpStep` derives its predicate from the _caller's argument_ (`OR: [{ mfaLastUsedTotpStep: null }, { mfaLastUsedTotpStep: { lt: step } }]`, `:152-158`), takes no prior read, and is monotone. That predicate can never re-match after a claim. The backup-code predicate re-matches whenever the reader read the post-claim state.

### 1.2 The interleaving

The exploitable window is **not** the adapter's own read-to-write gap — that one _is_ closed. It is the gap between the service's **deciding read** and the adapter's **snapshot read**.

`apps/api/src/admin/auth/MfaService.ts`:

```
:199  const found = await repo.findById(subject.id);        ◀ DECIDING READ
:226  const usedIndexes = new Set(Object.keys(record.mfaBackupUsedAt));
:228  if (usedIndexes.has(String(index))) continue;         ◀ the skip is a CHECK on :199
:231  if (await verifyPassword(hash, token)) {              ◀ argon2id, up to 8× SERIAL
:240  markResult = await repo.markBackupCodeUsed(...)       ◀ ACT (adapter re-reads at :91)
```

Trace, two requests A and B presenting the same code at index 0:

```
B: findById(:199) → usedIndexes={} ──── argon2 loop (:231) ─────► adapter read (:91)
     A: findById → argon2 → adapter read → CAS write {"0":tA} COMMIT ─┘
                                                            ▲
   A commits HERE ⇒ B's :91 snapshot is {"0":tA}
   ⇒ B's `equals {"0":tA}` MATCHES the live row ⇒ count===1 ⇒ ok(undefined)
   ⇒ B also overwrites tA with tB.
```

Both return `ok`, both mint a session (`authServiceCore.ts:294`, `AdminAuthService.ts:154-159`, `CompleteCustomerMfaLoginUseCase.ts:148-151`).

The window is wide by construction: `passwordHashing.ts:30-36` sets argon2id at m=64 MiB / t=3 / p=4, `adminAuthConfig.ts:40` sets `backupCodesCount: 8`, and the loop at `MfaService.ts:227-231` awaits one verify per iteration. Hundreds of milliseconds, not microseconds — which is exactly why a stagger is reliable while simultaneity is not.

Successive winners **chain**: each subsequent double-spender must read after the previous commit and write before the next, since its predicate is the previous winner's value. So N sessions are reachable with an N-way stagger, and after N spends the map holds **one** key carrying the **last** timestamp.

### 1.3 Why isolation levels do not fix it

`MfaService.runInTransaction` (`:499-501`) wraps only `:239-256`; the deciding read at `:199` is outside it. `PrismaUnitOfWork` is registered with no default options and only sets `isolationLevel` when explicitly supplied, so this is Postgres default **Read Committed**.

Raising it does not help, and reaching for `Serializable` would be treating the wrong thing. In the exploitable interleaving B's transaction **begins after A's commits** — there is no concurrency anomaly for SSI to detect. The execution is genuinely serializable; both commits are correct with respect to the predicate they were asked to evaluate. **The predicate is wrong, not the isolation.**

The simultaneous case (`Promise.all`) is the one that works, because both adapter reads precede both writes and Postgres RC row-locking re-evaluates the loser's qual against the winner's committed row version. That is the only interleaving the existing integration test exercises (`mfaBackupCodeSingleUse.integration.test.ts:96-99`).

### 1.4 Historical note — this code IS a prior fix for the same class

`git log` on the adapter: commit `7b245e3e` _"fix(security): atomic backup-code single-use (CAS)"_, body: _"markBackupCodeUsed was read-modify-write on the mfaBackupUsedAt map: two concurrent verifications of the SAME backup code ... both succeeded, minting two sessions ... Convert both Prisma adapters to a compare-and-swap ... mirroring claimTotpStep"_, and _"Concurrency proof: the live-DB race test asserts exactly one of two simultaneous verifications succeeds."_

That fix closed the narrow window and left the wide one open, and its stated proof tested only the window it closed. This is load-bearing context for §9: the next fix must be proved by the interleaving it claims to close, and — better — must not depend on an interleaving argument at all.

### 1.5 Severity — calibrated, not inflated

**HIGH, but it is a single-use-control failure, not an authentication bypass.** Precondition: the attacker already holds a valid backup code _and_ whatever gets them to the MFA step (password for `authServiceCore.ts:260`/`AdminAuthService.ts:132`; a valid step-1 challenge, hence the password, for `CompleteCustomerMfaLoginUseCase.ts:148`). Given both, one session is already theirs.

What the defect adds:

1. **Session multiplication** — one recovery credential mints N sessions inside the argon2 window. This is a verbatim NIST SP 800-63B-4 §3.1.2.2 SHALL violation (_"A secret from a look-up secret authenticator SHALL be used successfully only once"_). It matters most for the realistic disclosure vectors a backup code has: helpdesk, shared inbox, screenshot, printed sheet.
2. **Evidence destruction, which is arguably the worse half.** `:98` overwrites the winner's timestamp, so the post-attack used-map is byte-indistinguishable from one legitimate use, and `getMfaStatus` (`:429-430`) reports an arithmetically _correct_ remaining count. Meanwhile the HIGH audit `MFA_BACKUP_CODE_REUSE_REJECTED` (`:264`) fires only on `count === 0` — i.e. **only on the interleaving that already blocked the attack.** The alarm is wired to the non-event. The path that mints two sessions emits two indistinguishable `MFA_BACKUP_CODE_USED` MEDIUM rows (`:248`) and nothing else.

Not HIGH because it grants initial access. HIGH because it silently defeats a mandated single-use control and erases the only forensic record that it was defeated.

> **Explicit re-verification.** One adversarial verifier **refuted** the defect classification, arguing the whole-column `equals` CAS is strictly stronger than a per-index predicate and fails closed, citing the `7b245e3e` commit and the passing integration test. **I re-verified against the source myself and the refutation does not hold.** Its argument — _"any concurrent commit that could enable double-use necessarily mutates `mfaBackupUsedAt`, so the loser's `equals snapshot` predicate fails"_ — is true only when the loser's snapshot **predates** the winner's commit. The snapshot is taken at `PrismaCustomerMfaUserRepository.ts:91`, inside the adapter, **after** the service's decision at `MfaService.ts:199` and after the argon2 loop. When the winner commits inside that gap, the loser's snapshot _is_ the post-commit value, `equals` matches the live row, `count === 1`, and `:116` returns `ok`. The cited integration test proves nothing about this case: it only ever issues `Promise.all` (`:96-99`), the interleaving where both reads precede both writes. The verifier's own confirmation that the CAS "fails closed" is correct — for the narrow window `7b245e3e` closed. The wide window is untested and open. The defect stands.

**P-2 breaking interleaving.** Two requests carrying the same token, ~50 ms apart. Both `findFirst` hit (token still non-null). Both spend ~400 ms in `verifyPassword` × reuse-check (`:254`) plus `hashPassword` (`:261`). Both `update({ where: { id } })`. Both return success; last writer owns the account password. The window is _larger_ than P-1's and there is no CAS and no transaction at all. Fix is the identical shape as `claimTotpStep`: `updateMany({ where: { id, passwordResetToken: token }, data: {...} })`, `count === 0 → INVALID_TOKEN`.

**P-3 is worse than a race — it is broken single-threaded.** `ResetPasswordUseCase.ts:67` writes the new hash via `updatePasswordHash(user.id, newHash)`. Then `:73-74` calls `user.clearResetToken(); save(user)`. `PrismaCustomerUserRepository.save` computes `const hash = passwordHash ?? user.passwordHash` (`:172`), puts it in `baseData.passwordHash` (`:176`), and applies `update: baseData` (`:204`) — a full-column write from an entity reconstituted at `:50`, **before** the hash write. `clearResetToken` (`packages/core/domain/src/entities/CustomerUser.ts`) touches only `_resetToken`, `_resetTokenExpiry`, `_updatedAt`. **The second write reverts the password hash, and the use case reports `"Password reset successfully"`.** The sibling that gets it right is one file away: `RegisterCustomerUseCase.ts:149` calls `save(user, passwordHash)`. It is invisible to tests because `customerAuthUseCases.test.ts:449-450` injects a fully mocked repository.

Compounding it: `PrismaCustomerUserRepository` has **no** `getTransactionClient()` anywhere — constructor at `:63`, every method uses `this.prisma` directly. So both writes escape the surrounding `executeInTransaction`.

`claimTotpStep` (`Cust:152-158`, `Admin:145-151`) · `PrismaBillingEventRepository.ts:72-76` (`where: { id, processed: false }` → `{claimed: count > 0}` — candidate shape B, already in tree) · `PrismaTriageMessageAdapter.ts:76-91` · `PrismaPostRepository.ts:529-546` (OCC by version, where whole-aggregate compare IS the correct granularity) · `OutboxClaimService.ts:88-101` (`FOR UPDATE SKIP LOCKED`) · `RedisMfaChallengeStoreAdapter.ts:36-59` (`SET NX` / `DEL`+count) · `PrismaConversionRepository.ts:38` + `schema.prisma:940` (unique constraint + P2002 — candidate shape A, already in tree) · `schema.prisma:824` `@@unique([projectId, provider], where: { isPrimary: true, deletedAt: null })` — the partial-unique technique, verbatim, at that line.

### 3.4 Isolated slip or systemic habit?

**Systemic habit — but the authors demonstrably know better, which changes what the fix should target.** The decisive evidence is that both shapes co-exist _inside the same file_: broken `markBackupCodeUsed` at `Cust:104` and correct `claimTotpStep` at `Cust:152`, 48 lines apart. Same for `OutboxClaimService` (textbook claim `:88`, predicate-less release `:111`). Same for `schema.prisma` (partial unique at `:824`, none for structurally identical flags elsewhere).

The trigger appears to be **whether the author is holding a fact or an object.** Every safe site writes a row-level fact and naturally reaches for a predicate. Every vulnerable site is holding a domain object — an entity, a JSON map, an aggregate snapshot — and "saving the object" never prompts _what am I claiming?_

**What this means for scope.** Do **not** widen this change to all five sites — that trades a contained HIGH fix for a sprawling one. Instead:

- **This change:** P-1 only (2 adapters + port + double + tests), plus a **fitness function** that catches the class mechanically: _a Prisma `update`/`updateMany` whose `data` sets a consumption or terminal marker (`*UsedAt`, `*Token: null`, `consumed*`, `claimedAt: null`, `processed: true`) MUST name that same column, or the claimed sub-resource, in its `where`._ That grep catches P-1, P-2, P-3, P-5.
- **File immediately, separately, high priority:** P-2 and P-3. P-3 is a **live production defect** (customer password reset silently no-ops) independent of any race, and it should not wait behind an MFA change.
- **Backlog:** P-5, P-10.

> **Honesty about coverage.** The adversarial pass verified P-1, P-2, P-3, P-5, P-10 and the four schema citations line-by-line. A further eight candidate sites were reported by the pattern angle (event-store global `sequence`, "exactly one active/default" in template versions and approval workflows, JS-side `+1` on version and webhook retry counters, OAuth `state` get-then-delete, CRM disconnect, encryption key version) and were **not** independently verified. Treat them as leads for the fitness function's first run, not as findings.

**Tenancy — the non-obvious part.** `TENANT_SCOPED_MODELS` (`infra/prisma/src/extensions/tenantGuard.ts:91-150`) contains `customerUser`; `AdminUser` is global. The guard bypasses any model not in the Set, and bypasses again under a system context. **Customer MFA verification runs under `withSystemContext("customer-mfa-login")` (`apps/api/src/auth/customerAuthRoutes.ts:237`), so layer-1 tenant scoping is already inert during backup-code consumption today, and will be under either shape.** The only scope is `userId`, resolved from a signed challenge. Design must state this rather than assume the guard protects the claim.

The sanctioned way to give a claim table zero tenancy cost is the transitive precedent: `rls-tenant-isolation.test.ts:188` — _"`Post` (transitively scoped) does NOT have RLS enabled."_ A claim table with **no `accountId`**, tenancy implied through `customerUserId → CustomerUser.accountId`, needs zero guard entries, zero RLS migration, and does not disturb the bidirectional guard↔policy parity assertions (`rls-tenant-isolation.test.ts:149-177`).

**ADR-0020 (tenant-context-at-boundaries)** binds the fix against adding _any_ new `withSystemContext` call site in business or repository code. A claim table that threw `TenantContextMissingError` at login would tempt exactly that patch.

**ADR-0020 (audit-actor-exclusive-arc)** is _relevant but not binding._ It adjudicated the polymorphic actor columns of `AuditLog`, not a backup-code claim table. Applying its exclusive-arc ruling (`num_nonnulls(...) <= 1` + two nullable FKs, per Karwin _SQL Antipatterns_ ch. 7) to a hypothetical `MfaBackupCodeUse` is a **defensible inference from repo canon, not a prior decision on this question**, and the design should not present it as one. Two separate tables avoid the question entirely.

**ADR numbering collision, must be repaired:** `docs/technical/` contains **both** `ADR-0020-audit-actor-exclusive-arc.md` and `ADR-0020-tenant-context-at-boundaries.md`. Any ADR this change writes is **0021**, and the collision should be flagged.

**No MFA ADR exists.** `docs/technical/` holds ADR-0001..0020 with no MFA entry; the only trace of the MFA consolidation is `NORMALIZATION_ROADMAP.md:582`. The single-use model was never adjudicated in a document a canon reviewer could check against — which is a structural reason a wrong CAS could ship with a confident comment.

**Squawk migration rules — read the gate honestly.** `.squawk.toml` sets `assume_in_transaction = true` (`:16`) and excludes `adding-required-field` (`:9-13`). Neither shape trips a destructive rule (shape A is `CREATE TABLE` + indexes on a new empty table; shape B is `ADD COLUMN ... DEFAULT`, metadata-only on PG11+, and `docker-compose.yml:6` pins pg16). **But the gate is advisory, not blocking:** `.github/workflows/audit.yml:212-213` pipes into `squawk ... || echo "::warning::"` under `set +e` (`:209`), while `:16` of the same file advertises _"fail on critical rules."_ Do not rely on Squawk to catch a bad migration. Its detector also uses `git diff HEAD~1 HEAD`, which on a direct push misses a migration in any but the last commit.

**Migration conventions.** 12 of 68 migration directories carry a hand-written `down.sql` — a good minority convention, **not** a repo-wide invariant. Shipping one here is a deliberate choice worth making, not an existing rule the change must obey.

**Sensitive-edit gated paths** (`.claude/hooks-py/pre_edit.py:22-32`, unblocked by a 15-minute `omnipost-allow sensitive-edit` token, audited to `.claude/heuristic-overrides.log`): `infra/prisma/schema.prisma`, `infra/prisma/migrations/**`, and `.github/workflows/**` if the Squawk honesty fix is taken. Everything else the fix touches is ungated.

**External standard.** [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/) governs backup codes as _look-up secrets_, §3.1.2:

- **§3.1.2.2** — _"A secret from a look-up secret authenticator SHALL be used successfully only once."_ ← the violated clause.
- **§3.1.2.2 storage** — _"SHALL be stored in a salted and hashed form using a suitable password hashing scheme"_, salt ≥ 32 bits. **Satisfied** (`passwordHashing.ts:30-36`).
- **§3.1.2.1 / §3.1.2** — approved RBG; _"at least six decimal digits (or equivalent)"_. **Satisfied** — `crypto.randomBytes(4)` (`MfaService.ts:45`, `:451`) = 32 bits, clearing both that ≈19.9-bit floor and [OWASP ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md) §6.5.4's 20-bit floor.
- **§3.1.2.2 → §3.2.2** — _"the verifier SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100 by disabling that authenticator."_ **Partially satisfied** — see §5.

The OWASP Multifactor Authentication Cheat Sheet mentions recovery codes only in passing and carries no technical requirements; cite NIST + ASVS, not it.

## 6. Fix-shape recommendation

### Shape (A) — claim table, unique index, claim = insert

```prisma
model CustomerMfaBackupCodeUse {
  id        String   @id @default(uuid())
  userId    String
  codeIndex Int
  usedAt    DateTime @default(now()) @db.Timestamptz(6)
  user      CustomerUser @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@unique([userId, codeIndex])
  @@index([userId])
}
// + AdminMfaBackupCodeUse, identical, → AdminUser
```

Claim = `createMany({ data: [{ userId, codeIndex, usedAt }], skipDuplicates: true })`; `count === 0` → `ALREADY_USED`.

| For                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Against                                                                                                                                                                                                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Atomicity is enforced by a unique index**, i.e. by the storage engine — independent of query plan, isolation level, and whatever SQL Prisma emits. This is the _only_ candidate whose correctness needs no interleaving argument                                                                                                                                                                                                                                         | New table(s), migration + backfill                                                                                                                                                                                                       |
| **Forensics restored by construction.** One row per claim, `usedAt` immutable because a second insert conflicts instead of overwriting. G1 and G2 both close                                                                                                                                                                                                                                                                                                               | Requires a subject decision (two tables vs one with the exclusive arc) since `AdminUser` and `CustomerUser` are separate tables                                                                                                          |
| Tenancy costs **zero** on the `Post` transitive precedent: no `accountId`, no `TENANT_SCOPED_MODELS` entry, no RLS migration, no parity churn — and the write path bypasses both layers anyway (§4)                                                                                                                                                                                                                                                                        | **G10 is merge-blocking**: `replaceBackupCodes` and `clearMfa` must delete the subject's claim rows in the same transaction or regeneration bricks MFA. This is the two-column-agreement hazard relocated, not escaped — say so out loud |
| Pure typed Prisma; no fitness #23 exception. `skipDuplicates` is the right primitive over `catch(P2002)`: the claim runs inside `$transaction` (`MfaService.ts:239`) alongside the audit write, and a raised P2002 aborts the Postgres transaction (25P02) — catching it in TS does not un-abort it, and the later COMMIT silently degrades to ROLLBACK. `createMany({skipDuplicates:true})` emits `INSERT ... ON CONFLICT DO NOTHING`, returns `count: 0`, raises nothing |                                                                                                                                                                                                                                          |
| **Additive and revertible**: keep `mfaBackupUsedAt` as a shadow write, drop it in a second migration after a soak                                                                                                                                                                                                                                                                                                                                                          |                                                                                                                                                                                                                                          |
| Only shape that can later carry per-use `ip` / `userAgent`                                                                                                                                                                                                                                                                                                                                                                                                                 |                                                                                                                                                                                                                                          |
| Growth bounded at ≤8 rows per enrolled user (`adminAuthConfig.ts:40`)                                                                                                                                                                                                                                                                                                                                                                                                      |                                                                                                                                                                                                                                          |

### Shape (B) — `Int[]` ledger

`updateMany({ where: { id, NOT: { mfaBackupUsedIndexes: { has: idx } } }, data: { mfaBackupUsedIndexes: { push: idx } } })`.

| For                                                                                                                                                                                                                                                                                                                 | Against                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Smallest diff — one column per table, no new model, no tenancy question at all                                                                                                                                                                                                                                      | **It discards the timestamp entirely**, so G1 is not fixed, it is deleted. Keeping `mfaBackupUsedAt` alongside re-creates two sources of truth for one fact — the modelling error that produced this bug                                                                                                                                          |
| Predicate names the claimed resource and is monotone (append-only; `has` never becomes false)                                                                                                                                                                                                                       | **Its atomicity is unverified.** If Prisma emits `UPDATE ... WHERE id IN (SELECT id FROM t WHERE ...)`, the RC EvalPlanQual recheck re-runs the sub-select against the **original snapshot** — the anomaly PostgreSQL documents under Read Committed — and both racers pass. Nobody in this repo has captured the emitted SQL                     |
| API support confirmed from the generated client, not docs: `CustomerUserUpdateManyMutationInput.mfaBackupCodes?: CustomerUserUpdatemfaBackupCodesInput \| string[]` and `= { set?; push? }`, and `StringNullableListFilter` has no field-level `not` (negation must be `NOT: { col: { has } }` at WhereInput level) | Nullable-array footgun: `NOT (i = ANY(NULL))` is NULL → no match → `count 0` → `ALREADY_USED` → **permanent, silent, irreversible lockout** for that user. Fail-closed, but undiagnosable. (Mitigated in practice: every scalar list in this schema is non-nullable in the Prisma model, so this is a one-line assertion rather than a live risk) |
| In-place backfill from the JSONB keys                                                                                                                                                                                                                                                                               | Inherits the positional-identity and split-state modelling errors                                                                                                                                                                                                                                                                                 |

### Recommendation: **(A)**

The decisive argument is not elegance, it is **provability**. This code is already the second attempt: `7b245e3e` shipped a plausible concurrency argument, wrote a test for the interleaving that argument covered, and left the wider one open. Shape (B) asks the reviewer to accept another concurrency argument that rests on an unverified property of generated SQL. Shape (A) asks the reviewer to accept that a unique index is unique. For a HIGH security control with this history, the shape whose correctness requires no argument is the right one — and it is also the only one that restores the forensic evidence the defect destroys.

Concretely: **two tables** (not the exclusive arc — that ADR ruled on `AuditLog`, not this, and two tables make the unique key say exactly what it means and keep `ON DELETE Cascade` honest), **no `accountId`** (transitive tenancy per the `Post` precedent), claim via `createMany({skipDuplicates:true})`, mandatory `deleteMany` in `replaceBackupCodes` and `clearMfa` inside the same transaction, and `mfaBackupUsedAt` retained as a shadow write until a second migration drops it.

**What would change my mind**

1. **A captured `$on('query')` trace showing Prisma emits the plain `UPDATE ... WHERE ...` form for `updateMany`.** That settles (B)'s atomicity _and_ retro-validates `claimTotpStep`. With atomicity proven, (B)'s smaller diff and its immunity to G10 become genuinely attractive — but only paired with an explicit decision to lose or replicate the per-use timestamp. **This capture is worth doing regardless of which shape is chosen**, because if the answer is the sub-select form, `claimTotpStep` is racy and this exploration has surfaced a second HIGH two fields away in the same schema.
2. **A stakeholder requirement for per-use forensic metadata** (ip, user-agent) — (A) becomes not merely preferable but the only option.
3. **An unexpectedly large or dirty backfill population.** I could not measure it (no DB credentials reachable from this session; `.env` reads are policy-denied and the `CLAUDE.md`-documented `postgres:password123` does not authenticate against the homelab instance). Design should run: `SELECT count(*) FROM "CustomerUser" WHERE "mfaBackupUsedAt" IS NOT NULL AND "mfaBackupUsedAt" <> '{}'::jsonb` (and the `AdminUser` twin) before committing to a shape.

## 7. Deterministic red test

**The cheapest possible red test has been one line away, in a file that runs on every PR, and nobody wrote it.**

### Tier 1 — unit, merge-blocking gate

`apps/api/tests/unit/infrastructure/adapters/PrismaCustomerMfaUserRepository.test.ts`, mirrored in the Admin twin. Vitest, zero DB, zero timing, zero concurrency. Collected by `vitest.config.ts` (`tests/unit/**`) and sharded in `ci.yml`, so it gates every PR today.

The fake already in the file is **faithful**: `updateMany` at `:105-127` genuinely evaluates the real predicate through `usedAtEqualsMatches` (`:55-68`, decisive line `:67` `JSON.stringify(stored ?? {}) === JSON.stringify(equals)` — exactly Postgres JSONB equality). The `beforeEach` seed at `:154` already stores `mfaBackupUsedAt: { "0": "2026-01-01T00:00:00.000Z" }`. The existing merge test at `:305-315` deliberately marks index **1**. Ask for index **0**:

```ts
// in describe("markBackupCodeUsed")
it("returns ALREADY_USED when the index is already present in the used-map", async () => {
  // Single-use is a property of THE CODE, not of "nobody wrote this column
  // since my read". A second consumption of index 0 must be refused with no
  // concurrency at all.
  const result = await repo.markBackupCodeUsed(
    "customer-1",
    0,
    new Date("2026-02-02T12:00:00.000Z")
  );

  expect(result.ok).toBe(false);
  expect(!result.ok && result.error).toBe("ALREADY_USED");
});

it("preserves the first-use timestamp when a second consumption is refused", async () => {
  // The reuse alarm and any incident timeline depend on the winner's
  // timestamp surviving the loser's attempt.
  await repo.markBackupCodeUsed("customer-1", 0, new Date("2026-02-02T12:00:00.000Z"));

  expect(rows.get("customer-1")?.mfaBackupUsedAt).toEqual({ "0": "2026-01-01T00:00:00.000Z" });
});
```

**Why it is red 10/10 today, analytically forced.** Snapshot read returns `{"0": t1}`; `usedMap` becomes `{"0": t2}`; the predicate is `equals {"0": t1}`, compared against the value just read — trivially equal — so `count === 1`, `:116` returns `ok(undefined)` and the stored timestamp is `t2`. Both assertions fail. No pool, no scheduler, no Postgres involved.

**What it does and does not prove.** It proves the adapter's _control flow_ is wrong today and that the fix changes behaviour. It cannot prove the DB-level atomicity guarantee — and under shape (A) the fake changes shape entirely (the adapter stops touching the user row). That is why Tier 3 is mandatory, not optional.

### Tier 2 — port conformance, unit

There is no suite binding `InMemoryMfaUserRepository` and the two Prisma adapters to `MfaUserRepositoryPort`. Three implementations, two different semantics, nothing comparing them (§2, G11). Add a shared contract suite executed once per implementation, with sequential-reuse as its **first** assertion. This is what prevents the next instance of the same divergence.

### Tier 3 — integration, node:test, real Postgres, **and it must be wired**

Add to `mfaBackupCodeSingleUse.integration.test.ts`:

```ts
it("adapter: a second mark of the same index is refused and does not overwrite the first timestamp", async () => {
  // Staggered, not simultaneous: the SECOND snapshot read happens strictly
  // AFTER the first write commits — the interleaving Promise.all cannot
  // produce and the one an attacker pacing two logins produces every time.
  const first = await customerRepo.markBackupCodeUsed(
    customer.id,
    0,
    new Date("2026-04-04T10:00:00.000Z")
  );
  assert.strictEqual(first.ok, true);

  const second = await customerRepo.markBackupCodeUsed(
    customer.id,
    0,
    new Date("2026-04-04T10:00:05.000Z")
  );
  assert.strictEqual(second.ok, false);
  assert.strictEqual(!second.ok && second.error, "ALREADY_USED");

  const row = await prisma.customerUser.findUniqueOrThrow({ where: { id: customer.id } });
  assert.deepStrictEqual(row.mfaBackupUsedAt, { "0": "2026-04-04T10:00:00.000Z" });
});
```

and three repairs to the existing file: give the two racers at `:95-99` **distinct** timestamps so the assertion at `:107` stops being a tautology; inject the real `PrismaUnitOfWork` into the `MfaService` constructed at `:118` so the test runs production's transaction shape; and replace the service-level `Promise.all` (`:132`) with a **barrier-injected repository decorator** that blocks between `MfaService.ts:199` and `:240`, releasing only after the first verification commits — reproducing "two verifications mint two sessions" deterministically rather than relying on a millisecond window.

**Wiring is part of the fix, not a follow-up.** The file is currently referenced by no collector. Add it to a `run_batch` list in `apps/api/scripts/run-tests.sh` — do not hand-roll a `node` invocation, because `--conditions development` (fitness #27 Part A) comes free from `run_batch` and is lost otherwise. That script sources the root `.env` into the exported environment before spawning, which is how env reaches the per-file children.

**On the reported timings.** The brief's "deterministic under a 5-30 ms stagger" and the "1/10 flake" are not reproducible from the tree — there are no CI samples for a suite that has never run, and no measurement is recorded anywhere. The mechanism above _predicts_ both, and the Tier 1 test makes the frequency question moot for merge-gating purposes. If the proposal cites either number, this change should measure and record it.

## 8. Open questions for propose/design

1. **Shape (A) or (B)?** I recommend (A) with the reasons and the mind-changers in §6. This is design's call, and it is the only genuine fork of consequence.
2. **Under (A), one table with the exclusive arc, or two tables?** I lean two — ADR-0020's ruling is about `AuditLog` actor columns, and applying it here is inference, not precedent. The counter-argument (one canonical shape for polymorphic association across the repo) is legitimate.
3. **How does regeneration reset the claim namespace: `deleteMany` in the same transaction, or a generation/epoch column in the unique key?** Deleting is simpler and loses claim history; an epoch preserves it and widens the key. G10 makes this merge-blocking either way.
4. **Is per-use forensic metadata (`ip`, `userAgent`) required?** The answer decides whether (A) is preferred or mandatory.
5. **Does the port signature keep `codeIndex`?** Positional identity is the root modelling error (§2). Keeping it bounds the diff to one method; replacing it with a code identity is the correct destination but a much larger surface for a HIGH security fix. My read: keep `codeIndex`, record the entity model as the target state.
6. **Do P-2 and P-3 ride this change or ship separately?** I recommend separately and immediately — P-3 is a live functional bug in a different subsystem (customer password reset silently no-ops), not a race, and folding it in couples two independent risks.
7. **Does `claimTotpStep` get the emitted-SQL verification in this change, or is it its own item if it fails?** The capture is cheap; the consequence of a negative result is a second HIGH.
8. **Wiring the orphan suites: only `mfaBackupCodeSingleUse`, or all five?** Wiring one may surface failures in the others; SMELL-75 warns of exactly that.

## 9. Risks

**Data-loss risks in backfill**

- **Silent claim loss.** `normalizeUsedAt` (`Cust:22-29`, `Admin:20-27`) filters non-string _values_ but never validates _keys_, so the JSONB may contain non-numeric keys. A backfill guarded by `kv.key ~ '^[0-9]+$'` would **silently drop** such an entry — un-consuming a code. Count the anomalies first and either fail the migration on any non-numeric key or quarantine them; do not filter quietly.
- **Backfill volume is unknown** — the count query could not be run from this session (§6). A migration written blind against an unmeasured population is a risk in itself.
- **Dropping `mfaBackupUsedAt` in the same migration makes rollback lossy.** Two migrations, with the read-path cutover soaked between them.
- **Squawk will not catch a bad migration** (`audit.yml:212-213` swallows the exit code). Manual review is the actual gate.

**Correctness risks in the fix**

- **Regeneration lockout (G10)** — the single most likely way to ship shape (A) broken: stale claim rows make all 8 fresh codes return `ALREADY_USED`, i.e. a total, silent account lockout. Must have its own test.
- **Nullable-array lockout** under shape (B) — same failure mode from a different cause.
- **A second wrong fix.** The current code is the first fix, shipped with a concurrency argument that was correct about the window it closed and silent about the one it left. Any new argument must state which interleavings it covers, and Tier 3 must exercise the one it claims to close.
- **The double masks the fix.** If `InMemoryMfaUserRepository.ts:107-109` is not brought into line with the new mechanism, the new tests can pass green against a fake while production regresses — the exact failure mode that let this ship.
- **`replaceBackupCodes` / `clearMfa` racing a claim** (§2) is a second, independent correctness defect in the same predicate, untested in either direction. Whatever shape wins should close it or explicitly declare it out of scope.

**Process risks**

- **Sensitive-edit gate** blocks `schema.prisma` and `infra/prisma/migrations/**` without an `omnipost-allow sensitive-edit` token, which is audited and carries an ADR follow-up obligation. Plan for it rather than tripping it mid-apply.
- **Wiring `mfaBackupCodeSingleUse` may turn other orphans red** if the batch is widened (SMELL-75). Budget for it or wire exactly one file.
- **Scope creep from §3.** The pattern is systemic and the temptation to fix all five sites is real. The disciplined answer is one site plus a fitness function that catches the class, and separate high-priority filings for P-2 and P-3.
