# Proposal — `ci-live-tier-integrity`

---

## 1. Why this change exists

`main` is red. `integration:saga-live` reports `14 tests / 11 pass / 3 fail`, and the three failures are not slow — they are three exact burns of the 120 000 ms per-test budget with zero partial progress (`apps/api/tests/integration/sagaCustomerFlow.test.ts:306, 339, 608`).

**The mechanism, end to end.** The CI push tier boots exactly one process: `pnpm --filter @apps/api dev:test &` (`.github/workflows/ci.yml:342`), health-gated on `http://localhost:3000/health` (`:344`). The API is a _producer_ of publish jobs; the only consumer of `QUEUE_NAMES.PUBLISH` in the repo is `apps/workers/src/publishWorker.ts:194`. **No workflow in this repo has ever started `apps/workers`** — every match for `apps/workers` under `.github/workflows/` is a fitness-grep string (`fitness.yml:197, 272, 400, 454, 587, 606`), never a boot. So the jobs the three tests enqueue sit in BullMQ `waiting` forever; the queue adapter counts anything not `completed`/`failed` as pending (`packages/adapters/queue-bullmq/src/queue-adapter.ts:211-213`); the wait step therefore returns `{ outcome: "waiting" }` on every entry (`packages/shared/src/saga.ts:811-815`); and the engine, correctly, re-arms the poll and spends **no retry budget** (`apps/api/src/saga/SagaManagerExecution.ts:515-540`). The only remaining terminalizer is the 30-minute saga horizon (`packages/shared/src/saga.ts:1006`, swept on a 60 s tick) — **1815 s measured, against a 120 s budget. A 15× gap.** No runner speed closes it.

**The fact that reverses the intuition.** PR #184 did not break this. Before #184 the same "no consumer" condition was returned as a step _failure_ (`git show 699be4ff:packages/shared/src/saga.ts:743-745`), which spent the post-pivot retry budget — 5 + 10 + 20 s — and produced a **false `FAILED` in ~35 s** that `waitForTerminal`'s terminal set happily accepted. **The tests were green because of a bug.** #184 removed that bug; what it exposed is a CI tier that has never been able to exercise the publish path. The proof is an A/B on the same commit `8e89b21f`, only variable = workers: without → 11/14, three at ~120 s; **with → 14/14 in 170.3 s**.

**Production is unaffected and the engine is correct.** Measured in `api.log`: worker-free sagas terminalize on their own at the horizon (`reason: "timeout"`, Δ = 1815.4 s), and sagas parked 22 minutes resumed and terminalized within seconds of a worker draining the queue (`reason: "step-failure"`). Do not rewrite the engine.

**The process failure that let this land twice.** PRs get `TIER: pr-integration` (`.github/workflows/ci.yml:315`); only `push` gets `full-integration` (`:350`); and `run_live_api_batches()` — the guard on the block containing the saga-live batch — is true only for unset or `full-integration` (`apps/api/scripts/run-tests.sh:58-61`, batch at `:283-284`). So a saga-touching PR merges on evidence that **structurally excludes the saga's live path**, and the first signal arrives on `main`, after the merge. That is item `N-CI-2`, and it is in scope here.

## 3. What "done" means — observable properties

Each is a property of the running system, checkable by someone who did not write the change.

1. **The live batch is green on a push to `main` for the right reason.** `integration:saga-live` reports `14 tests / 14 pass / 0 fail / 0 cancel / exit 0`, **and** the three worker-dependent cases finish well inside the budget rather than at it — locally 59.70 s / 50.00 s / 59.65 s against 120 000 ms. A pass at ~120 000 ms is not this property.
2. **A publish consumer provably existed before the tests ran.** The workers readiness endpoint answered 200 on `:3300` before the test step opened, and the publish queue reported ≥ 1 consumer. Readiness alone is necessary but not sufficient: `/health/ready` checks only `database` + `redis` (`bootstrap.ts:140-141`); it proves the process is alive (and, because `startPublishWorker` is awaited at `:63` before `healthServer.listen` at `:222`, that `subscribe()` returned) — it does **not** prove registration on the queue. The consumer count is the only direct evidence.
3. **A worker-less environment fails fast and says why.** Run the identical job with the workers step removed: the suite aborts in **seconds** (target < 30 s) with a message naming _no consumer on the publish queue_, not `did not reach terminal state within 120000ms`. Provable by that A/B, not by assertion.
4. **No merge path exists that skips the evidence.** A PR touching any listed saga surface runs the live saga batch with workers booted, and that check is required. Checkable by opening a trivial PR against one of those paths and reading the checks.
5. **Nothing was made green by moving a number.** The diff leaves untouched: `SAGA_WAIT_POLL_MS`'s default of 30 000 (`env.ts:266`), the 30-minute horizon (`saga.ts:1006`), the `waiting` outcome (`saga.ts:811-815`), the 120 000 ms test budgets, and all 14 cases. Any CI-only poll-cadence override is visible as an env value on the CI step and nowhere else.
6. **The zero-consumer condition is observable in production, not only in CI** — a metric exists, an alert rule references it, a runbook says what to do — and the rule's expression is locked by a static test, the pattern already used for the existing saga rules (`apps/api/tests/unit/saga/sagaContextInvariants.static.test.ts:1884, 1936`). Per project rule #2, whatever is not locked by a test or check is worded as intent.
7. **The PR tier still fits its budget.** Saga-touching PRs complete inside the job's `timeout-minutes`, which today is **12 minutes for non-push** (`.github/workflows/ci.yml:221`) — or that cap is raised deliberately, with the measured number recorded.

## 4. The one decision for the owner — the alert threshold

**What already exists, and why it is not enough.** `prometheus/alerts/saga.yml` has `SagaWaitingRowsAccumulating`: `min_over_time(saga_waiting_rows[15m]) > 50`, `for: 10m` — it names this exact failure ("publish workers down or not consuming") but requires **more than 50 sagas waiting continuously for ~25 minutes**. It is volume-gated by construction. At low volume a total publish-worker outage never trips it; the affected sagas simply die one by one at the 30-minute horizon and then appear as `SagaTimeoutSpike`, which itself needs `> 3` timeouts in 10 minutes — still volume-gated, and **only after the damage**. And there is no `up{}` or `absent()` rule anywhere in `prometheus/alerts/` (verified across all three files), even though the workers scrape job already exists (`prometheus/prometheus.yml:53-58`, target `:3300`).

**Recommended: a zero-consumer rule on the publish queue, volume-independent.**

```
expr: max_over_time(publish_queue_consumers[5m]) == 0
for:  3m          # severity: critical, component: saga
```

- **Why this signal:** it catches the failure this incident actually is — _the queue has no consumer_ — including the cases a liveness probe misses: process up but subscribed to the wrong queue, or partitioned from the queue's Redis. `max_over_time` over 5 m means "no scrape in the window saw a consumer", so one failed collect does not page.
- **Why 3 minutes:** it must clear a rolling restart of the workers process and still beat the 30-minute horizon by 10×. Detection moves from ~30 min (or never, at low volume) to ~3–8 min end to end.
- **What it costs in noise:** it fires on any workers deploy whose zero-consumer window exceeds ~3 minutes. That is the same trade the repo already accepts and documents for `SagaParkedAtPivot` ("pair it with a silence for planned deploy windows") — so the mitigation is a deploy-window silence, not a longer `for`. Second cost: a new gauge on the API's collect path, i.e. one `getWorkersCount()` round-trip per scrape (10 s interval, `prometheus.yml:37-39`).
- **Honest limit:** with `alerting:` still commented out (`prometheus/prometheus.yml:12-18`), the rule evaluates and is visible on `/api/v1/alerts` but **pages nobody** until `§4.2.b` wires Alertmanager. What this change backs with a test is that the metric and the rule exist and the expression is the one written down; "an operator hears about it" is intent until routing lands.

**Alternative, if the owner prefers zero new metrics:** lower `SagaWaitingRowsAccumulating` from `> 50` to a small threshold. Cheapest possible, but it stays volume-coupled — it would fire on ordinary bursts (one slow provider holds waiting rows legitimately), and it still cannot distinguish "slow" from "nobody is consuming". I do not recommend it as the primary.

**Confirm:** the signal (`publish_queue_consumers == 0`) and the `for: 3m` window — or name a different window and I will carry it into the spec.

## 5. Risks — implementation only

1. **CI cost.** PR-tier Integration Tests today: **2 m 57 s**. Push-tier on the last green `main`: **6 m 02 s**. The saga-live batch alone: 98.5 s pre-#184, 362.3 s in the failing state, **170.3 s locally with workers** — expect it to roughly double once the tests take their real path. So **+3 to +4 minutes on saga-touching PRs**, path-filtered off every other PR. Against that: the current split has already cost two red merges on `main` and a full diagnosis session.
2. **The 12-minute PR job cap** (`ci.yml:221`) becomes binding. 2 m 57 s + boot + a real live tier lands near 9–10 min with little margin. Either the cap is raised deliberately with the measured number, or the PR gate runs a narrower batch set (the explore's smoke fallback: API + workers + only the three worker-dependent cases, ~3 min). **Do not settle for "run saga-live on PRs without workers"** — that is today's failure with extra steps. Which shape to take is a design-phase decision, not an owner one.
3. **Headroom on a shared runner.** Measured with workers: 59.70 s / 59.65 s against 120 s — on a homelab. A GitHub 4-vCPU runner will now host API + workers + Postgres + Redis + the test process. The tail is _quantized_: a missed completion event costs one full `SAGA_WAIT_POLL_MS` (30 s), so one miss → ~90 s (inside budget), two → ~120 s (at the edge). If it proves tight, the lever is `SAGA_WAIT_POLL_MS` **in the CI env only** (floor 1000, `env.ts:266`) — never the budget, never the default, never the horizon.
4. **The workers fail to boot, silently.** They require `DATABASE_URL`, `REDIS_URL`, `PLATFORM_ENCRYPTION_KEY` (`apps/workers/src/config/env.ts:52-62`) and load `.env.test` under `NODE_ENV=test` (`:21-22`); CI's synthesized `.env.test` carries all three (`scripts/ci-setup-test-env.sh:26-35`), so the boot should succeed — but a background `&` boot whose process dies is invisible without the gate. **The readiness gate must fail the job at that step**, or the failure reproduces exactly today's symptom with an extra step in the log. Same class of trap: probing `:3000` instead of `:3300` would pass with zero workers.
5. **Env drift between the two boot steps.** The API step sets `ENABLE_RATE_LIMITING: "true"` (`ci.yml:340`) for reasons specific to `integration:flows`; the workers step needs its own env block, not a copy.
6. **Resource pressure.** The test process already runs at `--max-old-space-size=6144` (`ci.yml:349`) on a 7 GB runner now split four ways, and the workers open their own Redis connections (`publishWorker.ts:186-188`). An OOM-kill of the workers mid-suite would present as _exactly_ the failure we are fixing — which is the argument for the consumer probe from property 3 running as a precondition, not only once at boot.
7. **A required live check enlarges flake blast radius.** Any live-tier flake now blocks every saga-touching PR. The batch is `CONCURRENCY=1` (`run-tests.sh:283`) and deterministic, but the surrounding live block has known cross-batch interference (the rate-limiter reset `wait_for_api` after `integration:flows`) — another reason the PR gate may want the narrow batch set rather than the whole tier.
8. **Making the API's readiness depend on worker presence would be a cascade.** If the consumer probe is wired into the API's `/health/ready` as a _critical_ dependency, a worker outage would flip the API to unhealthy and could take traffic down for a queue problem. The probe must be observable (metric + a non-critical or dedicated surface) without becoming an API liveness dependency.
