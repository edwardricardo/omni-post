# Design: PR2b — Customer Login MFA Challenge (mfa-consolidation, N-SEC-5)

> Companion design. The parent `design.md` governs PR1/PR2/PR3 (unified MFA service, customer persistence, backfill/retirement); this document governs ONLY the PR2b slice: the customer login MFA challenge, its companion TOTP single-use fix, the client-portal challenge UI, and the retirement of the orphan `POST /auth/mfa/verify`.

## Technical Approach

Owner-decided B/C hybrid (exploration-pr2b.md §Recommendation): step 1 (`POST /auth/customer/login`) stops minting a session when `targetUser.mfaEnabled` (`CustomerUser.ts:275`) and instead issues a short-lived signed `customer-mfa-challenge` JWT (carries `sub` + `accountId` + `jti` + IP/UA binding hashes); a NEW step-2 endpoint `POST /auth/customer/login/mfa` verifies challenge + TOTP/backup code under `withSystemContext` and mints the real session. Single-use is enforced SERVER-SIDE by atomically consuming the `jti` from a Redis-backed allowlist — the JWT alone is never trusted for replay protection. The gate is **fail-closed** end to end: a store outage blocks MFA logins by design, in deliberate contrast to the rate limiter's fail-open posture (`httpRateLimitPreHandler.ts:261-274`) — the limiter is an availability control (fail-closed would be a DoS amplifier, ADR-0015 §7); an MFA gate is an authentication control (fail-open would silently bypass the second factor).

Ships inside PR2b (owner-decided): the CRITICAL TOTP single-use fix (`MfaService.verifyMfaToken` TOTP path returns success without marking use, `MfaService.ts:197-199`; window ±2, `TOTP_WINDOW = 2` at `MfaService.ts:31` → ~150s replay; NIST SP 800-63B §5.1.5.2, OWASP MFA Cheat Sheet), the client-portal challenge UI + `authApi` step-2 wiring, the BF success-recording reorder, and the orphan route retirement.

**Citation caveat**: WebFetch was not available in the design session's toolset. RFC 8725 (BCP 225), NIST SP 800-63B, RFC 6238 and OWASP cheat-sheet citations below are from assistant knowledge with section numbers, labeled `[knowledge]`; the gate reviewer should spot-check section numbers via fetch. All `file:line` claims were verified at source in this session.

## Architecture Decisions

### Decision 1: Challenge single-use store — NEW dedicated `MfaChallengeStorePort`, allowlist model, atomic DEL-count consume (NOT a CachePort extension)

**Choice**: A new technology-free port `packages/ports/src/MfaChallengeStorePort.ts` with two methods (`issue`, `consume`, contracts below). Model is an **allowlist**: step 1 registers the `jti` with TTL; step 2 consumes it atomically. Redis adapter (`RedisMfaChallengeStoreAdapter`, composition-root-constructed on a dedicated `createRedisConnection()` — the exact pattern of the BF adapter at `setupServices.ts:839-855` and the token-bucket limiters at `:270-289`): `issue` = `SET key "1" EX ttl NX`; `consume` = `DEL key` — DEL returns the number of keys removed, so `1` means THIS caller uniquely consumed it and `0` means already-consumed/expired/never-issued. Single-command atomicity, no Redis ≥6.2 GETDEL requirement, no Lua. Errors are typed `err("STORE_ERROR")` — never swallowed. In-memory variant for unit tests lives in `apps/api/tests/unit/helpers/InMemoryMfaChallengeStore.ts` (trivially atomic: Node's single-threaded event loop + no `await` between the `Map.has` check and `Map.delete`).

**Alternatives considered**:

| Option                                                                                             | Why rejected                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Extend `CachePort` with `consume`/`getAndDelete`                                                   | Three verified mismatches. (1) **Error policy**: the Redis adapter's documented contract is "cache failures degrade silently" — `get` errors become misses (`redis-cache-adapter.ts:10-15, :31-38`), `delete` is best-effort (`:87-92`). An MFA consume must propagate errors loudly (fail-closed). One port with two contradictory error policies is a trap for the next consumer. (2) **L1 tiering**: `TOKENS.CachePort` wraps the L1(in-process LRU)+L2(Redis) manager (`redis-cache-adapter.ts:3-8`, `setupServices.ts:362-372`); a get+delete consume can be served from another pod's L1 within its local TTL — a cross-pod double-accept window far larger than the get/delete race itself. An atomic consume would have to bypass L1, i.e. bypass the very thing the port wraps. (3) **Semantics**: a cache is by definition evictable/reconstructible; a single-use consumption registry is the source of truth. LOGGING_CANON's "cross-pod cached state MUST go through TOKENS.CachePort" governs _caches_; this is security state, whose sanctioned precedent is a dedicated port + Redis adapter (`BruteForceProtectionPort` → `RedisBruteForceAdapter`, `setupServices.ts:835-855`; `RateLimiterPort` → `RedisTokenBucketRateLimiter`, `:270-289`). |
| get+delete over `CachePort`                                                                        | Race: two concurrent step-2 requests both `get` → both pass → both `delete` → double session mint from one challenge. The window is milliseconds server-side, but the L1 issue above widens it to seconds cross-pod, and NIST/OWASP single-use is absolute — a known race in an MFA gate does not ship.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| DB-persisted (reset-token style, `CustomerUser.setResetToken` precedent `CustomerUser.ts:477-502`) | Works and is transactional, but costs a row write per MFA login on the hot auth path, needs schema + expiry sweep semantics, and the challenge is by design ephemeral (≤180s). Redis TTL is the natural fit; DB persistence buys durability the artifact must NOT have (a challenge surviving a restart is a non-goal).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Denylist (record consumed jtis; JWT otherwise self-sufficient)                                     | A Redis flush/outage REOPENS the replay window (fail-open on data loss). The allowlist inverts it: flush kills pending challenges → users restart login → fail-closed. Decisive.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

**Fail-closed semantics, exactly**: `issue` fails (Redis down at step 1) → `LoginCustomerUseCase` returns new error `MFA_UNAVAILABLE` → route maps to **503** `{ error: "MFA_UNAVAILABLE", message: "Unable to complete multi-factor login right now. Please try again." }` + structured WARN `threat_type: "mfa_challenge_store_unavailable"` (mirror of the fail-open WARN convention at `httpRateLimitPreHandler.ts:269-272` — the posture differs, the telemetry discipline is the same; operational alerting on this signal is REQUIRED). `consume` errors at step 2 → same 503/WARN; `consume` returns `NOT_FOUND` → 401 `INVALID_CHALLENGE` (see Decision 6). Only `mfaEnabled` customers are affected during an outage; admin login and non-MFA customer login never touch the store. Fitness #14 unimplicated: the only `Map` lives in a test helper (`#14` scopes `apps/api/src` and excludes tests).

### Decision 2: TOTP single-use — DB column `mfaLastUsedTotpStep Int?` on BOTH subject tables + conditional-update claim

**Choice**: Track the last ACCEPTED TOTP time step per subject in the database. Schema: `AdminUser.mfaLastUsedTotpStep Int?` + `CustomerUser.mfaLastUsedTotpStep Int?` (nullable, no default → metadata-only ALTER on PostgreSQL 11+, same argument as parent design Decision 3; step = `floor(epochSeconds/30)` ≈ 5.9e7, comfortably `Int`). Port change: `MfaUserRecord` gains `mfaLastUsedTotpStep: number | null`; `MfaUserRepositoryPort` gains `claimTotpStep(userId, step): Promise<Result<"CLAIMED", "NOT_FOUND" | "ALREADY_USED">>`. Both Prisma adapters implement it as a **conditional `updateMany`** — `where: { id, OR: [{ mfaLastUsedTotpStep: null }, { mfaLastUsedTotpStep: { lt: step } }] }` — count `1` = claimed; count `0` = disambiguate via `findById` (missing → `NOT_FOUND`, else `ALREADY_USED`). The conditional single-statement UPDATE is the concurrency control: under READ COMMITTED, Postgres row-locks the UPDATE and the loser re-evaluates the WHERE after commit → exactly one claimer per step, no explicit transaction needed.

`MfaService.verifyMfaToken` TOTP path (`MfaService.ts:197-199`) becomes: `verifyTotp` ok → compute accepted step via `authenticator.clone({window: TOTP_WINDOW}).checkDelta(token, secret)` (`clone` precedent at `MfaService.ts:383`; step = current step + delta; otplib `checkDelta` API `[knowledge]` — verify signature at apply) → `claimTotpStep` → `ALREADY_USED` → audit `MFA_TOTP_REPLAY_REJECTED` (HIGH) + `err("INVALID_TOKEN")`. Rejecting `step <= lastAccepted` also rejects older-window tokens — NIST-conformant (RFC 6238 §5.2 resynchronization discipline `[knowledge]`) and never locks the user out: the next 30s step is always strictly greater.

**Alternatives considered**:

| Option                                                                  | Why rejected                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CachePort/Redis keyed `totp:used:<type>:<id>:<step>`, TTL ≈ window span | A cache flush REOPENS the replay window (the finding's exact failure mode, resurrected by an eviction); and it adds a Redis dependency to ADMIN login: fail-closed → a Redis blip blocks every TOTP login including admins (the parent design names admin lockout the highest-risk regression, design.md PR1 row); fail-open → the control evaporates exactly when attacked. The DB is already on the login critical path — the column adds NO new failure domain and is intrinsically fail-closed. |
| Reuse `mfaBackupUsedAt` JSON with a sentinel key                        | Conflates the backup-code index map with TOTP state; `regenerateBackupCodes` resets the map to `{}` (`MfaService.ts:247-251` semantics) → regenerating codes would silently reopen TOTP replay.                                                                                                                                                                                                                                                                                                     |

**Shared-service blast radius (explicit, verified)**: `verifyMfaToken`'s signature is UNCHANGED — zero mechanical churn. Behavior reaches every caller: admin login core `authServiceCore.ts:260-263`; admin-plane login `AdminAuthService.ts:132-135` (records `MFA_INVALID` BF failures `:137-143`); self-service `regenerateBackupCodes` (`MfaService.ts:240`) and `disableMfa` (`:270`) for BOTH subjects; the orphan `mfaRoutes.ts:204` (deleted in this slice); plus the NEW step-2 consumer. **Intended behavior change**: using the same TOTP for login and then immediately for disable/regenerate within the window is now rejected (NIST: a given OTP verifies once, regardless of operation); the user waits ≤30s for a fresh code. Documented + tested for both subjects. Known edge: a clock-ahead device accepted at step N+2 makes a later legit N+1 token rejectable within ~60s — accepted (conservative direction, NIST-permitted).

### Decision 3: Challenge TTL — 180s constant in the domain port, no env var

**Choice**: `export const CUSTOMER_MFA_CHALLENGE_TTL_SECONDS = 180` in `packages/core/domain/src/repositories/CustomerTokenService.ts` (@layer domain, pure number). Middle of OWASP's 2–5 min guidance for high-value short-lived artifacts `[knowledge]`. One source feeds the JWT `expiresIn` (via the signer) and the store TTL (via the use case). Precedent: `CUSTOMER_JWT_EXPIRY` is a module constant (`customerJwt.ts:42`), not env. An env var was rejected: no per-environment tuning need exists, and SECURITY_CANON's env machinery (`config/env.ts` + both `.env.example`s) buys only surface here; if operations ever needs tuning, promoting a constant to env is a 4-line follow-up. Fitness #16 unaffected (no `process.env` anywhere new).

### Decision 5: IP/UA binding — bind both, hash-only claims, HARD-REJECT on mismatch

**Choice**: The challenge JWT carries `iph` and `uah` = SHA-256 hex of the trusted client IP and of the raw `user-agent` header. Step 2 recomputes both and rejects on any mismatch with 401 `INVALID_CHALLENGE` (indistinguishable from expiry — no oracle) + structured WARN `threat_type: "mfa_challenge_binding_mismatch"`. Hash-only because the token reaches the browser: no raw IP/UA in a client-visible artifact.

**IP derivation**: NOT `request.ip` — with `trustProxy: true` (`index.ts:178`) Fastify's `request.ip` is the LEFTMOST `X-Forwarded-For` entry, which is client-spoofable; the canon derivation is the exported `resolveClientIp(...)` trusted-hop selection (`httpRateLimitPreHandler.ts:168-194`) with `env.TRUSTED_PROXY_HOP_COUNT` (`config/env.ts:256`). Both step-1 and step-2 route handlers compute `resolveClientIp` and pass it as the use-case `ip` input (also upgrading the BF forensic IP at `customerAuthRoutes.ts:142` from spoofable to trusted — deliberate, documented improvement consistent with cluster A / N-SEC-2).

**Portal reality (verified)**: both portal egress points relay the real client XFF (server action `auth.ts:62-67`; proxy `route.ts:79-81` — N-SEC-2), so IP binding is meaningful and consistent across steps. The UA the backend sees through the portal is the Next server's constant fetch UA (the proxy rebuilds headers and does NOT forward `user-agent`, `route.ts:70-73`) — so UA binding is trivially consistent for portal traffic (no false positives) and adds real binding only for direct API clients. Cheap, harmless, kept.

**Posture rationale (vs log-only / log+reject-IP-only)**: hard-reject is the fail-closed-gate posture; the false-positive cost is bounded by design — a mobile/CGNAT IP rotation mid-challenge forces ONE login restart within a ≤180s window (low probability), unlike session-binding where OWASP cautions against hard IP binding because invalidation cost is high `[knowledge]`. A stolen challenge token replayed from another host — the exact residual threat of a bearer challenge — dies at the binding check even before the jti consume.

### Decision 6: Step-2 endpoint — `POST /auth/customer/login/mfa`

**URL**: under `/auth/customer/*` (dedicated, subject-clear; owner decision #4 retires the orphan instead of repurposing). Registered in `customerAuthRoutes.ts` beside login (`:354-358` pattern), NO auth preHandler (pre-session by definition), whole handler wrapped in `withSystemContext("customer-mfa-login", ...)` — the sanctioned pre-identity path, mirroring login's `withSystemContext("customer-login", ...)` at `customerAuthRoutes.ts:131-137`.

**Zod** (in `customerAuthRoutes.ts`, local schema style like `RefreshSchema`):

```typescript
const MfaLoginSchema = z.object({
  challengeToken: z.string().min(1).max(2048),
  code: z.string().min(6).max(8), // TOTP (6 digits) or backup code (8 hex) — mirrors MfaTokenFlexibleSchema (mfaRoutes.ts:35-39)
  rememberMe: z.boolean().optional(), // consumed by the Next proxy/action cookie layer, ignored by the API
});
```

**Error taxonomy** (route `errorMap`, mirroring login's at `customerAuthRoutes.ts:148-160`; client-facing responses collapse internal granularity — anti-oracle):

| -------------------------------------------------------------------------------------------------------------------------------- | ---- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |

Please sign in again."         | One indistinguishable bucket. Which sub-case occurred lives in server logs only.                                                            |

| `INVALID_MFA_CODE`                                                                                                               | 401  | "Invalid MFA code."                                                  | No new oracle: possession of a valid challenge already proves the account existed at step 1. Challenge NOT consumed (below) — user retries. |
| `USER_INACTIVE`                                                                                                                  | 403  | "Account is inactive"                                                | Mirrors step-1 mapping (`customerAuthRoutes.ts:150`).                                                                                       |
| `RATE_LIMITED`                                                                                                                   | 429  | mirrors step-1 (`:155-158`)                                          | BF gate (per-account).                                                                                                                      |
| `MFA_UNAVAILABLE`                                                                                                                | 503  | "Unable to complete multi-factor login right now. Please try again." | Store outage — infra signal, not an auth verdict; distinct from 401 so users aren't told a correct code was wrong.                          |
| `INTERNAL_ERROR`                                                                                                                 | 500  | mirrors step-1 (`:159`)                                              |                                                                                                                                             |

**Consume-on-success (decided)**: the `jti` is consumed atomically AFTER the MFA code verifies, not before. A wrong code does NOT burn the challenge (a TOTP typo must not force password re-entry — re-typing the password more often was the core weakness of Approach A the hybrid exists to avoid). Guessing within one challenge is bounded by: per-account BF (`MFA_FAILED` failures, Decision 7), the per-IP AUTH cap, and the 180s TTL. Single-use holds under concurrency because the consume itself is the serializer: two concurrent step-2 requests with valid codes both pass verification, then race on `DEL` — exactly one gets count `1` and mints; the loser gets `NOT_FOUND` → `INVALID_CHALLENGE`. (For TOTP, Decision 2's `claimTotpStep` already rejects the second request even earlier; for backup codes — whose `markBackupCodeUsed` is a blind update, `MfaService.ts:208-214` — the jti consume is the last-line guarantee of one-session-per-challenge.)

**Rate limiting**: matching is first-`startsWith` (`httpRateLimitPreHandler.ts:205-214`), so the existing `/auth/customer/login` rule (`:107`) ALREADY prefix-covers `/auth/customer/login/mfa` with the AUTH preset — and the bucket key is `ip:path` (`:239-241`), so step-1 and step-2 get separate 5/15min buckets. An EXPLICIT entry `{ path: "/auth/customer/login/mfa", config: RateLimitConfigs.AUTH }` is still added (behaviorally a no-op) because SECURITY_CANON §How to extend #5 makes `AUTH_ROUTE_RULES` the documented inventory of credential endpoints — implicit prefix coverage is exactly how an entry silently disappears in a refactor. The `/auth/mfa/verify` rule at `:126` STAYS after the orphan retirement: it prefix-covers the LIVE `/auth/mfa/verify-setup` (comment at `:125` says so explicitly); only its comment is updated.

### Decision 7: Use-case architecture — challenge branch in `LoginCustomerUseCase` + new `CompleteCustomerMfaLoginUseCase`; MFA verification behind a new port

**Choice**: TWO use cases in `packages/core/customer-auth` (one file each, package pattern), not one use case with two entry points — the steps have disjoint inputs, outputs, and dependency sets, and a future admin migration to the challenge shape (backlog) maps 1:1 onto the second use case.

- `LoginCustomerUseCase` (modify): after the `isActive` check (`:152-160`) and transparent rehash (`:169-172` — stays put; the password was legitimately verified), branch on `targetUser.mfaEnabled`: generate `jti`, hash `iph`/`uah` from `input.ip`/`input.userAgent` (already inputs, `:33-36`), `store.issue(jti, TTL)` (fail → `MFA_UNAVAILABLE`), sign challenge, return `CustomerMfaChallengeOutput`. The MFA branch does NOT `recordLogin`/`save` (`:175-176`), does NOT `recordSuccessfulAttempt` (`:179-183`), does NOT mint (`:195-204`) — those stay only on the non-MFA path. **BF ordering fixed intrinsically**: password success is no longer terminal success. New constructor deps: `CustomerTokenService` (already injected, `:62`, extended) + `MfaChallengeStorePort` (new, appended). Return type widens to `Result<LoginCustomerOutput | CustomerMfaChallengeOutput, LoginCustomerError>`; error union gains `MFA_UNAVAILABLE`.
- `CompleteCustomerMfaLoginUseCase` (create): deps `CustomerUserRepository`, `AccountRepositoryPort`, `MfaVerificationPort` (new), `CustomerTokenService`, `MfaChallengeStorePort`, `BruteForceProtectionPort`, `UnitOfWork?` (LAST, optional — ARCHITECTURE_CANON UoW pattern). Flow: verify challenge JWT (statically) → binding check → load user by `sub` (route provides `withSystemContext`; the challenge's `accountId` claim keeps the lookup tenant-explicit) → re-check `isActive` + `mfaEnabled` → BF `checkLoginAttempt({identifier: user.email, ip, userAgent})` + honor `delaySeconds` (same identifier as step 1, `LoginCustomerUseCase.ts:88-92`, so counters aggregate per account) → `verifyMfaToken({type:"customer", id: sub}, code)`; on `INVALID_TOKEN` → `recordFailedAttempt({identifier: email, ip, userAgent, failureReason: "MFA_FAILED"})` (the port's documented intent, `BruteForceProtectionPort.ts:81-84`; NIST 800-63B §5.2.2 verifier throttling `[knowledge]`) → `INVALID_MFA_CODE` → `store.consume(jti)` (`NOT_FOUND` → `INVALID_CHALLENGE`; error → `MFA_UNAVAILABLE`) → UoW-wrapped `recordLogin()` + `save` → `recordSuccessfulAttempt` (Redis — OUTSIDE the tx per canon "no external calls inside the transaction") → fetch account JSON, mint fresh `sessionId` + access/refresh (same block as `LoginCustomerUseCase.ts:186-212`) → `LoginCustomerOutput`. Session minted only after MFA = OWASP "regenerate on privilege change" `[knowledge]`.
- **`MfaVerificationPort`** (create, `packages/ports/src/MfaVerificationPort.ts`): `verifyMfaToken(subject: MfaSubject, token: string): Promise<Result<MfaVerificationResult, MfaVerifyTokenError>>`. `MfaService` adds `implements MfaVerificationPort`, importing `MfaVerificationResult`/error union from `@ports/core` instead of its local copies (`MfaService.ts:55-58`, `:74`) — it already imports `MFA_SUBJECT_TYPE` from there (`:18`). Rationale: `MfaService` is an apps/api infrastructure service (extends `AuditableService`); a `@core` use case may depend only on ports (`LoginCustomerUseCase.ts:17` imports `@ports/core` — compile-proven seam). **No new DI token for the port**: `setupCustomerAuthUseCases` resolves the existing `TOKENS.MfaService` typed as `MfaVerificationPort` — a second token for the same instance would recreate the duality the parent change kills (parent design Decision 5 rationale).
- **Nested-transaction avoidance (explicit)**: `MfaService` runs its own UoW for `claimTotpStep`-adjacent audits and backup-code marking (`runInTransaction`, `MfaService.ts:390-396`); the step-2 use case therefore does NOT wrap the `verifyMfaToken` call in its own UoW — its transaction covers only its own writes (`recordLogin`+`save`). Cross-service atomicity is not required: a claimed TOTP step without a recorded login errs fail-closed (the code can't be replayed), never fail-open.

### Decision 8: Frontend — server-action-first, challenge lives in memory/DOM only, proxy gains the step-2 cookie branch

**Verified ground truth that shapes this decision**: the LIVE portal login is NOT `authApi`/`authContext` — `LoginPage` drives the `loginAction` Server Action (`app/[locale]/login/page.tsx:30`, `app/actions/auth.ts:47-97`). Today an MFA-challenge response would hit `!tokens?.accessToken` → "Authentication failed - no token received" (`auth.ts:80-82`): an MFA-enabled customer could NEVER complete portal login. The `authApi` scaffolding (`MfaChallenge`, `authApi.ts:66-70`; mapping `:129-135`) is dead code on the live path, and `authContext.login` treats a challenge as an ERROR (`authContext.tsx:111-115`). Also verified: the proxy persists cookies only on EXACT path match `auth/customer/login` (`route.ts:51`, `:135`) — without a proxy change, a step-2 response through the proxy would fall to pass-through and LEAK `accessToken`/`refreshToken` to the browser.

**Design**:

- `loginAction`: on `response.ok` with `data.mfaRequired` → return new state `{ mfaChallenge: { challengeToken, expiresInSeconds, rememberMe } }` (no cookies set). `AuthActionState` gains the optional field.
- NEW `completeMfaLoginAction(prevState, formData)` in `app/actions/auth.ts`: reads `challengeToken`/`code`/`rememberMe`, POSTs `${API_URL}/auth/customer/login/mfa` with the `forwardedForHeaders` relay (same N-SEC-2 pattern as `auth.ts:62-67` — REQUIRED, or the backend IP-binds/rate-limits against the Next server's IP), persists via `setSessionCookie`/`setRefreshCookie({rememberMe})` (`sessionCookie.ts:51-72`), `redirect` to dashboard. On 401 `INVALID_MFA_CODE` → keep `mfaChallenge` in state (retry code); on 401 challenge-invalid / 503 → drop `mfaChallenge` (back to password step) with the error message.
- `LoginPage` (`page.tsx`): two-step render — password form (unchanged) when no `state.mfaChallenge`; NEW `MfaChallengeForm` component (`apps/client/components/auth/MfaChallengeForm.tsx`, named export, `@component` + `@layer infrastructure`, props documented on the interface per CODING_STANDARDS; function order per REACT_STANDARDS) rendering the code input plus hidden `challengeToken`/`rememberMe` inputs wired to `completeMfaLoginAction` via `useActionState`.
- **Challenge token residence — memory/DOM only (owner-decided; justified)**: the token exists in the `useActionState` React state and a hidden form input of the active page — it dies on navigation/refresh (user restarts login; TTL is 180s anyway). NEVER localStorage/sessionStorage (persist across tabs/restarts and are the canonical XSS exfiltration target — OWASP HTML5 Security / Session Management cheat sheets `[knowledge]`) and no new cookie (it is not a session credential; cookie lifecycle machinery adds surface for zero gain). An XSS strong enough to read React state can also drive the login UI directly — browser storage is the only materially WORSE option, and it is excluded.
- `authApi`/`authContext` wiring (owner decision #3): `MfaChallenge` gains `challengeToken: string; expiresInSeconds: number`; `login` maps them (`authApi.ts:129-135`); NEW `authApi.completeMfaLogin({challengeToken, code, rememberMe}): Promise<AuthResponse>` → proxy POST `/login/mfa`. `authContext.login` return type becomes `Promise<MfaChallenge | null>` (challenge returned, not thrown) + new context method `completeMfaLogin`. - i18n: add `auth.*` keys for the MFA step to `apps/client/messages/en.json` + `es.json` (es in neutral professional Spanish).

### Decision 9: Orphan `POST /auth/mfa/verify` — RETIRED (evidence)

Verified orphan: registered WITHOUT preHandler (`mfaRoutes.ts:523-528`), handler hardcodes `MFA_SUBJECT_TYPE.ADMIN` (`:204-207`), takes `{userId, token}` (`MfaVerifySchema`, `:41-46`), returns `{verified, usedBackupCode}` and mints NOTHING (`:226-232`). Retirement scope: delete registration `:523-528`, handler `:191-233`, `MfaVerifySchema` `:41-46`; delete the 3 orphan tests; retarget `authRateLimit.test.ts` to `/auth/mfa/verify-setup` (the rule stays — Decision 6); regenerate `api-generated` types (dump:openapi flow); update `docs/api/auth.md:123`, `docs/api/README.md:131`, `docs/architecture/API.md:161`; fix or remove the k6 helper reference. Post-condition: `app.inject POST /auth/mfa/verify` → 404 (tested).

### Decision 10: Audit events — reuse existing seams; ONE new event type; anomalies are WARN telemetry, not audit rows

- **Step-2 code failures**: already audited inside the shared service as `MFA_VERIFICATION_FAILED` with the CUSTOMER actor via `resolveAuditActor` → `auditActor.customer(subject.id, accountId)` (`MfaService.ts:219`, `:432-441` — the A1 actor seam; a failed customer step-2 attributes to the customer actor, never a silent admin fallback). BF failures/successes are additionally audited by the BF adapter itself (`BruteForceProtectionPort.ts:116-128`).
- **NEW audit event**: `MFA_TOTP_REPLAY_REJECTED` (HIGH) inside `MfaService` on `ALREADY_USED` — a replayed OTP is a genuine attack indicator worth a durable row, and `MfaService` is an `AuditableService` (natural home; the `@core` use cases are not).
- **NOT audited** (WARN telemetry instead, `threat_type`-tagged, alertable — rate-limiter precedent `httpRateLimitPreHandler.ts:269-272`): challenge issuance (one per MFA login — volume without forensic value; BF already audits the successful step-1 password check), binding mismatches (`mfa_challenge_binding_mismatch`), store outages (`mfa_challenge_store_unavailable`). Rationale: audit rows are for attributable security events; infra anomalies and high-volume routine steps are observability signals. Step-2 SUCCESS is captured by the BF adapter's `recordSuccessfulAttempt` audit + `recordLogin` on the row.
