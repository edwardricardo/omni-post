## 5 · What this change does

Work items in dependency order. Every item is provable by a named test in §6.

### W1 — One key derivation, by route identity _(closes D1)_

Replace `httpRateLimitPreHandler.ts:198` with a single `bucketKey(req)` primitive:

```
`${resolveClientIp(req)}:${req.method}:${req.routeOptions.url ?? UNROUTED}`
```

- `routeOptions.url` is `context.config?.url` — the registered pattern (`fastify/lib/request.js:183,190`). Query-safe **and** parameter-safe by construction. No `split` to forget.
- **`method` is included deliberately.** Under raw-URL keying `GET /api-keys` and `POST /api-keys` already share a bucket (`apiKeyRoutes.ts:270,278`); pattern-keying would preserve that collision. Splitting them is a strict improvement and regresses nothing.
- **`UNROUTED` is load-bearing.** `request.is404` is literally `context.config?.url === undefined` (`fastify/lib/request.js:209-212`), so on a 404 the pattern is absent. Without an explicit named constant, template interpolation yields `ip:GET:undefined` — one global bucket for all 404 traffic, a self-inflicted DoS on 404 handling. Give it its own generous config.
- `findConfig` matches the **pattern**, not the raw URL. Verified non-breaking against every current row: `/analytics/project/:projectId/full`.startsWith(`/analytics/project/`) ✓, `/admin/accounts/:id/usage`.startsWith(`/admin/accounts/`) ✓, `/health/ready`.startsWith(`/health`) ✓.
- `resolveClientIp` is **not touched**. It is the (A)-grade half.

### W2 — Collapse the mechanisms _(closes D4's root)_

- **Delete M2** (`createNamespacedRateLimitPreHandler` `:155-188`, wiring at `linkRoutes.ts:294-305`). Its entire purpose — "make all `/r/*` hits from one IP share one bucket" (`:289-293`) — is what W1 produces for free. Replace with a rule row. **This deletion is the proof the redo is right: the workaround becomes unnecessary rather than being kept alongside.**
- **Delete M3** (`adminAuthMiddleware.ts:222-251`) and its three `preHandler` attachments (`adminAuthRoutes.ts:563, 580, 590`), plus the test/prod split at `:559`. Its key expression is promoted to W1; its three policies become three rule rows.
- **Delete M5** (`rbacMiddleware.ts:201-222`) and its four test cases (`tests/unit/rbacMiddleware.test.ts:449, 459, 472, 484`). It is the only writer of `X-RateLimit-Limit` in the repo and it gates nothing.

### W3 — Delete the seven inert blocks; do **not** wire the plugin _(closes D3)_

Delete `authRoutes.ts:334, 346, 358`, `customerAuthRoutes.ts:501, 553, 568, 580`; drop `@fastify/rate-limit` from `apps/api/package.json:183`; delete `apps/api/tests/unit/authRateLimit.test.ts`; update `apps/api/package.json:23` `test:ratelimit` (otherwise the CI step `security-testing.yml:155` runs a deleted file). Absorb each block's declared intent into a rule row per §4.

**Argument for delete over wire:**

1. **Ratified.** `openspec/specs/client-ip-rate-limit/spec.md:127` — _"no second HTTP limiter (e.g. a `config: { rateLimit: {...} }` route-config) is introduced."_ Wiring violates the change's own spec.
2. **Wiring installs a per-pod store.** The test's own comment records it: `authRateLimit.test.ts:140` — _"Register @fastify/rate-limit with global:false and NO Redis → uses in-memory."_ That is the cross-pod-coherence anti-pattern fitness #14 exists to block, on the credential path.
3. **Wiring would loosen two live caps.** `/auth/refresh` and `/auth/customer/refresh` declare 20/15min against a real 5/15min. A second limiter cannot tighten a bucket it does not share; the loosest declaration wins in practice.
4. **Two key derivations, two 429 shapes.** The plugin keys `ip + routeOptions.url + method`; ours would key the same after W1 — but in a different store, with a different body (`httpRateLimitPreHandler.ts:174-179` vs `errorResponseBuilder`).
5. **Precedent already in the file.** `customerAuthRoutes.ts:508-512` deleted one block and left the reasoning. Follow it.
6. **The test dies with them**, or "we removed a false signal" becomes "we removed the thing the suite proves."

### The shape that catches "a declared cap that enforces nothing"

**A unit test cannot express it in the general case, and a fitness function is the right answer.** An inert `config: { rateLimit }` is _syntax in a route options object that no runtime consumes_ — there is no function to call and no behaviour to assert. A runtime test can only see routes it registers, so it can never prove absence across route plugins it does not know about. The grep is **total over the tree**.

Its correct form is a **biconditional**, not a ban: `config.rateLimit` is only meaningless while `@fastify/rate-limit` is unregistered. Fitness #30 asserts `count(config: { rateLimit) == 0 OR count(register(fastifyRateLimit) in apps/api/src) > 0`, and drops the dependency in the same change so the second half is unambiguous forever. T10(a) is its runtime companion for the five credential route plugins — belt and braces, since the grep sees syntax and T10 sees what Fastify actually received.

## 8 · Open questions for design

**F1 — `/auth/login`: gate it, or delete the door?**
Two endpoints authenticate the same `adminUser` table: `/auth/login` (`authServiceCore.ts:165` → `PrismaAdminUserRepository`) and `/admin/auth/login` (`AdminAuthService.ts:81`). One has a brute-force port and a route-pattern key; the other has neither, and its only frontend client (`apps/admin/lib/api/clients/authClient.ts:31`) is re-exported but called by no component.
**(a)** Inject `BruteForceProtectionPort` into `AuthServiceCore` — small, provable, closes the asymmetry now, leaves a redundant door standing.
**(b)** Delete the whole `/auth/*` AuthService HTTP surface (six routes, `authRoutes.ts:330-390`) and repoint the portal — the correct end state, but a redo of the auth stack rather than the limiter.
Default assumed by this proposal: **(a)**, with (b) named as its own change. The owner's "redo, don't patch" rule argues for (b); reviewability argues for (a). **Genuine fork; needs a decision before W7.**

**F2 — Does `keyBy: "principal"` land now?**
`SECURITY_CANON §Rate Limiting` prefers an authenticated principal. `HttpRateLimitRule` (`:24-30`) cannot express it, and there is a real obstacle: the global preHandler (`index.ts:438`) runs **before** route-level `requireClientAuth`, so `request.auth` is unpopulated when the key is computed. Adding the dimension means either a second post-auth limiter stage or moving the hook — both are architectural. **(a)** ship IP-only and state the canon gap honestly in W8; **(b)** design the two-stage key now.

**F3 — `/admin/auth/login`: AUTH 5/15min or M3's 15/min?**
A 45× policy difference. AUTH gives parity with `/auth/customer/login` and is defensible because the account-keyed brute-force gate (`AdminAuthService.ts:67`) is the real guess budget. 15/min is the number that currently ships. Note that **no test exercises 15** — `adminAuthRoutes.ts:559` gives tests 100 — so any integration suite that logs an admin in repeatedly is at risk either way.

**F4 — SSO and invite tiering.**
`/auth/oidc/:accountId/{login,callback}` (`oidcRoutes.ts:277,336`), `/auth/saml/:accountId/{metadata,login,callback}` (`samlRoutes.ts:248,272,296`), `POST /team/invite` (`teamRoutes.ts:287`). Callbacks consume an IdP assertion (credential-verifying → AUTH-like); initiators are redirects (volume-sensitive → too strict breaks a large tenant). Under pattern-keying all tenants share one per-IP bucket per pattern. Numbers need a decision, not an invention.

**F5 — Does `ENABLE_RATE_LIMITING` survive?**
A single boolean (`index.ts:430`, `config/env.ts:241`) removes the entire mechanism, `scripts/ci-setup-test-env.sh:37` sets it `false` for every CI job but one (`ci.yml:340`), and **no test in the estate can observe it** — every unit test calls `createHttpRateLimitPreHandler` directly and bypasses the boot path. Keep it with a boot assertion, or delete it as an untested kill switch on a security control?

### Implementation risks

1. **Pattern-keying collapses per-id buckets — deliberately, but it is a real behavioural tightening.** A legitimate client iterating 30 projects against `/analytics/project/:projectId` now shares one 20/min bucket where it previously got 20/min _each_. Any existing integration suite that loops over ids may start 429ing. Sweep for looping suites before W1 lands.
2. **The 404 bucket.** Without the explicit `UNROUTED` constant (W1), `ip:GET:undefined` becomes one global bucket for all 404 traffic — a self-inflicted DoS on 404 handling introduced _by the fix_. T5 is merge-blocking.
3. **Deleting M3 removes the `NODE_ENV === "test" ? 100 : 15` escape hatch** (`adminAuthRoutes.ts:559`). Any test that logs an admin in more than the new cap allows per window will start failing — and it will fail _correctly_, which makes it easy to misdiagnose as a regression.
4. **`fakeReq` (`httpRateLimitPreHandler.test.ts:19-28`) has no `method` and no `routeOptions`.** Every existing case in that file must be updated in the same commit or the suite errors on `undefined` — a loud, correct failure that will nonetheless look like the change broke ten tests.
5. **`test:ratelimit` (`apps/api/package.json:23`) names two files by path.** Deleting `authRateLimit.test.ts` without updating the script makes `security-testing.yml:155` fail on a missing file — CI red for the wrong reason.
6. **T13 will not run unless it is hand-added to a `run-tests.sh` batch.** Twenty integration suites on disk are named by no batch and never execute; `run-tests.sh:8-13` admits this in its own header. An honest comment is not a gate.
7. **T13 will pass vacuously unless `ENABLE_RATE_LIMITING=true` is set for its job.** `scripts/ci-setup-test-env.sh:37` writes `false` for every CI job.
8. **Fitness #31's baseline is three sites, not one** (`adminAuthRoutes.ts:69`, `authRoutes.ts:61`, `:156`). Wiring the check before W7 completes lands a red CI.
9. **Deleting M2 changes `/r/:shortCode`'s bucket name**, not its semantics (`redirect:ip` → `ip:GET:/r/:shortCode`). In-flight buckets in a running Redis reset once — irrelevant here (no users), but note it so nobody reads the reset as a bug.
10. **W9 must not touch `httpRateLimitPreHandler.ts:218-222`.** The verification pass killed "it is dead code": that `try` also wraps `resolveClientIp` and both `reply.*` calls. Removing it converts a fail-open limiter into a 500 on every request.
