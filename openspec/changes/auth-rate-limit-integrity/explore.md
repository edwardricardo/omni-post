# `auth-rate-limit-integrity` — Explore + Proposal

**Change:** `auth-rate-limit-integrity` · **Repo:** `/root/omni-post` · **Mode:** read-only exploration, adversarially verified
**Binding context:** the app has never been used. No users, no compatibility, no migration. Badly-conceived code is redone, not patched. Scope is bounded by reviewability and provability only.

## 1 · The defects

Enforcement path under audit: `apps/api/src/index.ts:430` (`if (env.ENABLE_RATE_LIMITING)`, default `true` at `apps/api/src/config/env.ts:241`) → `:438` `typedApp.addHook("preHandler", …)` → `:440` `createHttpRateLimitPreHandler` → `apps/api/src/security/httpRateLimitPreHandler.ts:188`.

### D1 — The bucket key is the raw URL · **CRITICAL** · class **(B)**

`apps/api/src/security/httpRateLimitPreHandler.ts:198`

```ts
const key = `${resolveClientIp(req)}:${req.url}`;
```

`req.url` is the raw request target — query string included. `findConfig` (`:120-126`) matches `url.startsWith(rule.path)`, so `"/auth/login?x=1".startsWith("/auth/login")` is `true` and the AUTH preset (`:36`, 5 / 15 min) is **still selected**. The preset is right and the bucket is fresh. `POST /auth/login?x=1`, `?x=2`, `?x=3` … are three distinct Redis keys, each with its own 5 permits, each `PEXPIRE`d for 900 s (`apps/api/src/ai/providers/RedisTokenBucketRateLimiter.ts:60`).

**Concrete exploit.** Unbounded credential guessing against `/auth/login` from a single IP at whatever rate the box serves. Secondary: each distinct query mints a Redis hash held 15 minutes — a memory-amplification vector against the limiter's own store, driven entirely by attacker-controlled input.

**Why it is worst on `/auth/login` specifically.** That route authenticates **admin** rows: `AuthServiceCore` is typed on `AdminUserRepositoryPort` (`apps/api/src/auth/authServiceCore.ts:19,58`), wired to the admin repository at `apps/api/src/infrastructure/container/setupServices.ts:209`, reading credentials at `authServiceCore.ts:165`. And it is the **one** login endpoint with no account-keyed gate: `rg 'bruteForce|checkLoginAttempt'` over `authServiceCore.ts` returns nothing. Its only attempt tracking is `recordLoginAttempt` (`:156,297`) → `apps/api/src/auth/redisSessionHelpers.ts:122`, which is **write-only**: `LOGIN_ATTEMPTS_PREFIX` has exactly two references repo-wide — its declaration at `:14` and its writer at `:122`. Zero readers. The docstring at `:112` ("Record a login attempt in Redis for auditing **and rate limiting**") promises a control that does not exist.

The admin portal calls this door: `apps/admin/lib/api/clients/authClient.ts:31` → `apps/admin/lib/apiClient.ts:65`.

**Class (B) — five reasons, in weight order:**

1. **The query string is one of two instances.** The other is path parameters, and it is larger. Nine rule rows end in `/` and therefore mint one bucket per caller-controlled segment: `/analytics/project/` (`:56`), `/analytics/threads/` (`:70`), `/admin/accounts/` (`:74`), `/analytics/project/` (`:76`), `/analytics/post/` (`:77`), `/analytics/channel/` (`:78`), `/publish/` (`:104`), `/media/` (`:105`), plus the `STANDARD` default over every `:id` route in the app. `req.url.split("?")[0]` closes one instance and leaves the other wide open. A fix that covers some routes and not others is the owner's own (B) signal.
2. **The repo already diagnosed this class in its own source and answered it with a second mechanism.** `apps/api/src/links/linkRoutes.ts:289-291`: _"The global limiter keys by URL, so every guessed shortCode hits a fresh bucket → it does NOT throttle namespace enumeration."_ Stated verbatim, then routed around for exactly one endpoint (`:295-307`) while every other parameterized route kept the broken key.
3. **The correct key already exists in the repo, in a third mechanism.** `apps/api/src/admin/auth/adminAuthMiddleware.ts:227` uses `request.routeOptions.url` — the registered route pattern, which is `context.config?.url` (`node_modules/.pnpm/fastify@5.10.0/node_modules/fastify/lib/request.js:183,190`). Query-free and parameter-free **by construction**; no `split` to forget, nothing to drift. Three key shapes for one concept.
4. **The rule type cannot express what the canon requires.** `HttpRateLimitRule` is `{ path, config, contains? }` (`:24-30`). There is no `keyBy` dimension, so no route can ever bucket by authenticated principal (§2).
5. **The one-liner is not even available.** The prior branch fix `c64a718f` predates `resolveClientIp` — its diff is `${clientIp(req)}:${req.url}` → `${clientIp(req)}:${path}`. Cherry-picking it reverts the IP resolver, the single (A)-grade piece of this subsystem. Whatever ships is a re-implementation.

## 2 · Is the mechanism sound?

**Verdict: the substrate is sound and stays. The policy layer above it is class (B) and is redone.**

### Key derivation — **unsound**

`${resolveClientIp(req)}:${req.url}`. The IP half is canon-correct. The scope half is **client-controlled**, which is the exact property `resolveClientIp` exists to eliminate on the other half. Six path-matching seams exist in this codebase and the limiter is the only one that keeps the query:

| Seam                                                       | Expression                                 |
| ---------------------------------------------------------- | ------------------------------------------ |
| `apps/api/src/admin/auth/adminAuthMiddleware.ts:227`       | `request.routeOptions.url`                 |
| `apps/api/src/metrics/metricsMiddleware.ts:130`            | `routeOptions?.url \|\| url.split("?")[0]` |
| `apps/api/src/cache/autoCacheMiddleware.ts:89`             | `routeOptions.url \|\| request.url`        |
| `apps/api/src/security/csrfMiddleware.ts:38`               | `request.url.split("?")[0]`                |
| `apps/api/src/security/ipAllowlistMiddleware.ts:94`        | `request.url.split("?")[0]`                |
| **`apps/api/src/security/httpRateLimitPreHandler.ts:198`** | **`req.url`**                              |

Both candidate fixes are already in the tree, in sibling security middlewares, and neither was applied to the limiter. That is the structural signal — not the missing `split`.

### Store — **sound, and genuinely cross-pod**

One port, `packages/ports/src/RateLimiterPort.ts`. All mechanisms resolve the same singleton `TOKENS.HttpRateLimiter` (`index.ts:431`, `linkRoutes.ts:294`, `adminAuthMiddleware.ts:224`), bound at the composition root to `new RedisTokenBucketRateLimiter(…, { keyPrefix: "http:ratelimit:" })` (`setupServices.ts:283-286`). Refill+consume is a single atomic Lua `EVAL` (`RedisTokenBucketRateLimiter.ts:33-67`) — no cross-pod read-modify-write race — with buckets `PEXPIRE`d to one window (`:60`). `InMemoryTokenBucketRateLimiter` is wired nowhere in `apps/api/src`. **Nothing to change here.**

### Authenticated principal as key — **impossible today, and the type is why**

`SECURITY_CANON.md §Rate Limiting`: _"Prefer an authenticated principal over IP when one exists… reserve IP-based keys for unauthenticated traffic (OWASP)."_ `HttpRateLimitRule` (`:24-30`) has no `keyBy` dimension, and no `tryConsume` call site anywhere in the HTTP path keys by user or account. Every authenticated route in the app buckets per IP. With `TRUSTED_PROXY_HOP_COUNT` defaulting to `0` (`config/env.ts:278`), behind any proxy that collapses **every** caller into one shared bucket — the availability face of the same missing dimension. This is a missing dimension in the rule type, not a bug in a line.

There is a real obstacle, and it is the reason this is a design fork (§8): the global preHandler at `index.ts:438` runs **before** route-level auth preHandlers such as `requireClientAuth`, so `request.auth` is not populated when the key is computed.

### Parallel mechanisms — **five at the HTTP layer, plus one real second layer**

| #   | Mechanism                                                        | Key                                      | Sites                                                                                             | Status                                                                  |
| --- | ---------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| M1  | `createHttpRateLimitPreHandler` `:188`                           | `${ip}:${req.url}` `:198`                | global, `index.ts:438`                                                                            | live, broken key                                                        |
| M2  | `createNamespacedRateLimitPreHandler` `:155`                     | `${namespace}:${ip}` `:161`              | `linkRoutes.ts:295,301`                                                                           | live, exists only because M1's key is wrong                             |
| M3  | `rateLimit(max, windowMs)` `adminAuthMiddleware.ts:222`          | `admin:${ip}:${routeOptions.url}` `:227` | `adminAuthRoutes.ts:563,580,590`                                                                  | live, **correct key**, exists only because M1's table has no admin rows |
| M4  | `config: { rateLimit }`                                          | —                                        | 7 routes                                                                                          | **inert**                                                               |
| M5  | `roleBasedRateLimit()` `apps/api/src/auth/rbacMiddleware.ts:201` | —                                        | **zero** production call sites; 4 in `tests/unit/rbacMiddleware.test.ts:449,459,472,484`          | **dead** — sets `X-RateLimit-Limit` (`:217`) and consumes nothing       |
| L2  | `BruteForceProtectionPort`                                       | account/email                            | `AdminAuthService.ts:67`, `LoginCustomerUseCase.ts:110`, `CompleteCustomerMfaLoginUseCase.ts:134` | **sound, separate layer, stays**                                        |

**Verdict.** M1's port, adapter, `resolveClientIp` and numeric `trustProxy` (`index.ts:188`) are **(A)-grade and untouched**. M1's key derivation, M1's rule table, and the M1/M2/M3/M4/M5 split are **(B)**: one capability implemented five times, three of those implementations existing solely to work around the first one's defects. Consolidation is not a follow-up change — it _is_ this change. The repo's own parity doc already ratified the direction at `ADMIN_CUSTOMER_PARITY.md:366`: _"Rate-limit consolidation. One rule source; retire `adminAuthMiddleware.rateLimit`; add rules for …"_
